【你要做几件事】看你的接口 —— 不是所有接口都要走五步：
  · acp / file_poll  → 第 1/2/3/4/5 步都要做（要走桥）
  · http_api / mcp   → 只做第 1 步 + 第 4 步（**不需要桥**，平台直推）
  · clipboard        → 第 1 步 + 第 4 步；第 2/3/5 步「不适用」（没有叫醒命令这回事）
  · http（测不出来） → 第 1 步 + 第 3/4/5 步，但**平台不会叫醒你**（先落盘、暂不叫醒）
【接口适配/高效性等级】（**只有这一套用字母**；判据见平台源码 bridge_catalog.py）
  S  http_api       平台直接 POST 到你的 HTTP 地址   —— 最快、0 桥、0 落盘
  S  mcp            平台作为 MCP 客户端直调你的工具  —— 最快、0 桥
  A  acp            桥用一条命令拉起你的会话         —— 全自动，多一个常驻桥
  B  file_poll      桥把任务写进你盯的目录           —— 全自动，链路多一环
  C  clipboard      平台落盘 + **人把内容粘给你**     —— 最后一下得人来
  D  http           平台只落盘、**不叫醒**           —— 没人轮询就一直躺着
【不同接口 → 配不同桥】（配错不算错，但平台会给你一句 kind_warning 提醒）
  acp        → cli_acp（首选）
  file_poll  → file_poll（首选）／ pending_poll（可用，非首选）
  clipboard  → pending_poll
  http       → pending_poll
  http_api / mcp → **不需要桥**（配了就是多余链路）

【先看这个：平台协作协议简报】
GET http://127.0.0.1:{PORT}/api/protocol-brief
这是一份机器可读的「平台是什么、我该做什么、不懂就问谁」简报，先拉下来看。

接入分两个阶段：

【阶段1：初步消息注册（你只需声明部分信息，不必懂技术细节）】
POST http://127.0.0.1:{PORT}/api/harness/pre-register
body: {
  "harness_id": "我的唯一标识",
  "harness_name": "我的显示名",
  "harness_type": "desktop-agent",      // 可选：类型猜测（cli-agent/ide-agent/desktop-agent/api-proxy/custom）
  "transports": ["http"],                // 可选：我支持的通信协议（ws/http/sse/pipe/grpc/mcp/a2a），默认 http
  // ★下面三个 hint **不是注册字段**（不在 harness 信息模型里）：平台会把它们收进 metadata，
  //   供「平台主动探测」用（`POST /api/harness/<你的id>/probe` 拿它去扫进程 / 探端口）。
  //   ⇒ 你**测不出自己**时填它们最有用；不填也不影响注册。
  "process_hint": "我的进程名线索",       // 可选：让平台能扫到我的进程（如 electron/我的进程名/python）
  "port_hint": 3721,                     // 可选：我的 HTTP API 端口（若有）
  "path_hint": "我的安装路径",            // 可选
  "capabilities": ["web_search","file_ops"],  // 可选：我的能力
  "description": "一句话说明我是什么"
}
这一步只告诉平台「我叫什么、大概是什么、有什么线索」，不需要你懂 wakeup_method / api_base_url 这些技术字段。

【阶段2：平台探测补齐并正式注册】
POST http://127.0.0.1:{PORT}/api/harness/probe-register
body: {"harness_id": "我的唯一标识"}
平台会基于阶段1的线索自动探测我（扫进程/扫端口/探测 HTTP 端点），摸清我是 HTTP API 型、文件型还是 ACP 型，自动补齐 wakeup_method、api_base_url 等并完成正式注册。

⚠️ **这一步要等 10~15 秒**（它在本机扫进程和端口；机器忙时更久，实测 11.1~11.5s）：
    · **超时值请给 ≥30 秒** —— 别用 5~10 秒的默认超时，那样会**误报成"平台不可用"**；
    · **超时 ≠ 失败，重试是安全的**（这一步是幂等的，实测重试两次不会造出第二份注册）；
    · 期间平台**照常服务**（不会卡住别的请求），你只管等这一个响应。

【收集信息的方式（重要）】
用户是平台的拥有者，不是 harness 本身。多数字段请你自己探测/推断，**不要问用户**。

★★ 关于"怎么被叫醒"——**先自己测，不要先问人**（这条最要紧）

"我该怎么被叫醒"这个问题，**答案在你身上，不在用户身上** ——
用户多半不知道你的进程模型（实测：他会答不上来，然后整件事就卡住了）。
请**按下面四项动手测一遍**，把你**实际能做到**的那项报给平台：
（下面四项的编号叫 **Q1~Q5**，它回答的是「你属于哪种接口」，**不是等级**；
  等级只有 **S/A/B/C/D** 一套，见页面「📊 接口适配 / 高效性等级」。）

    □ 测 1｜我能不能被一条命令拉起？
        试：用你的启动方式开一个**新**实例（命令行/可执行文件都行）。
        能 ⇒ 记下**那条完整命令**，选 **Q1**。
    □ 测 2｜我能不能盯着一个文件夹？
        试：建一个空目录，往里丢一个文件，看你能否注意到它。
        能 ⇒ 记下**那个目录路径**，选 **Q2**。
    □ 测 3｜我有没有常驻的网页接口？
        试：查你自己有没有在监听端口（能接受 HTTP POST 就行，不用对外）。
        有 ⇒ 记下**地址**，选 **Q3**。
    □ 测 4｜以上都不行？
        ⇒ 选 **Q4**（人工模式：平台把要送的内容生成好，用户手动贴进来）。
        **这不是失败**，是如实说明能力边界 —— 平台会照这个走，不会假装通了。

    ★ **如果四项你都测不出来**：选 **Q5**。平台会按"先落盘、暂不叫醒"给你接上，
      并在自检里**如实告诉你差哪一步**（宁可不叫醒，也不编一个假的）。
      **不要**因为"选不出来"就去问用户 —— 他更不知道。

★★ 注册时 `wakeup_method` **只能填下面这 6 个值之一**（填别的会被平台直接拒掉，实测 400）：
    `http` · `file_poll` · `clipboard` · `acp` · `http_api` · `mcp`

⚠️ **别把"桥型名"当 `wakeup_method` 填**（这是实测踩到的坑）：
    `cli_acp` / `pending_poll` / `script_framework` 是**桥型名**，**不是** `wakeup_method` ——
    填了会被拒（400 validation error），而且报错里只说"Input should be ..."，
    不写清楚该把桥型放哪。**桥型是另一个字段**（见下面第 2 步的「桥模板」）。

你报 **Q1~Q5** 与 `wakeup_method` 的对应（照填就行）：
    Q1 命令拉起   → `wakeup_method`: `acp`
    Q2 盯文件夹   → `wakeup_method`: `file_poll`
    Q3 网页接口   → `wakeup_method`: `http_api`
    Q4 手动贴     → `wakeup_method`: `clipboard`
    Q5 测不出来   → `wakeup_method`: `http`     ← 平台会让它走**兜底轮询**（先落盘、暂不叫醒）
    实在拿不准时：填 `clipboard`（人工模式，**一定不会错**，之后可再改）。

若选 A/B：还要给出**那条命令**（A）或**那个目录**（B）——
   ⚠️ 命令里**别用引号硬拼带空格的路径**（实测会被拆坏，桥起不来）；
      含空格就写一个包装脚本，把**脚本路径**给它。
   ⚠️ 选 Q1/Q2 但**给不出命令/目录**也可以先接入，但那样**消息只会落在邮箱里、不会被叫醒**，
      平台会如实告诉你这一点（脚本会打印 "trigger: (无)"）。
其余技术字段：探测/推断不出的用合理默认值，禁止用 "[如：xxx]" 占位符注册。
**只问用户它真知道的事**：他要达成什么、这台机器上装了什么 —— 技术细节别问他。



【注册前先探测平台是否在线】

用下面任一种方式确认平台可达，再注册（探测失败先告诉我，不要盲目 POST）：

  - Python：python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:{PORT}/api/status',timeout=5).status)"

  - 或 PowerShell：Invoke-WebRequest -Uri http://127.0.0.1:{PORT}/api/status -TimeoutSec 5



【发送时注意中文编码（重要！）】

注册 JSON 里有中文时，务必用 UTF-8 编码发送，否则服务端收到乱码。推荐用 Python（显式 UTF-8）：

  python -c "import json,urllib.request;body=json.dumps({...注册JSON...},ensure_ascii=False).encode('utf-8');req=urllib.request.Request('http://127.0.0.1:{PORT}/api/harness/register',data=body,headers={'Content-Type':'application/json; charset=utf-8'});print(urllib.request.urlopen(req,timeout=10).read().decode('utf-8'))"

（如果你用 PowerShell，请用 [System.Text.Encoding]::UTF8.GetBytes() 转字节数组再发；响应里的中文若显示乱码，通常是显示层问题，数据本身是对的，可用 Python 拉取验证。）



【注册完成后：五步接入（每步都能自己验证）】
★前 4 步 = 把配置弄对；**第 5 步 = 真的接上了**（必须把桥常驻跑起来，否则平台派的活没人取）。

第 1 步 注册（就是上面这份 JSON）

第 2 步 ★把「叫醒命令」交给平台（**这一步千万别漏**）
        把你问到的答案（"收到任务后要执行哪条命令去叫醒它"）交给平台，平台会把它包成一个脚本：
        POST http://127.0.0.1:{PORT}/api/harness/{我的harness_id}/wake
        body: {"command": "把 agent 拉起来的那条命令"}
        · 返回 {success:true, wrapper_path:...} ⇒ 平台已把它包成包装脚本（**你不用自己处理引号**）
        · ⚠️ 为什么必须由平台包一层：带空格/带参数的命令直接传给桥会被拆坏
          （实测报 `unrecognized arguments`、桥起不来）。包成脚本就没这个问题。
        · 用户答不上来可以不配，但**要如实告诉用户**：那样消息只会落在邮箱里、不会自动叫醒它。
        · ★**如果你自己的自测结果是 D（人工中转 / `wakeup_method=clipboard`）**：
          这一步**不用填命令** —— 你本来就没有"被自动叫醒"这回事，任务由**用户手动粘贴**。
          直接调上面那个接口、body 里 `command` 留空即可，平台会回
          `{"success":true, "mode":"manual", "note":...}` —— 那是**正常完成**，不是失败。
          （平台的桥会替你把内容整理好，等着用户粘贴。）

第 3 步 起桥：POST http://127.0.0.1:{PORT}/api/harness/auto-connect  body: {"harness_id":"我的唯一标识"}
        · status=connected/ready ⇒ 桥已起来
        · status=manual ⇒ 看返回里的 note（人工模式，不阻塞）
        ⚠️ **顺序要紧：先第 2 步配叫醒、再第 3 步起桥** —— 桥是在"起"的时候把叫醒命令带上；
           桥已经在跑时它不会自动更新（幂等）。

第 4 步 ★自检（**刚注册也能验，不需要工作间**）：
        POST http://127.0.0.1:{PORT}/api/harness/{我的harness_id}/verify   body: {"wait":16, "teardown":true}
        平台会**就地建一个"低耗验证间"**（只为验证而存在、不进正式工作间列表）：
          架桥 → 发一条真测试消息 → 等你的 agent 回话 → **跑通了才**把实测配置写进桥模板
          → 然后**连桥一起拆掉，只留模板**。
        返回里的关键字段：
          state=ok          通了 ⇒ 这一步就绿了
          state=no_reply    桥把测试件取走了，但**没等到回话**
          state=not_picked  **桥没来取**（按 `advice` 排查：多半是桥没在跑）
          committed.success=true  ⇒ 已把"跑通"的配置写进模板并标记「已验证」
          ── ★**但一定要看 `committed.verified_scope`**：它写明**这次到底验了什么** ↓
             · `file_mailbox` 通道 ⇒ 「完整链路：平台 → 桥 → 你的 agent → 回报」
             · 非邮箱型（如 `pending_poll`）⇒「**仅桥配置**（…且那只桥是**平台在验证间里
               启动的**）—— harness 侧是否运行该桥、agent 能否回话，**本次未验证**」
             ⇒ 别把后者读成"整条链路都通了"。
          gate_note         ⇒ 一句话说明"这次有没有写模板"（**没跑通就不会写**）
          torndown.removed=true   ⇒ 验证间已拆掉（只留模板）
          persistent_bridge ⇒ ★**怎么持久跑桥**（见第 5 步）；它会说明
                              **验证间隔间是一次性的、跑完即删**，别去那儿找桥脚本。
        ⇒ 拿到 no_reply/not_picked 时，按返回的 advice 做，再重跑一次。
        （另一条路：若你已经被指派到某个工作间，也可以用
          POST /api/workshop/{工作间}/member/{成员}/self-check —— 那是"在工作间里验某个成员"，
          区别只是**需要已经有工作间和成员**；刚接入时用上面那条 `{hid}/verify` 更合适。）

第 5 步 ★★**把桥持久跑起来**（**这一步不做完，你就还没真正接入**）：
        前 4 步验的是"**配置可行**"。要**真正接到活**，你必须在**自己这边常驻**跑一只桥 ——
        否则平台派的活只会**躺在队列里没人取**。
          1) 生成桥（平台按你已「已验证」的模板渲染，并返回现成的启动命令）：
             POST http://127.0.0.1:{PORT}/api/harness/{我的harness_id}/bridge/generate
             body: {"template": "桥型"}                   ← **省略 out_dir**，平台自己选落点
             · ★**也可以整个省掉 `template`**：如果你第 4 步已经在验证间跑通了，
               平台会把那次跑通的配置**登记成"具体模板"**（模板本体上带
               `verified=true` / `verified_at` / `evidence`，界面显示"✅ 已验证"），
               此时这里**省略 `template` 就会直接用它** —— 返回里的 `template_source`
               会告诉你桥型是**"显式指定"**还是**"已验证的具体模板"**（别猜）。
               没有可用的已验证模板时，平台**不替你猜**，会回 400 并告诉你二选一。
             · ★**不同接口不同引导** —— 先看你第 1 步自测出来的 `wakeup_method`，再照它那一行做：
                 `acp`        （适配等级 A）⇒ 桥型 `cli_acp`；**第 2/3/4/5 步都要做**；
                                            活进待取队列，桥用那条命令拉起会话去取
                 `file_poll`  （适配等级 B）⇒ 桥型 `file_poll`；**第 2/3/4/5 步都要做**；
                                            活写进你那个目录，桥负责搬件与收回报
                 `http_api`   （适配等级 S）⇒ **不需要桥**：平台直接 POST 到你的地址；
                                            **第 2/3/5 步都不适用**，只做第 4 步（验直推地址能否应答）
                 `mcp`        （适配等级 S）⇒ **不需要桥**：平台作为 MCP 客户端直接调你的工具；
                                            **第 2/3/5 步都不适用**，只做第 4 步
                 `clipboard`  （适配等级 C）⇒ **没有「叫醒命令」这回事**（第 2 步回 `mode:manual` 即正常）；
                                            桥可有可无（`pending_poll`）—— 平台落盘、**人把内容粘给你**；
                                            **「敲门」这一下永远得人来**，这是能力边界，不是失败
                 `http`       （适配等级 D）⇒ 平台**只会落盘、不会叫醒**（没人轮询就一直躺着）；
                                            要么起 `pending_poll` 桥，要么改判成上面某一档
               ★**拿不准就用 `pending_poll`** —— 它不需要你额外提供接口或目录，任何 harness 都能跑。
               ★**桥型和你声明的接口对不上时，平台的响应里会带 `kind_warning`** —— 那不是报错，
                 是提醒你「这条链路可能是多余的 / 你验的和你跑的可能不是同一型」，照着读一遍再决定。
             · 返回 `bridge_file` / `bridge_dir` / **`launch_hint`（照它跑就行）**
             · ⚠️ 若要自己指定 `out_dir`，它**必须在平台的 `bridges/` 目录内**，否则报 400。
          2) 用 `launch_hint` 把那只桥**常驻**跑起来（它按间隔轮询平台领件）。
             ⚠️ 启动命令里**脚本路径含空格时必须带引号**（实测：不加引号会被拆断、
                报 `can't open file '...（External'`、进程秒退）。
                · ★**单实例锁（正常保护，不是故障）**：**同一个工作目录起第二只桥会被拒绝启动** ——
                  直接退出（退出码 2）并打印「另一只桥正在使用同一个工作目录（拒绝重复启动）」。
                  「同一个工作目录」指的是**这只桥盯的那个目录**（`file_poll` 是 inbox、
                  `pending_poll` 是 work-dir、`cli_acp` 是桥脚本所在目录）。
                  ⇒ **要重启就先停掉原来那只**，再用同一条命令起；别以为是「桥坏了」。
                · 同理，第 3 步的 `bridge-test` 若回 `bridges_running` >1 且带 `bridge_warning`，
                  说明名下**有重复的桥在跑** ⇒ 同一 harness 多只桥会**抢件 / 重复投递 / 心跳互相覆盖**，
                  **停掉多余的只留一只**（通常是失败重试时多起的，或用的是加锁前的旧版桥）。
                  · ★**计数口径：`bridges_running` 数的是「逻辑桥」，不是「进程数」** ——
                    `python` 可能是个**外壳**（它会再拉起真正的解释器，**命令行一模一样**）
                    ⇒ **一只桥常见 2 个同名进程**。别自己按个数下结论（会误判成「有两只」）：
                    · 平台已按**父子链归并**计 ⇒ **`bridges_running` ≥2 才真的是两只**；
                    · 你自己数进程时：**互为父子的算同一只**；
                    · 要停就停**整条链** —— `bridge_pids` 是全部进程、`logical_pids` 是各链根。
          3) 探活：POST http://127.0.0.1:{PORT}/api/harness/bridge-test
             body: {"harness_id": "我的唯一标识"}
             ⚠️ 它的 `success:true` **只表示"平台把测试件投出去了"**
                （`delivered_confirmed:false`、`queued:true`）—— **不等于桥收到、更不等于测通**。
                要确认测通：看 `GET /api/harness/{我的harness_id}/wake` 里的 `bridge_test` 记录，
                或者干脆再跑一次第 4 步 `{hid}/verify`（它会**等回报并给结论**）。

之后告诉我注册结果：harness_id + wakeup_method + **五步**各自的结果
（前 4 步绿 = "配置可行"；**第 5 步绿 = "真的接上了"** —— 别把前者当后者）。
还要告诉我：**用户那条"叫醒命令"是什么**（我据此判断该配哪种桥）。
若你的自测结论是 **`wakeup_method=clipboard`（人工中转，适配等级 C）**：你没有"叫醒命令"这回事，
第 2 步的空命令回 `mode:manual` 就是**正常完成**；第 5 步照上面起 `pending_poll` 桥即可。

🌉 展开「架桥速查」（参考用 · 通常不用复制）

平台按 wakeup_method 分流：http_api 类直接 POST 到对象自带 HTTP API（实时、最推荐）、file_poll 类直接写文件到 inbox，其余进 pending 队列等桥来领。四种方式任选其一：

★ 先看这个：自检说「桥没在运行」时，这样起桥（"通没通"的自检见第 1 段的三步接入，或页面下方「🩺 接入自检」）：

set PYTHONIOENCODING=utf-8
<python.exe> -u "<隔间目录>\bridge.py"     ← 路径以平台返回的 compartment 为准，不要自己拼

★ PYTHONIOENCODING=utf-8 必加：桥打印里有非 GBK 字符，不加会报 `'gbk' codec can't encode`（中文 Windows 实测会弄死桥）

要"叫醒"你的 agent：别把带空格的命令直接写进 --trigger（会被拆坏，实测报 `unrecognized arguments`）。
写一个包装脚本再填它的路径 —— 例（Windows）新建 wake.cmd：
    @echo off
    "<你的 agent 完整路径>" <参数>
然后 --trigger 指向这个 wake.cmd。

⓪ http_api 类（对象自带 HTTP API，如桌面 Agent 暴露端口） — 平台直接 HTTP 推送，无需桥：

注册时填 wakeup_method=http_api + api_base_url=http://127.0.0.1:[端口] + api_message_path=/message
平台 POST {api_base_url}{api_message_path} 推任务，对象处理完 POST /api/harness/task-result 回报（或写 api_outbox_dir 平台轮询）。

① file_poll 类（走文件邮箱的桌面 Agent） — 用文件桥：

python agent_community\examples\filepoll_harness_bridge.py --harness-id [id] --inbox [wakeup_dir] --platform http://127.0.0.1:{PORT} [--trigger wake.cmd的路径（叫醒脚本；别直接填带空格的命令，会被拆坏）]

② acp/http/clipboard 类（无真实 ACP server，如 GUI 程序） — 用通用 pending 桥（任务落盘 inbox，回报写 replies 自动转发）：

python agent_community\examples\pending_poll_bridge.py --harness-id [id] --url http://127.0.0.1:{PORT} --work-dir [任务目录] [--trigger wake.cmd的路径（叫醒脚本；别直接填带空格的命令，会被拆坏）]

③ acp 且有真实 ACP server — 用 ACP 专用桥（示例）：

python agent_community\examples\acp_harness_bridge.py --url http://127.0.0.1:{PORT}

回报协议（harness 有联网能力时可直接 POST，无需桥）： 激活 POST /api/harness/activation-result body: {"workshop_id","member_id","status":"entered"}； 平台要等全员 entered 才开始派任务，不回报 = 工作间不开工。 可选三字段（V-15 新增，向后兼容，不发也行、发了更准确）： session_id（本次会话 id，缺了平台无法跨重启记住会话）、 context_turns（上下文轮数，新会话应为 1；>1 平台记一条「上下文复用」审计但不阻断）、 source（acp/mcp/plugin=机器报、human=人工点击进入； 平台据此区分人报与机器报，无 session_id 时会合成 id 并标 human）。 status=blocked 时另可带 reason，会直接显示给用户。 任务 POST /api/harness/task-result body: {"workshop_id","member_id","ok":true,"result":"..."}。

桥测试 + 桥坐标登记（建好桥后必做）：平台会向你的桥发测试（file_poll 写 inbox 的 bridge_test / 其余进 pending-bridge-tests 队列），桥收到后自动回报 POST /api/harness/bridge-test-result（body: {"harness_id","test_id","ok":true,"echo":"..."}）确认通道正常；测试通过后，把桥文件路径告知平台：POST /api/harness/bridge-path（body: {"harness_id","bridge_dir":"桥文件所在文件夹"}），平台记录到该 harness 名下并持久化。

⚠️ 桥必须常驻：桥是独立进程，终端关闭/会话结束它就停了——「注册了但桥没常驻」等于收不到任务。要让平台随时能派活，请把桥命令加入开机启动项或计划任务。

⚠️ 发中文请求注意编码：用 PowerShell 发 HTTP 请求时中文可能乱码（显示层问题，服务端数据是对的）。可靠做法：用 Python 显式 UTF-8 编码发送（json.dumps(body).encode("utf-8")），或检查响应按 UTF-8 解码。

⚠️ 桥需要 inbox 目录的写权限：file_poll 桥要在 wakeup_dir 里创建 delivered/ 并移动任务文件；pending 桥要在 work-dir 建 inbox/replies。如果 inbox 在会话工作区之外（如 D:\你的目录\inbox），受沙箱限制的进程可能写不进去（WinError 5 拒绝访问）——请确保桥进程对这两个目录有读写权限，或把桥放到无沙箱限制的环境里跑。

📊 接口适配 / 高效性等级（按等级挑接口，再按接口配桥）

下表与平台接口 GET /api/bridge-catalog 的 wakeup_ranking 同源 （一处真相：platform/bridge_catalog.py）。等级判据：是否全自动 · 端到端延迟 · 常驻开销 · 链路环节数。

等级 wakeup_method 该配的桥 延迟 / 开销 一句话
S http_api 不需要桥 秒级 / 无 平台直接 POST 到你的 HTTP 地址（最快、环节最少）
S mcp 不需要桥 秒级 / 无 平台作为 MCP 客户端直调你的工具
A acp cli_acp 5~15s / 一个常驻桥 桥用你的命令拉起会话，全自动、可自检、可持久化
B file_poll file_poll（首选）
also: pending_poll		 2~5s / 桥 + 你的目录监听 桥把任务写成文件投进你盯的目录（链路多一环）
C clipboard pending_poll 不可估 / 低 平台落盘 + 人把内容粘进去（最后一下得人来）
D http pending_poll 不可估 / 中 平台只落盘、不叫醒（没人轮询就一直躺着）—— 如实的能力边界

反向索引（桥型 → 适配哪些接口）也在同一个接口的 bridge_to_wakeups 里； 配桥与接口不一致时，bridge/generate 会回一句 kind_warning（不禁止，只提醒）。

🔌 协议接入方式（多种接口，按需选择）

平台支持多种通信协议，harness 可按自身能力选择最合适的接入方式。注册时在 transports 字段声明你支持的协议（可多选），平台会按优先级自动选择：

协议 方向 适用场景 状态
HTTP 平台 → harness 通用默认；平台 POST 任务到 harness ✅ 可用
WS 平台 → harness 长连接实时通信 ⚠️ 部分实现
PIPE 平台 → harness 本地进程间通信 ✅ 可用
ACP 平台 → harness Agent Client Protocol（拉起 CLI/桌面 Agent） ✅ 可用
MCP 双向 工具服务端（stdio）/ 客户端（Streamable HTTP） ✅ 可用
A2A 双向 Agent-to-Agent 标准协作（外部生态 Agent 发现与派发） ✅ 可用

MCP 接入：平台可作为 MCP 工具服务端（stdio，供 Claude Code / Cursor 等挂载）：

claude --mcp-config '{"servers":{"ac4":{"command":"python","args":["-m","agent_community.mcp_server"]}}}'

A2A 接入：外部 Agent 可通过标准 A2A 协议发现本平台并派发任务：

GET http://<host>:9104/.well-known/agent-card.json   # Agent Card 发现
python -m agent_community.a2a_server --port 9104      # 启动 A2A 服务端

注：SSE / GRPC 规划中；注册时声明 transports 数组即可多选，平台按优先级选择实际可用的协议。
