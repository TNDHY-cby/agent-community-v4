# FE-02 设计稿 · 交付回执台（handover.html）

> **设计**：示例Harness-F（前端）｜ **日期**：2026-10-07 ｜ **状态**：待老板拍板
> **来源**：示例Harness-E 对话记录 4 号发言（新活，老板优先级第一的「交接体系」）；接口由我 2026-10-07 在运行实例逐条实测。
> **铁则**：每项完成声明必须附证据，**无证据不回执**——这个页面的存在意义就是把这条纪律变成可操作、可校验的界面。

---

## 1. 页面定位

新建 `agent_community/frontend/handover.html`，访问 `http://127.0.0.1:18920/handover.html`（静态挂载，零后端改动）。

- **是什么**：交付回执台。右侧提交回执（带证据栏，后端强校验），左侧浏览已受理回执（按 task_id），每条回执的每一项声明都带着它的证据。
- **是写页面**：全站唯一的 POST 是 `POST /api/handover/receipt`（本页核心功能）；除此之外全部 GET。**没有其他写操作入口**。
- **不动现有文件**：`index/workshop/register/ops/remote-modal` 均不碰；本页可以用链接指向它们（只写 href，不改对方文件）。

## 2. 数据源（5 个端点，全部实测 2026-10-07）

| 端点 | 实测返回（要点） | 用途 |
|---|---|---|
| `GET /api/handover/receipts?limit=&task_id=` | `200 {"receipts":[…]}`，条目为**拍平结构**：`ts, accepted, task_id, who, items[{n, claim, evidence{commit,file,test}}], delivered, reply_ref, note`（**没有嵌套 delivery**，与提交体不同，渲染必须按列表形状取） | 左栏列表 |
| `GET /api/handover/template?kind=receipt&task_id=&title=` | `200 {"success":true,"template":{items:[{n,claim,evidence{}}], evidence_hint, rule, delivery, delivery_rule}}`。⚠️ 实测 `kind=receipt` 时 `title` 参数被忽略（回显空串；`kind=task_order` 正常回显）——**仅作观察告知 示例Harness-E，不阻塞** | 「从模板预填」按钮 + 把 `rule`/`delivery_rule` 显示在表单旁 |
| `POST /api/handover/receipt` | 合规→`200 {success,accepted,receipt,note}`；某项无证据→`400 {error:"回执不合规", errors:["第 1 项无证据：…"], hint}`；`delivered=true` 缺 `reply_ref`→`400 {errors:["delivered=True 但缺 reply_ref：…"], hint}` | 提交（**errors 数组逐条原样展示，这是本页的意义**） |
| `GET /api/status` | `{"status":"running","version":"4.7.0",…}` | 页头健康徽标（与 ops 同款） |
| `GET /api/handover/template?kind=task_order&…` | 同模板结构（回显 title） | **本轮不做**（见 §8） |

**提交体形状**（与列表不同的地方用 ⚠ 标出）：
```json
{"task_id":"FE-01","who":"示例Harness-F",
 "items":[{"claim":"做了什么","evidence":{"commit":"","file":"相对仓库路径","test":"命令+计数"}}],
 "delivery":{"delivered":true,"reply_ref":"对方可读回复的凭据","note":""}}
```

## 3. 信息架构

```
┌─ topbar ─────────────────────────────────────────────────────┐
│ 🧾 交付回执台   [● running v4.7.0]   ⟳刷新   上次刷新 hh:mm:ss │
├─ main: 1fr / 420px ───────────────────┬──────────────────────┤
│ ┌─ 左：回执列表 ─────────────────┐    │ ┌─ 右：提交回执 ────┐ │
│ │ 摘要 N 份 · [task_id 筛选]     │    │ │ 规则条（后端 rule）│ │
│ │ ─ 回执卡片（倒序）─            │    │ │ task_id / who     │ │
│ │   声明 + 证据三栏 + 送达状态    │    │ │ 声明条目±（动态） │ │
│ └───────────────────────────────┘    │ │ 证据 commit/file/ │ │
│                                       │ │ test（每项三格）  │ │
│                                       │ │ ☑送达 reply_ref   │ │
│                                       │ │ [提交回执]        │ │
│                                       │ │ ⚠ errors 逐条红框 │ │
│                                       │ └───────────────────┘ │
├─ statusbar ──────────────────────────────────────────────────┤
│ 数据源 /api/handover/* · 无证据不回执 · 送达必须有 reply_ref    │
└──────────────────────────────────────────────────────────────┘
```

**三态**（与 ops 同规范）：加载=骨架脉冲；空=中文空态（"还没有受理过回执。完成一项工作后，带上证据来提交第一份。"）；错=面板内红条显示后端中文说明（兼容 `error`/`detail` 两套 404 形状）+ 保留上次成功数据。

## 4. 回执卡片（左栏核心）

```
FE-01 · 示例Harness-F                      🟢 已送达   3 分钟前
交付 FE-01 运维看板（设计稿 + ops.html + 8 条验收实测）
  📁 agent_community/frontend/ops.html; design-docs/FE-01_….md
  🧪 playwright e2e 8/8；示例Harness-E 独立复核 7/10 …
  💬 经协作对话记录送达 · 凭据: 10-7/2-示例Harness-E发言-….md
```

- 头行：`task_id`（mono 粗体）· `who` 胶囊｜右侧：送达徽章 + 相对时间（悬停绝对时间，epoch 秒 → `new Date(ts*1000)`）。
- **送达徽章**：`delivered=true` → 绿「已送达」；否则灰「未送达」。`reply_ref` 单独一行 mono 显示（它是"送达"的凭据本体，必须看得见）。
- 声明项逐条：`claim` 正文；**证据三栏只显非空**：`📁 file`（mono）、`🧪 test`（mono）、`commit`（mono，若有）。三项全空的（后端本不该受理）→ 红描边 + 「无证据」标记，如实暴露数据。
- 多条 items 用序号分隔；`note` 非空显示。
- **点击卡片展开原始 JSON**（收起默认）——回执是凭据，允许看原文是对抗幻觉的一环。

**筛选**：`task_id` 输入框（防抖 400ms → `?task_id=`）+ limit 下拉（20/50/100，默认 50）。空结果区分「无任何回执」与「该 task_id 无匹配」。

## 5. 提交表单（右栏核心）

1. **规则条**（进页拉一次 template）：把后端 `template.rule` 与 `delivery_rule` 原文展示在表单顶部——规则不是我们复述的，是后端发的。
2. 字段：`task_id`*、`who`*；**声明条目动态增删**（默认 1 条，"+ 再加一项"）；每条 = `claim`* 文本域 + 三证据格（commit / file / test，各一输入框，placeholder 用后端 `evidence_hint` 原文）。
3. 送达区：`delivered` 勾选；勾上后 `reply_ref` 变必填样式（前端提示，**最终判定仍交给后端**）；`note` 选填。
4. 「从模板预填」按钮 → 拉 `template?kind=receipt` 重置条目骨架与规则文案。
5. **提交失败（400）**：把 `errors[]` **逐条**渲染进醒目红框（每条一行，带序号），`hint` 灰色小字附下；**不清空用户已填内容**。
6. **提交成功（200）**：绿条提示「已受理」+ 立即刷新列表（新回执置顶）+ 表单重置为 1 条空骨架。
7. 前端只做**空壳必填**的即时提示（task_id/who/claim 全空时阻止提交并提示），**不做**证据合规判定——那是后端的职责，前端的职责是把后端的判定展示清楚。

## 6. 刷新与时间

- 列表：30 秒轮询（回执变化频率低，比 ops 的 12s 更保守）+ 手动 ⟳ + `visibilitychange` 回页立即刷（隐藏时暂停）。
- 表单不自动刷新、不自动重置（不能吞用户输入）。
- 时间：列表 `ts` 是 **epoch 秒** → `new Date(ts*1000)`；相对时间 + 悬停绝对（与 ops 同一函数）。

## 7. 窄窗口取舍（1920 基准；1280×720 与 1024 必不破版）

| 断点 | 布局 |
|---|---|
| ≥1400 | 左 `1fr` + 右 `420px`，各自内部滚动 |
| 1100–1399 | 右栏 `380px`，证据路径省略号 + title 悬停全文 |
| <1100（含 1024） | 单列堆叠：**表单在上、列表在下**（先能交，再能看；与 ops 的"先看后看"相反，因为提交是本页主动作）；页面整体滚动 |

优先级（挤了先砍）：① 卡片的 note 行 → ② 证据三栏合并为一行 → ③ statusbar 文案缩短。**永不砍**：errors 逐条红框、送达徽章、reply_ref 显示。

## 8. 本轮不做

- `kind=task_order` 任务书模板的预览/下发 UI（后端有端点；等流程需要再出 FE-03）。
- 回执的编辑/撤回/删除（端点也不存在；回执一经受理即只读）。
- 跨页入口（ops ↔ handover 互链）——涉及改现有页面，需要时另提。
- `checkpoint/aging/activate` 等 handover 家族其余端点（示例Harness-E 4 号发言未纳入本次范围）。

## 9. 验收自查（对应 示例Harness-E 4 号发言四条）

1. 表单证据全空提交 → 页面显示后端 `errors` 逐条（含"第 1 项无证据…"与 delivered/reply_ref 两种）。
2. 合规提交成功 → 列表出现该条（我已用真实的 FE-01 回执预验过接口侧 200）。
3. 1920 / 1280×720 / 1024 不破版（DOM 实测 scrollWidth==innerWidth）。
4. Console 无红字（含 favicon 处理，与 ops 相同）。

## 10. 接口变更申请

**本轮无**——5 个端点全部实测可用。一条观察随 5 号发言告知：`kind=receipt` 的 template 忽略 `title` 参数（`kind=task_order` 正常），若非有意请顺手对齐，不阻塞。
