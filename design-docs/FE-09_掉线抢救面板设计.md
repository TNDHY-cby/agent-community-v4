## 0. ★措辞契约（准则⑤ + 老板原话，设计层面钉死）

| 事实 | 界面必须这样说 | 禁止 |
|---|---|---|
| `verdict=idle`（没活） | 中性「**当前无进行中的工作**」+ 原样渲染 `pending_work_why` | ⛔ 红色警示、"掉线"、"异常"字样 |
| `verdict=healthy` | 绿「正常」（有活且没事） | 不显示抢救按钮 |
| `verdict=rescue` | 「**⚠ 需要抢救**」+ `reasons[]` 逐条 + `attempts/max_attempts` + `cooldown_left` | 不自动触发（自动扫默认关，按钮=主路径） |
| `escalated=true` | 红徽章「**需要你处理**」 | —— |
| scan `idle_skipped` | 「N 名成员当前没有在进行的工作，**未打扰**」（后端 `summary` 原文即是） | ⛔ 把"没动"算进"已抢救" |
| scan `acted` 空 | 后端 `summary`「本轮无需动作」 | ⛔ "整合/抢救成功"类自创措辞 |
| **`available`（36 号必修：硬/软拆分）** | **不当状态主判据**（主判据=`verdict` 三态）；「联系不上」**只在 `hard_reasons` 非空时显示**（实证：桥进程已退出）；`soft_reasons`（心跳失联——**本项目心跳可选**）只放**详情展开**里 | ⛔ 拿 `available=false` 直接报警；⛔ 把软信号（心跳）说成"联系不上" |

**计数字段纪律（36 号提醒2）**：界面文案只用 `needs_rescue[] / idle[] / escalated[]` 三个数组，**不用 `offline_count`**（名字有歧义，虽值=救数）。
行字段补充：`display_name`（36 号提醒1，标题行用它，缺省回退 `member_id`）。

**反向断言（验收用）**：`verdict=idle` 的卡片内不得出现「掉线」与红警示样式；scan 返回 `acted={}` 时，我方文案不得出现「已抢救/抢救成功」；**软信号成员卡片不得出现「联系不上」**。

## 1. 数据源（形状=源码实测口径）

| 端点 | 用途 | 关键形状 |
|---|---|---|
| `GET /api/workshop/{ws}/offline-report` | 面板唯一读源（`offline_report_api`） | `{success, max_attempts, members[], offline_count(勿用于文案), needs_rescue[], idle[], escalated[], summary}`；member 行：`member_id/display_name/role/harness_id/verdict/needs_rescue/pending_work/pending_work_why/available/hard_reasons[]/soft_reasons[]/reasons[](=硬+软,兼容)/attempts/max_attempts/escalated/cooldown_left/entry_state/entry_reason` |
| `POST …/member/{mid}/recover` | 单人手动抢救（`recover_member`） | `{success, member_id, entry_state, entry_reason, …_run_one 输出(action/attempts/reasons/revive 等)}` |
| `POST …/recover-scan` | 全间手动扫描（`recover_scan`） | `{success, results{mid→out}, acted{mid→action}, idle_skipped[], summary}` |

**写操作仅后两个 POST**（手动触发即主路径；有审计/讨论区留痕）。自动扫描是环境变量开关的后端行为，**界面不提供开启入口**（不越权）。

## 2. 放哪、长什么样

**`workshop.html` 右栏，FE-08「📇 会话流程」面板之下**，同级新面板「**🛡 成员状态**」（v1.3 标题中性化，39 号建议）：

```
┌ 🛡 掉线抢救     [summary 原文胶囊]   [⟳]  [🔄 全间抢救扫描] ┐
│ ┌ 成员卡（按 verdict 三态）───────────────────┐         │
│ │ idle  ：⚪ 当前无进行中的工作                    │         │
│ │         「当前没有在进行的工作（空闲是正常态）」原样     │         │
│ │ healthy：🟢 正常 · 有活在进行                     │         │
│ │ rescue ：⚠ 需要抢救  attempts 1/3 · 冷却 59s     │         │
│ │         · 硬信号非空 →「联系不上（桥已退出）」红标     │ ← 36号：只认 hard_reasons │
│ │         · reasons 逐条；soft 信号收在「详情 ▸」       │         │
│ │         [对该成员抢救]   ← 仅 rescue 卡有          │         │
│ │ escalated → 红徽章「需要你处理」置顶                │         │
│ └──────────────────────────────────────┘         │
│ ─ 扫描结果（点「全间抢救扫描」后展开）─              │
│   后端 summary 原文 + acted 明细（mid→action）       │
│   + idle_skipped 列表（文案=「未打扰」）             │
└──────────────────────────────────────────┘
```

- `entry_state` 按惯例显示（读它不读 status）；`pending_work=false` 的行不渲染任何"异常"底色。
- 头部 `summary` **直接显示后端原文**（它已按老板口径写好四种情形）。
- 卡片骨架/错误态/两套 404 形状：与 FE-08 同规范（黄条中文，不冒充"待抢救"）。

## 3. 交互

- **拉取时机**：进工作间载入（与 `loadSessionFlow` 同时机）+ 单人 recover / 全间 scan 成功后立刻刷新 + 头部 ⟳ 手动刷新；**零新轮询**。
- 按钮飞行中禁用（「抢救中…/扫描中…」）；**仅 `verdict=rescue` 的卡显示抢救按钮**——idle 卡连按钮都没有，物理上杜绝"打扰空闲"。
- 单人 recover 结果：卡内展示 `action/attempts/reasons`（`action=idle` 时文案=「空闲，未执行任何动作」——与后端口径一致）。
- 全间 scan 结果：面板底部结果区，`acted` 与 `idle_skipped` **分两栏**渲染，绝不合并成"完成 N 项"。

## 4. 不做

- 不做自动扫描开关 UI（老板定的"自动兜底默认关"，属后端配置）；
- 不在 ops/booths 页重复本面板；不动 FE-08 面板；不加轮询。

## 5. 验收（隔离实例 + AC_FE_BASE + 自建自清）

1. 自建间+成员（无在进行的活）→ `offline-report` 实渲染：**idle 卡中性措辞**，全文无「掉线」、无红警示（反向断言之一）；
2. 点「全间抢救扫描」（真实）→ 结果区：summary「本轮无需动作；另有 N 名…**未打扰**」，`acted` 空、`idle_skipped` 含该成员；**我方文案无「已抢救/抢救成功」**（反向断言之二）；
3. 罐头 `verdict=rescue`（route 拦截 offline-report）→ 红黄卡、reasons/attempts/冷却、抢救按钮出现；点按钮走罐头 recover 展示 action/reasons；
3b. 罐头软信号（`hard_reasons=[]`、`soft_reasons=[心跳失联…]`）→ **卡片不出现「联系不上」**，soft 只在详情里（反向断言之三）；`hard_reasons` 非空的罐头 → 才显示「联系不上」红标；
4. 罐头 `escalated=true` → 「需要你处理」徽章；
5. 业务 404（不存在成员）→ 中文错误条；1600/1280/1024 无横向溢出；写请求仅两个 POST 且在隔离实例自建数据上；Console 无红字。
