# V101 · 外部 agent 的"自报"不算通过：接入联调的统一判据

> 起因（2026-10-25，老板原话「**浪费了一堆成本**」）：
> 为了让 Cherry Studio 的 MCP 插件"在它自己的会话里发消息给我看"，我陪它来回改了四五轮：
> 它每次返回 `ok:true / in_session:true / message_id`（每次还都不一样），
> 平台再用它给的 `session_messages` 读回，**也找到了口令**，我就判"通了"。
> 结果用户界面上什么都没有 —— 我用只读副本去读它自己的 SQLite 才发现：
> **12:58 之后一条都没落库**，口令全库 0 命中。它"读回"的是它自己的缓存。

## 1. 铁律（写进验收口径，不许再犯）

**接受外部 agent 的接入成果时，只认这三类证据：**

| # | 证据 | 判据 |
|---|---|---|
| ① | **对方应用自己的存储**（数据库/文件/日志） | `python tools/verify_session_truth.py --db <它的库> --needle <口令>` → **exit 0 才算通** |
| ② | **用户的眼睛**（他自己在那个界面上看到） | 用户说看到才算看到；界面截图不能替代"我正在看的窗口" |
| ③ | **平台自己真做的事**（我们自己写盘、我们自己真调的接口） | 平台侧代码可复现、可回查 |

**凡是"对方返回的字段"（`ok / in_session / message_id / session_id / title`…）一律只当线索，不当证据。**
尤其是它自己提供的"读回工具"—— 那可能读的是它自己的缓存，**不能用来证明它写了别人看的界面**。

## 2. 联调顺序（先定判据，再联调）

```
① 先写判据（怎么算通、读谁的库/看谁的界面）
② 再让对方改插件
③ 每次它说"改好了"，直接跑判据，不信自报
④ 判据不过就停，不做第四、第五轮猜测
```

这次多烧的成本，全在"没先定判据 → 它说好了 → 我去猜为什么"上。

## 3. 已知的具体结论（Cherry Studio，2026-10-25）

- `session_post` / `session_messages` 返回体**结构对**，但 13:00 之后不再写入 `cherrystudio.sqlite`
  的 `agent_session_message`（真库最后一条对话是 12:58:06，口令 `5BAB71`）；
- ⇒ 该插件的"会话内发言"**当前不可用**；平台不能因此打"能在自己会话里说话"的勾；
- 什么时候可以再试：它说清写到哪张表/哪个字段，我用 `verify_session_truth.py` 验到 exit 0 为止。

## 4. 平台侧要跟着改的（待办）

1. `test-now` / `deliver` 的 `in_session_verified` 加一句限定：
   **"这只代表对方的读回工具看到了，不代表界面看到了"**（文案要写清，别让人误读）；
2. 对接中心给一个「**真相核对**」入口：填对方库路径 + 读口令，exit 0 才亮绿勾（可选，默认不填）；
3. 永不把对方自报字段写进"验收通过"的分支。
