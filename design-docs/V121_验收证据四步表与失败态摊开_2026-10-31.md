# V121 · 验收失败态摊开（证据四步表）与「L1 无核对」漏洞

> **日期**：2026-10-31 ｜ **状态**：**已拍板（2026-10-31 老板定，按本稿实施）**
> **老板拍的两条**：① `L1` 走 **B 方案**——必须带凭据，没凭据按 `L4`（人眼确认）算；
> ② **产物空不许判「通过」**，且这条**写进 `V116`** 当正式规则（不再只活在代码里）。
> **起因**：继承书 §6 第 1 项 —— 「第 14-15 步（产物 → 验收）失败态照派活那样摊开（缺哪级证据 / 该谁补 / 补完点哪儿）」
> **实测环境**：临时实例（换端口 + 换数据目录 + 换心智根，`AC_PORT/AC_DATA_DIR/AC_MIND_ROOT` 全换）真派活真验收。
> **证据来源标注**：`【实测】`＝临时实例真 HTTP 请求返回；`【源码】`＝读实现确认；`【未验证】`＝推断。

## 1. 大白话：现在用户卡在哪

平台第 14-15 步是「员工交产物 → 组长验收」。派活那一段（第 13 步）已经做得很好：真机上失败会告诉你**卡在哪一步**，
比如「前三步已落盘，但触达失败」「manifest 没登记这条任务（G0 会拦后续派活）」，还写着该点哪儿。

**验收这一段没有。** 用户点「通过」时，如果条件不满足，平台只回一句话：

```
【实测】POST …/tasks/1/review  {"result":"通过"}
HTTP 400  {"ok": false, "code": "EVIDENCE_REQUIRED",
           "error": "「通过」必须给 evidence_level（≥L1）",
           "next": "带上 evidence_level：产物目录 diff 过 ⇒ L0；人工看过 ⇒ L4"}
```

用户看完仍然不知道三件事：

1. **我手上现在有什么？** —— 产物目录里到底有没有文件？扫过没有？回执收到没有？（得自己再去点三个端点拼）
2. **该谁去补？** —— 是让员工重写产物、让组长自己看一眼给 L4、还是平台重扫一次？
3. **补完点哪儿？** —— `next` 只说"带上 evidence_level"，没说先后顺序（先扫描→再验收）。

---

## 2. 顺带抓到的两个真问题（比原计划更严重，必须先说）

### 2.1 `L1` 档**没有任何核对**，随便填就过 【实测】

`L1` 的设计语义是「它库已有」（去外部 agent 自己的库里查得到）。但**验收代码里没有任何人去看那个库**：

```
【实测】第一次运行（产物目录是空的）：
POST …/tasks/1/review  {"result":"通过","evidence_level":"L1","note":"接口写清了"}
HTTP 200  {"ok": true, "state": "accepted", "evidence_level": "L1",
           "artifacts": {"total_files": 0, "empty": true,
                         "note": "`产物/` 里一个文件都没有 —— 自报'做完了'不算（L3）"}}
```

也就是说：**产物一个都没有、也没有任何核对，只要在 `evidence_level` 里写个 `L1`，任务就判「通过」了。**
`L3`（大模型自报）被明确拒绝，理由是"永不采信"；而 `L1` 这个"平台没核对过的自述档"却畅通无阻——
这正是 2026-10-25 那条教训的同类：**对方说通了不算，得去它自己的库里查**（`tools/verify_session_truth.py` 那套判据）。

### 2.2 先扫过产物、再验收 ⇒ `new` 变空，容易被看反 【实测】

`summary_for_task()` 的 `new`/`changed` 是**相对上一次快照**的 diff。所以：

| 顺序 | `new` | `total_files` | `empty` |
|---|---|---|---|
| 先验收（内部自动扫） | `["前端组/api.md"]` | 1 | false |
| **先点过「扫描产物」再验收** | `[]` | 1 | false |

两次都是**同一个盘上事实（1 个文件）**，但 `new` 一个有一个没有。前端若用 `new` 判断"有没有交东西"，
就会把"已经交好了"显示成"什么都没交"。**【实测】两次真返回已抓下。**

## 3. 方案：验收也走「四步表」，和派活同一个形状

### 3.1 形状（沿用派活，前端不用学新东西）

```json
{
  "steps": [
    {"n": 1, "name": "派活记录",   "ok": true,  "what": "T-001 派出于 …（触达：人工）", "level": ""},
    {"n": 2, "name": "产物在盘上", "ok": true,  "what": "1 个文件：api.md（5 B）",      "level": "L0"},
    {"n": 3, "name": "回执留痕",   "ok": false, "what": "还没收到回执",                 "level": "L2"},
    {"n": 4, "name": "人拍板",     "ok": false, "what": "还没人给结论",                 "level": "L4"}
  ],
  "evidence_have": ["L0"],
  "blocking": "人拍板",
  "who_should_fix": "组长",
  "why": "产物已有 1 个文件，但还没人给结论",
  "next": "看过 `前端组/产物/` 后点「通过」；没看过就点「返工」",
  "manual_required": false,
  "manual_hint": ""
}
```

**为什么是四步、且第 1/4 步与第 2/3 步性质不同**（这条最要紧，写错就会假红）：

- **第 1 步「派活记录」** 是**硬前置**：账本里没有这条任务，验收根本无从谈起（现在直接 `NO_SUCH_TASK`）。
- **第 2/3 步「产物在盘上 / 回执留痕」** 是**可用的证据档**，**不是必须全绿**——
  老板的规则是「有一档够格就行」：产物真有 ⇒ `L0`；回执留痕 ⇒ `L2`；都没有、但组长自己看过 ⇒ `L4`。
  把它们画成"必须都打勾的进度条"就是撒谎。
- **第 4 步「人拍板」** 是**硬收尾**：必须有人给 通过/返工/拒收。

### 3.2 字段语义（一处真相，前端照着渲染）

| 字段 | 含义 | 谁算出来的 |
|---|---|---|
| `steps[]` | 四步，`ok` 只表示"这步的事实成立与否"，**不代表整体能不能过** | 平台 |
| `steps[].level` | 这步对应的证据档（`L0`/`L2`/`L4`；第 1 步空） | 平台 |
| `evidence_have` | 这条任务**现在真有的**证据档（只列真成立的） | 平台 |
| `blocking` | 卡在哪一步（名字，与派活 `stuck_at` 同词表） | 平台 |
| `who_should_fix` | 该谁去补：`组长` / `员工` / `桥` / `平台` | 平台 |
| `why` | **具体**原因（带真实数字，如"产物 0 个文件""账本里没有 T-007"） | 平台 |
| `next` | 下一步**动作**（点哪个按钮 / 打哪个端点 / 先做哪步） | 平台 |

### 3.3 `L1` 的处置（**已拍板：走 B**）

| 选项 | 做法 | 代价 |
|---|---|---|
| A. L1 也由平台真核对 | 接 `verify_session_truth` 那套：必须给"核对凭据"（查哪个库/口令/时间），核不到就拒 | 最严，但外部 agent 形态各异，很多根本给不出库路径 ⇒ 会大面积走不通 |
| **B. L1 必须带凭据，没凭据按 L4 算** ← **老板 2026-10-31 选定** | `evidence_level=L1` 时**必须**同时给 `evidence_ref`（谁核的/核的什么/工具或命令）；不给 ⇒ 400 `L1_NEEDS_PROOF`，并在 `next` 里教它怎么补；给了就落账本并在界面标「L1（人工凭据，平台未核对）」 | 中等；**不假装平台验证过**，也不因形态差异把路堵死 |
| C. 取消 L1 | 只留 L0/L2/L4 | 最干净，但与已发布模型（`V116` 证据档）冲突，改动面大 |

**落地口径（照此写码）**：

1. `evidence_level=L1` **且** `evidence_ref` 为空 ⇒ `400 L1_NEEDS_PROOF`，`next` 明确教怎么补
   （"填 `evidence_ref`：哪个库/哪个会话/谁核的/用什么工具核的"），并在 `steps` 里把 `blocking` 指到「人拍板」这一步；
2. 给了 `evidence_ref` ⇒ 照过，但账本记 `evidence_ref` 与 `evidence_ref_is_manual=true`；
3. **界面/响应一律标「L1（人工凭据，平台未核对）」**，不许显示成"平台已验证"；
4. 老板特别交代的推论：**没有凭据的 `L1` 降级成 `L4`**——即"你说是它库里有，但拿不出凭据 ⇒ 按人眼确认算"，
   所以 `evidence_have` 里要如实只标 `L4`，不标 `L1`。

## 4. 端点契约（只加不改）

### 4.1 新增只读端点 `GET /api/workshop/{id}/tasks/{task_seq}/evidence-view`

为什么需要它：用户点「通过」**之前**就得看见缺什么。现在只有 `POST …/review` 的**失败后**才有一句话，
而 `POST` 会写盘 —— 不能在"看"的时候写盘（与 `GET …/artifacts` 只读不代扫同一原则）。

- **只读**：不扫产物、不写 `_meta/`、不改账本；拿的是上次快照 + 账本现状。
- 返回 §3.1 那个结构 + `artifacts_snapshot`（`scanned_at` / `total_files` / `slot_exists` / 最近 3 个文件名）。
- 没扫过产物时：`steps[2].ok=false, what="还没扫过产物（点「扫描产物」；直接点「通过」时平台也会自动扫一次）"`，**不代扫**。
- `next` 给具体动作，例如「先 `POST …/verify-artifacts`，再回来看」。
- **`?level=L0|L1|L2|L4`（实现时补上的）**：预演"我打算按这档验收会卡在哪"。
  不传时 `blocking` 按"还差人拍板"算；传了才与真打 `POST` 的 `blocking` 对等（响应回填 `given_level`）。
  没有它，前端只能在**点了之后**才知道卡点 —— 而这正是本稿要消除的体验。

### 4.2 `POST …/review` 失败态补上同一张表

现有 `code`/`error`/`next` **一个都不删**（兼容），在响应里**追加** `steps`/`evidence_have`/`blocking`/`who_should_fix`。
即：老前端不动也照跑，新前端能渲染四步表。

### 4.3 `artifacts` 里补两个字段（修 §2.2 那个看反的坑）

`summary_for_task()` 追加：

- `files_now`：盘上**现在**的文件名清单（最多 10 个）—— 判"有没有交东西"只看它，**不看 `new`**；
- `new` 的语义在响应里明确成 `"上次快照之后新增（可能为空，不代表没产物）"`（现在是隐式的）。

### 4.4 「产物空不许通过」的落点（老板拍板第 ② 条）

现有 `ARTIFACTS_EMPTY` 只拦 **`L2` + 空产物**。按拍板口径扩大成：**任何档位在"盘上真扫到 0 个文件"时，
只允许 `L4`**；`L0`/`L1`/`L2` 一律拒，错误码仍用 `ARTIFACTS_EMPTY`，但 `error` 文字要按档位说清：

- 选 `L0` ⇒ "你说产物已在盘上，但真扫是 0 个文件 —— 这次扫描结果与你的说法冲突"（`next`：先 `verify-artifacts` 看一眼，或把目录名对上）；
- 选 `L1`/`L2` ⇒ "只有自述/留痕、产物目录是空的 —— 只能按 `L4` 人眼确认，或让它真写出产物"。

`L4` 不受限（人眼确认本来就不依赖盘上文件）。

## 5. 前端口径（交给前端会话）

- 验收区改成「四步表」卡片：**第 1/4 步实心、第 2/3 步标成"证据档"并给勾/叉 + 档位徽章**（不要画成 4 个必过的进度点）。
- 「通过」按钮旁显示 `evidence_have`：「现在可用：L0」，点开显示每个档"谁核过、核的什么"。
- 失败时把 `why` + `who_should_fix` + `next` 原样显示（与派活卡同款排版）。
- **不许**在界面上把 `L1` 写成「平台已验证」。

| # | 判据 | 怎么真判 |

| 2 | 「通过」不给等级 ⇒ `EVIDENCE_REQUIRED` + `steps` 里第 2/3 步如实反映现状 | 临时实例真打 |

| 5 | `L1` 无凭据 ⇒ 400 `L1_NEEDS_PROOF`（老板选 B，**已定**） | 真打 |
| 6 | 四步表在**同一个实例、同一份数据**上，`POST` 失败返回与 `GET evidence-view` **事实层一致**：`evidence_have` 相等、`steps[].{name,ok,level}` 相等（规则 20 一处真相）；`blocking` 用 `?level=` 对齐后再比 | 两边真打比对 |

| 7 | 全程 `evidence-view` 不写盘：调用前后 `_meta/artifacts.json` 的 mtime 与 sha256 不变，账本字节不变 | 真文件比对 |
| 8 | 产物空 + `L0`/`L1`/`L2` ⇒ 一律 `ARTIFACTS_EMPTY` 拒；`L4` 放行（老板拍板第 ② 条） | 四种档位各真打一次 |

> **判据 6 的边界（实测踩过，写下来免得下次又当 bug 修）**：`POST …/review` 会**真扫一次**产物，
> 只读视图按设计**不扫** ⇒ 同一时刻一个说「扫过了，0 个文件」、一个说「还没扫过」，
> 两句都是真话，**不许**去比对 `what` 的措辞；`blocking` 取决于「这次想用哪档」，
> 所以 `POST` 从 body 知道、只读视图要用 `?level=` 才对等。

## 7. 拍板结果（2026-10-31，老板亲定）

1. **`L1` 处置 ⇒ B**：必须带 `evidence_ref` 凭据；没凭据按 `L4` 算（见 §3.3 落地口径 1~4）。
2. **`who_should_fix` 词表**：**沿用** `组长 / 员工 / 桥 / 平台`（老板未要求改；界面如需显示具体人，
   由前端从名单取工位名，后端只给角色 —— 避免同一件事两个来源）。
3. **产物空能不能通过 ⇒ 不能**：`L0/L1/L2` 一律拒、只许 `L4`；**并写进 `V116`** 当正式规则（不是只在代码里）。
