> 状态：**已实施**（2026-11-04 老板批「可以批准进入实现」后当天落地）。

---

## 1. 为什么要它

现在平台对 MCP 客户端是一套**工具**：`list_harnesses` / `list_tasks` / `get_task` / `create_workshop` …
客户端要"知道平台里有什么"，只能**调工具**，而且每次都得先想清楚调哪个、参数怎么填。

MCP 规范里另有一层：**Resources**——只读、可按 URI 定位、客户端可以列出来当"目录树"给人点。
典型差别：

| | 工具（已有） | 资源（本文） |
|---|---|---|
| 语义 | "**做**一件事" | "**看**一样东西" |
| 谁发起 | 模型决定调用 | 客户端列出、用户点开 |
| 结果形态 | 一段文本 / JSON | 一份**可按 URI 再取**的内容 |
| 副作用 | 可能有 | **保证没有**（只读） |

老板要的就是后者：**客户端能直接"看"到工作间**，不用先学会调工具。

## 3. 范围（**只读**，写的一律不做）

### 做

1. `initialize` 声明 `capabilities.resources = {"subscribe": false, "listChanged": false}`；
2. `resources/list` —— 列出**固定入口**（不带参数的资源）；
3. `resources/templates/list` —— 列出**带参数**的资源模板（如某个工作间）；
4. `resources/read` —— 按 URI 取内容；
5. 两个入口（stdio / HTTP）**同一份实现**，HTTP 侧只做分发；
6. 判据工具 `tools/mcp_resources_check.py`（§7）。

### 不做（每条都有理由，不是省事）

| 不做 | 理由 |
|---|---|
| `resources/subscribe` 实时推送 | 我们唯一的"事件"是服务端内存态变化，没有总线；stdio 单进程下推送收益远小于复杂度。**如实声明 `subscribe: false`** |
| `resources/listChanged` 通知 | 同上；列表变化时客户端下次 `list` 自然能看到 |
| 通过资源**写**东西（改状态/派活） | Resources 在规范里就是只读；写一律走工具，别发明第二套写入口 |
| 把产物文件整包塞进资源 | 产物可能很大且是用户的；只给**清单 + sha256**（与 v5 验收同口径），要看内容走工具 |

## 4. URI 面（**待老板确认的就是这张表**）

命名空间用 `ac://`（agent community）。**全部只读、全部来自已有 API**，不新增数据源。

### 4.1 固定资源（`resources/list` 直接列出）

| URI | 名称 | 内容 | 来源（**真实端点，已逐个核实**） | mimeType |
|---|---|---|---|---|
| `ac://status` | 平台状态 | 版本 / 端口 / 启动时长 / 六协议可用性 | `GET /api/status`、`GET /api/protocols` | `application/json` |
| `ac://harnesses` | 接入清单 | 每个 harness 的 id / kind / 档位 / 是否在线（**脱敏**，见 §6） | `GET /api/harness/list` | `application/json` |
| `ac://agents` | 员工清单 | 平台登记的 agent（与接入清单不是一回事） | `GET /api/agents` | `application/json` |
| `ac://workshops` | 工作间清单 | id / 名称 / 状态 / 成员数 / 任务数 | `GET /api/workshops` | `application/json` |
| `ac://tasks` | 平台任务清单 | 任务（**默认 50 条**；再多用 §5.4 的游标翻页） | `GET /api/tasks` | `application/json` |
| `ac://protocols` | 协议目录 | 每条协议的 `layer` / `semantics` / `status` | `GET /api/protocols` | `application/json` |

### 4.2 模板资源（`resources/templates/list` 列出，客户端按需展开）

| URI 模板 | 名称 | 内容 | 来源 |
|---|---|---|---|
| `ac://workshop/{workshop_id}` | 一个工作间 | 工作间主体：状态、组长、成员、当前阶段 | `GET /api/workshop/{id}` |
| `ac://workshop/{workshop_id}/members` | 工作间成员 | 成员清单（工位 / 角色 / 状态 / 是否已接上） | `GET /api/workshop/{id}/members-status` |
| `ac://workshop/{workshop_id}/tasks` | 工作间任务 | 任务清单（序号 / 标题 / 账本状态） | `GET /api/workshop/{id}/tasks` |
| `ac://workshop/{workshop_id}/tasks/{seq}` | 一条任务 | 单条任务的**证据四步 + 验收结论** | `GET /api/workshop/{id}/tasks/{seq}/evidence-view` |
| `ac://workshop/{workshop_id}/manifest` | 产物清单 | `产物/` 的清单 + `sha256`（**不搬文件内容**） | `GET /api/workshop/{id}/manifest` |

### 4.3 为什么不给"工具清单"当资源

`tools/list` 已经是协议层能力，再做一个 `ac://tools` 资源等于**两处口径**。不做。

## 5. 协议语义（三处硬要求）

### 5.1 响应形状

```jsonc
// resources/list
{"jsonrpc":"2.0","id":N,"result":{"resources":[
  {"uri":"ac://workshops","name":"工作间清单","description":"只读：...","mimeType":"application/json"}
]}}

// resources/templates/list
{"jsonrpc":"2.0","id":N,"result":{"resourceTemplates":[
  {"uriTemplate":"ac://workshop/{workshop_id}","name":"一个工作间","description":"...","mimeType":"application/json"}
]}}

// resources/read
{"jsonrpc":"2.0","id":N,"result":{"contents":[
  {"uri":"ac://workshop/ws-demo-01","mimeType":"application/json","text":"{...}"}
]}}
```

- `text` 里是 **JSON 字符串**（`ensure_ascii=False`）——不是"给人看的散文"，客户端要能直接解析；
- `description` 是**给人看的一句中文**（客户端 UI 会显示它）；
- 目标不存在 ⇒ **错误码 `-32002`**（MCP 规范的 Resource not found），消息里带"找不到哪个 URI"；
- URI 语法不合法 ⇒ `-32602`（Invalid params）。

### 5.2 大小上限（防把客户端上下文撑爆）

- 单次 `read` 的 `text` 上限 **可配置**：环境变量 `AC_MCP_RESOURCE_MAX_BYTES`，默认 **65536**（64 KB）；
- 超了：**截断**并在正文里加
  `{"truncated": true, "full_size": <字节>, "next": "ac://<同类>?cursor=<opaque>"}`；
- **禁止**"悄悄截断"——那是"看起来成功"的死状态；
- 清单类资源（`tasks` / `workshops` / `agents` / `harnesses`）超限时**优先翻页**（§5.4），
  只有单条对象本身超限才真截断（那种情况给 `next` 说明"用工具取完整内容"）。

### 5.4 游标翻页（清单类资源）

- **协议层**：`resources/list`、`resources/templates/list` 支持 `params.cursor`，响应带 `nextCursor`
  （页面大小 50；条目不足时**不返回** `nextCursor`，客户端据此停）；
- **资源层**：清单内容超限时在正文里给 `next`＝`ac://tasks?cursor=<opaque>`，
  读带 `?cursor=` 的 URI 就取下一页。`cursor` 是**不透明**字符串（base64 的整数偏移），客户端不许解析；
- 两套游标互不影响：协议层管"有多少个资源条目"，资源层管"一个资源里有多少条记录"。

### 5.3 一处真相

| 内容 | 唯一位置 |
|---|---|
| 资源 URI 表 / 模板表 / `read` 的取数逻辑 | `mcp_server.py`（`RESOURCES` / `RESOURCE_TEMPLATES` / `read_resource()`） |
| HTTP 入口分发 | `routers/mcp_http.py` 只调上面三个名字，**不重写取数** |
| 状态字符串归一化 | `platform/a2a_result_poll.raw_state_of()`（已有，别再造一份） |

## 6. 安全与脱敏（**硬要求**）

| 风险 | 处理 |
|---|---|
| 令牌 / key 明文 | `ac://harnesses` **只给** `has_token: true/false`；沿用 `tools/credential_check.py` 的"只给位置/指纹"口径 |
| 本机绝对路径 | 资源正文里**不出现**真实本机路径；受限字段一律相对路径或省略 |
| 别人的数据 | 只读**本平台**，无横向越权面（没有多租户） |
| 敏感字段 | 平台侧已有脱敏函数优先复用；没有的字段**不出现在资源里**，别自己拼 |

> 判据（§7 第 ⑧ 格）会**逐条真读**并断言正文里不含 `token` / `sk-` / 盘符路径。

## 7. 判据：`tools/mcp_resources_check.py`（**12 格**，真起实例真走协议）

参照 `mcp_tools_check.py` 的做法：起**临时实例**（换端口 + 换数据目录），用一个**真 MCP 客户端**走 JSON-RPC。

| # | 格 | 断言 |
|---|---|---|
| ① | 能力声明 | `initialize` 回来 `capabilities.resources` 存在且 `subscribe=false` |
| ② | 固定资源非空 | `resources/list` ≥ 5 条，每条有 `uri/name/mimeType` |
| ③ | 模板非空 | `resources/templates/list` ≥ 5 条，含 `ac://workshop/{workshop_id}` |
| ④ | 逐个真读 | ②③ 里每个 URI 都能 `read` 成功，且 `text` **能 `json.loads`** |
| ⑤ | 数据是真的 | 临时实例里**真建一个工作间 + 派一条任务**，`ac://workshops` 与 `…/tasks` 里能查到它（不是空壳） |
| ⑥ | 模板展开 | 用 ⑤ 的真实 `workshop_id` 展开模板，读到同一个对象 |
| ⑦ | 不存在就说清 | 读 `ac://workshop/不存在的ID` ⇒ `-32002` + 消息里带该 URI |
| ⑧ | 脱敏（**双平台**） | 所有 `text` 里 **不含** 令牌明文、`sk-` 前缀、Windows 盘符路径（`X:\`）、**POSIX 绝对路径**（`/` 开头且深度 ≥ 2 段，排除 URI 与 URL）；实测 `GET /api/status` 里有 `pipe_dir` 真实路径 ⇒ 资源层必须**白名单投影**掉它 |
| ⑨ | 超限翻页/截断 | 塞一个超上限的清单（测试夹具）⇒ 返回 `truncated=true` 且 `next` 可读下一页，两页合起来 = 全量、无重复无遗漏 |
| ⑩ | 只读 | 资源路径**不改任何状态**：读前后 `harnesses.json`/`workshops.json` 的 sha256 不变 |
| ⑪ | HTTP 入口同源 | 同一个 URI 走 `POST /mcp` 与 stdio **返回一致**——比对用 **`ac://workshops` + `ac://protocols`**（不含时间/启动时长的稳定资源），并**剔除已知动态键**；`ac://status` 因含 uptime 不参与逐字比对，只断言两边同版本 |
| ⑫ | 未知方法不崩 | `resources/unknown` ⇒ `-32601`，进程仍活着（后续 `tools/list` 正常） |

跑完删临时实例与临时数据目录（与 `mcp_tools_check.py` 同款收尾）。
