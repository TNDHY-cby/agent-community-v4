## 1. 先把一件事说清：**MCP 没有"账本条目"这个概念**

上一场汇报里把这件事写成"MCP 异步结果要不要自动回写**账本**"，这句话本身**不准确**，先纠偏——
否则做出来一定是个"看起来成功"的死状态：

| | A2A 派活 | MCP 工具调用 |
|---|---|---|
| 平台先做了什么 | **建了一条任务**（`dispatch` 建 `task_seq`） | 只是**调了一次工具**，什么都不建 |
| 有没有账本条目 | 有，`task_ledger` 里那条 | **通常没有** |
| 所以能不能"回写账本" | 能（现在就是自动的） | **不能**，除非这次调用本来就挂在某条任务上 |

⇒ 现状的"要手动查"不是懒，而是**结果没有家**。所以设计的第一件事是**给它一个家**，而不是"自动写账本"。

## 2. 现状（2026-11-04 实测）

| 事实 | 位置 |
|---|---|
| 平台调外部 MCP 工具，遇到 `pending` 会**交出句柄** | `mcp_client.mcp_call_tool` → `{ok: False, async: True, handle}` |
| 句柄能按约定查一次（`tasks/get` 或对方的查状态工具） | `mcp_client.mcp_task_get`（状态归一化成 `working/done/failed/cancelled/unknown`） |
| 有个**只读端点**能手动查 | `GET /api/docking/harness/{hid}/mcp-task/{handle}` |
| A2A 侧是**自动**的 | `a2a_result_poll.sweep_once()` 由 `_autonomy_recovery_loop` **20 秒**调一次，终态就 `task_ledger.note_external_result` 并出队 |
| MCP 侧**没有任何自动动作** | 全仓无 `mcp_result_poll` / 无 MCP 待查队列 |

⇒ 两边标准差一截：**同一个平台，A2A 的活自己会回来，MCP 的活要人动手查。**

## 3. 结果往哪去（**本文的核心决定**）

### 3.1 两条去向，按"有没有家"分

| 情形 | 去向 | 判据 |
|---|---|---|
| 这次调用**挂在某条任务**上（`workshop_id` + `task_seq` 都给了） | 写**任务账本**（`task_ledger.note_external_result(source="mcp")`） | 账本里那条从 `issued` 推进到 `delivered`，`external.source == "mcp"` |
| 没有挂任务（对接中心"试一下 / 送话 / 可视探测"） | 写**出站调用结果表** `mcp_outcalls.json` | 表里那条 `state` 从 `pending` 变终态，带 `text` / `error` / `at` |

> **不做的假动作**：不许"没有账本条目也硬塞一条账本"。那会污染验收历史（谁干的活说不清）。

### 3.2 出站调用结果表长什么样

```jsonc
// mcp_outcalls.json（有界：MAX_OUT=200，只留最近）
[{
  "call_id": "mcp-20261104-153000-3f9a",     // 幂等键
  "harness_id": "<接入 id>",
  "url": "<MCP 端点>",
  "tool": "<工具名>",
  "handle": "<对方给的句柄>",
  "convention": {"kind": "tasks"|"job_tool", "tool": ""},
  "workshop_id": "",                          // 空 = 没挂任务
  "task_seq": 0,
  "added_at": 0.0, "last_at": 0.0, "tries": 0,
  "state": "pending"|"working"|"done"|"failed"|"cancelled"|"unsupported"|"expired",
  "text": "", "error": "", "why": ""
}]
```

- 界面上"对接中心 → 该 harness → 最近调用"直接读它（**只读**，不加新的写入口）；
- 端点：`GET /api/docking/harness/{hid}/mcp-calls?limit=20`（新增一个**只读** GET）。

## 4. 队列与轮询（与 A2A **一处真相**，不另造一套骨架）

### 4.1 队列：`mcp_pending.json`

**为什么不复用 `a2a_pending.json`**：

| 复用（一个文件 + `kind` 字段） | 分开（本文选这个） |
|---|---|
| 一个 sweep 一处统计 | 两个 sweep，但各自字段**完全不同**（A2A 有 `a2a_task_id`，MCP 有 `handle`/`convention`/`args_key`） |
| 但 A2A 那条现在**在跑真数据**，改结构要迁移，风险落在"已经在工作的功能"上 | MCP 这条**全新**，坏了不影响 A2A |

⇒ 文件分开，**纪律共用**：与 `a2a_result_poll` 同款上限/TTL/节流/统计口径（常量值一致：`MAX=200`、`TTL=24h`、`GAP=30s`）。
两边共用 `raw_state_of()`（已有）做状态归一化 —— 那才是真正必须一处真相的部分。

### 4.2 轮询：并入现有 20 秒循环

```python
# server._autonomy_recovery_loop（现有）
_a2a_stats = _a2a_sweep()
+ _mcp_stats = await mcp_result_poll.sweep_once()      # mcp_task_get 是 async，直接 await
+ if _mcp_stats.get("done") or _mcp_stats.get("failed") or _mcp_stats.get("dropped"):
+     print("[mcp-poll] 本轮：%s" % json.dumps(_mcp_stats, ensure_ascii=False), flush=True)
```

- **不新起线程**（多一个常驻线程就多一处"谁在跑、跑没跑"说不清）；
- 单轮最多查 **5 条**（别把别人的 MCP 端点打爆，与 A2A 的节流同思路）；
- 循环整体已在 `try/except` 里，MCP 这段再包一层 + `_warn_once("mcp_poll", ...)`（失败要说话）。

### 4.3 状态机

```
登记(pending) ──查一次──┬─ working      → 留在队列，等下一轮
                        ├─ done/failed/cancelled → 写去向（账本或出站表）→ 出队
                        ├─ unsupported → 出队 + 写 why（"它不支持异步约定"），不再重试
                        ├─ 连不上/超时 → 记 last_error，重试到 TTL
                        └─ 账本里没这条任务（工作间被删）→ 出队 + 写 why，不无限重试
超 TTL（24h）→ 出队，state=expired，写明"对端一直没给终态"
```

## 5. 登记点（谁负责 `add()`）

**不在 `mcp_client` 里登记**（那是纯协议层，不该依赖平台存储）。
在调用方包一层，做成**一处真相**：

```python
# routers/docking.py 内部
async def _mcp_call_tracked(harness_id, url, tool, args, *, workshop_id="", task_seq=0):
    """调一次外部 MCP 工具；遇到 pending 就登记进待查队列。所有挂点都走它。"""
```

挂点清单（现有代码里 `mcp_call_tool` 的 5 处调用）：

| 挂点 | 用途 | 挂任务？ |
|---|---|---|
| `POST …/test-now`（带 text 时） | 对接中心"试一下" | 否 |
| `POST …/deliver`（`via_session` 走 MCP 时） | 送话 | 否 |
| `POST …/visual-run` / `visual-probe` | 视觉探测 | 否 |
| `GET …/sessions`（挑工具真调一次） | 探活 | 否 |
| **未来**：MCP 派活（若老板要，见 §8 方案 B） | 派活 | **是** |

⇒ 当前落地后：**5 个挂点都登记，但都进"出站表"**；`task_seq` 的分支先留着（有就要真写，没有不装）。

## 6. 失败要说话（**逐条写清，不许静默**）

| 情况 | 用户会怎么误解 | 处理 |
|---|---|---|
| 对端不支持异步约定 | "它在跑，等着就行" | `state=unsupported` + `why` 原文（复用 `mcp_task_convention.why`），界面标灰 |
| 对端一直不给终态 | "可能还在跑" | TTL 到点 `state=expired` + 说明；出站表里留着，不删 |
| 连不上 | "平台没在管" | `last_error` 记**真实原因**（异常类名 + 前 160 字） |
| 队列满 | "我登记的还在" | 丢最老 + 打印一条（与 A2A 同口径） |
| 账本里那条任务没了 | "写进去了" | 出队 + `why="账本里没有这条任务"`，**不假装写成功** |

## 7. 判据：扩展 `tools/mcp_task_check.py`（9 格 → **14 格**）

现有 9 格已经是**真起假 MCP Server**（不是 mock）。新增 5 格：

| # | 格 | 断言（真跑） |
|---|---|---|
| ⑩ | 登记与出队 | 调一个返回 `pending` 的假工具 ⇒ `mcp_pending.json` 里出现一条；查到终态后**自动消失** |

## 8. 三个方案，供拍板

| 方案 | 做什么 | 成本 | 风险 |
|---|---|---|---|
| **A（本文，推荐）** | 出站结果表 + "有账本条目才写账本" + 自动轮询 | 代码 ~260 行、判据 ~120 行、1 天 | 低：不动 A2A 现有队列 |

## 10. 实施记录（2026-11-04 落地时按实际情况改了两处，**都在这里如实写**）

### 10.1 挂点从「5 处」缩到「2 处」

原 §5 表格列了 5 个挂点。真去读代码才知道其中 **3 个是"读"**（读会话 `session_messages`、
列会话 `sessions_list`、test-now 的读回核对）——读请求几乎不会异步，登记只会白占待查队列，
还会让"待查数"虚高。**实际登记点只有两个"发送/执行"**：

| 位置 | 用途 |
|---|---|
| `docking._dispatch_via_session_post()` | 派活/送话走会话 |
| `POST …/test-now`（带 text 时） | 对接中心"试一下" |

其他两处（`_verify_session_readback` / `sessions_list`）**明确不登记**，理由写在代码注释里。

### 10.2 抓到并修掉一个**既有 bug**（非本次引入）

`mcp_client.mcp_task_get()` 在"调用方没给 convention、要现场探测"时：

```python
conv = mcp_task_convention(tools, ((init or {}).get("result") or {}).get("capabilities"))
```

而 `mcp_open_session()` 返回的**已经是解包后的 result** ⇒ `capabilities` 永远为空
⇒ **「标准 Tasks 扩展」永远探测不到**（只有 `job_tool` 那条靠工具名能命中）。
2026-11-03 那次提交引入，之前的判据①走"显式探测"所以没暴露；本次判据第 ⑩ 格第一次走自动探测就抓到了。
已改成两形状都兼容（`_init.get("result")` 存在就用它，否则用 `_init` 本身）。

### 10.3 单测把真实数据写了（**已修 + 已还原**）
