## 2. 建议做的前三项（按价值/成本排）

### 2.1 `prompts` —— **最值得做**

我们平台上已经有大量"给外端 agent 的成段话术"，但现在散在各处：注册话术（`/api/harness/register-prompt`）、
组长对接单（`…/lead-kit`）、成员 kit、自检清单、回执格式…… 用户要自己找端点、自己拼。

**做成 MCP prompts 之后**：客户端里直接出现「接入自检」「组长对接单」「交回执」这些**一键取用的模板**，
参数由平台填好（工作间 id、工位、任务号），人/模型都不用记端点。

| 提示名 | 参数 | 内容来源（**一处真相**，不另写一份文案） |
|---|---|---|
| `onboard-self-check` | — | 现有的"先自己测，不要先问人"五项自测 |
| `lead-kit` | `workshop_id` | `GET /api/workshop/{id}/lead-kit` |
| `member-kit` | `workshop_id`, `member_id` | 现有成员 kit |
| `task-receipt` | `workshop_id`, `task_seq` | 回执格式与判据（`/api/harness/task-result` 的契约） |
| `artifact-manifest` | `workshop_id` | `…/manifest` 的 G0 四要素 |

协议面：`prompts/list`（返回 `name/description/arguments`）、`prompts/get`（返回 `messages[]`，`role=user`，
`content.type=text`）。**参数不合法就报 `-32602` 并说明缺哪个**。

### 2.2 `completion` —— 便宜好用

`completion/complete` 让我们给客户端**补全候选**：填 `ac://workshop/{workshop_id}` 时把真实 id 列出来；
填 `lead-kit` 的 `workshop_id` 时同理。客户端体验会从"盲填"变成"选"。
数据源与资源面**同一处**（`/api/workshops` 等），不新增查询逻辑。

### 2.3 `logging` —— **只在 stdio 下做，HTTP 如实说不支持**

`notifications/message` 是服务端 → 客户端的单向推送。
- **stdio**：本来就是一个长连接，能做；
- **HTTP（Streamable HTTP）**：需要 SSE 流，而项目**明确不做 SSE**（`protocol_catalog` 里写着原因）
  ⇒ HTTP 入口**如实返回不支持**，不假装推送成功。

内容只推**平台自己真发生的事**（派活、回执到达、轮询出队），不推"我觉得你在等"这种猜的。

#### 规范核实（2026-11-04，老板要求"实施前核一次，不臆造"）——**核出一个规范断层**

我们当前支持的最高协议版本是 **`2025-06-18`**（`mcp_server.SUPPORTED_PROTOCOL_VERSIONS`），而 MCP 已经出了 **`2026-07-28`** 版，那一版是**减法**：

| 项 | 2025-06-18 / 2025-03-26 | **2026-07-28** |
|---|---|---|
| `logging` 能力声明 | `capabilities.logging = {}` | 仍是能力之一，但**用法变了** |
| `logging/setLevel`（客户端设最小级别） | 存在，客户端 **MAY** 发 | **整条删除**（不是弃用） |
| 日志级别怎么定 | 一次 `setLevel` 定全程 | **每个请求**在 `_meta` 里带 `io.modelcontextprotocol/logLevel` |
| `notifications/message` 能不能发 | 按级别随时发 | **不得为"没带 logLevel 的请求"发**；且它只在该请求自己的响应流上（request-scoped），**不在** `subscriptions/listen` 流上 |
| `initialize` 握手 / `Mcp-Session-Id` | 有 | **全删**（无状态：每请求自带 `_meta` 的版本与能力） |
| `ping` | 有 | **删** |
| `resources/subscribe` / `unsubscribe` | 有 | **删**，改为 `subscriptions/listen` |
| 新增 | —— | `server/discover`、MRTR（多轮往返替代 sampling/elicitation 回调）、`Mcp-Method`/`Mcp-Name` 头、列表结果可缓存（`ttlMs`/`cacheScope`）、`resultType` 必填 |

**两条结论**（写下来防以后踩）：

1. **`logging` 按 `2025-06-18` 做**（stdio 支持、HTTP 如实说不支持）——因为我们目前只支持到那一版。
   按新版做等于要求我们同步改成无状态传输，那是**另一次迁移**，不能混在 logging 里做；
2. **"上不上 2026-07-28"是一个独立的、要老板拍板的产品决定**（影响：删 initialize/会话、加 `server/discover`、
   改 `resources` 订阅、列表加缓存字段）。若客户端只支持新版、我们又只支持旧版，会协商不上——
   **这是兼容性风险，必须如实写进对外文档，不许说"支持 MCP"了事。**

> 来源：[MCP Logging 规范（2025-03-26）](https://modelcontextprotocol.io/specification/2025-03-26/server/utilities/logging)、
> [MCP 2026-07-28 无状态化变更（WorkOS 分析，2026-09-16）](https://webflow.workos.com/blog/mcp-stateless-spec-2026-07-28)

## 3. 明确不做的两项（理由要写清，别留悬案）

| 不做 | 理由 |
|---|---|
| `sampling` | 它让**平台借用客户端的模型**来生成内容。我们的口径是"平台自带 AI + 零 token 兜底"，借用客户端模型会把成本与责任边界搞乱；且各家客户端对 sampling 支持差异极大 |
| `roots` | 它是"客户端告诉服务端我的磁盘边界"。平台不读写客户端磁盘（桥/投递都走各自的适配器），拿到 roots 也没处用 |

## 4. 判据（新工具 `tools/mcp_prompts_check.py`，**10 格**）

| # | 格 | 断言 |
|---|---|---|
| ① | 能力声明 | `initialize` 里 `capabilities.prompts` 存在（`listChanged=false`） |
| ② | 列表非空且参数齐 | `prompts/list` ≥ 5 条，每条有 `name/description/arguments` |
| ③ | 取值可用 | `prompts/get` 回 `messages[]`，每条 `role`+`content.type=text` |
| ④ | 参数真的进了模板 | 传 `workshop_id`，正文里出现该 id（不是写死的示例） |
| ⑤ | 数据是真的 | 临时实例真建工作间后再取 `lead-kit`，正文含该间真实信息 |
| ⑥ | 缺参数说清 | 不传 `workshop_id` ⇒ `-32602` + 说明缺哪个 |
| ⑦ | 参数不存在说清 | 传不存在的 id ⇒ 明确"没有这个工作间"，不返回空模板 |
| ⑧ | 补全 | `completion/complete` 对 `workshop_id` 返回真实候选（≥1 条，且是临时实例里真建的那个） |
| ⑨ | logging（stdio） | stdio 下能收到 `notifications/message`；HTTP 下**如实拒绝**（不是静默丢） |
| ⑩ | 不越界 | 取提示**不改任何状态**（读前后 `workshops.json` sha256 不变） |

**新出现一个要老板拍的事（来自 §2.3 的核实）**：

> **要不要跟进 MCP `2026-07-28`（无状态一代）？**
> 现状：我们最高支持 `2025-06-18`，而新版删掉了 `initialize` 握手、`Mcp-Session-Id`、`ping`、
> `resources/subscribe`、`logging/setLevel`，加了 `server/discover`、MRTR、`Mcp-Method`/`Mcp-Name` 头、列表缓存字段。
> 跟进 = 一次独立迁移（传输层重构），不是加个功能。
> **不跟进也可以**（版本协商允许我们回旧版），但要如实写"只支持到 `2025-06-18`"，
> 且要接受"只支持新版的客户端连不上"。

—— 这件事**不阻塞 4.43.0 的三项**（都按 `2025-06-18` 实现），但会决定下一批要不要排传输层迁移。
