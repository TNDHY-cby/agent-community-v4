### 1.5 L 体系的真值（代码一处真相，2026-11-04 复核）

`platform/v5_evidence_view.py` 的定义是**唯一口径**，而且比外部描述更细：

```python
LEVELS = ("L0", "L1", "L2", "L4")          # ⚠️ 没有 L3
LABEL  = {"L0": "平台实做", "L1": "它库已有（须带凭据，平台未核对）",
          "L2": "平台留痕（回执流水）", "L4": "人眼确认"}
```

| 档 | 语义（原文） | 证据是谁产生的 | 进验收的条件 |
|---|---|---|---|
| **L0** | 平台实做 | **平台自己**（产物目录真扫 `sha256`） | 可直接进 |
| **L1** | 它库已有（**须带凭据，平台未核对**） | **对方**（凭据指向对方的库/会话） | 必须带 `evidence_ref`，否则按 L4 算并拒 `L1_NEEDS_PROOF`；放行时界面**不许显示成"平台已验证"** |
| **L2** | 平台留痕（回执流水） | 平台记录、内容是对方报的 | 可进（弱） |
| **L3** | 大模型自报 | 模型 | **永不采信**（`EVIDENCE_L3_REJECTED`），连 `LEVELS` 都不在里面 |
| **L4** | 人眼确认 | 人 | 兜底可进 |

**⇒ 一个待确认项当场可以销掉**：外部方案 §8 第 2 条问"『不可控证据源』对应 L1~L4 哪一级"——
答案由代码直接给出：**是 `L1`**（"它库已有、平台未核对"就是不可控来源），而且代码已经给它加了 UI 警告。

⚠️ **另一个必须记住的坑**：`L` 前缀在本仓库**跨域重复**，不是全局唯一：

| 出现处 | 含义 |
|---|---|
| `v5_evidence_view.LEVELS` | 证据档 L0/L1/L2/L4 |
| README「系统级 L1/L2」（插话优先级） | 插话紧急度 |
| README「心跳超时 L0 重试、失败升级 L1 提醒」 | 重试升级级 |

⇒ 任何文档/字段提到 `L1` **必须带域限定**（写"证据 L1"而不是裸 `L1`），否则就是第四处同名。

## 2. 两套档位必须分开命名（这是当前最容易误读的地方）

评审为什么会把 A/B/C 当成"证据强度"？因为文档里两套字母挨着写、谁也没说清关系。**先改名再谈规则。**

| | **通道活性档**（原 A/B/C） | **结果证据档**（L1~L4） |
|---|---|---|
| 回答的问题 | "这条回执渠道**通不通**？" | "这个结果**能不能被独立复核**？" |
| 谁产生 | 平台自己的探针（发口令/写测试消息）或人点一下 | 交付方给证据，接收方复核 |
| 例子 | A＝它答对了口令；B＝桥把测试消息取走了；C＝用户说"我看到了" | L1＝带凭据的实据；L2＝产物目录证据；L3＝模型自报（**拒**）；L4＝无证据 |
| 能不能被伪造 | **能**（一个活着的恶意节点照样答对口令） | **较难**（sha256 可重算、凭据要求指向具体位置） |
| 现状 | 有判据（`protocol_parity_check` 13 格「三档同账」） | 有判据（`test_v5_p4` / `p4_check`） |

**建议的对外表述（一处真相）**：
> 平台把"渠道活没活着"和"结果能不能复核"**分开记**；前者证明通路，后者才进验收。
> **通过验收必须 ≥ L1**；只有"渠道活性"没有任何结果证据的，一律算 L4。

改名改动面：`model/05`、`项目完整模型` §15、`AGENTS.md` 一句、界面文案。**不改代码字段**（`source=A/B/C`、`evidence_level=L*` 保持，避免破坏既有账本）。

## 3. 缺口精确定位：有"标"、没有"判"

现在遇到两方证据对不上时，平台的唯一动作是（`workshops_evidence.py:151-159`）：

```python
# 冲突标记：两卡互链，都打 disputed（平台不判谁对）
other["evidence"]["disputed"] = True
res["evidence"]["disputed"] = True
```

**这是诚实的设计**（平台确实没有裁决权），但它把"我不管"变成了"什么都没发生"：
- `disputed` 只影响摘要里多一行「⚠️有争议」（`evidence.py:209`）；
- **不影响**任务能否验收、不影响跨组织结果是否被接受、不留处置记录；
- 没有"争议未决"这个状态，所以界面上看起来和"没事"一样。

⇒ 这就是评审说的"证据如何变成跨组织可采信的裁决，这一步没有闭合"——**准确**。

## 4. 建议的规则（三条，不需要新协议）

### 规则一：**谁验证** —— 接收方复核，交付方自证只算"自报"

| 角色 | 能做什么 | 不能做什么 |
|---|---|---|
| 交付方 | 给产物 + `sha256` + 证据等级 + 凭据 | 不能给自己的结果打"已采信" |
| 接收方 | **独立重算** `sha256`、检查 `evidence_ref` 指向的东西是否真的存在 | 不能只凭"对方说通了"就采信（这正是 2026-10-25 的教训） |
| 平台 | 记录双方结论、跑可自动跑的那部分（重算 hash、查凭据是否存在） | **不替人判"谁在撒谎"**（保持现在的诚实） |

→ 落点：任务账本里 `external` 段增加 `peer_accepted`（接收方复核结论）与 `peer_checked_at`；值域见规则三。

### 规则二：**验什么** —— 只认"可重算 / 可指向"的东西

| 证据形态 | 怎么验 | 判"通过"的最低要求 |
|---|---|---|
| 产物文件 | 两边各自算 `sha256`，**逐文件比对**（含字节数） | 全部一致，或差异有明确说明（如"本侧未生成，只做登记"） |
| 凭据（L1） | 检查 `evidence_ref` 指向的位置**真的存在且可读** | 指向的东西存在；读不到 ⇒ 不算 L1 |
| 回执原文 | `raw_hash` 比对（防"事后改口") | hash 一致 |
| 只有"我干完了"这句话 | —— | **只能是 L4**，不许进验收 |

→ 落点：`v5_evidence_view` 增加"跨组织复核"入口（只读：喂进对方给的 `sha256` 清单，本侧重算后给差异表）。

### 规则三：**分歧怎么办** —— 三档处置 + 一个明确的采信态

| 处置 | 何时用 | 平台做什么 | 留痕 |
|---|---|---|---|
| ① **重算对齐** | 双方都给了产物/hash | 本侧重算，给逐文件差异表 | 差异表入账本（`peer_diff`） |
| ② **第三方复核** | ①对不齐，且双方都认某个第三方（或人） | 出一份**只读复核包**（产物清单 + hash + 双方主张），交给人/第三方 | 复核包路径入账本 |
| ③ **挂争议、不采信** | ①②都不成 | 标 `disputed`，**并且**把这条从"可验收"里摘出去（不是删，是标不可采信） | `dispute` 记录：谁发起、双方主张、待谁裁 |

**采信态（新增，四值，写进账本与界面）**：

| 值 | 含义 | 界面怎么说 | 能不能进验收 |
|---|---|---|---|
| `accepted_self` | 只有交付方自证 | 「**未复核**：只有它自己说」 | **不能** |
| `accepted_peer` | 接收方独立复核通过 | 「已复核：本侧重算一致」 | 能 |
| `disputed` | 有争议且未决 | 「**有争议，不采信**」 | 不能（冻结待裁） |
| `refuted` | 已被证据证伪 | 「**已证伪**」 | 不能（可直接降级） |

> 关键：`accepted_self` **不是**"通过"。它对应 L4 或"有证据但没复核"，验收上仍受限
> （≥L1 才可能通过，且 L1 必须有凭据）。这样"自报"永远换不到"采信"。

## 5. 判据（扩 `tools/cross_company_check.py`，20 → **26 格**）

现在 20 格验的是"两个独立实例真投 / 真收 / 回查 / 鉴权 / 数据隔离 / 产物清单"。新增 6 格：

| # | 格 | 断言 |
|---|---|---|
| ㉑ | 自证 ≠ 采信 | 只给"我干完了"的跨组织任务 ⇒ 采信态 `accepted_self`，**验收不给过** |
| ㉒ | 复核通过 | 对方给产物 + sha256，本侧真重算一致 ⇒ `accepted_peer`，账本有 `peer_checked_at` |
| ㉓ | 复核不通过 | 故意给错 sha256 ⇒ 采信态停在 `accepted_self` + `peer_diff` 列出不一致文件 |
| ㉔ | 凭据不存在 | L1 但 `evidence_ref` 指向不存在 ⇒ 按 L4 算（复用既有 `L1_NEEDS_PROOF` 口径） |
| ㉕ | 挂争议后不可验收 | 两方主张冲突 ⇒ `disputed` 且**从可验收里摘出**（不是删数据） |
| ㉖ | 争议有留痕 | `dispute` 记录含发起方、双方主张、待裁对象；只读视图能查到 |

## 6. 与"评分/审计日志"的区别（评审那句话的正解）

评审说"证据模型被理解为带分级的审计日志"。**要避免这个理解，唯一办法是让证据有后果。** 本稿给的后果只有一种，但它是硬的：

> **没有独立复核（`accepted_peer`）的跨组织结果，不算验收通过。**

这不是评分、不是排序，就是一条**准入规则**。它比"再多一个档位"有用得多。

## 9. 与 PCM 的对照（2026-11-04 抓 arXiv 摘要逐条核对，**数字全部准确**）

> 来源：[PCM: A Proof-Carrying Message Protocol for Verifiable Multi-Agent Communication](https://arxiv.org/abs/2610.39109)（arXiv:2610.39109，2026-10-29，Cygnux Labs）

| 它怎么做的 | 我们现在的对应 | 差距 |
|---|---|---|
| **每条 claim 自带证据**：append-only Merkle log 的**包含证明** + 由 **agent 不能控制**的 signer 签名 | 产物 `sha256` + `manifest.content_hash` + `attestations`（HMAC 自签） | 我们只证明"这份东西没被改"，**不证明"它在某个不可写日志里"**；跨组织时对方用自己的密钥签，我方无法验 |
| 接收方**离线**检查，给三值 `proven/unproven/failed` | V130 提议 `accepted_peer/accepted_self/disputed` | 我们缺 `failed`（已证伪）这一档 —— 这就是 §8 第 2 条 |
| **"仅凭 agent 自身报告的 claim 永远不得 proven"** | 本稿规则一（`accepted_self` 不算通过）+ 既有 `L1_NEEDS_PROOF` | **口径一致**，可以直接引用它的这句作为依据 |
| 基准 926 条真实消息、712 条谎言；纯 A2A 接受 **712**，PCM 接受 **10**（全是 stale evidence，1.4%，95% CI 0.8–2.6%）；六种已部署协议模型接受 504–712；两个独立验证器判断完全一致；验证约 **1 ms** | 我们没有任何"谎报率"基线 | 这是**要补的实测**（见 §5 判据扩展），不是靠文档声明 |

**结论**：PCM 的路线与 V130 同向（自报永不采信 + 接收方离线复核），但它把"可验证"做到了**密码学证明**级别，
我们目前到"可重算 hash + 凭据可指向"这一级。**这一步差距要如实写进对外表述，不许说成"已实现可验证消息协议"。**

### 11.3 诚实边界（别把这一版说大）

- **不是"可验证消息协议"**：我们只到「可重算 hash + 凭据可指向」，**没有** PCM 那种 append-only Merkle log 的包含证明与第三方签名（§9）；
- 平台**不判谁在撒谎**：它只重算 hash、查凭据存不存在、把双方主张留痕；`disputed` 永远是"冻结待裁"，不是"自动裁决"；
- 复核比对**只按相对 `产物/` 的路径**：两边工位目录名天然不同；同名同内容才算一致，同名不同内容会如实报 `sha_mismatch`；
- `evidence_ref` 只有**像本机路径**时才真 `stat`；文字凭据（"哪个库/谁核的"）平台核对不了，如实标「人工凭据，平台未核对」，**不许因此误拒**。
