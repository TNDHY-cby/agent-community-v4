## 〇、先说三件会改变结论的事（全是实测，不是推断）

### 0.1 ★多选现在**一注册就 400**：向导的协议 id 与后端 `TransportType` 不是同一套

实测（`temp/probe_transports_enum_20261106.py`，直接拿 `HarnessInfo` 做模型校验）：

| 集合 | 合法值 |
|---|---|
| `TransportType`（传输层） | `ws` / `http` / `sse` / `pipe` / `grpc` / `mcp` / `a2a` |
| `WakeupMethod`（激活方式） | `http` / `file_poll` / `clipboard` / `acp` / `http_api` / `mcp` / `a2a` |
| 接入向导的 7 张卡（`protocol_tree.PROTOCOLS`） | `a2a` / `mcp` / `http_api` / `acp` / `file_poll` / `clipboard` / `http` |

⇒ 向导的 7 个 id 里，**只有 `a2a` / `mcp` / `http` 是合法 `TransportType`**；
`http_api` / `acp` / `file_poll` / `clipboard` **不在枚举里**。

前端多选后发的 body 是 `transports: [全部选中]`，于是：

```
多选 A2A + HTTP_api → 400
  harness_name  -> Field required
  transports.1  -> Input should be 'ws','http','sse','pipe','grpc','mcp' or 'a2a'
```

**这不是设计问题，是现在的真 bug**：用户在界面上多选一张 `HTTP_api` 卡，注册就失败。
（单选 `HTTP_api` 也一样——`transports` 默认值被前端显式覆盖成了非法值；老的单选路径之所以没炸，
是因为那时只发 `wakeup_method`，不发 `transports`。）

### 0.2 平台**不能给 MCP 派活**，但现在的代码会"发出去然后记成已触达"

`dispatch.activate()` 的分支只有三种：`a_protocol` 真发请求（其中 `transports` 含 `a2a` 才走 A2A 信封）、
`b_bridge` 写唤醒标记、`c_visual` 人工。

⇒ 首选选 `mcp` 时，派活会按**普通 HTTP POST** 打到它的 MCP 端点；MCP 服务端只认 JSON-RPC（`initialize`/`tools/*`），
不认 `{"event":"task.assigned"}`。对端不会派活、我们却可能记成"已真发唤醒请求"——**这正是最坏的那种假成功**。

### 0.3 必填项只按"首选"算 ⇒ 多选白选

界面详情按 `WIZ.protocol`（首选）取 `required`。选 `A2A + ACP` 时它只要 `api_base_url`，
**`acp_command` 不填也能提交**，可 ACP 那头根本起不来。多选只是"记了个数组"，没有产生任何约束。

## 一、范围

**做**：把"用户选中的协议集合"变成一份**可执行计划**——能干什么、不能干什么、还缺什么、各自怎么自验、
派活到底走哪条路；并且让注册载荷**真的合法**（把 0.1 修掉）。

**不做**（写清，防以后扯皮）：

- ❌ 不替用户选协议，也不给"协议排行"（协议不是高低线，是四层：身份/任务契约/传输调用/触达）；
- ❌ 不改 `TransportType` 的语义（`transports` 仍只表达"传输层"）；
- ❌ 不做"自动切换协议重试"（A 档失败不会自动改走 B 档，那是另一件事）；
- ❌ 不在本稿里改前端渲染（前端域，见 §10 的对接要点）。

## 三、映射表（本稿的核心，落地进 `protocol_tree`）

| 向导 id | `wakeup_method` | 能进 `transports` 吗 | `protocols`（新字段） | 一句话 |
|---|---|---|---|---|
| `a2a` | `a2a` | ✅ `a2a` | ✅ | 能派活（JSON-RPC `tasks/send`），能回查 |
| `mcp` | `mcp` | ✅ `mcp` | ✅ | **工具面**：它调我们；平台**不能**给它派活 |
| `http_api` | `http_api` | ❌（映射成 `http`） | ✅ | 平台直接 POST，能派活 |

## 四、新字段与新端点

### 4.1 `HarnessInfo` 加 `protocols: list[str]`

- 值域＝§3 第一列；未知值 **400 + 列出可用值**（不许静默丢）。
- `wakeup_method` 仍是**首选**（决定派活主路径）；`protocols` 是**全量**。
- 兼容：老的注册体没有 `protocols` ⇒ 默认 `[]`，读的时候按 `[wakeup_method]` 兜（不追溯改老数据）。

## 五、能力矩阵（7 种协议 × 6 件事）

| 协议 | 平台能派活 | 能收到回执 | 平台能读它会话 | 它能调平台工具 | 平台能自动叫醒 | 需要人 |
|---|---|---|---|---|---|---|
| `a2a` | ✅（`tasks/send`） | ✅（`tasks/get` 回查 + 主动回报） | ⚠️ 它有读会话工具时 | ❌ | ✅ | ❌ |
| `mcp` | ❌ **（工具面，不能派活）** | ✅（工具返回即结果） | ⚠️ 同上 | ✅ | ✅（调它的工具） | ❌ |
| `http_api` | ✅（普通 POST） | ⚠️ 要它给回调 | ❌ | ❌ | ✅ | ❌ |
| `http` | ❌（只落盘） | ❌ | ❌ | ❌ | ❌ | ⚠️ 它自己来取 |
| `acp` | ✅（拉起子进程 + prompt） | ✅（会话轮次内） | ✅（平台就是它的宿主） | ❌ | ✅ | ❌ |
| `file_poll` | ⚠️ 桥搬件（不算"派出去"） | ⚠️ 桥取走/回报 | ❌ | ❌ | ❌ | ⚠️ |
| `clipboard` | ❌ | ❌ | ❌ | ❌ | ❌ | ✅ |

> 这张表就是"适合的功能"：用户选了两三个协议，界面直接告诉他**这套组合整体能干什么**，
> 不允许把"MCP 选了"读成"能派活了"。

## 五·五、什么才是"最优解"：按角色闭环，不按协议数量

> 老板 2026-11-06 晚追问：「多选不同协议项目应该怎么达到最优解呢」。这一节就是答案，
> 也是 §5 能力矩阵的**用法**。

### 5.5.1 先想清楚你要它扮演哪个角色（四个角色，逐条对号）

| 你想让它干什么 | 需要的协议 | 这些协议负责什么 |
|---|---|---|
| **给它派活**（它去干活，平台等结果） | `a2a` / `http_api` / `acp` 三选一 | 任务语义 + 投递 |
| **把它当工具用**（平台调它的能力） | `mcp` | 工具面（它来调我们、或我们调它） |
| **它自己来取件**（异步、不催） | `file_poll` / `http` | 落盘 + 桥 |
| **只能人搬运**（桌面型、无接口） | `clipboard` | 半自动（平台放剪贴板/视觉激活） |

### 5.5.2 最优＝"覆盖你要的角色"所需的最小集合

- **不是越多越好**：多选一个同角色协议，只会让界面上多一条"备用"，不增加能力；
- **闭环才算通**："能派活"＋"能收回执"两个都成立，才是"派出去、有结果"；
  只有 `mcp` 时这两条都成立不了（它不接收派活）；
- **首选只决定"从哪条路先走"**，不决定"能不能干"——平台会按 §6.4 的优先级选真正能走的路，并在
  用户首选走不通时明说（`honest_note`）。

### 5.5.3 三个现成模板（覆盖 90% 的接入场景）

| 场景 | 选什么 | 为什么这是最优 |
|---|---|---|
| 远程 agent 干活 + 还想用它当工具 | **`a2a` + `mcp`** | 派活走 A2A（有任务语义、能回查），工具面走 MCP；两者互补不重复 |
| 本机进程型 agent（能被拉起） | **`acp`**（若它也给工具面再 + `mcp`） | 平台你自己拉起、自己控会话，结果是会话轮次里直接拿到的 |
| 桌面型、没有任何接口 | **`clipboard`**（若有落盘目录再加 `http` 兜底） | 只能半自动；`http` 兜底让它自己来取件，比纯人工多一条路 |

**反例（要点明，避免用户自己凑出坏组合）**：

- `mcp` 单独选 ⇒ 平台永远不能给它派活（只能它来调我们）——**这不是错，但要知道**；
- `http` + `http_api` ⇒ 同一条 HTTP 通道的两种行为，选一个作首选即可（平台会提醒，不拦）；
- `file_poll` + `clipboard` ⇒ 两套都要部署（桥 + 人工），通常只留一个。

### 5.5.4 平台怎么帮用户"达到最优"（而不是让他背规则）

1. **选完就出账单**：`/api/docking/protocol-plan` 直接给"能干什么 / 缺什么 / 走哪条路"；
2. **缺什么标在哪个协议上**（不是笼统报错）：`ACP 缺 acp_command`、`A2A 缺 api_base_url`；
3. **首选选错只提醒不改**：`first_advice` + `honest_note`，用户的决定保留；
4. **重复组合明说**：`duplicates` 告诉用户"这俩是同一层"，但不拦；
5. **每个协议各自怎么自验**（`probes`）：注册完逐项测，不靠"注册成功"当通。

## 五·六、`clipboard` 到底能不能用视觉脚本（老板 2026-11-06 追问，这里说明白）

> 老板原话：「**clipboard 是不是可以用视觉脚本，记得说明**」。

**能，但只到"把话送进去"为止。** 分三层说清，别让任何一层被读成"任务完成了"：

| 层 | 事实 | 依据（代码里的一处真相） |
|---|---|---|
| **开箱** | `clipboard` **叫不醒**：没有脚本时平台只能把话放到剪贴板/给一句可复制的话，**靠人点** | `protocol_tree` 的 `can_be_woken: false` |
| **配了视觉脚本** | 平台能**自动把话送进它的窗口**：按 `cdp → 原生 → UIA → 半自动` 四通道选，能核实投递就核实（`verified=true`），核不了如实说未核实 | `activation_script`（标题/关键词 + 一句话）+ `delivery.deliver_by_name`；派活走 `dispatch.activate` 的 `c_visual` 分支 |
| **结果** | **核不到**：`投递成功 ≠ 它执行了`。`result` 仍是 `manual`，`delivered/verified` 只描述投递本身，**平台绝不把它记成任务完成**；结果要靠人看产物或它自己回报 | `protocol_plan.capabilities.can_receive_result = no`；`dispatch.activate` 返回值 |

**在计划里怎么显示**（用户选 `clipboard` 时会看到）：

- `capabilities.can_wake_with_script = true`、`can_dispatch = false`、`closed_loop = false`；
- `route.why` 明说："这类接入靠**视觉脚本**：存了脚本后平台能把「看下 T-003」自动送进它的窗口；
  **但只能证明话送进去了，它有没有执行核不到**"；
- `warnings` 里再补一条："**投递成功 ≠ 任务完成**"；
- `protocols[]` 上 `visual_script: true`，方便界面标"可用视觉脚本"。

**视觉脚本的字段与边界**（`protocol_tree.VISION`，界面/文档/计划都读这一份）：

- `activation_script.text`（给人看、能手工改的正文）、`.title`（最精确的定位键）、`.keywords`、`.verified`（**没自证过就是 false，不假装**）；
- 适用：`clipboard`（主要）；桌面型的 `file_poll` / `http` 兜底也可配，能力归"视觉这一档"；
- 入口：对接中心「脚本激活」工作台；一键激活 `POST /api/docking/harness/{id}/activate`；
- **派活路径也走同一条投递**（2026-11-06 新增）：以前 `c_visual` 档一律返回"只能人工"，
  现在有脚本就真投一句"看下 T-003"——但返回的 `result` 仍是 `manual`、带 `needs_human=true`。

### 5.6.1 「不止把话送进去吧，它能把消息发给组长吗」（老板 2026-11-06 追问）

**能发，但不能读回。** 三句话说清：

1. **能发任意一段话**（不是只能发"看下 T-003"）：`POST /api/docking/harness/{id}/send-text`
   —— `{"text": "对接单：岗位 前端组/员工01 …"}`。它按该接入档案里的**视觉脚本**定位窗口并投递，
   所以「把对接单发给组长」是它的标准用法之一（**组长也是一个接入**，`harness_id` 指向它即可）。
   与「一键激活」的分工：一键激活发的是**固定激活话术**，send-text 发**调用方指定的原文**。
2. **不能读回回复**：`verified=true` 的含义只是「输入框里读回来的字与我送的一致」（`WM_GETTEXT` / cdp 读 DOM），
   **不是**读对方的回答。对方回复的可靠来源只有三条：① 人看它的窗口 ② 它自己交回执
   （`/api/harness/task-result` / 桥文件）③ 平台抓帧（`monitor`，图片、不结构化）。
3. **没有脚本就说没有**：`400 NO_VISUAL_SCRIPT` + 指路「脚本激活」工作台；投递找不到窗口时
   `ok=false` + 真实原因 + `next`（换一档 / 人工转达），**绝不返回"已发送"**。

> 所以"把消息发给组长"这件事的正确形态是：**平台负责把话送到组长窗口并核实送进去了；
> 组长的回答要么人看，要么组长自己按协议交回执**。想让它自动回话，就得给它一个能回执的协议
> （A2A / HTTP_api / MCP 工具面），而不是指望视觉通道读回复。
> 接口返回里固定带一句 `note`：**「平台只核实话确实送进了它的输入框；读不到它的回复」** —— 界面要原样显示。

## 六、组合规则（算计划时按顺序执行）

1. **逐项算可用性**：每个协议 → 必填项对照 `fields` → `missing` → `usable`（缺必填的标不可用 + 说清缺什么）。
2. **合并必填**：所有选中协议的 `required` 取并集（去重、保序），界面按它渲染表单。
3. **同层重复提示**（不是错误，是提醒）：
   - `http` + `http_api`：都是 HTTP 通道，一个"只落盘"一个"真推" ⇒ 提示"选一个作首选，另一个只会被当成备用"；
   - `file_poll` + `clipboard`：都要桥/人工 ⇒ 提示"两套都要部署，通常没必要"。
4. **派活路线**（`route.dispatch_via`）优先级：
   `preferred_transport`（若该协议能派活）→ `a2a` → `http_api` → `http`（bridge 落盘）→ `acp` → `manual`；
   **`mcp` 永不作为派活路线**（它没有派活语义；选了它也不算）。
5. **首选建议**（`first_advice`，只建议不改）：能派活 > 只能被调 > 只能人工；
   若用户的首选不可派活而集合里有能派活的 ⇒ `warnings` 里明说"派活将走 X，不是首选 Y"。
6. **诚实提示**：`can_dispatch=false` 的协议必须在 `picked[].why` 里给原因，不许留空。

## 十一、三处选择点（**已定**，2026-11-06 晚）

> 老板把技术细节交回（「不太清楚」），按 §5.5 的角色闭环取最优解；三处都取"不破坏既有契约 + 不假装"那一侧。

1. **全量记哪** → **新增 `protocols` 字段**（`transports` 语义不动，老档案不追改）。
   理由：扩 `TransportType` 会把 `ws/pipe/grpc` 这些既有值和 `http_api/acp` 混在一层，后面每处判断都要重看。
2. **`http_api` 在 `transports` 里怎么写** → **映射成 `http`**（它确实跑在 HTTP 上，派活就是普通 POST）。
   `acp` / `file_poll` / `clipboard` **不映射**（传输层表达不了，`transports` 留空是事实）。
3. **缺必填拦不拦** → **只警告不拦**（该协议标"不可用：缺 X"，其余协议照常用）。
   理由：注册被整单 400 会让人卡在"先填哪个"上；而"哪条不可用"是逐协议的，标清比整单拒更有用。
