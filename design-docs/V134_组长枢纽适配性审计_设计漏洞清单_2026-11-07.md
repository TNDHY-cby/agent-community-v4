# V134 · 以"组长枢纽"为前提的适配性审计：10 个设计漏洞与修补顺序

> 状态：**审计结论（只读分析）＋ P0 四条与 ⑦ 已落地（2026-11-07 下午）** —— 落地物与判据见 §四。
> 老板前提（原话）：「**组长最适配，功能最全，所以可以用来带动不适配者**」。
> 本稿就是拿这条前提去对代码：现在平台**有没有能力**"让最适配的一端带动不适配的一端"，缺哪几块。
> 审计方式：读实现 + 跑既有判据（不看文档自述）；每条漏洞都给**代码位置**与**验收判据**。

---

## 〇、一句话结论

**平台现在没有"适配度"这个事实，也没有"谁来补位"这个决策。**
`tier`（a_protocol / b_bridge / c_visual）只描述"怎么触达"，不描述"能干什么、缺什么、谁补"；
而"组长"这个角色在代码里只是名单里一行 `slot_dir == "_lead"`，**没有任何能力面**。
⇒ 所以"用组长带动不适配者"目前靠**人记着**，平台既不阻止漏，也不提醒补。

下面 10 条按"被吞掉时用户会不会把'坏了'当'正常'"排序（越靠前越危险）。

## 一、漏洞清单

### ① 验收署名可伪造：账本记"组长验收"，实际谁都能点

- **现象**：`POST …/tasks/{seq}/review` 的验收人来自请求体 `body.get("who") or "lead"`
  （`routers/p4_v5.py:193` → `task_ledger.review(who=...)`），**没有身份校验、没有凭据**。
- **后果**：任何人（或任何 agent 拿到的令牌）调一次，账本就写"验收人=lead"。
  ⇒ "组长带动"的**责任链是假的**；出事时无法回答"这单是谁放的"。
- **这为什么最危险**：它长得完全正常（有验收记录、有结论），**只有对证据时才露馅**。
- **修补建议**：`who` 不再取请求体默认值；三档来源（组长 A 档令牌 / 人工确认 / 平台自动）各自留证，
  账本记 `who_source` 与凭据指纹；对不上就 403，并在证据四步表里标"署名未核"。
- **判据**：不负责人调 review ⇒ 403 `WHO_NOT_PROVEN`；负责人调 ⇒ 账本 `who_source` 与令牌一致；
  界面显示"验收人 + 凭什么"。

### ② "组长最适配"在代码里没有依据：没有能力面，就没有"谁带动谁"

- **现象**：`lead_eligible` 只看 `fs_write` +（`protocol_call` / `bridge_poll`）（`p5_v5.py` 的 lead-roster），
  只是"能不能当"的门槛；**没有"组长现在能做什么、缺什么"的清单**。
- **后果**：平台无法回答：这个组长能不能读文件？能不能收通知？能不能代不适配者转发？
  ⇒ "带动"变成人的口头安排；换一个组长（能力不同）就得重新安排，**产品化不成立**。
- **修补建议**：给组长（以及每个接入）一份**能力面**（能被读的字段，不是新状态）：
  `can_read_files / can_receive_notice / can_dispatch / can_review / can_see_visual`
  —— 直接由 `tools` + `transports` + `activation_script` 派生（一处真相，别手填）；
  再由它算**补位建议**："它读不到 `_notice.md` ⇒ 平台改发视觉/讨论区；它不能写文件 ⇒ 平台代收产物"。
- **判据**：`GET …/lead-capabilities` 对三种组长（A2A / 桥 / 视觉）给出**不同**清单；
  每条"不能"都带 `why` 与"平台替它做什么"。

### ③ 产物与任务无绑定：收件目录发现了文件，但不知道是哪条任务的

- **现象**：`artifact_inbox.scan_workshop` 的事件只有 `slot_dir + file + sha256`，**没有 `task_id`**；
  而 `artifacts.snapshot()` 也是按**工位**扫、按工位 diff（`artifacts.py:44-72`），不按任务。
- **后果**：一条任务有没有交东西，仍然只能"人看工位里有没有新文件"；
  "发现"与"验收"之间**没有可编程的桥**。任务状态也停在 `issued`（`dispatch_v5.py:302` 只 `issue`）。
- **修补建议**：事件里带 `task_id`（由"该工位当前未完成任务"推导；多任务时**不确定就不猜**，标 `task_id_ambiguous`）；
  并把"发现产物"推进成任务状态 `delivered`（**不等于验收通过**，只表示"它有东西了"）。
- **判据**：派活后放文件 ⇒ 事件带正确 `task_id` 且任务从 `issued` → `delivered`；
  有两条未完成任务时 ⇒ 事件标 `task_id_ambiguous` 且不硬绑。

### ④ 平台发现了产物，但"待验收"没人被叫

- **现象**：`artifact_inbox` 只写 `_lead/_notice.md` + 事件流；**不改任务状态、不通知用户界面待办**；
  派活时也**只给成员写 notice**，不给组长写（`dispatch_v5.py:182`）。
- **后果**：链条断在"发现"这一步：组长/用户不知道"有东西可以验收了"；
  而 `read_marks` 的未读水位**只算 discussion 消息**（`read_marks.py` 口径），管不到事件。
- **修补建议**：事件生成"待办"（`pending_review`），并入现有未读口径；
  按 ②的能力面选择通知通道（notice / 视觉投递 / 讨论区）。
- **判据**：放文件后，`GET …/inbox-events` 里该事件带 `needs_review=true`；
  前端未读徽标 +1；点开后水位推进（与 discussion 同一套 `read_marks`）。

### ⑤ 外部收件目录与"证据链"是两套口径

- **现象**：`artifacts.snapshot()` 固定扫 `<工作间>/<工位>/产物/`（`artifacts.py:46`）；
  但 `artifact_inbox_dir` 允许指向**外部目录**。于是：事件看得见，**验收与 peer-review 扫不到**。
- **后果**：用户以为"它交了文件"，点验收却报"产物目录为空"（`ARTIFACTS_EMPTY`）——
  **最典型的"看起来成功"**，而且两条命令各说各话。
- **修补建议**：验收/采信的产物扫描也认 `artifact_inbox_dir`（同一处真相：`artifact_inbox.inbox_of()`），
  或明确禁止外部目录走验收（二选一，**必须选一个**）。
- **判据**：文件放外部收件目录 ⇒ `verify-artifacts` 能列出它（真扫盘）；peer-review 的 `local_files` 含它。

### ⑥ `artifact_inbox_dir` 无路径校验（新面）

- **现象**：档案字段直接当路径用（`artifact_inbox.py:164`），**没有 `validate_wakeup_dir` 那样的加固**。
- **后果**：能被设成任意绝对路径（含系统目录）；监视器会把那里的**文件名、大小、sha256**
  写进事件与组长通知 —— 只读，但等于把一片目录的指纹外泄。
- **修补建议**：复用 `validate_wakeup_dir` 的白名单/禁止项；跨盘符要显式确认；越界一律 400 + 说清。
- **判据**：设 `C:\Windows` / 网络路径 / 盘根 ⇒ 400 且给"允许什么"；设正常工作区子目录 ⇒ 200。

### ⑦ 对接单只能"人去复制"：组长是视觉型时仍要人工粘一次

- **现象**：`GET …/lead-kit` 返回文本（`p5_v5.py:116`），**没有"发给组长"的编排**；
  上一轮做的 `send-text` 是通用件，谁也没把它接上。
- **后果**："组长最适配"的前提在"组长自己不适配"时失效 —— 要人复制粘贴，
  与"平台带动"的承诺不符（这正是老板说的"带动"要解决的场景）。
- **修补建议**：`POST …/lead-kit/send`：按组长能力面选通道（A2A 派活 / HTTP 回调 / 视觉投递 / 只返回文本），
  结果如实回报（投递≠组长收到并执行）。
- **判据**：组长是视觉型 + 有脚本 ⇒ 真投递且返回 `method=visual`；无脚本 ⇒ 400 + 指路"脚本激活"。

### ⑧ 通知落点单一，且没有"谁没看到"的账

- **现象**：转组长只有 `_lead/_notice.md`（`artifact_inbox.py:329`）；派活只给成员 `_notice.md`。
  **没有任何"通知已送达/未读"的记录**（除 discussion 的 read_marks）。
- **后果**：组长不看文件就等于没通知；平台仍然显示"已通知"，**失败被吞**。
- **修补建议**：通知统一走一个"投递记录"（`notice_deliveries`：目标/通道/结果/时间），
  三类结果分开记：`written`（写进文件，不知有没有看）/ `delivered`（真投递）/ `failed`。
- **判据**：`GET …/notice-log` 能看到每条通知的通道与结果；`written` 不许显示成"已送达"。

### ⑨ `tier` 与"能带动什么"没有对照表，分支散在各处

- **现象**：`tier` 由名单证据推（`v5_roster.py:448-457`：`protocol_ok` / `bridge_ok`+`mailbox_ok` /
  `paste_seen`+`press_ok`+`rename_seen`），但"这一档在派活/通知/产物/验收四件事上分别怎么处理"
  **没有任何一处清单**——`dispatch.activate`、`artifact_inbox`、`p4_v5.review` 各写各的。
- **后果**：加一档或改一档语义时**必漏**（本项目已经踩过：B 档"只通没取件"被判 active，
  `v5_roster.py:449` 那条注释就是当时的补丁）。这正是"同一件事多处口径"的典型。
- **修补建议**：一张 `TIER_MATRIX`（三档 × 四件事：触达/通知/产物/验收），
  由它驱动 `dispatch` 与 `artifact_inbox`；新增档位必须填满整行，缺格即测试失败。
- **判据**：新增一个 tier 而不填矩阵 ⇒ 单测红；三档各自的四件事在判据里都能真跑出来。

### ⑩ 资料库/资源库与收件通道没接上

- **现象**：`ws.resources` 是**登记表**（名字/路径/备注，`workshops_task.py:217-284`），不扫盘；
  收件事件也不进资源库。老板原话里问的就是"资料库/隔间？"——答案是**都不是**，但它俩也没被连起来。
- **后果**：成员交的文件散在各工位 `产物/`（或外部目录），组长要"看全貌"只能一个个工位翻；
  资源库里的登记与实际文件**可能对不上**（没人核）。
- **修补建议**：收件事件可选"登记进资源库"（带 sha256，标 `source=inbox`）；
  资源库条目加"存在性核对"（路径在就绿、不在就红，不假装）。
- **判据**：事件登记后 `GET …/resources` 能看到它且 `exists=true`；删文件后显示 `exists=false` 且有说明。

## 二、修补顺序（建议）

| 批次 | 漏洞 | 为什么这个顺序 |
|---|---|---|
| **P0（先修，都在"责任/真相"上）** | ① 署名可伪造、③ 产物与任务无绑定、④ 发现后没人被叫 | 这三条让"带动"**无法追责、无法推进**；不修，后面所有"能力面/通知"都建在沙子上 |
| **P1（"组长带动"能不能成立）** | ② 能力面缺失、⑤ 外部目录与证据链两套口径、⑦ 对接单不能自动发 | ②是枢纽模型的地基；⑤⑦是"最适配带动不适配"的具体动作 |
| **P2（结构债与安全）** | ⑥ 路径无校验、⑧ 通知没有送达账、⑨ tier 无矩阵、⑩ 资料库没接 | ⑥是安全面；⑧⑨是防"下次改坏"；⑩是体验收口 |

**建议一次做 P0 三条 + P1 的②**（这四条同一个主题：**"组长凭什么带动、带动到哪一步有账"**），
其余按批次进 4.43.0 之后。

### 落地时**又抓到一条漏洞**（原清单没列，现补第 ⑪ 条）

**`v5_roster.effective_members()` 返回的 `harness` 字段永远是 `None`**：
成员记录里字段叫 `harness_id`（`v5_roster.py:376`），而 `effective_members` 读的是 `m.get("harness")`（原第 130 行）。
⇒ 任何"按工位找它的接入档案"的代码（能力面、收件目录、派活路线）都拿不到 info。

- **影响**：这类 bug 不报错，只让结果"看起来正常但全是 null"（能力面全 None、收件目录退回默认）；
  与清单第 ⑨ 条（tier 没有对照表）同源：**字段级口径没有守卫**。
- **修法**：两个名字都认（`m.get("harness") or m.get("harness_id")`），并同时给出 `harness_id` 别名。
- **判据**：`lead_hub_check` ② 直接钉住"能力面不是空壳"（注册 200 但能力面全 null 会判红）。

## 五、P2 三条落地（2026-11-07 夜，⑧⑨⑩）

| 漏洞 | 落地物 | 一句话 |
|---|---|---|
| ⑧ 通知落点单一、没有"谁没看到"的账 | `platform/notice_log.py` + `GET …/notice-log`；接进 `artifact_inbox`（产物转组长）与 `ailp`（点名通知） | 三类结果**分开记**：`written`（只写进文件，**对方看没看平台不知道**）/ `delivered`（真投递且核过）/ `failed`（带真实原因）。`written` 的标签里明写"不知道"，**不许暗示送达** |
| ⑨ `tier` 与"能带动什么"没有对照表 | `platform/tier_matrix.py`（**4 档 × 4 轴** 行为码）+ `GET /api/tier-matrix` + `GET …/tier-plan` | 派活/通知/产物/验收四件事的行为码**只有这一处**；新增档位不填满整行 ⇒ `gaps()` 报出来、守卫变红 |
| ⑩ 资料库与收件通道没接上 | `GET …/resources` 每条加 `exists`（**真 stat**）+ `why` | 登记 ≠ 文件还在：在就 `true`、不在就 `false` 并说清为什么、核不了就 `null`（link 类 / stat 失败） |

**判据**：`tools/notice_tier_check.py` **8 格全过**；`tests/test_tier_matrix.py` **5 条全过**。

### 落地时踩的坑

`notice_log` 落在 `env_spec.data_dir()` 上 ⇒ **单测会写真实 data**（这是本项目第三次踩同一个坑）。
已按规矩在 `conftest.py` 第 8 节登记（`_path` 重定向到 tmp），注释里写明"新落盘模块必须在这里登记"。

### ⑥ 收件目录路径校验（同日补做）

`artifact_inbox_dir` 原来直接当路径用（没有 `wakeup_dir` 那层加固）⇒ 能指到系统目录/盘根/网络路径，
而监视器会把那里的**文件名、大小、sha256** 写进事件与组长通知（只读，但等于外泄一片目录的指纹）。

- 新增 `artifact_inbox.validate_artifact_inbox_dir()`：相对路径必须落在工作区内（挡 `../..`）；
  绝对路径不能是盘根、不能落系统目录（复用 `SYSTEM_DIR_PREFIXES`）、不能是网络/设备路径（`\\server\share`、`\\?\`）；
- **三处受理**：注册（400 `BAD_INBOX_DIR`）、改档案（同上）、扫描时兜底（非法 ⇒ 这轮不扫它，并说清"不是没有新文件"）；
- 判据：`test_artifact_inbox.py` 加 2 条（越界/系统目录/网络路径都拒；空值合法）。

**写实现时自己犯的错**（判据抓出来的）：三个 `return False, "…"` 少了第三个元素（`resolved`），
函数有时返回 2 元组 ⇒ 解包失败。不是测试写错，是实现少写了一个值 —— 已补齐。
