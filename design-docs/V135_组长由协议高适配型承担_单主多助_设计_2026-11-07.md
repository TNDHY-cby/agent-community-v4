# V135 · 组长由"协议高适配型"承担：一个主组长 + 多个助手

> 状态：**待拍板 → 按最优解落地**（老板 2026-11-07：「组长要用协议高适配型（单个/多个？）的agent来承担」）
> 前置：`V134`（组长枢纽：能力面 / 验收署名 / 产物绑任务 / 对接单投递）已落地。

---

## 〇、先回答问题："单个还是多个？"

**一个主组长（唯一拍板与验收）+ 多个助手（只搬运/催办，不拍板）。**

三条理由（都能落到代码上）：

1. **验收责任必须唯一**。`V134` ① 刚把"验收署名可兑现"修好：组长令牌 → `reviewed_by=_lead`。
   如果两个组长都能拍板，"这单谁放的"就再次无解；而平台**不做"判断谁对"**（`V130` §4 原话：
   只做能自动做的那部分）。⇒ **主组长只能一个**。
2. **"带动"需要一条臂**：主组长是协议高适配型（能派活、能收回执、能写/读文件），
   助手是不适配型（视觉/落盘）。主组长把活拆给助手、把产物收上来——**助手就是那条臂**。
   这不需要"第二个组长"，需要的是"能被主组长驱动的成员"。
3. **多个主组长会引入冲突裁决**：谁有最终决定权（两组长结论相反怎么办）没有产品答案，
   而现在也没有人要求它。**不做**，并在文档里写明。

> 一句话：**拍板权唯一，执行臂可多**。

---

## 一、"协议高适配型"怎么算（可计算，不排名）

复用 `V134` 的能力面（`lead_capabilities.capabilities_of`），加一个**适配度**事实（`protocol_fit`）：

| 项 | 取值 | 为什么算 |
|---|---|---|
| `channel` | 有协议通道（能派活 **且** 能收回执） | 组长必须"派得出去、收得回来" |
| `files` | `fs_write=true` | 要写任务文件、要读产物 |
| `read` | `can_read_files=true` | 要能看产物/证据 |
| `wake` | `can_wake_automatically=true` | 要能催得动 |
| `protocols` | 声明了多少种协议（`transports` + `protocols` 去重） | "多协议"是高适配的直接体现 |
| `visual` | 有可用视觉脚本 | 加分项：能带动纯桌面型 |

**等级**（解释在响应里，不只给一个字母）：

- `high`：`channel` + `files` + `read` 都成立；
- `medium`：`channel` + `files`（读不了文件）；
- `low`：其余（含"测不到"：`null` 不算通过）。

**不做**：不按分数排序推荐（`lead_roster` 既有纪律：按名排序、不推荐）；只把事实摆出来。

## 二、门槛（谁能当主组长）

1. `lead_eligible`（既有：`fs_write` + 协议/桥通道）**且** `protocol_fit == "high"` ⇒ 可当**主组长**；
2. `lead_eligible` 但 `fit == "medium"` ⇒ 可当**主组长（降级）**，响应里明说"它读不了文件，产物要靠平台代读"；
3. `lead_eligible=false`（视觉/落盘型）⇒ **只能当助手/成员**，选它当主组长 ⇒ `409 NOT_LEAD_FIT` +
   说清"缺哪一项、怎么补"（给工具/给视觉脚本/换接入方式）。

> 与既有 `NOT_LEAD_ELIGIBLE`（409）并存：那是"根本不合格"，这是"合格但适配度不够当拍板人"。

## 三、助手怎么用（不新增角色）

**不新增 `helper` 角色**（避免动名单语义）。助手＝工作间里**任何成员**：

- `GET /api/workshop/{id}/lead-team`（只读）给出：
  - `lead`：主组长 + 它的能力面 + `protocol_fit`；
  - `helpers[]`：每个成员"能给主组长补什么"（补齐建议）：
    - 它是视觉/落盘型 ⇒ "主组长派活给它时由平台代投递/代收产物"；
    - 它有读文件 ⇒ "可以让它核对产物 sha256"；
    - 它能收回执 ⇒ "它自己能交回报"；
  - `coverage`：这套团队在"派活/收回执/读产物/催办"四件事上的覆盖情况（缺哪项就点出来）。
- 主组长驱动助手 = **既有 `dispatch`**（写任务文件 → 触达），`V134` 的产物发现与验收接在后面。
  ⇒ **不需要新机制**。

## 四、失败与降级

| 情况 | 用户看到 |
|---|---|
| 选了一个 `low` 的当主组长 | `409 NOT_LEAD_FIT`：「它只能当助手：缺 `能收回执`（`clipboard` 没有回执通道）」+ 怎么补 |
| 团队缺"能读产物"的人 | `lead-team.coverage.read_artifacts.missing` + 「平台代读（L0 扫盘），但结论要人复核」 |
| 两个"高适配"候选 | 不推荐、不排序；给两边事实，人选（`sort_note` 原样保留） |

## 六、不改什么

- 不改 `lead_roster.eligible()` 的既有语义（它仍是"能不能当"的门槛；适配度是**加在上面的一层事实**）；
- 不新增名单角色（助手＝成员）；
- 不做"多个主组长"（无产品答案）；不做自动选组长（人选）；
- 不碰冻结实现与信誉/身份定位方案。

### 口径更正（实测发现，写下来防以后又造错）

原稿 §二 写"`fit=low` ⇒ `409 NOT_LEAD_FIT`（新错误码）"。实测发现**这是死分支**：
`fit=low` ⇔ 缺"能派活+能收回执"或写不了文件 ⇒ 必然 `lead_eligible=false`
（既有门槛就是 `fs_write` + 协议/桥通道）⇒ 永远先被 `NOT_LEAD_ELIGIBLE` 拦掉。

⇒ 改成**复用既有闸门**：`NOT_LEAD_ELIGIBLE` 的响应里带上 `protocol_fit` 与"缺哪一项"的合并 `why`，
并附 `policy: 拍板权唯一：主组长一个；助手可多个（只搬不拍板）`。**不新增错误码**。
