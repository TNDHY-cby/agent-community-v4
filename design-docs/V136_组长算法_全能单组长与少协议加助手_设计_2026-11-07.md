# V136 · 组长算法：两条路（全能单组长 / 少协议组长 + 助手互补）

> 状态：**按最优解实现**（老板 2026-11-07：「做组长算法，两条路：单一多协议全能组长；少协议组长搭助手互补」）
> 前置：`V134`（能力面/验收署名/产物绑任务）、`V135`（协议适配度 + 单主多助团队视图）。
> 与旧纪律的关系：`lead_roster` 原口径是"**不排序、不推荐**"；本次是老板**明确要求算法给建议**，
> 所以算法**只给两条路的可行配置 + 理由**，**仍不给分数、不给单一"最佳"排名**（见 §4 的防假精确口径）。

---

## 〇、输入与输出

**输入**（都可算，不手填）：
- 候选＝已注册接入的能力面（`V134`：`can_dispatch / can_receive_result / can_read_files / can_write_files /
  can_wake_automatically / lead_eligible / protocol_count / protocol_fit`）；
- 需求（`needs`）：默认四项 —— `dispatch`（派活）/ `receive_result`（收回执）/ `read_artifacts`（能看产物）/ `wake`（能自动唤醒）。

**输出**：
```
{mode: "solo" | "team" | "blocked",
 lead: {...}, helpers: [...], coverage: {...},
 why: [...], alternatives: [...], blocked?: {...}}
```

---

## 一、路径 A：单一多协议全能组长（solo）

**条件**：存在 `lead_eligible=true` **且** `protocol_fit=high` 的候选
（high ＝ 能派活 + 能收回执 + 能写文件 + 能读文件）。

**选谁**：`protocol_count` 最大者（"多协议全能"的直接度量）；同分按 `harness_id` 字典序（稳定可比）。

**输出**：`helpers: []`，`coverage` 四件事全 `covered`，`why` 里写清"它是唯一/第一个满足 high 的"。

**为什么不给"评分"**：`protocol_count` 是**事实**（它声明了几种协议），不是"能力分"；
两个候选一个 3 协议一个 1 协议时，前者不是"更好的人"，只是"更多协议能走"。这一点写进 `sort_note`。

## 二、路径 B：少协议组长 + 助手互补（team）

**触发**：没有 `high` 候选（A 不可行）。

**选主组长**：`lead_eligible=true` 的候选里，按 `medium` 优先、`protocol_count` 降序、`harness_id` 升序；
对每个候选试一次"能不能补齐"。

**补缺口（贪心集合覆盖，不做加权评分）**：

1. 算主组长已覆盖的 `needs`；
2. 缺口集合 `missing`；
3. 每轮从**其余候选**里挑"能补最多缺口"的那个（同分按 `protocol_count` 降序、`harness_id` 升序）；
4. 直到 `missing` 为空，或再没有候选能补（**blocked**）。

**为什么贪心而不是"最优组合"**：候选规模是个位数到十几个，贪心结果稳定、可解释、**每次给出"谁因为哪一项被选"**；
穷举所有子集虽然"更优"，但赢得的是"少一个助手"，代价是解释不清 + 组合爆炸。**够用且诚实**。

**助手清单要写清"它补了什么"**：`adds: ["read_artifacts"]` + `why: "它能读文件 ⇒ 主组长读不了产物时由它核对"`。

**blocked 时**（补不齐）：
```
blocked: {missing: ["read_artifacts"],
          who_could_fix: [{harness_id, why_not}, ...],
          next: "给某个成员加读文件工具 / 让它交产物时带 sha256（平台代读）/ 换一个 high 候选"}
```
绝不返回一个"看起来能跑"的配置。

## 三、路径选择的先后顺序

1. 有 `high` ⇒ **A**（solo）——最少协作成本；
2. 否则能补齐 ⇒ **B**（team）——用助手补；
3. 都不可行 ⇒ **blocked** + 说清缺哪项、谁能补、怎么补。

`alternatives` 同时给出**另一条路为什么不可行**（例如"没有 high 候选：`示例Harness-A` 读不了文件"），
让人一眼看到取舍，而不是只看到结果。

## 四、防"假精确"（与既有纪律的衔接）

- ❌ 不输出 0~100 的分数、不输出"最佳人选"排名；
- ✅ 只输出：**两条路是否可行 + 具体配置 + 每条选择的理由 + 缺口**；
- ✅ 同分一律 `harness_id` 字典序（可复现、可对比，不掺偏好）；
- ✅ 响应里固定带 `sort_note`：「按协议数/名字排序是**技术性稳定**，不是推荐度」。

## 五、判据（`tools/lead_plan_check.py`，12 格）

| # | 格 | 断言 |
|---|---|---|
| ① | 有 high ⇒ 走 solo | `mode=solo`、`helpers=[]`、四件事全覆盖 |
| ② | 多个 high | 选 `protocol_count` 最大的；同分按名；`others` 列出同为 high 的 |
| ③ | 无 high 但能补 ⇒ team | `mode=team`、`helpers` 非空、每个助手带 `adds` |
| ④ | 助手确实是补缺的 | 主组长缺 `read_artifacts` ⇒ 助手里有能读文件的 |
| ⑤ | 补不齐 ⇒ blocked | `blocked.missing` 非空 + `next` 给三条可走的路 |
| ⑥ | 不返回假配置 | blocked 时 `lead/helpers` 为空或明确标 `feasible=false` |
| ⑦ | 稳定可复现 | 同输入两次调用结果逐字相同（tie-break 走名字） |
| ⑧ | 无候选 | 空列表 ⇒ `blocked` + 说明"先注册接入" |
| ⑨ | 需求可变 | 传 `needs=["dispatch"]` ⇒ 只需一件，solo 门槛相应降低 |
| ⑩ | 只读 | 调用前后状态文件 sha 不变 |
| ⑪ | 端点 | `GET /api/lead-plan` 200；坏参数 ⇒ 400 说清 |
| ⑫ | 与 sign 一致 | 按算法选出的主组长去 `POST …/lead` 能成功（真注册 + 真选） |

## 六、不改什么

- 不改 `lead_eligible`（仍是"能不能当"的门槛）；算法是**在合格者里排配置**，不是放宽门槛；
- 不新增长期状态（算法是纯函数 + 只读端点；推荐不落库）；
- 不碰冻结实现与信誉/身份定位方案。

### 落地时纠正的两处（都写在代码注释里）

1. **`read_artifacts` 只认"能读"，不认"能写"**：首版把 `can_write_files` 也算作覆盖"看产物"，
   于是"读不了文件的主组长"被判成"四件事全覆盖" ⇒ **助手永远配不出来**（B 路径形同虚设）。
   现在 `covers_of()` 与 `lead-team` 的 coverage 同一口径：只看 `can_read_files is True`。
2. **判据工具里的改档案路径错了**：写成 `POST /api/docking/harness/{id}/edit`（**没有 `/edit` 后缀**，真实端点是
   `POST /api/docking/harness/{id}`）⇒ 405，而 `errors` 恰好来自别的工位 ⇒ **假绿**。
   已修，并把 ⑧ 的断言加强成"改档案真生效（`archive.artifact_inbox_dir` 等于目标）"。
   （同一错误也存在于 `artifact_inbox_check` 的 ⑧，已一并修。）

## 八、这是为了做「组长列表」（老板 2026-11-07）

算法与能力面的**落点**是 `GET /api/lead-roster` —— 它现在不只是一串"谁能当组长"，
而是**可以直接渲染的组长列表**（前端不用再自己算）：

| 字段 | 内容 |
|---|---|
| `candidates[]` | 每个候选加上 `protocol_fit`（high/medium/low）、`covers`（覆盖四件事哪几件）、`solo_feasible`（自己能不能闭环）、`needs_helpers`（缺什么）、`helper_options`（谁能补、补哪项） |
| `groups.solo_ready` | **① 可独立胜任**（四件事全包） |
| `groups.needs_helpers` | **② 需配助手**（缺的项列在 `needs_helpers`，补的人在 `helper_options`） |
| `groups.helpers_only` | **③ 只能当助手**（不合格当组长、但能补事 —— 视觉型/落盘型在这里） |
| `helpers[]` | 助手池：`covers` + `can_do_for_lead`（人话） |
| `needs_def` | 四项需求的定义与人话标签（一处真相：`lead_algorithm.NEED_LABELS`） |
| `plans` | `V136` 两条路的结论（solo/team/blocked），**与分组同一份事实** |
| `group_hint` | 三组的说明 + 「顺序按 `harness_id` 字典序，**不是推荐度**」 |

**纪律照旧**：组内按名字排序、**不打分、不推荐**；不合格的候选仍进 `excluded` 并给原因。
