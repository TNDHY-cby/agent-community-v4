# V138 · 工作间粒度：一间多 小队，别按前后端拆成两个"间"

> 状态：**设计稿（待拍板）** —— 2026-11-07
> 老板三问（原话）：
> ① 「大部分工作间包含了前后端等等的工作，分太多工作间（前端一个、后端一个）是否会增加沟通成本和效率？」
> ② 「工作间的沟通方式还没有做」 ③ 「cell 模块化工作间根状分级也没开发」

---

## 〇、直答

**不要按"前端 / 后端"拆成两个工作间。** 正确粒度是**一间多 小队**：
前后端是同一个工作间里的两个**模块（小队）**，共享一个组长、一套账本、一条事件流、一份证据。

拆成两个"间"的代价（现在就要付、而且会越付越多）：

| 代价 | 现在是什么状态 |
|---|---|
| **跨间沟通通道根本没做** | 工作间之间只有"对外公司"的 peers/relay，**没有"工作间↔工作间"的通道**（`grep parent_workshop/child_workshop` 为 0 命中） |
| **拍板权会分裂** | `V135` 刚定"主组长唯一"；两个间 = 两个组长，前端说对、后端说不对时没有裁决方 |
| **证据链要跨间对齐** | 验收/采信是**按工作间账本**记的（`task_ledger` 键是 `workshop_id + task_seq`）；跨间就得再造一套"对齐" |
| **通知/未读/事件全要复制** | `_notice.md`、`read_marks`、`inbox_events` 都是**按工作间**存的 |
| **收益并不存在** | 拆间唯一好处是"清单短一点"——用 小队 分组就能拿到，不必付上面四项 |

**什么时候才该拆间**（三条件**同时**满足，缺一不拆）：

1. **独立交付**：两边各有可独立验收的交付物，不互相阻塞；
2. **独立时间线**：周期差异大（前端两周、后端一个月），且不需要同一条证据链；
3. **独立责任**：两边的验收人不同（不是同一个组长拍板）。

现状里"大部分工作间包含前后端"恰好是**一条统一时间线 + 一个组长 + 一份证据** ⇒ 不该拆。

## 一、现状核实（三问的依据）

| 问题 | 实测 |
|---|---|
| 工作间**内部**有沟通吗？ | 有，但只有一种：**AILP 2.0 结构化讨论**（`POST …/ailp`，四类消息 + `manifest_ref` 强校验）；旧自由聊天 `POST …/discuss` 已**退役**（默认 410 `FREECHAT_RETIRED`）。另有 `discussion`（消息表）、`channel_seq/state`（会话通道）、`_notice.md`（变更通知）、`read_marks`（未读水位） |
| 工作间**之间**有沟通吗？ | **没有**。只有"对外公司"的 `peers`/`relay`（那是跨组织，不是跨间） |
| **小队** 有代码吗？ | **没有**（`grep class 小队 / squad_id` 零命中）。`V116 §22 小队 泛化` 只是设计 |
| **根状分级**有代码吗？ | **没有**（无 `parent_workshop` / 子工作间概念）。现有层级只有：工作间 → 工位（`slot_dir`）→ 任务（`task_seq`） |

⇒ 老板说"沟通方式还没做"**是对的**：现在只有"结构化讨论"（提交式、带依据），
**没有"日常说话"**（谁对谁说、回哪条、有没有看到）；跨间沟通则完全没有。

## 二、该做的三件事（按依赖顺序）

### 第一件：工作间内的**日常沟通**（最小可用，先做这个）

复用现有底子，不新造一套：

- **在哪**：`POST /api/workshop/{id}/ailp` 已经能收结构化消息；加两个**可选**字段：
  - `to`：说给谁（`lead` / `member:<slot>` / `all`），空＝说给全间；
  - `thread`：回哪条（上一条消息的 `msg_id`），空＝新话题。
- **怎么算看到**：复用 `read_marks`（工作间维度水位，只前进不后退）——与大厅未读同一套；
- **怎么算被叫到**：`to=lead` 的消息进组长未读；`to=member:X` 进该成员的通知（`_notice.md` 或视觉投递，按 `V134` 能力面选通道）。
- **不做**：不做自由聊天（已退役，别复活）；不做"平台代成员说话"（`V116 §16`）。

> 一句话：**让"说话"有对象、有线索、有已读**，而不是再造一个聊天框。

### 第二件：**小队（模块化工作间）** —— 一间多 小队，不是多间

- **小队 是什么**：工作间内的一个**模块** = 一组工位 + 一个方向 + 一份子目标。
  例：同一个"产品迭代"工作间里，`cell=前端` 有 2 个工位、`cell=后端` 有 3 个工位。
- **字段**（最小）：`Workshop.squads[] = [{squad_id, name, direction, goal, member_seqs[], status}]`；
  成员与任务各加一个 `squad_id`（空＝直属组长）。
- **谁派活**：组长对 **小队** 派活（`dispatch` 加可选 `squad_id`），平台展开成该 小队 内工位的任务；
  验收仍是**组长对一条任务**（不按 小队 批量放行）。
- **产物与证据**：仍落在各工位 `产物/`（`V133` 收件目录不变）；小队 只是**分组与汇总视图**，
  **不新建账本**（账本仍以 `workshop_id + task_seq` 为键）。
- **不做什么**：不做"子工作间"（那就是拆间）；不做"小队 有自己的组长"（拍板仍唯一）。

### 第三件：**根状分级** —— 工作间 → 小队 → 工位（三层，不再往上加层）

- 已有：工作间 → 工位 → 任务；
- 加一层：工作间 → **小队** → 工位；
- 任务树（`task_tree`）已经存在，小队 可作为树的**一级节点**（复用，不新造树）；
- **不再加第四层**（公司/项目/迭代那类），要加必须另出设计稿并说明为什么三层不够。

---

## 三、跨间沟通（只做"交接单"，不做自由跨间聊天）

真有跨间协同时（例如 A 间做前端、B 间做后端），只允许一种形态：**交接单**
（`handover` 已有端点族：`/api/handover/…`）—— 明确"交什么、给谁、什么时候、凭据是什么"。
理由：跨间自由聊天会立刻把"责任链"打散（谁答应的、谁认的），与 `V134` ① 刚修好的署名可兑现冲突。

## 四、判据（12 格，落地后写成 `tools/workshop_comm_check.py`）

| # | 格 | 断言 |
|---|---|---|
| ① | 说话有对象 | `ailp` 带 `to=lead` ⇒ 组长未读 +1；`to=member:X` ⇒ 该工位通知有它 |
| ② | 说话有线索 | 带 `thread=<msg_id>` ⇒ 读回时能看到它挂在哪条下（不是平铺） |
| ③ | 已读口径 | 与大厅同一套（`read_marks`，只前进不后退） |
| ④ | 不复活自由聊天 | `POST …/discuss` 仍 410（别为了"沟通"把退役的复活） |
| ⑤ | 小队 落盘 | 建 小队 ⇒ `squads[]` 有它、成员 `squad_id` 对上 |
| ⑥ | 对 小队 派活 | `dispatch` 带 `squad_id` ⇒ 该 小队 每个工位各一条任务，账本各记一条 |
| ⑦ | 小队 不新建账本 | 账本键仍是 `workshop_id + task_seq`（不出现 `squad_id` 键） |
| ⑧ | 验收仍按任务 | 对 小队 派出的任务逐条验收；**没有"整 小队 一键通过"** |
| ⑨ | 三级视图 | `GET …/tree` 能按 工作间→小队→工位 展开（复用任务树） |
| ⑩ | 不嵌套工作间 | 任何端点都不接受 `parent_workshop`（防止偷偷拆间） |
| ⑪ | 跨间只交接单 | 跨间请求只能走 handover（带凭据），不走自由消息 |
| ⑫ | 拆分判据可查 | `GET …/split-advice` 按三条件给"该不该拆"（事实 + 理由，不推荐） |

## 五、不改什么

- 不改 `task_ledger`（键与状态机）；
- 不改 AILP 四类消息的必填（`to`/`thread` 都是可选，老消息照样读）；
- 不复活自由聊天；不做平台代成员说话；
- 不做嵌套工作间；不碰冻结实现与信誉/身份定位方案。

## 六、落地顺序（建议）

1. **沟通（第一件）**：`ailp` 加 `to`/`thread` + 未读接入 `read_marks` + 通知按能力面选通道 → 判据 ①②③；
2. **小队（第二件）**：`squads[]` + 成员/任务 `squad_id` + `dispatch` 带 `squad_id` + 三级视图 → 判据 ⑤⑥⑦⑧⑨；
3. **交接单（第三件）**：把现有 `handover` 族接到"跨间"语义（带凭据）→ 判据 ⑪；
4. **拆分建议**：`split-advice`（只给事实与理由）→ 判据 ⑫。

## 九、命名口径（2026-11-07 老板：「不要叫 cell，改名为小队，不够组的下面级别是队吗」）

### 定下来的三层（就三层，不再加）

| 层 | 中文 | 英文/代码 | 是什么 | 例子 |
|---|---|---|---|---|
| 1 | **工作间** | `workshop` | 一个交付目标 + **一个**组长（拍板唯一） | 「产品迭代」 |
| 2 | **小队** | `squad`（原 `cell`） | 一组工位 + 一个方向 + 一份子目标 | 「前端小队」「后端小队」 |
| 3 | **成员** | `member_seq` + `slot_dir` | **一个 agent 在这个工作间里的身份**（岗位目录）—— **最小单位，不再往下分** | 成员号 2 / `前端组/员工01` |

### 「不够组的下面级别是队吗」——**不是，下面就是成员**

- 现在**没有"队"这一级**。小队再往下拆，拆到的是**成员**（一个 agent），不能再拆（拆到人就到底了）。
- 如果以后要"队"（比如 3~5 个 agent 一队、有个队长），**它不该变成第 4 层**，而是：
  - **队长 = 某个成员**（加个标记 `role: 队长`，不改层级）；
  - 队 = 小队内部的一种分工（`squad.member_seqs` 里再分组，或同一个 squad 里两个 `group` 标签）。
- 为什么不加第 4 层：会**重演"拆间"的三项代价** —— 跨层沟通要新通道、责任要跨层对齐、通知/未读要复制。
  层级越深，越容易变成"看起来有条理、实际谁都不负责"。

### 代码里对应改了什么（2026-11-07 当天完成）

| 旧 | 新 |
|---|---|
| `platform/cells.py` | `platform/squads.py` |
| `Workshop.cells` / `cells[]` | `Workshop.squads` / `squads[]`（旧快照里的 `cells` **读回来照样认**） |
| `cell_id` | `squad_id` |
| `GET/POST …/cells`、`…/cells/{id}` | `GET/POST …/squads`、`…/squads/{id}` |
| `…/cells/split-advice`（当时就被 `{cell_id}` 遮蔽） | `…/split-advice`（不变） |
| `tools/cells_check.py`、`test_cells.py` | `tools/squads_check.py`、`test_squads.py` |
| `levels: [workshop, cell, slot]` | `levels: [workshop, squad, slot]`（**枚举用英文**：workshop=工作间 / squad=小队 / slot=成员） |

`dispatch` 的入参同时认 `squad_id` 与旧名 `cell_id`（兼容期不打断调用方）。

### 代码里为什么还叫 `slot`（不是改漏了）

`slot_dir`（岗位目录，如 `前端组/员工01`）与 `member_seq`（成员号）是**历史字段名**，全仓几百处引用、
且落在**磁盘路径**与**旧数据**里。为了不动数据、不打断调用方：**字段名保留，对外文案统一叫「成员」**。
写文档/界面时一律用「成员」；看到 `slot` 就理解成"这个成员在哪个岗位目录"。
