# V140 · 分队资产化：团队履历 + 分队模板化

> 状态：**待拍板**（老板 2026-11-09 指出「工作间团队培养」应指团队资产而非选人工具，方向认可，方案待定稿）
> 起因：老板原话「它应该是由**经常做一类工作**的团队组成，它们**有大量经验**，但又可以**清理其他任务的上下文影响**，同时可以**复制供其他任务使用的团队**，现在看来应该属于**小队的分级**」
> 影响面：分队（squad）新增两个只读/写端点 + 一份按队聚合的履历；**不改**派活闸门、验收流程、账本结构
> 回滚：`AC_SQUAD_TEMPLATE=0`（模板端点 404）、`AC_SQUAD_HISTORY=0`（履历返回空并说明原因）

## 〇、结论先行

现在的「分队」只是**分组标签**（有 direction / goal / status / member_seqs），它能表达"这几个人一起干"，
但**不能回答**：这支队干过多少同类活？通过率多少？能不能把这支队复制出来接新任务？

老板说的"团队培养"要的是**团队资产**：**专业化 → 积累 → 隔离 → 复制**。
本设计只做**资产化的最小闭环**（履历 + 模板），**不做** agent 内部上下文清理，**不引入**评分/信誉（那是暂停项，见 §六）。

## 二、目标（做两件事，都很小）

### 2.1 分队履历（只读，最有价值）

`GET /api/workshop/{id}/squads/{squad_id}/record`

从**现有任务账本**聚合出来，不新建表（一处真相）：

```json
{
  "ok": true, "squad_id": "squad-2839", "name": "前端分队", "direction": "前端",
  "members": 3,
  "tasks": {"total": 12, "accepted": 9, "rework": 2, "rejected": 1, "open": 0},
  "quality": {"accept_rate": 0.75, "avg_rework": 1.2, "avg_hours": 6.5},
  "recent": ["T-012 通过 · 2026-11-08", "T-009 返工 1 次 · 2026-11-07"],
  "note": "只统计**已完成**的任务；进行中的不算进通过率（否则越忙的队越难看）"
}
```

**口径纪律（三条，都有教训）**：
1. **只算终态**（accepted / rework / rejected / 烂尾）；进行中的不进分母；
2. **不给分数、不排名**（全项目口径：`no score/rank`）—— `accept_rate` 是**比例事实**，不是评分；
3. **样本不足要说**：`total < 3` 时附 `"insufficient": true` + 一句"样本太少，别据此判断"。

### 2.2 分队模板化（写，但要克制）

`POST /api/workshop/{id}/squads/{squad_id}/clone` → 生成新分队

body：`{target_workshop_id?, name?, member_seqs?, copy_experience?}`

复制**什么**与**不复制**什么，是本设计的核心：

| 复制 | 不复制 |
|---|---|
| `direction`（方向） | **任务历史**（新队从零开始记履历） |
| `goal`（目标，可被 body 覆盖） | **账本条目**（绝不复制 T-xxx） |
| 成员**构成**（member_seqs，可换人） | **成员的会话上下文**（平台本来就管不到） |
| `copy_experience=true` 时：**经验索引指针**（指向心智根里已归档的几条 memories 路径） | **经验正文副本**（避免把旧任务的上下文灌进新任务） |

**为什么只搬指针不搬正文**：老板要的"清理其他任务上下文影响"正是这一点 ——
新任务拿到的是"我们以前踩过这些坑（路径在这）"，而不是"上一个任务的来龙去脉"。
真需要看，自己去心智根读（按索引按需读，`mind.py` 现有机制）。

## 三、不做（明确列出，防止越界）

1. **不做 agent 内部上下文清理**：成员的会话在它自己的工具里，平台不代管（这是"平台不替 agent 干活"的一部分）。
   我们能做的只有"**不让上一件事跟过来**"（继承只搬产物 + 模板只搬指针）。
2. **不引入评分/信誉/能力指纹**：老板 2026-10-08 暂停项，本设计一个字不碰
   （`experience_v2.py` 里已有的 `capability_ledger` 信誉加分也**不在对外材料与界面里出现**）。
3. **不做跨工作间的"团队迁移"**：`target_workshop_id` 只允许**同一工作间内**新建分队（跨间迁移涉及成员接管，属另一档）。
4. **不做自动建队**：模板只是"复制配置"，**谁来当组长、要不要建**仍由人决定。

## 四、判据（`tools/squad_record_check.py`，6 格，真跑临时实例）

| # | 格 | 断言 |
|---|---|---|
| ① | 履历只算终态 | 有 open 任务时 `tasks.total` 不含它；`accept_rate` 分母 = 终态数 |
| ② | 无分数无排名 | 响应里没有 `score` / `rank` / `recommend` 字段 |
| ③ | 样本不足要说话 | `total < 3` ⇒ `insufficient: true` + 人话 |
| ④ | clone 生成新分队且**不复制任务历史** | **账本条目数不变**（任务归属是按**工位** `member_seq`，账本里没有 squad_id ⇒ 同一批人换队名仍看到同一批历史；~~新队 total == 0~~ 这句与数据模型不符，2026-11-09 落地时更正） |
| ⑤ | clone 复制方向/目标/成员构成 | 三者与源队一致（可被 body 覆盖） |
| ⑥ | `copy_experience=true` **只给指针不给正文** | 返回里是路径列表；响应中不含 memories 正文片段 |
| ⑦ | `AC_SQUAD_TEMPLATE=0` ⇒ clone 404、`AC_SQUAD_HISTORY=0` ⇒ 履历为空并说明 | 开关真生效 |

## 六、与竞品的关系（诚实）

竞品里 paperclip 有 `teams-catalog`（组织即代码：TEAM.md → agents/*/AGENTS.md → projects/*，含 `MIGRATION.md` 整包迁移），
那是**团队模板 + 整包迁移**的完整形态，比我方 §2.2 强得多。

**我方不做的部分及理由**：目录包 + 迁移机制的价值要在**成员规模上台阶**（几十个 agent、多项目并行）才显现；
我方现在的工作间是个位数成员，先做**履历 + 同间复制**这个最小闭环，等规模上来再谈整包迁移。
