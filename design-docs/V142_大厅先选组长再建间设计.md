# V142 · 大厅先选组长，再建工作间（流程前移）

> 状态：**老板 2026-11-09 定方向，后端已落地**（前端列表归前端会话）
> 影响面：`POST /api/workshop` 多一个可选参数；`GET /api/lead-roster` 多一句 `how_to_use`；`POST …/lead` 行为不变
> 回滚：不传 `lead_harness_id` 就还是**老流程**（先建间、后选组长）—— 一条参数开关

---

## 一、老板原话（口径以这段为准）

> 「应该是用户在外界整理好大致方向之后，来平台**直接在大厅的组长列表**里选组长，
> **点击选定组长后才建立工作间**，不用在大厅发言然后建工作间最后才拉组长。」

## 二、现状 vs 目标

| | 现在 | 要变成 |
|---|---|---|
| ① | 大厅输入一句话 → 建工作间 | **大厅先看组长列表 → 点一个** |
| ② | 建完间再进工作间选人当组长 | **选完才建间**（建间那一刻组长已在名单里） |
| ③ | 组长是谁要进到间里才知道 | 大厅卡片上就能看出"这个人能不能当组长、适合什么方向" |

**为什么这样更对**：老板在外界（跟人聊、看材料）已经把方向想清楚了，
来平台是**执行决策**（选谁带队），不是重新讨论。让他在大厅发言再拉组长，
等于把"已经想好的事"又走一遍**没必要的两步**。

## 三、后端怎么做（一处真相）

选组长的逻辑**已经存在**（`POST /api/workshop/{id}/lead`：校验 → 落 `_lead` 槽位 → 置 `lead_in`）。
本批**不重写它**，只做两件事：

1. 把那段逻辑抽成 `platform/pick_lead.py::apply(ws, harness_id, model)` ——
   **老端点与建间端点调同一个函数**（否则两条路迟早长出两套校验规则）；
2. `POST /api/workshop` 接受 `lead_harness_id`（可带 `lead_model`）：
   - **先预检**（`precheck`：harness 存在？`lead_eligible`？）——不满足就 **400/409 且不建间**
     （不留"建了间但没组长"的半成品）；
   - 预检通过才建间，建完**立即** `apply` 绑定；绑定失败 ⇒ 建间成功但响应里如实带 `lead.error`（不静默）。

### 接口

```
GET  /api/lead-roster                 # 已有：只列能当组长的人（不排序不推荐），新增 how_to_use 一句
POST /api/workshop                    # 新增可选 lead_harness_id / lead_model
     body: {name?, hall_content?, workshop_path?, lead_harness_id?, lead_model?}
POST /api/workshop/{id}/lead          # 不变（老路径：建完间再选）
```

`lead-roster` 的 `how_to_use` 会明确写：**选中谁，就把它的 `harness_id` 传给 `POST /api/workshop`**
——前端不需要再打第二个接口去"拉组长"。

## 四、不做（明确划界，防止越界）

1. **不替用户挑组长**：`lead-roster` 仍然**不排序、不推荐**（`no_score`/不排名是全项目口径）；
   只给事实（能不能当组长、缺什么、适合哪些方向）；
2. **不改名单结构**：`_lead` 槽位还是那个槽位（`V139` 的 `reports_to` 也照旧指向它）；
3. **不做"选组长后自动派活"**：派活仍然在工作间里显式做（派活要写任务文件、要过闸门，不能顺手完成）；
4. **前端列表不在本稿**：大厅那张卡片列表归前端（要方向/适配度/契约四要素，见 §五）。

## 五、给前端的契约（四要素）

| 要素 | 内容 |
|---|---|
| 数据源 | `GET /api/lead-roster`（`candidates` 数组；每项含 `harness_id` / `name` / `lead_eligible` / `tooling` / `fit_directions`） |
| 选中动作 | `POST /api/workshop` 带 `lead_harness_id`（+ `name` / `hall_content`） |
| 空态 | `candidates` 为空 ⇒ 写「还没有能当组长的 agent」+ 指向「对接中心」去接一个（**不要显示空白列表**） |
| 失败态 | 400/409 时把响应里的 `error` + `why` + `next` **原样显示**（那是给人和 agent 看的人话） |

## 六、判据（`tools/pick_lead_check.py`，6 格，真跑临时实例）

| # | 格 | 断言 |
|---|---|---|
| ① | 建间时带合格组长 ⇒ 建间成功**且**名单里已有 `_lead` | `roster` 里有 `_lead` 槽位，`status=lead_in` |
| ② | 组长不合格 ⇒ **拒绝且不建间** | 409 `NOT_LEAD_ELIGIBLE`，工作间总数不变 |
| ③ | 不带 `lead_harness_id` ⇒ 老三步不变 | 建间成功、`status` 不是 `lead_in`、名单里没有 `_lead` |
| ④ | 不存在的 harness ⇒ 404 且不建间 | `NO_SUCH_HARNESS` |
| ⑤ | `lead-roster` 给了 `how_to_use`（前端不必猜第二步） | 响应里有 `how_to_use` 且提到 `POST /api/workshop` |
| ⑥ | **一处真相**：两条路绑出来的 `_lead` 记录逐字相同 | 建间绑定 vs 事后 `POST …/lead`，槽位字段集合一致 |
