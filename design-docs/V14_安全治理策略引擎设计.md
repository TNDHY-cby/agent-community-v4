## 二、目标与非目标

### 目标（第一片）
1. **策略引擎**：`ALLOW / DENY / ASK` 三态决策，可配置规则，落在所有**能执行命令/写敏感文件/出网**的入口
2. **ASK 链路**：被标记为"需审批"的操作 → 进入待审批队列 → 有人（或平台 AI）批准后放行，全程审计
3. **审计覆盖率**：写端点从 **4% → 高风险全覆盖**（本片先把工具/配置/插件/桥这几类高危端点打满）
4. **决策可追溯**：每次放行/拒绝/审批都进审计，带 `decision / rule_id / actor / op`

### 非目标（诚实声明）
- ❌ **不做 DID/VC 去中心化身份** —— 那是联邦跨组织场景，本地单机用不上；本片只做**策略与审计**
- ❌ **不做多 Worker 分布式**（状态仍本地）
- ❌ **不做全量 83 个端点审计**（分批，本片只覆盖高风险类别）
- ❌ 不改现有 `_is_dangerous` 的黑名单语义（作为策略引擎的一条内置规则）

## 三、方案

### 3.1 新模块 `platform/policy.py`（核心）

```python
class Decision:
    ALLOW = "allow"
    DENY  = "deny"
    ASK   = "ask"        # 进待审批队列，阻塞执行

class Operation:          # 操作类别
    SHELL_EXEC      = "shell.exec"
    FILE_WRITE      = "file.write"        # 敏感目录（data/ 配置/桥脚本）
    FILE_DELETE     = "file.delete"
    NETWORK_EGRESS  = "network.egress"    # 外呼未知域名
    PLUGIN_INVOKE   = "plugin.invoke"
    PLUGIN_INSTALL  = "plugin.install"
    CONFIG_MUTATE   = "config.mutate"
    HARNESS_BRIDGE  = "harness.bridge"     # 生成/执行桥脚本

class Rule:
    id: str
    op: Operation            # 或 op 集合
    match: 匹配表达式         # 命令串/路径/域名/插件名 的 glob 或正则
    decision: ALLOW|DENY|ASK
    note: str

class PolicyEngine:
    def evaluate(op, *, actor, target, detail) -> Decision
    def request(op, *, actor, target, detail) -> PendingId   # ASK 时入队
    def resolve(pid, approve, by) -> None                    # 批准/拒绝
```

**决策顺序**（先匹配先生效，最后是默认值）：
1. 内置 DENY 规则（危险命令黑名单 → 这条从现有 `_is_dangerous` 提升而来）
2. 用户规则（`data/policy.json`，按 op + match）
3. 默认值（见 §3.4 拍板点）

### 3.2 接入点（第一片接 7 个，全是真能执行的）

| 接入点 | 操作类别 | 说明 | 默认等级 |
|---|---|---|---|
| `platform/tools/shell_tool.py` | `shell.exec` | AI 能直接跑命令，**最危险** | **ASK** |
| `platform/tools/assistant_tools.py` | `shell.exec` / `file.*` | 平台工具，含 subprocess | **ASK** |
| `platform/tools/file_tools.py` | `file.write` / `file.delete` | 写/删工作区文件 | write=ALLOW / delete=**ASK** |
| `platform/tools/web_tool.py` | `network.egress` | 出网 | ALLOW |
| `platform/routers/plugins.py` | `plugin.invoke` / `plugin.install` | 插件安装与调用（现有 `_is_dangerous` 已在用） | invoke=ALLOW / install=**ASK** |
| **`/api/harness/{id}/bridge/generate`** | `harness.bridge.write` | **实测：真落盘可执行脚本** | **ASK** |
| **`/api/harness/auto-connect`** | `harness.bridge.launch` | **实测：`Popen` 启动进程** | 见下 ·actor 分级 |

#### 桥端点的事实依据（2026-10-03 实测，非推断）

```
harness_bridge.py  import: generate, safe_slug, list_templates, BridgeTemplateError
bridge_factory.py  L117  def generate(...):  bridge_file.write_text(text, encoding="utf-8")
```

**关键发现**：端点函数体里看不到 `write_text`，但 `bridge_factory.generate()` 会**真的把可执行脚本写入磁盘**。
只看端点体得出的「仅返回数据」结论是**错的**——必须跟到被调函数去。

| 端点 | 实测行为 | 判定 |
|---|---|---|
| `bridge/generate` | 生成文本 **+ 写入磁盘**（经 `bridge_factory.generate`），**不启动** | 落在「写盘但不启动」→ 按拍板口径取严：**ASK** |
| `auto-connect` | `_os.makedirs` + **`subprocess.Popen` 真启动进程** | 「自动写入并启动」→ **最严档** |

#### actor 分级（解决安全与产品的冲突）

`auto-connect` 是 V-12 的**一键注册核心功能**。若无差别 ASK/DENY，会把产品主流程堵死。
正解是**按 actor 分级**（策略引擎 `evaluate()` 本就带 `actor` 参数）：

| 操作 | `actor=operator`（本机前端 / 人发起） | `actor=external_ai` / `harness`（AI 发起） |
|---|---|---|
| `harness.bridge.write` | ALLOW | **ASK** |
| `harness.bridge.launch` | ALLOW | **ASK**（不设 DENY：AI 架桥是平台核心能力，一刀切会废掉功能；但必须留痕并可拒） |

**逻辑**：威胁模型是「**AI 驱动的代码执行**」，不是「操作者自己点按钮」。
人从本机 UI 点一键注册，与 AI 自主生成并启动脚本，风险完全不同。

**接入方式**：在执行前一行调 `engine.evaluate(...)`；
- `ALLOW` → 继续
- `DENY` → 返回 403 / 工具报错，**不执行**
- `ASK` → 入队 + 返回"待审批"，执行**挂起**（调用方拿到 `pending_id`）

### 3.3 ASK 链路（**第一片只做人工审批**）

被标记 `ASK` 的操作 → `pending_approvals` 队列 → **前端「待审批」面板**由**人**决定。

| 阶段 | 审批人 | 权限 |
|---|---|---|
| **第一片（本片）** | 平台主人（前端面板） | **决定权** |
| 第二片（延后） | 第二通道 `/api/assistant/chat` 的平台 AI | **仅建议权**（给「建议批准/拒绝 + 理由 + 置信度」），**决定权仍在人** |

#### 为什么第一片不给 AI 决定权（拍板理由，记录在案）

**信任根不能被可攻击组件替代。** 第二通道的 AI 本身也是 AI，可能被 prompt injection 污染；
若它握有批准 `shell.exec` 的权力，攻击者只需先污染它的输入、再触发一个 ASK，就可能拿到执行权。
而人工审批的信任根是**人**——慢，但不可被 prompt injection 绕过。

**若第二片要做 AI 代判，必须先满足三条约束**：
1. 只能对**明确低风险类别**代判（如 `network.egress` 的 ASK），**不含** `shell.exec` / `bridge.launch`
2. 代判必须带**理由 + 置信度**，低置信度**自动升级给人**
3. 所有 AI 代判**必进审计**，`rule_id` 标注 `approved_by: ai`，便于事后追责

> 第二通道从"答疑"升级为"授权参与者"的结构性价值**保留**，但走「建议权 + 人决定」，不一步到位给决定权。
> **安全治理里，信任根的不可替代性优先于架构对称性。**

审批结果 → 执行或拒绝 → **必进审计**（`policy.decision` / `policy.approval` 事件）。

### 3.4 默认策略（**已拍板：C**）

| 选项 | 语义 | 结论 |
|---|---|---|
| A. fail-closed（默认 DENY） | 没匹配到 → 拒 | ✗ 开箱即坏用 |
| B. fail-open（默认 ALLOW） | 没匹配到 → 放 | ✗ 策略形同虚设 |
| **C. 分类别默认** | `shell.exec`/`plugin.install`/`file.delete`/`bridge.*` → **ASK**；其余 → **ALLOW**；黑名单 → **DENY** | ✅ **采用** |

**补充约束（拍板明确要求）**：默认策略 C 是**出厂设置**，不是硬编码。
`policy.py` 的规则表与分类默认值**全部加载自 `data/policy.json`**，用户可改。
不同团队对「哪些操作必须人工确认」容忍度不同——**代码里不写死任何策略**。

**我建议 C**：零配置就有保护，又不把正常开发堵死。

### 3.5 审计扩展（第一片范围）

`AuditLog.record(event, actor, target, detail)` 已够用，本片：
1. 新增事件：`policy.decision`（ALLOW/DENY/ASK）、`policy.approval`（批准/拒绝）
2. 把高风险写端点接上 `_audit_log`（`config`、`plugins`×3、`harness_bridge`×8、`workshops_task` 的 halt/reset 等）
3. `detail` 里带 `rule_id` + `decision`，满足"决策依据可追溯"

**目标：写端点审计 4% → ≥35%**（高风险全覆盖，剩余协作类端点第二片）。

### 3.6 端到端追踪（**本片只做最小钩子**）

- 审计记录加 `trace_id`（请求进来时生成，贯穿同一次操作）
- **不做** OpenTelemetry/span 那套（第二片再评估）

```json
{
  "version": 1,
  "default_by_op": {
    "shell.exec": "ask",
    "plugin.install": "ask",
    "file.delete": "ask",
    "harness.bridge.write": "ask",
    "harness.bridge.launch": "ask",
    "network.egress": "allow",
    "plugin.invoke": "allow",
    "file.write": "allow",
    "config.mutate": "allow"
  },
  "actor_overrides": {
    "operator": {
      "harness.bridge.write": "allow",
      "harness.bridge.launch": "allow"
    }
  },
  "rules": [
    {"id": "builtin.danger", "op": "shell.exec", "match": "__builtin_dangerous__", "decision": "deny", "note": "危险命令黑名单"},
    {"id": "shell.rm_rf", "op": "shell.exec", "match": "rm -rf *", "decision": "deny"},
    {"id": "net.exfil", "op": "network.egress", "match": "*pastebin.com*", "decision": "deny"}
  ],
  "pending": []
}
```

- `default_by_op` —— 出厂策略 C（分类别默认），**改这个文件就能改策略**
- `actor_overrides` —— 按 actor 覆盖（解决 `auto-connect` 的安全/产品冲突，见 §3.2）
- `rules` —— 有序规则，先匹配先生效；`__builtin_dangerous__` 是哨兵，指向现有 `_is_dangerous`
- `pending` —— 待审批项（`id/op/target/actor/created/reason`）

### 9.3 步骤 2 顺带修掉的对外 bug（V-12 遗留，已发布）

**现象**：`/api/assistant/chat` 只认 `{"message": ...}`，但 **V-12 写的 `protocol_brief.py` 第二通道示例与 `register.html` 注册话术里都写成了 `{"content": ...}`** —— 外部 AI 照着平台自己发的简报调用会直接 **400**。
（前端自身用的是 `{message: msg}`，是对的；**只有对外文档错了**。）

**处置**（两步都做，不只改文档）：
1. 服务端**兼容两种键名** `body.get("message") or body.get("content")` —— 既有文档已发布，已按旧文档接入的一方不该因我们改文档而踩坑
2. 文档统一改为 `message`（`protocol_brief.py` 加 `body`/`note` 字段；`register.html` 加注「服务端亦兼容 content 别名」）

**实测**：两种键名均 HTTP 200。

> 这是**同一个坑的第三次**（「改 API 前先读 schema」已记入 `pitfalls.md`）。区别是这次由**活服务实测**发现，不是靠读代码 —— 印证铁律 #3「改完必须重启服务再实测」的价值。
