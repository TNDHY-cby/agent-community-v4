## 一、背景与需求（负责人给的四条语义）

### 1.1 会话必须新建的三个理由

1. **隔离上下文** —— 避免过长上下文加剧 token 消耗与卡顿
2. **不污染** —— 避免旧项目上文影响新项目
3. **并行** —— 多个会话可同时参与多个工作间，**甚至多个会话参与同一个工作间**

### 1.2 建间与工作区

- 新建工作间时**让用户自定义工作区文件**（类似 DSH）
- **一个工作间对应一个工作区文件夹**

### 1.3 三层桥模型（负责人原话）

> 第一次注册 harness 后列入列表中的应该是"harness 利用通用模板注册**具体桥模板**"；后期新建工作间时，平台利用这个**具体桥模板**与 harness 和用户配合落地一个**具体桥（存至工作区文件夹）**，并做好提醒工作。

### 1.4 会话创建的责任

- 强制 harness 建会话**技术上可行**（给平台 agent 鼠标键盘能力），**但不如让用户自建方便**
- 负责人选：**用户自建 + 平台提醒**
- **桥的数量**：选 **B**（一间一份脚本、进程共用）
- **协议要分化**，各协议用法应该不同
- **无协议但有插件市场的 harness** → 引导用户

## 三、概念模型：把三样东西拆开

**现状的抽象错误**：`注册 harness ≈ 接上「那个会话」`（标量）——一旦出现第二个会话，模型里没它的位置，于是**失忆**。

**正确拆分**：

| 概念 | 属于谁 | 数量 | 生命周期 | 承载 |
|---|---|---|---|---|
| **Harness** | 实体（进程/环境） | 1 | 注册起 → 注销止 | 身份、token、桥坐标、唤醒方式、**持久通道** |
| **Session** | **harness 的子对象** | **N（可并行）** | 创建起 → **显式关闭** | 独立上下文（理由 1/2 的隔离） |
| **Binding** | 会话 ↔ 工作间成员 | N:M | 随会话生灭 | 角色、工作区、**平台侧可见性** |

**核心原则**：

> 平台不拥有会话，只拥有**对会话的观察**。
> 平台能保证的是"**我认识并记录每一个会话**"；不能保证的是"**每个会话上下文确实干净**"——后者只能以**可审计的自述**要求。

## 四、承诺分层（回答"能否确保"）

| 层 | 承诺 | 平台控制力 | 可达性 |
|---|---|---|---|
| **L0** 桥在场 | 桥进程活着 | 强（`proc.poll()`） | 全类型可达 |
| **L1** 投递 | 消息进了某个通道 | 强（HTTP 200 / 文件写入 / 入队） | 全类型可达 |
| **L2** 会话建立 | harness 建了绑到本工作间的会话 | **断崖**：仅 ACP/插件能促成 | 见 §六 三档 |
| **L3** 工作就绪 | harness 真的理解了角色与任务 | **零** | 只能自述 |

**设计目标因此是**：把 L0/L1 从"假成功"改成"真状态"，把 L2 从"不可知"改成"**可审计**"，L3 只做可见性不做承诺。

## 五、三层桥模型

### 5.1 三层结构

```
L1 通用模板        bridge_templates/{cli_acp,file_poll,pending_poll}/*.tmpl + template.json
      │  + harness 参数（注册期采集）
      ▼
L2 具体桥模板      【新增实体】持久化于该 harness 的注册条目内
      │  + workspace_dir（建间期注入）
      ▼
L3 接入产物        落在工作区文件夹，类型按唤醒方式派生（见 §五.3）
```

### 5.2 L2 是新增层（当前缺失）

现状：`bridge_factory.generate(template, params, out_dir)` **每次现取模板 + 现取 params**，没有"这个 harness 的具体模板"这个持久化实体。

**L2 的内容**（注册期生成一次）：

```json
{
  "harness_id": "...",
  "template": "cli_acp",              // 来自 L1
  "wakeup_method": "acp",              // 探测/声明所得
  "params": { ... 只有 harness 相关、与工作间无关的参数 ... },
  "artifact_kind": "script",           // L3 产物类型
  "capabilities": [...],               // 由 MCP tools/list 或声明采集
  "created_at": "..."
}
```

**L2 的价值**：建间期不再需要重新探测 harness，**一次采集、多次落地**。

### 5.3 L3 必须泛化为「接入产物」（关键）

**「具体桥」只对有桥的协议成立。** 按唤醒方式派生：

| `wakeup_method` | 接入产物 | 存放位置 | 进程数（B 方案） |
|---|---|---|---|
| `ACP` | **可执行脚本**（ACP 客户端） | `workspace_dir/` | **1 进程管 N 会话**（B 的原生形态） |
| `FILE_POLL` | **轮询器脚本** | `workspace_dir/` | 1 进程需支持**多 work-dir**（现为单值 `--work-dir`） |
| `HTTP_API` | **连接契约**（callback URL + 工作区坐标 + 回执格式） | `workspace_dir/`（JSON） | **0（无桥）** |
| `CLIPBOARD` | **激活提示词** | `workspace_dir/`（txt） | **0（人粘贴）** |

**若对 http_api 型要求"生成脚本"，该要求本身就是错的。**

## 六、会话创建：三档 + 插件引导

### 6.1 分档

| 档 | 途径 | 会话能力 | 平台可验证 | 提醒 |
|---|---|---|---|---|
| **A** | ACP 原生 | `session/new(cwd=工作区)` | ✅ 拿到 `session_id` | 不需要 |
| **B** | MCP 工具补偿（harness 暴露 `new_session`） | 半可验 | ⚠️ 看是否返回 id | 不需要 |
| **D** | **插件市场装插件获得协议** | 取决于插件 | 装后按 A/B 判定 | **需要引导（见 §六.3）** |
| **C** | 无协议且无插件市场 → **用户自建** | 仅自述回执 | ❌ | **必须提醒 + 回执契约** |

### 6.2 接入路径是棵树

```
注册探测
├─ 有原生协议？        → 按协议走 A / B
├─ 无协议但有插件市场？ → 引导装插件 → 插出协议 → 回到 A / B
└─ 都没有              → C 档：用户自建 + 回执
```

**B 档可行性已具备**：`mcp_client.py` 已有 `mcp_list_tools()` / `mcp_call_tool()`（`L131`/`L146`），平台可直接调用。

### 6.3 D 档的「引导」怎么做（避免 N× 集成成本）

**原则：表达需求，不指定实现。** 平台**不为每个 harness 写安装步骤**——那是已被否掉的思路。

提示文案（建间/注册时按需展示）：

> 你的 harness 无原生接入协议。可通过其插件市场获得接入能力，按优先级需要：
> ① 平台能把消息发进来 ② 结果能发回平台 ③ 能按工作区建立独立上下文
> 装好插件后**重新注册**，平台会自动探测新协议并回到自动接入路径。

**引导产出**：在该 harness 的注册条目上标记 `needs_protocol=true` + 引导文案，随 §十 的「提醒工作」一并呈现。

### 6.4 C 档的回执契约（新增协议字段）

`POST /api/harness/activation-result`：

```json
{
  "workshop_id": "...", "member_id": "...", "status": "entered",
  "session_id": "<你的会话ID>",       // 新增：平台据此认得会话
  "context_turns": 1                  // 新增：可审计自述，新会话应为 1
}
```

**`context_turns` 是把"隔离"从承诺变成可查事实的最小代价**：若回报 200，说明复用了旧上下文，理由 1 未达成 → 平台记录并提示，但**不阻断流程**。

## 七、协议分化矩阵（负责人问的"各协议如何利用应该不同"）

### 7.1 先分清两个正交的轴

| 轴 | 枚举 | 回答的问题 |
|---|---|---|
| **协议轴**（V-11 目录） | `ws / http / sse / pipe / grpc / mcp / a2a` | 用什么语言说 |
| **唤醒轴**（`WakeupMethod`） | `HTTP / HTTP_API / FILE_POLL / CLIPBOARD / ACP` | 怎么把它叫醒去干活 |

### 7.2 一个协议只解决一个问题

| 层 | 问题 | 协议 | 为什么只能是它 |
|---|---|---|---|
| 发现 | 我在哪、谁找得到我 | **A2A** | 只有它有 `agent-card` |
| **会话** | **怎么进隔离上下文** | **ACP** | 只有它有 `session/new(cwd)` |
| 能力 | 我会什么 | **MCP** | 只有它有 `tools/list`（**L2 模板的输入源**） |
| 投递 | 消息怎么送、结果怎么回 | **HTTP** | 万能，**所有通道的共同回执面** |
| 前端 | 浏览器实时 | **WS** | 浏览器专用 |
| 传输底座 | 本地免网络 | **Pipe** | `pipe_dir` 已存在 |
| 占位 | — | sse / grpc | 未实现 |

**核心**：不是"哪个协议都能进工作间"，**只有 ACP 能**；其余各答各的问题。

### 7.3 各阶段协议分工

| | 发现(A2A) | 会话(ACP/MCP/人) | 能力(MCP) | 投递(HTTP) |
|---|---|---|---|---|
| **注册期** | 写入 agent-card | — | **读 `tools/list` → 写入 L2 模板** | 探测可达性 |
| **建间期** | — | A/B/C/D 三档选路 | B 档调 `new_session` 工具 | 生成回执契约 |
| **运行期** | — | 桥管 N 会话 | 工具按需调 | 推送 + 回执 |

## 八、V-6 护栏的绕行方案（不拆护栏）

`harness_bridge.py:192-200` 的限制是**对的**（caller 任意指定 `out_dir` ≈ 任意文件写入）。目标"桥存工作区"与它冲突，解法是**区分路径的来源**：

```
❌ caller 传 out_dir            → 调用方定路径 → 危险（保留现有限制）
✅ 平台从 workshop_id 推导路径   → 平台自算、不可被输入影响 → 安全，可进工作区
```

**具体做法**：新增一条专用通路（如 `POST /api/workshop/{ws_id}/connect-artifact`），
路径由 `ws.workspace_dir` 派生，**不在请求体里接受任何路径字段**。
caller-supplied `out_dir` 的原限制**原样保留**。

## 九、`_trash_bridge_dir(ws.workspace_dir)` 的定性（**已查清：命名误导，非伏笔非 bug**）

`workshops_lifecycle.py:170,233` 调 `_trash_bridge_dir(ws.workspace_dir)`，被调函数参数名却是 `bridge_dir`。曾有两种假设，**实测均不成立**：

| 假设 | 判定 | 证据 |
|---|---|---|
| **(a) 伏笔**（桥当初就在工作区） | ❌ **不成立** | 全库**无任何证据**表明桥曾在工作区；`bridge_dir` 只写在 `platform/bridges/` 路径上 |
| **(b) 传错参数**（本应 `ws.bridge_dir`） | ❌ **物理上写不出** | `Workshop` 模型**没有 `bridge_dir` 字段**，只有 `workspace_dir` —— 那个属性根本不存在 |
| **(c) 命名误导**（第三种，实际真相） | ✅ **成立** | 见下 |

**(c) 的三条证据：**

1. **两处调用点都在"删工作间"语义里** —— `delete_workshop()` 与 `recycle_stale_workshops()`，意图都是「这个工作间不要了」
2. **函数实现是完全通用的** —— `def _trash_bridge_dir(bridge_dir)` 的函数体只做「把**任意**目录移入回收站（不物理删除，可恢复）」，**不检查、不关心它是不是桥**
3. **`Workshop` 唯一的目录属性就是 `workspace_dir`** —— 调用方传的是它唯一能拿到的路径

**结论**：
- **行为正确**：删工作间 → 工作区进回收站（可恢复），这是应有语义，**不用改**
- **函数名误导**：叫 `_trash_bridge_dir` 却收 workspace —— 历史遗留的命名（建议实施时改名为 `_trash_dir_to_recyclebin` 之类，**仅改名、不改行为**）
- **「桥在工作区」不是历史伏笔** —— V-15 的这个语义是**全新设计**，不存在"补上生成侧即自洽"的既成事实

> 教训：本该先查 `Workshop` 有没有那个字段，再谈"是不是传错了"——**缺一个字段的存在性检查，就会编出一个不存在的假设**。

## 十一、进入状态机（把"已派发 N 名"换成真相）

每个 `(工作间, 成员)` 一个状态机：

```
pending → dispatched → acked → entered
                    ↘ timeout → needs_human
```

**每档 `wakeup_method` 声明可达的最高状态**：

| 唤醒方式 | 最高可达 | 靠什么 |
|---|---|---|
| `ACP` | **entered** | 桥建会话并回报 |
| `HTTP_API` | **acked** | HTTP 200；entered 靠其自述 |
| `FILE_POLL` | **dispatched** | 文件写入成功 |
| `CLIPBOARD` | **entered** | **人工点击**（见 §11.1） |

### 11.1 人工进入入口（**原稿缺失，2026-10-03 补**）

**缺口**：`CLIPBOARD` 型**按定义没有程序**——人把提示词粘到聊天窗口，harness 那侧无法调 HTTP 回报。
原稿只写到「等人粘贴」就断了，**没有回答"粘完之后怎么告诉平台"**。

**后果比"卡在等待"更严重**：`harness_activation_result` 里有

```python
if ws.members and all(m.status == "entered" for m in ws.members):
    asyncio.create_task(_assign_tasks(ws))      # ← 要求全部 entered 才派任务
```

CLIPBOARD 型永远进不了 `entered` → **整条链路走不通，任务永远不派发**，不是卡住。

**现状核验**：`entered` 的三个来源全是机器路径
（`_apply_harness_reply` 内部函数 / `sm_resume`·`sm_drop` 状态机 / `harness_activation_result` 桥调），
**前端 0 个手动漫进按钮** —— 缺口属实。

**补法（方案 A，但做成通用入口而非只给 CLIPBOARD）**：

| 项 | 设计 |
|---|---|
| 入口 | 工作间详情页，**每个成员一个「确认已进入」按钮**（hover 显示"人工确认"） |
| 动作 | 点击 → 复用现有 `POST /api/harness/activation-result`（`status=entered`，`session_id` 留空或 `null`） |
| 来源标注 | 新增 `source: "human"` —— 与 `session_registry` 的 `source` 字段对上，**审计可区分"人报"与"机器报"** |
| 审计 | `member.manual_entered`，target=workshop_id:member_id |

**为什么做成通用入口而不是 CLIPBOARD 专用**：

1. **CLIPBOARD 是必需**（按定义无程序，人工是唯一路径）
2. **其他类型是兜底** —— `HTTP_API` 推送失败、`FILE_POLL` 轮询没跑、ACP 建会话失败，**都需要同一个入口收场**
3. 一个入口服务五档，避免"每档一个特例按钮"

**信任与可审计**：人工点击本质是"人替 harness 作证"，所以**必须留痕**（`source=human` + 审计），而不是把人点的与机器报的混为一谈。

**`_dispatch_to_harness` 必须停止假成功**：队列分支改为

```
桥活着            → 入队，return (True, ...)
桥未运行（未接入） → return (False, "桥未运行，已生成接入指引")
```

上层据此把成员标 `blocked` 并把指引推给用户。

**前端呈现**：`3 名已入工作间 · 1 名桥未运行 · 1 名等待人工粘贴`
（替代当前可能全是假的"已派发 N 名"；**待人工的成员旁边直接给上面那个按钮**）。

## 十二、session_registry 与关闭链路

### 12.1 平台侧注册表（新增）

```python
session_registry = {
  "(harness_id, session_id)": {
     "workshop_id", "member_id", "role", "workspace_dir",
     "created_at", "last_seen", "status",   # active / closed / stale
     "source": "acp" | "mcp" | "user" | "plugin",
     "context_turns": int,
  }
}
```

**落盘**（不放桥内存）：`data/sessions.json`，**与用户可编辑的配置分离**（复用 V-14 的独立落盘纪律）。

### 12.2 关闭策略（**已拍板：默认保留待复用**）

负责人拍板 #4：**保留待复用** —— 工作间结束**不关**会话，同一 `(workshop, member)` 再激活时复用已有会话。
（与现有桥行为一致：`acp_harness_bridge.py` 里 `_sessions.get(key)` 命中即复用、注释写死「不关闭」。）

| 触发 | 动作 | 理由 |
|---|---|---|
| 工作间**结束**（completed） | **保留**（标 `idle`） | **拍板 #4：待复用**；下次进入直接复用，省一次建会话 |
| 工作间**删除** / stale 回收 | **发起 `session/close`** | §九已查实：删除时工作区**已进回收站** → `cwd` 失效 → 会话成孤儿，必须关 |
| 成员移出工作间 | **保留** | 该成员可能回到同一工作间 |
| 注销 harness | **全关 + 移出注册表** | harness 没了，会话无宿主 |
| 会话长时间无回报 | 标 `stale`，**不自动关** | 关闭非平台可强制；`stale` 只影响可见性 |
| 人工（前端/策略） | 可发起 close | 提供入口，不自动 |

**「删工作间要关」与「保留待复用」不矛盾**：
保留的前提是**工作区还在**（`cwd` 有效）；删除时工作区进回收站，`cwd` 失效，会话已无意义。
**会话清理必须与工作区清理同步** —— 这正好接上 §九 的结论。

**明确边界**：平台只能**发起**关闭，harness 可以不听 → 发起后标 `close_requested`，以自述为准。

#### 12.2.1 「保留」必须配可见性（否则回到现状）

既然会话**只增不减**，就**必须让人看得见**，否则重蹈「桥内存里一堆无人知晓的会话」：

| 交付物 | 用途 |
|---|---|
| `GET /api/sessions?harness_id=&workshop_id=` | 列出活跃会话（`session_id` / 归属 / `created_at` / `last_seen` / `status`） |
| 前端展示「当前 N 个活跃会话」 | 在 harness 卡片与工作间详情页 |
| 「关闭此会话」按钮 | 人工回收入口 |
| 审计事件 `session.open` / `session.close` | 关闭链路可追溯 |

**这是「保留」策略的必要成本** —— 不做可见性，保留就等于泄漏。

## 十三、安全：输入注入必须进 V-14 闸门

负责人提到"给平台 agent 鼠标键盘能力"。现状**不存在**：

- `server.py:916-946` 的 `keybd_event` **只模拟 ALT 键**配合窗口置顶（用于 `activate` 端点），非通用输入
- CDP mirror **只读**（提取页面状态），默认关（`AC_CDP_MIRROR_ENABLED=1`）
- 全库无 `Input.dispatchMouseEvent` / `dispatchKeyEvent` / `pyautogui`

**若将来新增输入注入**，必须同时：

1. `data/policy.json` 的 `default_by_op` 加 `"harness.gui_input": "ask"`
2. **无法用黑名单**：`builtin.danger` 匹配的是命令串，GUI 操作没有可审计文本 → **ASK 是唯一防线**
3. 审计事件 `policy.decision` 记录每次输入注入的目标与时机

> 理由：`shell.exec` 至少有命令行可查，GUI 操作出事**无从回溯**——这是比 shell 更需要人工闸的一类能力。

## 十六、拍板结论与非目标（2026-10-03 全部落定）

### 16.1 四项拍板结果

| # | 议题 | 结论 | 落点 |
|---|---|---|---|
| 1 | `_trash_bridge_dir(ws.workspace_dir)` 定性 | **已查清：命名误导**（既非伏笔也非 bug）。行为正确、不用改；函数名建议改名**仅改名不改行为** | §九 |
| 2 | B 档（MCP 工具补偿） | **静默能力发现，不立跨侧契约**（详见下） | §六 |
| 3 | `harness_ids[0]` → 遍历（18 处） | **本片不改**（详见下） | §十六.3 |
| 4 | 会话关闭默认策略 | ✅ **负责人拍板：保留待复用** | §12.2 |

#### #2 我的决定：B 档做「静默能力发现」，不立契约

**理由**：
- 平台侧成本**极低** —— `mcp_client.mcp_list_tools()` / `mcp_call_tool()` 已实现，而 `tools/list` 本来就要调（用于 L2 的能力采集）
- 但**跨侧契约成本高** —— MCP 规范没有 `new_session` 工具，强行约定会造一个**没人实现的标准**

**做法**：
- 注册期：`tools/list` 结果里若含 `new_session` / `create_session` 类工具 → **记进 L2 模板**（`session_tool` 字段）
- 运行期：该字段存在 → 走工具层建会话（B 档）；不存在 → 落 C 档（用户自建）
- **不写进对外文档、不作为接入要求** —— 只是"平台认得就用"

> 效果：零承诺、零成本，将来若某个 harness 恰好暴露了该工具，自动化路径**自动生效**。

#### #3 我的决定：本片不改 `harness_ids[0]`

**理由**：
- 18 处 `[0]` 的现状语义是**「备选取一」**（该成员可由哪个 harness 承担），`[0]` 是"选第一个"——**在"选一"语义下它是对的**
- 改成遍历等于把语义改成"**一个成员由 N 个 harness 并行承担**"，随之而来的问题无人回答：
  - 谁该回报任务结果？
  - 信誉/经验记在哪个 harness 头上？
  - 一个成员出现 N 份输出，谁是最终产出？
- 负责人 reason #3 说的是**会话**并行，**不等于**成员由多 harness 并行

**做法**：**本片保持 `[0]`**，在代码注释处标注「当前语义为备选取一，多 harness 并行需先定义成员与产出归属」。
若将来要做，**单独立项**并先定义归属语义。

### 16.2 非目标（本稿不做）

- **不做**输入注入能力（仅记录其必须进 V-14 闸门，见 §十三）
- **不做强制关会话**（平台只能发起；且默认**保留复用**，见 §12.2）
- **不做多 Worker / 分布式**（`session_registry` 仍本地）
- **不改 `_trash_bridge_dir` 语义**（§九已定性为命名误导，行为正确）
- **不改 `harness_ids` 语义**（§16.1 #3）
- **不立 MCP `new_session` 跨侧契约**（§16.1 #2 只做静默发现）
