# V17 · 会话关闭兜底设计（`close_requested` 宽限期惰性收敛）

> 状态：**已实施**（2026-10-05，按负责人「继续」推进；§7 三项仍可回退/调整）
> 触发事由：2026-10-05 实测 `/api/sessions` → `count=18 active=1 close_requested=17`
> 关联：V-15 §12.2（会话可见性与关闭链路）、拍板 #4（**保留待复用**）
> 落地提交：`agent_community/platform/session_registry.py` + 3 个事件点 + 配置键
> 实测结果：真实数据 17 条 `close_requested` 一次性收敛为 `closed`（记录保留，`total` 仍 18）；
> 二次调用幂等；审计 `actor=system` 留痕（等待 ~47833s）。
> 测试：`agent_community/tests/test_session_close_grace.py`（28 条）+ 变异验证 **12/12 KILLED**。

## 1. 问题（有实测证据，不是推测）

V-15 步骤 8 的关闭链路设计是**两段式**：

```
工作间删除 / stale 回收 ──► close_requested ──(等 harness 自述)──► closed
harness 注销            ──► closed（直接移除记录）
```

第二段依赖 harness 主动自述确认。**没有任何兜底**：只要对面不来消息，
记录就永远停在 `close_requested`。

实测（2026-10-05，服务 18920）：

| 指标 | 值 |
|---|---|
| 会话总数 | 18 |
| `active` | **1** |
| `close_requested` | **17** |
| `idle` | 0 |

17/18 卡在等待态。**这不是缺陷**——`close_requested` 正是设计要求的状态；
**缺的是它的出口**。后果：

1. **可见性被稀释**：界面上"待确认关闭"长期占满，真正活跃的 1 个被淹没；
2. **语义漂移风险**：`close_requested` 本意是"短暂等待中"，长期不变就退化成
   "已废弃但没人敢动"，日后没人能判断哪些是真在等、哪些是该清的；
3. 平台**只增不减**地把记录留在 `sessions.json`（拍板 #4 的既有成本）。

## 3. 设计

### 3.1 宽限期常量

新增 `platform/session_registry.py`：

```python
CLOSE_GRACE_SECONDS = 600.0      # 默认 10 分钟
CLOSE_REASON_GRACE = "grace_expired"   # 平台兜底关闭
CLOSE_REASON_SELF  = "self_reported"   # harness 自述关闭
```

**取 600s 的依据**（锚定平台既有常量，不是拍脑袋）：

| 既有常量 | 值 | 含义 |
|---|---|---|
| `waker_protocol.WAKER_TIMEOUT` | 30s | 单次唤醒投递 |
| `harness_adapter.heartbeat_timeout` | 60s | 心跳超时 **→ 判 harness 离线** |
| `ai_external.DEFAULT_TIMEOUT_S` | 120s | 单次 AI 调用上限 |

判据：**平台已经认定"60s 无心跳 = 离线"**。那么一个连心跳都没有的 harness，
再过 **10× 心跳窗（600s）** 仍未自述关闭，就不该继续占着"等待中"的名分。
反过来，600s 也足够覆盖一次收尾动作（远大于任何单次调用上限）。

> 可调：新增配置键 `session_close_grace_seconds`（`config.DEFAULT_CONFIG`），
> 缺省用上面的常量。**阈值最终由负责人定** —— 这里给的是有理据的默认值。

### 3.2 惰性收敛函数（唯一入口，绝不自己跑）

```python
def sweep_expired_close_requests(self, now: float | None = None) -> list[dict]:
    """把超过宽限期的 close_requested 强制置 closed。返回本次收敛的记录。

    纯函数式副作用：只改状态 + 落盘 + 返回；不启线程、不注册定时器、不发网络。
    """
```

语义：

- 仅处理 `status == close_requested` 的记录；`closed` / `active` / `idle` / `stale` **一律不碰**
  （**以 `status` 判据为准，不看 `close_requested_at`** —— 残留时间戳的 `idle` 也不会被误收）；
- 返回**本次真正被关闭**的记录；只做"补记起算点"的那次**不算关闭、不进返回值**；
- `now - close_requested_at >= grace`（**宽限期走满即算到期**）→ `status = closed`、
  `closed_at = now`、`close_reason = "grace_expired"`（区分"harness 自述关闭"与"平台兜底关闭"）；
- **记录保留**（不删除）：晚到的自述仍可更新它，也留住审计轨迹；
- **老记录无 `close_requested_at`**：首次见到时**补记当前时间**（宽限期从现在起算），
  不立即关闭 —— 避免上线瞬间把历史数据成批误清。

### 3.4 审计

收敛时写一条 `session.close`：

```
actor   = "system"
target  = <harness_id>
detail  = "宽限期到期（harness 未自述），强制置 closed；session_id=... 等待 <n>s"
```

与既有"harness 自述关闭"的审计**同事件名、不同 detail**，便于 `GET /api/audit?event=session.close` 一条查询看清两类关闭的比例。

## 4. 边界与不做的事

| 场景 | 处理 |
|---|---|
| `idle`（工作间结束，保留待复用） | **不动**（拍板 #4） |
| `active` | 不动 |
| `closed` | 幂等跳过，不重复记审计 |
| 宽限期内 | 不动，继续显示"待确认" |
| 晚到的 harness 自述 | 记录仍在 → 正常更新（可能覆盖 `closed`，符合"以对面为准"） |
| 落盘失败 / 注册表异常 | 打印并继续，**绝不阻断** 调用方（同 `audit.py` 纪律） |
| 记录没有 `close_requested_at` | 补记当前时间，宽限期重新起算 |

### 5.2 ⚠️ 措辞澄清：#8"审计可区分"的真实机制

- **记录级**：`close_reason` 区分（兜底 `grace_expired` / 自述 `self_reported`，`session_registry.py:68-69,244,395`）——**这是主要判据**。
- **审计级**：兜底关闭写 `detail` 前缀「**宽限期到期（harness 未自述）**」（`session_registry.py:471`）；
  「自述关闭」**并没有一条同名审计**（`set_status()` 不写审计），审计里的另一类是调用点写的
  「harness 注销（宿主消失）」（`harness_register.py:498`）与「工作间删除 / stale 回收」（`workshops_lifecycle.py:184,263`）。
- 结论：**"同事件名不同 detail"成立**，但"两类关闭的比例"只能靠**文案前缀**统计，`detail` 里**没有 `close_reason` 字段**。
