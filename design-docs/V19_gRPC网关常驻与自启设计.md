## 2. 现状勘察（真实代码坐标）

### 2.1 看门狗（`agent_community/tools/watchdog.py`）

| 能力 | 实现 | 对候选 A 的含义 |
|---|---|---|
| 目标数 | **单端口单目标**：`--port`、`--spawn-cmd`、`--interval` | 一个进程只看一个端口 |
| 健康判据 | `probe()` = **TCP 可达 AND `GET /api/status` 返回 `status=="running"`**（`watchdog.py:62-67`） | ⚠️ **网关没有 `/api/status`** —— 直接复用会让健康**恒为 false** → 守护**每轮都重拉** → 端口抢占/反复重启 |
| GUI 壳只守护 | `_gui_shell_exists(port)` 的正则里**硬编码 `18920`**：`-match '18920\|{port}'`（`watchdog.py:147`） | ⚠️ **缺陷**：给 9105 用时，只要平台 GUI 在跑（其命令行含 18920）→ 9105 的守护会误判"只守护模式" → **网关挂了也不拉** |
| 启动方式 | `--daemon --port P --interval N --spawn-cmd "..."`；`--spawn-cmd` 含空格必须整体加引号 | 已有 `_split_spawn_cmd` 支持引号路径 |
| 日志 | 两个守护可同写 `watchdog.log`（append） | ✅ 今天已实测过两个守护共存写同一日志，无冲突 |
| 单次健康/取证 | `--check` / `-Action evidence`（抽恢复证据链） | 取证能力可直接复用 |

### 2.2 管理脚本（`watchdog_autostart.ps1`，五动作）

| 动作/函数 | 现状 | 对候选 A 的影响 |
|---|---|---|
| `Get-WatchdogProcs` | 匹配 `watchdog.py` + `--daemon`，**不带端口过滤** | `stop`/`uninstall` 天然覆盖两个守护 ✅ |
| `Start-Watchdog` | **幂等闸**：`已有任意守护 → "不重复启动" 返回`（`:83-87`） | ⚠️ 第二个实例会被这个闸**直接跳过** |
| `Get-Health` | 固定查 `$Port/api/status` | ⚠️ 对 9105 恒失败（无该端点） |
| `Show-Status` | 单目标：一行守护 + 一行健康 + 一行 token | 需扩成按目标分行 |
| `Install-Autostart` | 写**一个** `.cmd`（纯 ASCII + `-EncodedCommand`），命令含 `--port 18920` | 需要决定：第二个 `.cmd` 还是一个 `.cmd` 拉两个 |

### 2.3 关键事实：**本机回环访问不需要 token**（改变了 token 议题）

- 代码：`server.py:244-252 _auth_check` **先放行 localhost**：`if _is_localhost(request): return`，之后才查 token。
- 实测（今天，服务 18920）：`GET /api/protocols` 与 `/api/status` **不带 `Authorization` 均 200**，带 Bearer 也 200。

**推论**：只要网关的 `--api` 指向 **本机**（默认 `127.0.0.1:18920`），**完全不需要 token** ——
不需要"读取、传递、存放"任何东西。26 号要求的"token 从启动脚本读取、不另存副本"仍然成立，
但它**只在未来把 `--api` 指向非本机时**才需要兑现（见 §6 与 §10 决策点 ③）。

## 3. 目标与非目标

**目标**

1. 网关开机自启、进程挂了自动拉起，**与平台守护同等运维待遇**（装/停/查一条命令）；
2. **失败隔离**：网关守护出问题不得影响平台守护，反之亦然；
3. **不改平台服务主线**（`server.py` / `identity.py` / REST 一律不动）；
4. token 若需要，**运行时从启动脚本读取、不落盘副本**。

**非目标**

- ❌ 不做 TLS / 不做公网暴露（沿用 V18 风险登记）
- ❌ 不给网关加持久化状态、不改 proto
- ❌ 不做 gRPC 流式健康（`grpc.health.v1`）—— 列为后续增强（§8）
- ❌ 不动平台 GUI 手动模式的使用习惯

## 4. 决策点 ①（26 号点名）：单守护多目标 vs 第二守护

| 维度 | **A. 单守护多目标**（一个进程看 18920 + 9105） | **B. 第二守护实例**（两个进程各看各的） |
|---|---|---|
| **失败隔离** | ❌ 差：两个目标共用一个进程，`daemon_loop` 里任何未捕获异常 → **两个守护同时消失**（平台守护也没了，风险面反而扩大到最不该出事的组件） | ✅ 好：进程独立 PID，网关守护崩了平台守护照跑；反之亦然 |
| **资源占用** | ✅ 省一个 Python 进程（约 20-30 MB 常驻） | ❌ 多一个进程（约 20-30 MB）。**判断：常驻守护的代价可接受**，且换来隔离 |
| **启动时序** | 单目标列表内有先后，但网关健康是 TCP（不依赖平台已起）→ 实际无序依赖 | 两个 `.cmd`（或一个 `.cmd` 两条命令）各自独立启动，同样无序依赖。**平手** |
| **与 watchdog 冲突面** | ⚠️ **要重写 `daemon_loop`**：改成遍历目标（每目标独立 spawn-cmd/interval/健康模式），核心循环被改写 → **回归风险落在最关键的平台守护上**；且原"平台守护"这条路已被 632 条回归与 45 项校验背书 | ✅ **只加旁路能力**：现有 18920 路径的参数、循环、健康判据**一字不动**（新增开关默认关闭 = 行为零变化），第二个实例走新参数 |
| 实施面 | 1 处大改（`watchdog.py` 核心循环）+ 管理脚本目标语法 | 2 处小改（`watchdog.py` 加 `--health tcp` 与 GUI 正则修正，均默认不改旧行为）+ 管理脚本按目标扩展 |
| 日志 | 单文件多目标（现有格式已带 port ✅） | 同一 `watchdog.log` 双进程 append（今天已实测共存无冲突）✅ |

### 4.1 建议：**选 B（第二守护实例）**

**理由（按权重）**：
1. **失败隔离**是本项的核心价值 —— 网关是"锦上添花"的可选组件，它的守护绝不能和平台守护绑在一条命上；
2. **回归风险最小**：平台守护的现有行为零改动（新增开关默认关），不需要重写被充分验证过的 `daemon_loop`；
3. 资源代价（一个 Python 进程）对"常驻守护"场景微不足道；
4. 实施面更小、可分阶段、可随时只回退网关这一侧。

**选 B 必须做的四处适配**（见 §5），全部**不触碰** 18920 现有路径的默认行为。

## 5. 推荐方案（B）的改动清单

### 5.1 `watchdog.py`（2 处，均默认不改旧行为）

| 改动 | 必要性 | 形态 |
|---|---|---|
| **`--health tcp`**（新增开关） | **必须**：网关无 `/api/status`，不加则健康恒 false → 每轮重拉 | `probe(port)` 在该模式下只判 TCP；默认关闭 → 18920 路径行为不变 |
| **GUI 壳正则去掉硬编码 `18920`** | **必须**：`watchdog.py:147` 的 `'18920\|{port}'` 会让 9105 守护因平台 GUI 在跑而误入"只守护" → **网关挂了不拉** | 改为按**本守护自己的 port** 匹配（`{port}`）；对 18920 自身行为**等价**（原本就含 18920） |

> 这两处**无论决策点 ① 选谁都需要** —— 是网关能否被"守护"的前置条件。

### 5.2 `watchdog_autostart.ps1`（按目标扩展，默认仍是"只管 18920"）

| 函数 | 改动 |
|---|---|
| 参数 | 加 `-Target platform|grpc|all`（默认 `platform`，**保持现有行为不变**）；网关端口固定 9105（可 `-GrpcPort` 覆盖） |
| `Start-Watchdog` | 幂等闸改为**按目标端口**判断（现闸是"任意守护已存在即跳过"，会挡住第二实例） |
| `Get-Health` | 按目标选健康方式：platform = HTTP `/api/status`；grpc = **TCP**（与 5.1 一致） |
| `Show-Status` | 两行分别显示 platform/grpc 的守护 PID 与健康 |
| `Stop-Watchdog` | 现逻辑"杀全部守护"保留给 `all`；加按目标过滤（`platform`/`grpc` 只停自己那半） |
| `Install-Autostart` | **建议写两个 `.cmd`**：`ac_v4_watchdog.cmd`（既有）+ `ac_v4_watchdog_grpc.cmd`（新增）。理由：与"两个独立守护"的隔离模型一致，删任一即停用其一，不把两个命运绑在一条批处理里 |
| spawn 命令 | platform：沿用 `python -m agent_community.platform.server --port 18920`（token 从 `start_18920_v26.ps1` **运行时读取**，不变）；grpc：`python -m agent_community.grpc_gateway --port 9105 --api http://127.0.0.1:18920`（**本机访问无需 token**，见 §2.3） |

## 6. token 议题（26 号要求的"从启动脚本读取、不另存副本"）

| 场景 | 处理 |
|---|---|
| **本机平台（默认，当前唯一用法）** | **不需要 token**（§2.3 代码 + 实测双证据）。不读、不传、不存 → 天然满足"不另存副本" |
| **未来 `--api` 指向非本机** | 届时**运行时**从 `start_18920_v26.ps1` 读取并以**环境变量**传给网关进程（进程内存中，**不写进 `.cmd`、不写进配置**）；与看门狗取 token 的现有做法同源 |
| ❌ 明令禁止 | 把 token 写进自启 `.cmd`、写进 `.bat`、写进 `config.json` 的明文区 |

> 注意：非本机平台同时受 V18 §TLS 风险约束 —— 非本机暴露公网前必须先补 TLS，两者一并处理。

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| TCP 健康只判"在监听"，进程假死（监听但不服务）不会被发现 | 网关**无状态、重启廉价**；后续增强可加 `grpc.health.v1`（需 `grpcio-health-checking` 依赖，本期不做） |
| 两个守护写同一日志 | append 模式，今天已实测多实例共存无冲突 |
| GUI 正则修正影响 18920 现有行为 | 修正后对 18920 **语义等价**（原本即含 18920），并有回归兜底 |
| 回退 | 网关侧完全可逆：删第二个 `.cmd` + `taskkill` 第二个守护 → 回到"仅平台守护"现状；`watchdog.py` 改动用 `.bak` 还原 |
