## 0. 开发准则（老板的批评 → 转成本项目的硬准则）

> 老板原话：**「没有把项目当可复制沿用的产品，没有从市场角度开发，没有以用户角度落地，全是在给自己私人定制。」**

转成可执行的六条准则，**后续所有设计与取舍都按它判**：

| # | 准则 | 反面（要警惕的"私人定制"） |
|---|---|---|
| 1 | **可复制沿用**：别人拿到仓库能装、能跑、能改 | 只有本机某条路径下能跑；写死绝对路径 / 写死某台机器的环境 |
| 2 | **面向市场**：能力是"产品能力"，不是"给某人打的一次性补丁" | 为一个特定协作者定制通道（如硬编码某个外部信箱目录） |
| 3 | **用户视角落地**：每一步都对应界面上一个用户动作 | 功能只在 API/日志里存在，界面里点不到 |
| 4 | **装好就能用**：默认配置即可完成主流程，不依赖口头交代 | 需要开发者手工改代码/手工调端点才能走通 |
| 5 | **失败要说话**：做不到就明确报错，不留"看起来成功"的死状态 | 静默建出一个空壳，让用户以为在跑 |
| 6 | **不依赖特定外部方**：外部协作对象换成谁都成立 | 通道、路径、身份都绑死某一个对象 |

## 1. 用户主流程（老板口述，逐步转写）

```
① 用户在大厅广播任务
        ↓
② 系统自动新建工作间
        ↓
③ 平台内部 AI 与用户进行【一级讨论】——初步了解任务方向
        ↓
④ 了解大概后，用户点击选定成员：
     · 平台 AI 先按【依赖注册列表中 harness 写的能力】自动初选
     · 用户可自定义增删
        ↓
⑤ 确定后开启【二级讨论区】：
     · 自动激活外端 agent 的新对话
     · 按【具体桥模板 + 真实路径】架桥
     · 与【组长（外端 agent）】深入讨论任务
        ↓
⑥ 讨论完成 → 更新【共享资料库】：
     放入分工安排、项目框架等详细信息
        ↓
⑦ 开启【三级讨论】：
     · 同时激活其他员工的新对话与桥
     · 架桥过程中【告知他们该工作间的共享资料库路径】
     · 让他们去资料库找「项目框架」与「自己的分工资料」
        ↓
⑧ 开启分工合作：
     · 每个员工有自己的【文件夹隔间】——避免多人改同一个文件冲突
     · 阶段性任务完成后，由【一个 agent】整合成果
```

### 1.1 接通状态（2026-10-07 实测）

| 步 | 环节 | 状态 |
|---|---|---|
| ① | 大厅广播任务 | ✅ `POST /api/command`（返回新增 `workshop_id`） |
| ② | **系统自动新建工作间** | ✅ **本日接通**：`_auto_create_workshop_for_task()`，幂等、失败不打断广播；`status=discussing` |
| ③ | 平台 AI 与用户一级讨论 | 🟡 原有 `_orchestrated_flow` 仍在；房间已是讨论容器 |
| ④ | 用户点选成员（AI 初选） | 🟡 后端有 `POST /api/workshop/{id}/select-members`（AI 初选）与 `/members`（手工）；**前端未接** |
| ⑤ | 二级讨论：激活组长 + 架桥 | ✅ 架桥已成（`76964df`）；组长路径实测 |
| ⑥ | 共享资料库 | ✅ **本日接通**（形态由老板 2026-10-07 定为「**自动建立的文件夹**，也可为 git 之类的库」，见 §10） |
| ⑦ | 三级讨论：激活其他员工 | ✅ **本日接通**：进 `review` 时补激活 `pending`/`blocked` 成员（各自建隔间与桥）；**`activating` 的不打断**。自动流转那条路（`_maybe_auto_review`）要求全员已 `completed`，无需补激活 |
| ⑧ | 成员级隔间 | ✅ 见 §9（一成员一隔间一桥，架桥那一步创建） |

**②为什么此前是缺的**：`Workshop.status` 早就写着整条流程
（`draft → discussing → selecting → division → running → review`），**设计是有的**；
但实测全库**只有注释提到"自动建间"、没有实现**——而 A2A 入站那条路建出的还是
**无成员的空房间**、停在 `draft`，人来了没房间可进。

反查口：`GET /api/tasks/{task_id}/workshop`（无则 404，前端据此区分"还没建间"与"去选人"）。

## 2. 员工掉线的处理流程（老板口述）


```
员工掉线
  ↓
通知【组长】
  ↓
组长去检查 → 能调起就用【鼠标控制调起】（窗口激活）
  ↓
多次仍调不起 / 无法调起
  ↓
通知【用户】
```

> ⚠️ 注意：这**否定了**我此前给的两个选项（"只标记" / "自动改派"）——
> 老板要的是**先由组长就地抢救，抢救失败才上报人**。这比"自动改派"更省事也更安全（不会造出两份工作）。

### 4.1 ⚠️ 更正与病灶：⑤「按桥模板架桥」不是"有"，是**零件齐但无人驱动**

> **本节是对本稿首版结论的更正。** 首版写 ⑤ 是「✅ 有（最完整的一块）」，**这是错的**。
> 错因：我用"函数名/文件名存在"当成了"功能可用"——**关键词命中 ≠ 能跑通**。
> 老板当场纠正："二级讨论 + 自动激活 + 按桥模板架桥恰恰是半成品，自动架桥没有测试过，
> 双模板也没有落地。"

**核实后的准确状态**（三层桥模型，规范见 `design-docs/V15_工作间会话联动与三层桥设计.md` §五）：

| 层 | 实体 | 状态 |
|---|---|---|
| **初级模板（L1 通用模板）** | `bridge_templates/{cli_acp,file_poll,pending_poll}/` 各含 `template.json` ＋ `*.tmpl`。`template.json` 用 `required_fields` 声明该类型 harness 要提供什么 | ✅ **文件在**，注册期被读来采集参数 |
| **具体桥模板（L2）** | `platform/bridge_template.py`，持久化于 `info.metadata["bridge_template"]`；注册期由 `harness_register.py` 生成 | ✅ **代码在、能生成能持久化**，单元测试通过 |
| **接入产物（L3）** | `platform/connect_artifact.py`，按唤醒方式派生 script / contract / prompt 并落盘工作区 | ✅ **能渲染能落盘**，单元测试通过 |

**但整条链没有任何驱动方**（实测）：

- **前端 0 引用**：`connect-artifact` 在 `frontend/` 下**一处都没有** ⇒ 用户在界面上点不到。
- **后端激活路径不调它**：除 router 文件外，平台代码里**没有任何地方**调用 `connect_artifact` 的 `plan()`/`render()`。
  `架桥` 一词在激活路径（`_activate_single` 一带）里**只出现在给 harness 的提示词文本中**
  （"请据此掌握目标信息并配合用户完成沟通与架桥"）——**平台只是"让 harness 自己去架"，自己并不产出桥**。
- ⇒ **只有人手工调一次 `POST /api/workshop/{ws_id}/connect-artifact` 才会落桥产物**；老板要的
  "建间时**自动**按具体桥模板与真实路径架桥"**实际不会发生**。
- **无端到端测试**：`test_bridge_template.py`（tier 映射 / 持久化 / 完整性 / token 流）与
  `test_connect_artifact.py`（产物类型 / 落盘 / 路径护栏）都只测**模块**；**没有任何测试**
  走通"真 harness 注册 → 建工作间 → 自动产出桥 → harness 真连上"。

### 4.2 病灶：这个项目的通病是「**零件齐、缺驱动、缺端到端验证**」

把 ②⑤ 与「失联孤儿回收」（V22）放在一起看，它们是**同一个病**：

| 现象 | 零件 | 缺的东西 |
|---|---|---|
| ② 外部任务进来 | 建工作间端点 | 无人组队 ⇒ 死工作间 |
| ⑤ 架桥 | L1/L2/L3 全在 | **无驱动方 + 无端到端测试** |
| 失联回收 | 心跳 + 卡死回收 + 锁过期钩子 | **两者之间没有连接**，且全靠人工调端点 |

⇒ 这正是老板那句"私人定制、不是产品"的技术表现：**零件是照着一次次具体需求加出来的，
没有一条"用户从进到出"的贯通路径，也没有任何端到端验证**。

**因此本稿的施工原则改为：每做一块，必须同时交付「驱动方」（谁触发）与「端到端验收」**
（不能只交付模块 + 单元测试）。本仓已有的"只差最后一根线"的零件已经太多。

## 9. 成员级隔间与「一会话一桥」（2026-10-07 老板口述，本节即其设计稿）

> **老板原话**：「单个会话拥有一个隔间和一个具体桥」。

**这一条从设计上消掉了一个实测缺陷**：此前所有成员共用 `ws.workspace_dir`，
各自的具体桥产物又都叫 `bridge.py` → **后写的覆盖先写的**（2026-10-07 隔离实例实测：
两条 `bridge.auto` 审计都在，工作区里却只剩一份 `bridge.py`，内文只有后者的 harness_id）。

### 9.1 规则（**权威定义在代码本体**：`platform/compartment.py` 模块头部）

> ⚠️ **本节与 `platform/compartment.py` 模块头部的定义块必须同步**；两者不一致时**以代码为准**，
> 并立刻回来改本节。前端（FE-03）**不得**自行镜像路径公式——见下面"唯一事实源"。

| 项 | 归属 | 生存期 | 说明 |
|---|---|---|---|
| **隔间**（目录） | **岗位（成员）** | **跨会话存活** | 交接单里的「文件夹路径」就是它；换新会话后仍指向同一目录，否则文件全丢 |
| **具体桥**（接入产物） | **会话** | 每次激活/续作新发一份 | 落在该成员自己的隔间内，故**永不与他人相撞** |

**唯一事实源**：隔间路径由**后端**给出，前端**不要自行推导**（公式会随后端改动漂移）。
接口：`GET /api/workshop/{ws_id}/compartments`（返回每个成员隔间的**磁盘实况**：
`dir`／`exists`／`subdirs`／`files`／`bridge_files`）。
> 该接口是应答 MiMo 在 FE-03 §7 提的申请；动机成立——**审计只能证明"何时发过桥、落在哪"，
> 证明不了文件此刻在不在**，而公式镜像迟早漂移（这正是要主动消掉的隐患）。

> 上表「隔间跟岗位、桥跟会话」是 DSH 的**推断**（依据：D7 交接单必须写明文件夹路径，否则新会话接不上班）。
> 老板一句话即可推翻。

### 9.2 路径与**创建时机**

```
<ws.workspace_dir>/<职位>_<成员id>/{input,output,temp}      # 隔间（老板 43 号 / D8 的口径）
<ws.workspace_dir>/<职位>_<成员id>/bridge.py               # 该成员的具体桥（L3 接入产物）
```

**创建时机（老板 2026-10-07 更正两次后的结论）**：

```
新建工作间  →  选定员工  →  架起具体桥  →  ★此刻创建隔间（桥产物正好落进刚建好的隔间）
```

- ❌ **不是**"建工作间就建隔间"：我一度把建隔间塞进 `write_workspace_files()`（放早了，已退回）。
  未选中的员工、还没架桥的房间，本来就不该有空隔间。
- ✅ 唯一创建点：**架桥那一步**（`server._auto_bridge_for_member()`，在激活派发之前）。
- `compartment.ensure_compartment()` 是幂等的，所以续作/重派时会复用同一隔间，不会重复建。

工作间根 `ws.workspace_dir` 仍是**共享区**（`hall.md`／共享资料库在这里）；
**隔间是该成员唯一可写的地方**——激活提示词必须把这两个路径都讲清，不能只给一个。

### 9.3 实现落点

1. `platform/compartment.py`：隔间路径推导 + 建 `input/output/temp`（纯函数，可单测）。
2. `connect_artifact.plan()` 增可选 `target_dir`：调用方按成员推导后传入；
   **仍不接受任何来自请求体的路径**（原不变量「target_dir 只来自平台派生」保持不变）。
3. `server._auto_bridge_for_member()`：产物落**该成员的隔间**，不再落工作间根。
4. 激活提示词（员工路径与组长路径）新增：工作间根（共享物）+ **你的隔间（只在此写文件）**。

## 10. 共享资料库（老板流程 ⑥，2026-10-07 老板定形态）

> **老板原话**：「共享资料库**可以是一个自动建立的文件夹**，也可以是 git 之类的库」。

**本实现取「自动建立的文件夹」**，理由：零依赖、离线可用、与本项目「开放自托管」的定位一致；
且布局**纯文本**，日后 `git init` 即可升格为库，**不需要改结构**（见下 `.gitignore` 占位）。

### 10.1 位置与归属

```
<ws.workspace_dir>/library/          # 工作间**共享区**（全成员可读）
├─ README.md      索引与规矩（谁写、谁能读）
├─ plan.md        **分工安排**——平台按当前名单+委派记录**自动生成**（勿手改）
├─ framework.md   **项目框架**——讨论收敛后写入；**已有内容不覆盖**（尊重人的编辑）
└─ .gitignore     为日后 `git init` 预留（当前不忽略任何内容）
```

- **与 `resources/` + `RESOURCES.md` 的区别**（别合并）：那两者是**上传资源清单**（谁传了什么文件）；
  本目录是**协作共识**（谁干什么、项目怎么搭）。
- **创建时机**：与 `hall.md`/`AGENTS.md` 一样在**建间时**建好（它属共享区，**不是**成员隔间——
  与 §9「隔间在架桥时才建」不冲突，两者是不同东西）。

### 10.2 接口

| 端点 | 作用 |
|---|---|
| `GET /api/workshop/{ws_id}/library` | 目录 + 文件实况 + `plan.md`/`framework.md`/`README.md` 预览；`form` 字段标明当前形态 |
| `POST /api/workshop/{ws_id}/library/update` | 更新：`plan.md` 永远重生成；传 `framework` 才写 `framework.md`（不传则保留人工内容） |

### 10.3 成员怎么拿到它（流程 ⑦ 的落点）

激活提示词（`_compartment_hint`）里**明确点名资料库路径**，并说明
「`plan.md`=分工安排，`framework.md`=项目框架；**读它拿分工**」。
实测（隔离实例）：派给成员的 payload 里确有该路径。
