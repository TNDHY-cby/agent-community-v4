# V25 唤醒与寻址设计（2026-10-08）

> 本轮由老板连续追问驱动：「如何唤醒外端 Agent，不同 harness 可接受协议不同，可能无法实现平台对他的唤醒」
> → 「B 脚本如何进行，需要反向工程吗」 → 「B 远没这么简单，harness 内部还有多个会话栏，顺序不可预测」
> → 「一个员工一个具体桥和隔间，这样就能隔离，不会发生谁收到就是谁的」
> → 「用视觉脚本时也要确定**会话名**，最初的名字是 Agent 自定义的很片面、用户可能会改，所以脚本里的名字定位要**可改**」。
> **状态：待老板拍板**（§6 列出待决项）。

## 0. ★老板定稿的「会话建立与命名」流程（**本节为权威流程**，2026-10-08 老板口述原文登记）

> **老板原话（逐字登记）**：
> 「0. 注册 harness（**harness 模板**（包括**新建对话脚本**和**对话重命名脚本**，包含具体桥模板）
> ＋**具体桥模板**（用于填入具体路径和名，匹配相应工作间）），1. 新建工作间，2. 一级讨论，
> 3. 选定成员，4. **自动按照 harness 模板打开 harness 新对话**，5. 发送具体桥模板架起具体桥，
> 6. 平台与 harness 对接具体桥和隔间，7. **平台给出新命名**（例如"工作间id-项目-职位-成员id"，
> 最好要有项目名给用户看）8. **复制粘贴重命名对话名**，8. **更新视觉脚本**，9. 开启二三级讨论」

### 0.1 这条流程解决了什么（**我先前把方向搞错的地方**）

我此前花了好几轮去解「**怎么在一个未知的多会话列表里找到我们的那个会话**」——
那是**在解一个不必要的问题**。老板的流程里：

```
平台自己「新建会话」（步骤4）→ 所以它知道刚建的是哪一个
平台立刻「重命名」它（步骤7-8）→ 于是它有了平台指定的、确定的、人和机器都能认的名字
平台把该名字写进视觉脚本的匹配数据（步骤9）→ 之后所有视觉操作按这个名字匹配
```

⇒ **会话身份由「平台自己建立」而来，不靠猜、不靠 OCR 认随机名。**
"新建时名字随机""用户会改名"这两个问题在流程上被绕开：**随机名只存在于"建立"与"重命名"之间的瞬间**。

### 0.2 与现有实现的对账（哪些已有、哪些要新做）

| 步 | 要什么 | 现状 |
|---|---|---|
| 0 | 注册 harness 时提交 **harness 模板**：**新建对话脚本** + **对话重命名脚本** + **具体桥模板** | 🟡 **半有**：已有 L2 具体桥模板（`bridge_template`），但**没有"新建对话脚本 / 对话重命名脚本"这两个字段** ⇒ **本设计要新增** |
| 0 | **具体桥模板**：填入具体路径与名，匹配到相应工作间 | ✅ 已有（L2→L3，`connect_artifact` 落成员隔间） |
| 1 | 新建工作间 | ✅ 已有（含 ② 自动建间） |
| 2 | 一级讨论 | ✅ 已有 |
| 3 | 选定成员 | ✅ 已有（AI 初选 + 手工） |
| 4 | **按 harness 模板自动打开 harness 新对话** | ⬜ **要新做**（调用该 harness 的"新建对话脚本"） |
| 5 | 发送具体桥模板、架起具体桥 | ✅ 已有（`_auto_bridge_for_member`，落在成员隔间） |
| 6 | 平台与 harness 对接**具体桥和隔间** | ✅ 已有（今日完成的**成员级邮箱** `c1e96d8` + 隔间 + `compartments` 接口） |
| 7 | **平台给出新命名**：`工作间id-项目-职位-成员id`（**最好带项目名给用户看**） | ⬜ **要新做**（命名生成 + 落库） |
| 8 | **复制粘贴重命名对话名** | ⬜ **要新做**（调用该 harness 的"重命名脚本"） |
| 9 | **更新视觉脚本**（把平台给的名字写进匹配数据） | ⬜ **要新做**（名字是**数据**，脚本不写死） |
| 10 | 开启二三级讨论 | ✅ 已有（②③⑦） |

### 0.3 命名规则（步骤 7）

- 格式：**`<工作间id>-<项目>-<职位>-<成员id>`**
- **必须含"项目"**（可读，给用户看）；建议项目名取工作间 `name`（广播时由任务内容生成，已有）。
- 该名字同时是：**用户看到的会话名** + **视觉脚本的匹配键** + **平台侧可反查该成员的索引**。
- 用户后续改名 ⇒ 属已知变化，走 §4.5 的"改名即重跑步骤 8/9"（**平台重命名一次并把新名写回数据**），
  而不是靠模糊匹配去猜。

### 0.4 与我先前探索的关系（**不必删，但降级为兜底**）

- §4.1.1 的「内容 + 一次性 token」**降级为兜底**：用于"用户把名字改成了平台完全不知道的东西、
  且步骤 8/9 没能跑成"的场合——此时靠内容里的 token 仍能定位。
- §4.3 的匹配链**仅在步骤 4/8 无法执行**（该 harness 没有可用脚本）时才需要。
- §5 的 CV/RPA 分档**仅在步骤 4/8 都做不到**时才需要（那时才真的要"从一堆随机名里找"）。

> 一句话：**能"自己建、自己命名"的 harness，走 §0 流程，零识别成本；
> 不能的，才逐级降级到 token 兜底 → 视觉匹配 → 人工。**

## 1. 把问题拆成两件（混在一起谈必然绕）

| | 问的是什么 | 难点 |
|---|---|---|
| **唤醒** | 怎么让那个 Agent 动起来 | 不同 harness 接受的协议不同；有的完全没有可推的接口 |
| **寻址** | 这条消息该给**哪一个会话** | 一个 harness 里多个会话栏、**顺序不可预测** |

**关键判断：寻址才是主难点，唤醒是次难点。** 因为"送不进去"我们至少有 5 条路（§2），
而"送进去了但给错了会话"是**正确性事故**——它不报错、只是让另一个会话替别人干活。

## 2. 现状实测（2026-10-08，本仓库）

### 2.1 唤醒路径（平台侧已有 5 条）

| 路径 | 怎么唤 | 寻址粒度 |
|---|---|---|
| `http_api` | 平台 POST 到 harness 自带 HTTP 地址 | harness 级 |
| `cli_acp` | 平台按 `acp_command` 拉起会话（可拿 `session_id`） | **会话级** ✓ |
| `file_poll` | 平台写邮箱 → 桥脚本轮询 → `run_trigger(TRIGGER_CMD)` | 见 §2.2 |
| `pending_poll` | 同上，给"没有 ACP 也拉不起来"的 GUI 桌面 Agent | 见 §2.2 |
| `clipboard` | 平台调起窗口（`ShowWindowAsync`/`SetForegroundWindow`/`keybd_event`） | 无（靠人） |

**`TRIGGER_CMD` 目前是空的**：`bridge_template.build()` 给 `file_poll` 只生成
`HARNESS_ID/INBOX_DIR/PLATFORM_URL`，`connect_artifact.plan()` 对它 `setdefault("", ...)`
⇒ **桥脚本拿到任务只会写进 inbox，没有任何"叫醒"动作**。这条腿现状是断的。

### 2.2 邮箱（寻址的关键，**今日已改完**）

- 旧：`INBOX_DIR = info.wakeup_dir` ⇒ **harness 级** ⇒ **哪个会话先轮询谁就拿走**。
- 新（`c1e96d8`）：`<隔间>/inbox`（成员级）⇒ **谁的桥只取谁的邮箱**。
  实测：两个不配 `wakeup_dir` 的 harness → 每人各得 `bridge.py` + 自己的 inbox，各恰好 1 条任务。
  附带修好旧失败模式：没配 `wakeup_dir` 时"缺少 INBOX_DIR"导致桥渲染失败。

### 2.3 会话身份

- `session_registry`：key = `(harness_id, session_id)`，含 `human:{ws}:{member}:{ts}` 人工合成 id ⇒ **身份有定义**。
- `WorkshopMember.session`：**只有 ACP 路径会填**。
- **没有 claim/绑定端点** ⇒ 一个会话**无法告诉平台"我是谁、我代表哪个成员"**。

## 3. 设计：寻址三层 + 唤醒辅助

```
第一层  协议寻址    平台按 session_id 派发（ACP/MCP 天生支持）        —— 最稳，首选
第二层  自领邮箱    会话内跑成员桥 → 只取该成员的邮箱                —— 不依赖 GUI/OCR（§2.2 已落地）
第三层  人工寻址    平台出"唤醒单"（含标识与要做什么）→ 人粘到对的会话   —— 永远可行
        └ 辅助：界面注入（调起窗口 + 把唤醒单放进剪贴板）——**不承担"选会话"**
```

> **这三层的关系是"降级链"**：上层可用就不用下层。只有当某 harness 既无协议、又不肯自领邮箱时，
> 才落到第三层——**而第三层必须由人点那一下**，平台绝不替用户猜会话。

## 4. ★老板本条要求：**名字不能当身份**（本节是新增的硬约束）

老板原话：「用视觉脚本的时候也需要确定**会话名**，一开始的会话名是 **Agent 自定义**的会很**片面**，
用户可能会改，所以**脚本里面的名字定位要可改**」。

拆成三条设计决定：

### 4.1 身份由**平台发**，不由 agent 自取

- 会话的**稳定标识 = 平台生成的 `session_alias`**（例：`AC-<ws短id>-<member_id>`，机器可核查）。
- **平台绝不把 agent 自取的名字当身份**——它只作"附加线索"，不作匹配依据。

### 4.1.1 ★身份凭据 = **内容 + 平台一次性 token**（老板两次补充后定，推翻最初的"改名"方案）

老板补充两条，**先后否掉了两个方案**：

1. 「打开 harness 后**没打开会话就看不到别名**，只能看到侧边栏里的会话名」⇒ 否掉"别名只写在内容里"。
2. 「**新建会话时会话名有随机性，不一定按照要求命名**」⇒ **连"把别名写进会话名"也不可靠**。

⇒ **会话名三重不可控**：agent 自取（**片面**）／用户改（**不稳定**）／**harness 自动随机命名（不服从）**。
**结论：名字不能当身份凭据。**

**改用的办法——平台发一次性 token，要求会话在内容里回显（挑战-应答）**：

| | 做法 | 为什么这样最强 |
|---|---|---|
| 平台 | 给每个成员生成一串**一次性随机短 token**（在激活提示词里下发） | 随机 ⇒ 不会撞名；一次性 ⇒ 可判定"这就是我等的那次激活" |
| 会话 | 要求它**在首条消息里原样回显该 token** | **内容 agent 可控**；名字它可能根本控不了 |
| 判定 | 平台/脚本 **只认"该会话内容里有没有这个 token"**，**不看会话名** | 抗改名、抗随机名、抗同名 |

**附带好处（重要）**：token 是**一次性**的 ⇒ 找到它等于**证明"这个会话确实收到了我的激活"**
—— 同一张凭据同时回答了两个问题：**给哪个会话**（寻址）＋ **有没有真的叫醒**（准则⑤）。

- 「会话名含别名」**降为加分项**（若该 harness 恰好允许改名，则未打开即可见、可省一次探测），
  **任何逻辑都不得依赖它**。
- 界面仍要提醒用户：该会话带平台标识，**改名前请保留它**（改了也不致命，只是要多探测一次）。

### 4.2 别名是**数据**，不是常量；**用户可改可加**

- 每个成员持有 **`session_aliases: list[str]`**（第一项是平台生成的标识；用户可增删改）。
- 视觉脚本的匹配词**从平台读**（`GET /api/workshop/{id}/compartments` 或新端点带出来），
  **脚本里不写死任何名字**（准则① 可复制沿用：换个仓库/换个用户都不用改脚本）。
- 用户改名 → 只改这一份数据 → 脚本下一次运行即生效，**无需改脚本**。

### 4.3 匹配链（**按"不受会话名影响"的程度**排）

1. **搜索框按 token/别名搜内容** ← 最强：**随机名、改名都不影响**（前提：该 harness 的搜索搜的是内容，须逐 harness 实测）
2. **逐个打开 → 查会话内容里有无该 token → 返回/下一个** ← 无搜索时的探测循环（慢但确定；需"打开无副作用"）
3. 侧边栏/标题含别名 ← **加分项**（该 harness 恰好允许改名时才有）
4. 标题含 agent 自取名 ← **仅线索，必须人工确认**
5. 全部失败 → **半自动**：脚本只把唤醒单放剪贴板，**人点一次会话**，脚本粘贴（§5.f）

命中多个候选**不猜**：按相似度排序后**让人确认**。
（老板材料里的"候选排序 + 半自动兜底"即此意。）

> ⚠️ **本条同时说明了一件更根本的事**：凡是"平台既不能自己建会话、也不能直接投递"的 harness，
> 视觉匹配是**唯一**手段，而它面对的恰恰是**名字不可控**的环境
> ⇒ **视觉匹配绝不能当主路径**；主路径只能是 §3 的第一层（协议寻址）与第二层（成员邮箱自领）。

### 4.4 数据模型（拟）

```python
# WorkshopMember 新增（都带默认值，旧数据兼容）
session_aliases: list[str] = []      # [0] 平台生成；其余用户可加
session_ref: dict = {}               # claim 成功后填 {harness_id, session_id, source, bound_at}
                                     # source ∈ acp / claim / human（与 session_registry 对齐）
```

## 5. 视觉脚本（CV/RPA）的定位与边界

**能实现，不是反向工程**（用有文档的 Windows API / DOM / UIAutomation），但它是**最后一层**，且分档：

| 档 | 手段 | 需要 OCR | 备注 |
|---|---|---|---|
| a | 网页版 harness → Playwright（可无头、后台） | 否 | 最稳 |
| b | 桌面版 → UIAutomation / pywinauto 直接 set 文本 | 否 | 能读到控件就不用视觉 |
| c | 搜索框优先（Ctrl+K/F/P → 输标识 → 点最高分） | 是 | **按 §4.3 匹配标识** |
| d | 滚动 OCR + 模糊匹配（记录已扫哈希、到底判据） | 是 | 会话乱序时的主要手段 |
| e | 固定锚点（输入框常在底部） | 是 | 只解决"激活输入框" |
| f | **半自动**：脚本只放剪贴板，人点一次会话，脚本粘贴 | 否 | **兜底，永远可用** |

**实测（本机 2026-10-08）**：`inject_window.ps1` 的 `WM_PASTE` **两次两次完整送达**；
`SendKeys` **系统性丢首字符**（等 900ms 无效）；`clipboard+Ctrl+V` 依赖焦点状态。
⇒ 注入**用 WM_PASTE 优先**，键注入仅作最后手段。

**硬边界（材料里我认同的部分）**：防截图 / 黑屏 / 无障碍树为空 且 屏幕不可读 ⇒ **无解**，
只能官方 API 或人工；纯 CV（截当前屏 + 全局鼠标键盘）**基本必须前台**；后台最稳是
**虚拟机 / 独立用户会话**（但那要作为**产品要求**来谈，不能悄悄假设）。

**依赖决定（建议）**：OCR/模糊匹配/CV 这一坨（PaddleOCR/EasyOCR/Tesseract + pyautogui/mss）
与准则④「装好就能用」冲突 ⇒ **核心不依赖它们**；CV 适配器做成**可选组件**（对齐老板"插件化内核 /
Skill 形式拉取"的方向），**按具体 harness 逐个落地**，不预先为假想需求写脆弱代码。

## 6. 待老板拍板 / 待确认

1. **一次性 token 格式**：短随机串（如 `AC7F3K9Q`）可否？**它取代"别名当身份"**（§4.1.1）。
2. **是否接受"把 token 回显进会话内容"写进激活提示词**（要求 agent 在首条消息原样回显）？
3. **会话 claim 端点**是否现在就做（第二层的正式化：会话内桥带 token 声明身份）。
4. **CV 适配器**是否按"可选组件"走（不进口核心依赖）？
5. **虚拟机 / 独立用户会话**要不要写成产品要求（影响"本地部署"的部署形态）。
6. **搜索框能力（只能实测）**：本机这些 harness 的搜索**搜标题还是搜内容**？
   —— 决定 §4.3 第 1 条（最强那条）能否用，**必须逐 harness 测**。
7. **内容可控性（只能实测）**：这些 harness 里 agent **能不能控制自己会话的内容**（写入 token）？
   若连内容都不可控 ⇒ 只剩协议层与人工两条路。
