# V26 通用脚本框架设计（2026-10-08）

> 老板要求：「**每个 harness 对应的脚本会不太一样，要提前设计好通用脚本框架**」。
> 本文是框架的**设计稿**（铁律 1：先稿后码）。**状态：待拍板**（§7）。

---

## 1. 为什么需要"框架"而不是"给每个 harness 写脚本"

V25 §0 的流程里，平台要在流程中**主动做三件事**：建会话（步骤4）、重命名（步骤8）、把东西送进会话（步骤5）。
每件事**在不同 harness 上的做法完全不同**（有的有 CLI、有的只能点界面、有的只能人工）。

⇒ 若平台为每个 harness 写一套逻辑，就变成**私人定制**（老板明确批评过的做法）、且**不可复制沿用**（准则①）。

⇒ 正确做法：**平台只依赖"契约"，不依赖"实现"**。任何 harness 提交符合契约的脚本即可接入（准则⑥ 不依赖特定外部方）。

---

## 2. 框架按「**动作**」组织（这是与现有 L1 的关键区别）

| | 现有 L1（保留） | 本次新增的框架 |
|---|---|---|
| 组织维度 | **桥的协议形态**：`cli_acp` / `file_poll` / `pending_poll` | **动作**：建会话 / 重命名 / 送消息 / 桥 |
| 回答的问题 | "这个 harness 用什么方式收活" | "这个 harness 怎么被操作" |
| 目录 | `bridge_templates/{cli_acp,file_poll,pending_poll}/` | `bridge_templates/script_framework/`（**并列新增**，不改前者） |

**四个动作**（动作名即契约名，平台按名字调用）：

| 动作 | 干什么 | 对应老板流程 |
|---|---|---|
| `new_session` | 打开该 harness 的**一个新对话** | 步骤 4 |
| `rename_session` | 把该对话**改名** | 步骤 8 |
| `deliver` | 把一段文本**送进指定会话**（架桥/传话） | 步骤 5 |
| `bridge` | 长驻：轮询成员邮箱 → 回报平台（**已有**） | 步骤 6 |

> `bridge` 已有实现（`bridge.py.tmpl`），本框架**不重写它**，只把它纳入同一契约（补 stdout 规范与退出码）。

## 3. 统一调用契约（**唯一必须遵守的东西**）

### 3.1 调用方式

```
<脚本> --input <输入JSON路径>          # 推荐：任何语言都好实现
<脚本>                        # 或：从 stdin 读同一份 JSON
<脚本> --self-test            # 可选：自检模式（见 §6）
```

环境变量同时提供（脚本可不解析 --input，直接用 env）：

```
AC_ACTION        动作名（new_session / rename_session / deliver）
AC_HARNESS_ID    该 harness id
AC_WORKSHOP_ID   工作间 id
AC_MEMBER_ID     成员 id
AC_ROLE          职位
AC_PROJECT       项目名（给人看的可读名）
AC_WORKSPACE_DIR 该成员的工作区（**有隔间时就是它的隔间**）
AC_PLATFORM_URL  平台地址
AC_DATA_DIR      平台数据目录（只读参考）
```

### 3.2 输出与退出码（**准则⑤ 的落点**）

- **stdout 只允许输出一个 JSON 对象**；日志/调试一律走 **stderr**（否则平台解析不了）。
- 退出码语义固定：

| 退出码 | 含义 | 平台怎么处理 |
|---|---|---|
| `0` | 成功，且脚本**能证明**（`evidence` 非空） | 平台**独立复核** evidence |
| `10` | 成功，但**无法自证** | 平台标「**未核实**」；不得当成已确认 |
| 其它非 0 | 失败 | 平台按降级链处理（V25 §0.4），**不得当成成功** |

- 输出 JSON 必填字段：

```json
{ "ok": true, "action": "new_session", "evidence": {...}, "error": "" }
```

- **超时**：默认 30s（L2 可按 harness 覆盖，如界面类动作需更久）。超时=失败。
- **幂等**（强制）：`new_session` 重跑**不得建出两个会话**（要么复用、要么先检测已存在）；
  `rename_session` / `deliver` 重跑**不得产生副作用**。

### 3.3 各动作的输入/输出（字段最小集）

```jsonc
// new_session  in
{ "action": "new_session", "harness_id": "...", "workshop_id": "...", "member_id": "m1",
  "role": "码农", "project": "某某项目", "name_hint": "<工作间id>-<项目>-<职位>-<成员id>" }
// new_session  out.evidence（至少给一个平台能复核的定位信息）
{ "session": { "id": "", "name": "", "window": { "pid": 1234, "hwnd": 0, "title": "" } } }

// rename_session  in
{ "action": "rename_session", "session": { ...上一步的 session... }, "new_name": "<目标名>" }
// rename_session  out.evidence
{ "applied_name": "<实际生效的名字>", "readback": "<回读到的名字>" }

// deliver  in
{ "action": "deliver", "session": { ... }, "text": "<要送进去的内容>", "submit": true }
// deliver  out.evidence
{ "method": "wmpaste|clipboard|sendkeys|api", "readback": "<能回读就回读>" }
```

**evidence 是"凭什么说成功"**——平台不采信声明（老板的防幻觉纪律）；
平台能复核就复核，不能复核就标「未核实」，**绝不写进"已完成"**。

## 4. 目录与骨架（拟）

```
agent_community/bridge_templates/script_framework/
  SPEC.md                     # 本契约的可读版（给接入者看）
  _common.py                  # 骨架：读输入、写 JSON、stderr 日志、超时、幂等锁、evidence 校验
  new_session.tmpl            # L1 骨架：新建对话
  rename_session.tmpl         # L1 骨架：重命名对话
  deliver.tmpl                # L1 骨架：送消息进会话
  reference/
    cli_based/                # 参考实现①：harness 自带 CLI（如 `xxx --new`）
    ui_based/                 # 参考实现②：只能界面操作 → 调 tools/inject_window.ps1
    manual/                   # 参考实现③：人工（打印提示、等确认，返回 exit 10 未核实）
  conformance.py              # 一致性自检工具（接入者自己跑）
```

**三种参考实现覆盖现实**（而且它们的**契约完全相同**，这正是框架的意义）：

| 形态 | new_session 怎么做 | rename_session 怎么做 |
|---|---|---|
| CLI 类 | 跑 `harness --new-session`，从 stdout 取 session id | 跑 `harness --rename <id> <name>` |
| 界面类 | 快捷键/菜单新建 → 读窗口标题 | `inject_window.ps1` 双击标题+输入+回车（**WM_PASTE 已实测可靠**） |
| 人工类 | 提示用户"请新建一个对话"→ 用户确认 | 平台给"复制粘贴"按钮 → 用户操作后确认（`exit 10` 未核实） |

## 5. 平台侧接线

1. **注册 harness 新增字段** `scripts`（可选，缺哪个就**如实标"该 harness 不支持第 X 步"**）：
   ```jsonc
   { "scripts": {
       "new_session":    { "cmd": "...", "timeout": 45 },
       "rename_session": { "cmd": "...", "timeout": 45 },
       "deliver":        { "cmd": "...", "timeout": 30 }
   } }
   ```
2. **流程步骤**：步骤4 调 `new_session` → 落 `member.session_ref`；
   步骤7 生成名字 `<工作间id>-<项目>-<职位>-<成员id>`；
   步骤8 调 `rename_session` 并**校验 `applied_name`**；
   步骤9 把最终名字写进 `member.session_aliases`（**视觉脚本从这里读，不写死**）。
3. **缺脚本 ⇒ 降级链**（V25 §0.4）：token 兜底 → 视觉匹配 → 人工；并在**界面上说明缺哪一步**。

## 6. 一致性自检（给接入者一把尺子）

`conformance.py` 对任何提交的脚本跑四类检查，**不需要平台在跑**：

1. **契约**：`--self-test` 能否返回合法 JSON；stdout 有无杂质；退出码是否符合 §3.2；
2. **幂等**：连跑两次 `new_session`，不得出现两个会话（由脚本自报 evidence 判定）；
3. **evidence 完整性**：各动作的 evidence 是否含 §3.3 的最小字段；
4. **超时**：在标称超时内返回。

⇒ 接入者**自己就能知道**脚本合不合格，不用来回问平台（也就避免了"看起来接上了其实没接"）。

## 7. ★不得打扰用户（老板 2026-10-08 产品级要求，**一等属性**）

老板原话：「**而且这一切最好在后台或者新桌面进行，不要弹出来影响用户**」。

⇒ 框架把「**是否抢占前台**」做成**动作与参考实现的一等属性**，而不是事后补救：

```jsonc
// 注册 harness 时，每个动作声明它的打扰等级
{ "scripts": { "new_session": { "cmd": "...", "foreground": "never" },
               "rename_session": { "cmd": "...", "foreground": "never" },
               "deliver": { "cmd": "...", "foreground": "optional" } } }
```

- 取值：`never`（绝不抢前台）/ `optional`（视实现而定）/ `required`（**必然打扰**）。
- **平台优先选最不打扰的路径**；若某动作只能是 `required`，
  **必须在界面上提前告诉用户**"这一步会占用你的桌面"（准则③ 用户视角 + 准则⑤ 失败要说话）。

### 7.1 打扰度阶梯（**低 → 高，按此顺序选**）

| 级 | 做法 | 打扰 | 备注 |
|---|---|---|---|
| ① | **完全不碰界面**：会话自己轮询**成员邮箱** | **零** | ✅ 已落地（`c1e96d8`）——**首选** |
| ② | harness 自带**无头 / CLI / API**（ACP、`--new`、headless） | **零** | 建会话/重命名/送消息都在进程层完成 |
| ③ | **UIAutomation 直接操作控件**（`set_edit_text` 等） | 近零 | 不依赖前台焦点；但 Electron/Qt 常读不到控件树 |
| ④ | **独立 Windows 用户会话 / 独立桌面**里跑界面自动化 | 低 | 真隔离；代价是部署成本（见 §7.2） |
| ⑤ | **当前桌面 + 全局键鼠**（CV/RPA/pyautogui） | **必然打扰** | 抢焦点、抢鼠标、截屏可能截到用户隐私 ⇒ **仅最后手段，且需用户同意** |

### 7.2 「新桌面」到底指什么（**已实测修正**）

> 老板 2026-10-08 指出 Windows 任务视图里有「新建桌面」功能，并给出截图。
> **我最初一句"虚拟桌面不可用"是说粗了**——实测后修正如下。

**实测（2026-10-08，本机）**：公开 COM 接口 **`IVirtualDesktopManager`**（CLSID `aa509086-…`）**可用**，
三项调用全部成功：

| 调用 | 实测结果 | 用途 |
|---|---|---|
| `IsWindowOnCurrentVirtualDesktop(hwnd)` | 返回 `1` | ★**操作前先问"这个窗口在不在用户眼前"** |
| `GetWindowDesktopId(hwnd)` | 返回 GUID `04f1d36e-…` | 拿到它所在桌面 |
| `MoveWindowToDesktop(hwnd, guid)` | 返回 `0`（S_OK） | 把窗口移到指定桌面 |

（注意：PowerShell 不能直接把 COM 对象转成该接口，**转换必须写在 C# 里**——踩过一次。）

### 7.3 结论：虚拟桌面**能用，但不是隔离边界**

| 操作类型 | 在"别的虚拟桌面"上能否后台进行 | 会不会打扰用户 |
|---|---|---|
| **消息式**：UIAutomation 设值 / `WM_PASTE` / `PostMessage` / `SetWindowText` | ✅ 可以（不需要窗口可见/激活） | **不会切视图** ✓ |
| **键鼠式**：`SendInput` / `SendKeys` / 纯 CV 截屏 | ❌ 不行（输入只投给**活动桌面**） | 若强行激活 ⇒ **会把用户切到那个桌面** ✗ |

⇒ **可用组合 =「独立虚拟桌面 + 消息式操作」**，这是**新增的一级**（插在"独立用户会话"之前）：

| 级 | 做法 | 打扰 | 条件 |
|---|---|---|---|
| ① 完全不碰界面（成员邮箱） | | 零 | ✅ 已落地 |
| ② harness 自带无头/CLI/API | | 零 | |
| ③ UIAutomation 直操控件 | | 近零 | 控件树可读 |
| **③.5 虚拟桌面 + 消息式操作** | | **近零**（用户视图不切走） | 需**已存在第二个桌面**；操作须是消息式 |
| ④ 独立 Windows 用户会话 / 虚拟机 | | 低 | 部署成本；真隔离 |
| ⑤ 当前桌面 + 全局键鼠 | | **必然打扰** | 最后手段 |

**两个必须说清的限制**：

1. **公开接口不能"新建"桌面、也不能枚举桌面** —— 建第二个桌面这一步要么**用户手工点一下**（任务视图 → 新建桌面，一次性），
   要么走**未公开**的 `IVirtualDesktopManagerInternal`（不建议：随 Windows 版本变动、易碎）。
2. **虚拟桌面不是安全边界** —— 同一登录会话，用户随时能看到/切过去；它只解决"**别弹在他眼前**"，
   不解决"**别抢他的焦点**"和"**别让他看到**"。要那两条 ⇒ 必须上 ④（独立用户会话/虚拟机）。

**由此得到一个可执行的安全原语**（"不打扰用户"从口号变成判定）：
> **任何窗口操作之前，先调 `IsWindowOnCurrentVirtualDesktop`；
> 若它就在用户当前桌面（返回 1），则不得使用键鼠式操作** —— 只能走消息式，或先请用户确认。
