## 1. 为什么需要"停用通道 / 新建通道"（现状与缺口）

**触发场景（老板原话）**：① 用户对成员/对话不满意；② **agent 上下文过长导致老化** ⇒ 要改成员，或改成员的对话。

**现状（实测/源码 2026-10-09）**：

| 场景 | 现状 | 缺口 |
|---|---|---|
**换人**（把成员从名单移除） | `POST …/members` 增量同步：移除时**清空未领取的激活队列 + 释放平台侧会话引用**（`workshops_assign.py:235/258`） | 有雏形，但**只在"移除成员"里**，没有独立的"停用通道"动作，也**不留痕** |
**换对话**（同一个人，换新会话） | **没有端点**；且 `establish_one` 见 `session_aliases` **非空就跳过** ⇒ **根本重建不了** | ★**完全缺失** —— 这就是老板要的"新建通道" |
**停用后的数据** | 隔间 `<职位>_<成员id>/` 跟成员，**跨会话存活** ✓ | 需明确：停用时**不删隔间**、只断通道 |
**留痕/可回退** | 审计有 `audit`（ring 500） | 停用/新建要进审计 + 成员卡要能看到"上一个通道" |

**要害结论**：现在这套系统里，**通道是"一次性"的**——建了就建了，不能退役、不能换新会话。
上下文老化这条场景**完全没有对应能力**。

## 2. 通道生命周期模型（核心建模）

**名词先定死**（避免我们仨说法不一）：
- **通道**＝某成员在本工作间里"通着的那条路"：**一个会话 + 它的桥 + 它的邮箱收发**
- **隔间**＝成员的**数据目录**（跟人、跨通道存活；**不属于任何通道**）
- **成员**＝岗位占位（`<职位>_<成员id>`），**可以换人、也可以换对话**，但隔间一直是他的

**状态机**：

```
                ┌──────── 新建通道 ────────┐
                │  (步骤4/7/8/9 重跑)      │
                ▼                          │
   [待接入 pending] ─激活→ [运行中 active] ─┐
                                   │        │
                    用户不满意 / 上下文老化 │
                                   ▼        │
                             [停用 retiring]│  （停桥、清队列、释放会话引用、记审计）
                                   │        │
                                   ▼        │
                             [已停用 retired]（**隔间与历史留痕保留**）
                                   │        │
                                   └─── 可再次"新建通道" ─────────────┘
```

**规则（每条都要能被界面如实显示）**：
1. **一个成员同时只有一个 `active` 通道**（多通道会串消息，违反"一员工一桥一邮箱"）；
2. **停用 ≠ 删除**：停用**保留隔间、产物、历史会话名**；只有用户明确"删除成员"才动数据；
3. **停用必须**：① 停桥/清未领取队列 ② 释放平台侧会话引用 ③ 写审计 ④ 成员卡显示"当前通道：已停用"；
4. **新建必须**：走既定步骤 4/7/8/9（配脚本且 `foreground != required` 才自动）；**新的会话名要与旧名可区分**（见 §3）；
5. **停用后不许再往旧通道投消息**（否则"停用了还能收到"= 假状态）；
6. 失败要说话：停用/新建**逐项返回真实结果**，没停掉的进 `still_running` 类似结构。

## 3. 新会话怎么命名（避免新旧混淆）

老板定的格式：`<工作间id>-<项目>-<职位>-<成员id>`。

**问题**：换对话后仍是同一格式 ⇒ 新旧同名，界面与人都分不清哪个是当前的。

**★已拍板（老板 2026-10-09）**：「**命名可以更加具体化，可以加序号，可以加职位等等**」

⇒ 定稿规则（已实现）：
- **第 1 个通道**沿用原格式（**向后兼容**，既有工作间的名字不变）：
  `<工作间id>-<项目>-<职位>-<成员id>`
- **第 2 个通道起追加序号**：`<工作间id>-<项目>-<职位>-<成员id>-<序号>`
  例：`cb6d1d01-通道验证2-码农-m0-2`（职位与项目名本来就在名字里 ⇒ 已经能看出"谁、干什么、第几个对话"）
- **还想更具体**：用 `new_name` 追加自己的标注（如 `…-2-重做前端`）——
  **平台生成的部分始终在前**（身份凭据不会被用户改名顶掉，V25 §4.1）。

## 4. 新端点草案（拍板后实现）

| 端点 | 语义 | 关键返回 |
|---|---|---|
`POST /api/workshop/{ws}/member/{mid}/channel/retire` | **停用当前通道**（body 可带 `reason`：`用户不满意`/`上下文老化`/自填） | `{success, retired_channel:{seq, session_name, at}, still_running:[…], detail:{}}` |
`POST /api/workshop/{ws}/member/{mid}/channel/establish` | **新建通道**（可显式 `new_name`） | 与 `establish-session` 同形状（`steps/verified/all_verified/manual`），**并返回 `channel_seq`** |
| `POST /api/workshop/{ws}/members` （改） | 移除成员时**同时**做"停用 + 留痕"（复用同一实现） | 同上 |
**只读**：`GET /api/workshop/{ws}/member/{mid}/channels` | 列出该成员历次通道（含当前哪个 active、各自何时停用、原因） | `{current:{…}, history:[{seq, name, at, reason}]}` |

**归属（★老板 2026-10-09 最新裁定，取代早前口径）**：
- 「**另外的通道接入后面直接在工作室（工作间）里面做**」⇒ 通道的**接入/停用/新建，界面一律落在工作间**；
- 「对接中心看起来更像说明书，没有实际用途，**不如就直接改成说明书吧**」⇒ hub 改为**使用说明书**、
  **零写请求**（复核：live `hub.js` 无任何写调用），速查表里写明"通道操作在工作间"；
- 端点 URL 本来就是工作间作用域（`/api/workshop/{ws}/member/{mid}/channel/...`）⇒ **接口无需改动**，
  改的只是"界面归属"这件事。

### 4.1 ★必须先定的规则：**新建通道不得覆盖旧桥**（2026-10-09 第二轮比对发现）

**事实**：接入产物写在**该成员隔间内**，文件名固定 `<隔间>/bridge.py`（一员工一桥一隔间）。
`server.py:5891` 的注释正好记着一个同型历史 bug：「此前所有人都往工作间根写同名的 `bridge.py`，
**后写的覆盖先写的**（隔离实例实测）」。

⇒ 若 V28 的"新建通道"直接复用现名，**第二次建通道会覆盖第一次的桥文件**，
而"停用≠删除、旧通道留痕"这条规则就落空了（甚至旧进程若仍引用该文件就会被换掉内容）。

**规则（写进实现）**：
1. **停用时**：把当前 `bridge.py` **归档**为 `<隔间>/channel_<seq>/bridge.py`
   （或等价：`bridge_v<seq>.py`；实现期二选一，但**归档动作必须存在**）；
2. **新建时**：写**新**的 `bridge.py`（当前通道只用这一份），并在 `connect_contract` 里记 `channel_seq`；
3. **`GET .../compartments`** 的 `root_files` 需能区分当前桥与归档桥（否则界面会把旧桥当活的）；
4. **示例Harness-F 文档 §4 的"具体桥…永不互相覆盖"** —— 现状成立，**本规则落地后仍需成立**；
   两份文档应在实现后**一起复核这条**。

老板原话：二级讨论是「**与组长讨论项目要求和分工情况（给项目建模；组长不被员工隔间框住）**」。

**要点拆解**：
1. **二级讨论＝与组长**（不是与全员）⇒ 讨论对象是组长一个；组长对内（员工）做分工深谈。
2. **给项目建模**＝二级讨论的**产出物**必须是"项目模型"，不是散聊记录：
   - **模型放哪**：`library/model.md`（新增）——它回答"这个项目由哪些部分组成、谁负责哪块、谁依赖谁"
   - **谁写**：组长（二级讨论收敛时写入）；平台**不覆盖**已有内容（与 `framework.md` 同规则）
   - **模型至少包含**：① 目标与验收 ② 组成（模块/任务分解）③ **成员↔任务的对应（分工）** ④ 依赖与顺序 ⑤ 产物落点（谁的 `output/`）
   - **界面**：资料库页面显示"项目模型"，与"分工安排/项目框架"三块并列
3. **"组长不被员工隔间框住"**＝组长要能**看全局**：
   - 现状：`library/` 是共享只读区 ✓、组长有自己隔间 ✓；
   - **要补的**：组长在**二级讨论里能看到所有成员的隔间状态/进度**（`members-status` 已提供 ✓），且**组长可以写 `library/model.md`**（讨论产物写=工作间侧）——
     ⇒ 需要确认"共享资料库写"的权限模型：目前 `library/update` 只支持写 `framework.md`，**需要扩展为可写 `model.md`**（且由平台判定"只有组长/整合者能写"）。
