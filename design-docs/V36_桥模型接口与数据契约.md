## 0. 一句话

把 L2「具体桥模板」从 **①一条 ②自动派生 ③只有 4 种传输层**
扩成 **①多条（可命名）②可手工填具体路径与名 ③带匹配条件**，
并新增"**在工作间里用模板架起一条绑定了具体会话的桥**"这一步 ⇒
**一条桥 = 一个具体会话**（老板要的 ①②③）。

---

## 1. ★三个对象（名词先钉死，防我们仨说法不一）

| 对象 | 是什么 | 粒度 | 存在哪 |
|---|---|---|---|
**① 员工本体** | harness：谁 + 怎么唤醒 + 建/改名会话的脚本 | 一个 harness 一条 | `harness_manager` 状态（`info.metadata`） |
**② 具体桥模板** | 一条桥的**做法**：名字 + 落点路径 + 匹配条件 + 形状参数 | **一个 harness 可多条** | `info.metadata["bridge_templates"]`（**列表**，新键） |
**③ 具体桥（实例）** | 真正跑起来的那条：**绑一个具体会话** + 该成员隔间 + 邮箱 | **每个成员每次一条** | 成员隔间内 + 成员字段引用 |

> ⚠️ **与现有键的关系（防迁移出错）**：现有单条模板在 `info.metadata["bridge_template"]`（**单数**）。
> 新键叫 **`bridge_templates`（复数，列表）**。**迁移**：读到旧`bridge_template`且没有新键时，
> **把它包成单元素列表**并标 `source="auto"`、`name="默认（自动派生）"` ⇒ **旧数据不丢**。

## 2. 数据模型

### 2.1 具体桥模板（`bridge_templates[i]`）

```jsonc
{
  "name": "示例Harness-B-CDP 桥",              // ★用户可读名，harness 内唯一；缺省 = "默认（自动派生）"
  "path": "D:\\...\\bridge.py",       // ★具体落点路径（可执行/脚本/目录，按 kind 解释）
  "kind": "cli_acp",                  // 形状参数：cli_acp | file_poll | pending_poll | script_framework
  "params": { "ACP_COMMAND": "...", "ACP_CWD": "...", "INBOX_DIR": "..." },  // 与现有 build() 同形状
  "match": {                          // ★匹配条件 —— 缺省 = 全局可用（老板裁定 2）
    "workshop": null,                 //   null=任意工作间；或具体 ws_id
    "role":     null                  //   null=任意职位；或如 "码农"
  },
  "source": "auto" | "user" | "ai",   // 谁给的：自动派生 / 用户手填 / AI 自查
  "complete": true,                   // 参数是否齐（缺啥见 missing）
  "missing": [],                      // 缺的参数名（"失败要说话"）
  "created_at": 0.0,
  "updated_at": 0.0
}
```

**默认值规则（老板裁定 2 的落地）**：`name` 缺省自动命名；`match` 缺省 **`{workshop:null, role:null}` = 全局可用**。
**不得**因 `match` 为空而拒绝保存。

### 2.2 具体桥（成员上的引用）

`WorkshopMember` 新增一个字段（形状对齐 V35 §4）：

```jsonc
"bridge_ref": {
  "template_name": "示例Harness-B-CDP 桥",     // 用了哪条模板
  "bridge_path": "…\\隔间\\bridge.py", // 实际落点（在该成员隔间内）
  "session_ref": "…",                  // ★绑定的会话（一条桥 ↔ 一个会话）
  "session_name": "ws-项目-码农-m0",   // 平台命名（V28 §3），便于界面直显
  "state": "attached" | "none" | "retired",   // 未架接 / 已架接 / 已停用
  "verified": false,                   // 平台不采信声明（准则⑤）
  "verified_at": 0.0,
  "attached_at": 0.0
}
```
- `state="none"` ⇒ 界面**必须明说"未架接"**（V35 §6，**不许空白**）；
- **一个 harness 可有多条桥/多个会话**（老板裁定 3）；**同一工作间内同一时间只有一条"当前通道"**（V28 口径不变，由 `channel_state` 管）。

### 2.3 存储布局

| 现在 | 改成 |
|---|---|
`platform/bridges/<harness_id>/` | `platform/bridges/<harness_id>/<template_name>/`（**模板产物**）|
（无） | 具体桥**实例**落在**该成员隔间内**（一员工一桥一隔间，保持 V28 §4.1「不得覆盖旧桥」的归档规则）|

⚠️ **模板名进路径必须转义**（防 `../` 穿越与中文名冲突）；**同名模板覆盖前备份**（与资料库同一纪律）。

## 3. 接口契约

### 3.1 桥模板（新，示例Harness-E 写）

| 方法 | 路径 | 语义 | 关键返回 |
|---|---|---|---|
`POST` | `/api/harness/{hid}/bridge-template` | 新增/覆盖一条具体桥模板（同名即覆盖，**覆盖前 `.bak`**）| `{success, template:{…}, replaced:bool}` |
`GET` | `/api/harness/{hid}/bridge-templates` | 列出该 harness 全部模板 | `{templates:[…], count}` |
`DELETE` | `/api/harness/{hid}/bridge-template/{name}` | 删一条模板（**不删已架起的桥**）| `{success, deleted}` |
`POST` | `/api/harness/{hid}/bridge-template/draft` | **AI 自查产出草案**（老板裁定 1：AI 自查+平台默认建议，**用户可改**）| `{success, draft:{…}, source:"ai", hint}`；**不落盘** |

**`draft` 的口径**（对齐 V29 的 `model/draft` 成功先例）：**只返回草案、不落盘**；
AI 不可用时 **400 + `error` + `hint`（含"可手工填"）** ⇒ **不许变成"注册不了"**（老板裁定 1 的约束）。

### 3.2 架接（新，示例Harness-E 写）★这就是老板说的"在工作间里发送具体桥模板、架起具体桥"

```
POST /api/workshop/{ws}/member/{mid}/bridge/attach
body: { "template_name": "示例Harness-B-CDP 桥" }        # 可省略 ⇒ 用该 harness 唯一/默认模板
返回: {
  "success": true,
  "bridge": { "template_name", "bridge_path", "session_ref", "session_name",
              "state": "attached", "verified": <bool>, "verified_at" },
  "steps": [ … ],            # 与 establish-session 同形状：每一步真实结果
  "verified": false,         # 平台不采信声明（准则⑤）—— false 时界面显示"⚠ 待人工"
  "detail": { … }
}
```
配套只读：
```
GET /api/workshop/{ws}/member/{mid}/bridge      ⇒ {template, path, session{ref,name}, state, verified}
GET /api/workshop/{ws}/bridge-bindings          ⇒ 供看板第一栏（FE-17 §4）
```

### 3.3 通道（复用，不新增）

换会话（上下文老化）**照旧**走 V28 的 `channel/retire` + `channel/establish`，
但**桥要跟着换**：`establish` 成功后，若该成员有 `bridge_ref`，**用同一条模板重新架接、绑到新会话**。
⇒ 实现点：`establish_channel()` 末尾追加"若已架接则重架"，并把结果**如实返回**（不许静默）。

### 3.4 旧式（harness 级）桥

- **不删除**（老板裁定 4：等新的跑通、他说一声再清）；
- 界面上标 **「旧式 · 未绑会话」**；
- 到期处理 = **人工发话后一次性清掉**（`界面不再出现、不再可用`，保留审计）。
  ⚠️ **不写定时器**（老板裁定 4 + "自动兜底默认关"）。
  ⇒ 示例Harness-E 提供一个**显式入口**（一次性工具/端点），由老板发话时执行。

## 4. 兼容与迁移（别把现有用法弄坏）

1. **旧 `bridge_template`（单数）自动升级**为复数列表的一条（`source="auto"`），**读到即迁移、不丢**；
2. **现有 `bridge/generate`（harness 级）保持可用**（旧式），界面标注"旧式"；
3. **现有 `bridge-verify` / `bridge-path` / `auto-connect` 不动**；
4. **架接时选择顺序**：显式 `template_name` → `match` 命中的模板 → 唯一模板 → **旧式回落（并提示"未绑会话"）**；
5. **`deliver-bridge` 不变**（按成员投递），但**投的应是新桥的产物**（若已按新方式架接）。

---

## 5. 验收（示例Harness-E 侧）

1. **迁移**：造一条只有旧 `bridge_template` 的 harness ⇒ 读出后变列表一条，**参数不丢**（回归测试）；
2. **多条**：同一 harness 存 3 条模板（含中文名/带空格名）⇒ 都能存、能列、能删；**同名覆盖前有 `.bak`**；
3. **默认全局**：`match` 省略 ⇒ 保存成功且**任意工作间都能架**（反向断言：不得报"未指定工作间"）；
4. **★一条桥=一个会话**（老板 ①③ 的验证点）：同一 harness 的两个成员 ⇒ **各架一条桥、各绑不同会话**；
   `GET …/bridge` 分别返回各自的 `session_name`，**不串**；
5. **`verified=false` 路径**：真实返回 `verified=false` ⇒ 接口层如实返回，**不得写成成功**；
6. **换会话跟着换桥**：`channel/establish` 后 `bridge_ref.session_ref` 更新为新会话；
7. **AI 不可用**：`draft` 返回 400+`error`+`hint`，且**手工填模板+架接仍能走通**（老板裁定 1 的约束）；
8. **旧式仍在**：旧式桥可跑、被标"旧式"；
9. 隔离实例 + 自建自清；全量回归不降（当前基线 **1050 passed / 10 xfailed**）。
