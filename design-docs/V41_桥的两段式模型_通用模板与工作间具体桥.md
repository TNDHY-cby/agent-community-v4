## 1. 两段式模型（我建议的定稿口径）

```
① 注册 harness（大厅/接入页）        ── 平台级、与工作间无关
     产物 A：列表里的身份（harness_id + 名称/能力/唤醒方式…）
     产物 B：**通用桥模板**（= L2 具体桥模板；一个 harness 可有多条，其中一条为默认）
             每条模板表明：接口类型（四种之一）+ 该类型要填的字段（"该填什么"取自 `bridge_catalog`）
     ⇒ 这一步**不需要**知道任何工作间坐标

② 在工作间里架"具体桥"（工作间页）   ── 工作间级、坐标现成
     在某成员的卡上点「架桥」→ 从**它 harness 的通用桥模板**里挑一条
     ⇒ 平台用**工作间坐标**（ws + 成员隔间）把模板**渲染成该成员专属的桥产物**（= L3），
       并**绑到该成员的具体会话**（老板口径：一条桥 = 一个具体会话）
     ⇒ 这一步**不用挑工作间**（人已经在里面了）
```

**术语固定**（避免歧义，与我此前的用法对齐）：
- **通用桥模板** = `bridge_templates` 里那条（按 harness 存，可复用、与工作间无关）；
- **具体桥** = 渲染到某成员隔间、绑了该成员会话的那份产物（`bridge_ref` 指向它）。

## 2. ★真正的缺口（这才是要做的活）

| # | 缺口 | 影响（用户视角） |
|---|---|---|
**G1** | 工作间里**没有"挑哪条通用桥模板"的入口** | 用户手里有两条模板（比如「本地 CLI」和「远程 HTTP」），到成员卡上**无从选择**；平台只能按 `pick_for` 猜 ⇒ **猜错了他也不知道** |
**G2** | **看不到该 harness 有哪些模板** | 同上；且失败时只报"该 harness 还没有任何具体桥模板"，用户不知道去哪儿建 |
**G3** | 建好之后**不能换/不能看** | 成员卡上只能看"已绑什么"，**换一条模板**没有入口（要重架整个通道） |
**G4** | 通用桥模板的**四个字段**与 `bridge_catalog` 的**四种类型**没在界面上挂起来 | 用户建模板时**不知道每个空填什么**（而这正是 V38 花大力气做的"该填什么"） |
**G5** | **默认模板**看不见、也改不了 | 多条模板时，"平台会默认用哪条"不可知 ⇒ 结果不可预期 |

**另有一处需要合并的重复**：现在"叫醒命令"有两处存法 ——
`GET/POST /api/harness/{hid}/wake`（我 V38 加的，**平台级**）与 L2 模板里的 `TRIGGER_CMD` 字段。
**两处口径必须合一**（规则 20），否则用户配了 A 处、桥用 B 处 ⇒ 又是"看起来配好了却不生效"。

## 3. 我建议的做法（待你点头后再写码）

**P1（先做，直接回应你这句话）**
1. 成员卡上加「🔧 选桥」入口：列出**该 harness 的通用桥模板**（名字 + 类型 + 是否默认 + 来源：用户/AI/自动），
   选中后调**既有**的 `attach`（带 `template_name`）⇒ **不新增语义，只新增入口**；
2. 没有模板时，**就地给"去建一条"的路**（跳转带 harness_id），而不是只报错；
3. 成员卡显示当前绑的：**桥名 → 绑的会话名 → 隔间 → 邮箱**（`GET …/member/{mid}/bridge` 已能取到）。

**P2**
4. 建模板的界面接 `GET /api/bridge-catalog/{kind}`：**类型选哪种 ⇒ 就显示那种的"该填什么"**
   （谁提供/怎么填/怎么自证/常见坑都是现成的），把 G4 补上；
5. 支持**设为默认**（G5），并在成员卡上显示"默认会用它"。

**P3（口径合一，必须做但可稍后）**
6. `wake` 与 L2 的 `TRIGGER_CMD` 合并为**一处真相**：建议**以 L2 模板字段为准**，
   `wake` 端点保留为"改这一条模板字段"的便捷入口（对外仍是一个动作），
   并在界面/模板里都取自同一处。

## 4. ★老板裁定（2026-10-11 18:13，**已定，实施不得自行增删**）

**问题 1 → 选 B：一个 harness 只允许一条通用桥模板。**

落实口径：
- `POST /api/harness/{hid}/bridge-template` 改为**幂等覆盖**：同一 harness 再建一条 ⇒
  **替换**那唯一一条（行为上等同"编辑"），**不再支持并存多条**；
- 已有并存多条的历史数据：**按"默认那条"保留**（`default_one`），
  其余**不静默删**——移入该模板记录的 `superseded` 列表（保留可回看，与"停用≠删除"一致），
  并在响应/界面里**如实说明"已按 B 收敛为一条，旧的留在历史里"**；
- 因此 **G5（默认模板看不见/改不了）自动消失** —— 只有一条，它就是默认；
  工作间**没有"挑哪条"的问题**（G1/G2 从"选择器"降级为"显示这一条 + 去建/去改"）。

**问题 2 → 选 A：工作间里换桥 = 停用旧通道 + 建新通道，旧记录保留可回看。**

落实口径：
- 换桥走既有 `channel/retire` → `channel/establish`（V28），**不覆盖**；
- 成员卡上能看：**当前桥（名字 → 绑的会话名 → 隔间 → 邮箱）** + **历史通道（已停用，可回看）**；
- 与既有 `bridge_ref.state="retired"` 口径一致（`retired_at` / `retired_session_name` / `retired_channel_seq` 保留）。
