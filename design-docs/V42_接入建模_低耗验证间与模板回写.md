## 0. 一句话

**通用桥模板从"让人手填的表"变成"跑通过之后的产物"**：
大厅里给每个 harness 一个**低耗验证间**（等价于工作间、但只服务于验证），
在那儿把桥架起来、真跑通（消息送达 + 被叫醒 + agent 回话），
**把实测到的配置回写成模板并标记"已验证"**，然后**连桥一起拆掉，只留模板**。

---

## 1. 为什么这么改（现状的三个毛病，都实测过）

| 病 | 现状 | 后果（真实发生） |
|---|---|---|
**模板靠人填，填了也不知道对不对** | 注册页让人选桥型、填字段、填命令 | 我昨天在模板里写错映射（把桥型名当 `wakeup_method`）⇒ 外端 agent 照填**注册被 400 拒**，它回「我什么接口都没有」 |
**填的东西从没被验证过** | 模板有 `complete/missing`，但没有"这条配置**真的跑通过**" | 用户配完看到的是"已保存"，实际能不能叫醒**没人知道** |
**验证只能在真实工作间做** | 自检端点要 `ws_id` + `member_id` | 想在接入时就验证，必须先在某个工作间里挂个成员 —— **把"接入"和"开工"绑死了** |

★另外还有一处**顺序自相矛盾**（今天读代码发现的）：
`attach_bridge_core` 要求"该 harness **已有**桥模板"才能架桥（没模板直接报错），
而你的模型是"**架桥跑通后**才写模板" ⇒ **先有鸡还是先有蛋**。本设计把这个环打开。

## 2. 三层建模（这次要"更新完善"的核心）

```
① 身份          harness 注册的产物之一：列表里那一行（名字/框架/模型/能力）
      ← 大厅注册，**只需要这个**；技术上只要平台知道你是谁、怎么联系你

② 通用桥模板    这个 harness "怎么被叫醒"的**已验证**记录（一个 harness 一条，裁定 1B）
      ← 不是表单填出来的，是**在低耗验证间里跑通后回写**的
      ← 字段：桥型 + 用户给的输入（命令/目录/地址）+ **验证证据**（何时、结果、探针 id）

③ 具体桥        某个工作间某成员的桥产物（落它自己的隔间、绑它的具体会话）
      ← 工作间里做；**照着 ② 直接实例化**，不再重新试错
```

**术语收敛（顺手修掉今天踩的那个坑）**：
- 对用户/AI 只说**桥型**（`file_poll` 文件夹邮箱 / `cli_acp` 命令行拉起 /
  `pending_poll` 通用轮询 / `script_framework` 动作脚本）；
- `wakeup_method` 是**存储层的旧字段名**，**只许平台内部用**，界面上不再出现
  （模板里混用两者 = 今天那次 400 的根因）。

## 3. 低耗验证间（"等价低耗工作间模型"）是什么

**定义**：一个**只为验证桥而存在**的最小工作间，由平台在注册流程尾部自动创建：

| 属性 | 取值 | 为什么 |
|---|---|---|
名字 | `验证间 · <harness_id>` | 用户一看就知道它是干嘛的 |
成员 | **1 个**，角色 `验证员`，绑该 harness | 桥必须挂在"某个成员"上（平台的既有模型） |
落盘 | `<data>/verify_sandbox/ws_<hid>/…`（**不进正式工作间列表**） | 低耗、不污染大厅 |
隔离 | 标记 `sandbox=true` | 界面折叠显示、可用后即拆 |
用途 | 架桥 + 自检（含真探针） | 与真实工作间**同一套**桥/隔间/邮箱管线 |

**关键：它必须走同一套管线**（`connect_artifact` → 隔间 → 邮箱 → 桥 → 回报），
否则"在验证间跑通"不能保证"在真实工作间也能跑通"。**等价**就是指这个。

## 4. 四条流程（每条都说清"谁做什么、失败怎么办"）

### F1 注册（大厅）
1. 用户贴一次话术 → 外端 agent **自测**（能否被命令拉起 / 盯文件夹 / 有网页接口 / 都不行）；
2. agent 调注册接口（`wakeup_method` **由平台内部映射**，不让它填桥型名）；
3. 平台建**低耗验证间**，并按自测结果**派生一条"未验证"的草稿模板**（复用既有自动派生逻辑）。

### F2 验证（在低耗验证间里）
4. agent/用户触发「**验证这条桥**」→ 平台在验证间里架桥（用草稿模板）；
5. 跑**自检**：真发一条探针 → 看「桥取走了没 / agent 回话没」→ 三态
   （`ok` / `no_reply` / `not_picked`，与今天已有的自检同一套）；
6. **不通就地给原因与怎么办**（准则⑤），不写模板。

### F3 回写（跑通才写）
7. `ok` ⇒ 把**实测到的真实配置**写进该 harness 的**唯一那条**通用桥模板，
   并标注：`verified=true`、`verified_at`、`evidence{probe_id, session_name, artifact_kind}`；
8. **`no_reply`/`not_picked` ⇒ 不写"已验证"**（可写"草稿+失败原因"，界面如实显示）。

### F2.5 ★平台侧主动探测（老板 22:30 加的关键一环）

**问题**：外端 agent 被沙箱限制时**测不出自己的接口**（截图里 示例Harness-B 就回"我什么接口都没有"）
—— 而这种"没有"往往是**它看不到**，不是**真没有**。

**做法**：**平台主动去测它**（平台跑在宿主上，看得见它）。三层，**前两层纯脚本、零 token**：

| 层 | 探什么 | 用什么 | 花 token？ |
|---|---|---|---|
**① 进程** | 有没有在跑的进程像它（命令行/进程名） | `Win32_Process`（`server.py` 已有） | **否** |
**② 端口/HTTP** | 有没有在监听、有没有能接 POST 的端点 | `probe_http_api`（`platform/api_wakeup.py` 已有）、socket 连接测试 | **否** |
**③ 文件/路径** | 安装目录、可执行入口、是否能被一条命令拉起 | 路径线索 + `Test-Path` + 试跑 | **否** |
（可选）④ 只能拿到模糊结果时，**才**请平台 AI 读一次探测结果做判断 | 平台 AI | **是**（少量） |

**纪律**（避免越界与浪费）：
1. **只探本机/用户自己的东西**（接入场景本来就发生在同一台机器上）；
2. **用户点了才探**（老板原话：自动检测太浪费），不做后台轮询；
3. **探测只产出"候选"，不直接定论**：把 `进程✓ 端口✓ 端点✓` 这类**证据**摆出来，
   由用户/agent 确认后**才写模板**（写模板仍走 F3 的"跑通"门槛）；
4. **零 token 的层先跑完**，AI 只在必要时用一次 —— 界面上标明**哪一步花了 token**。

**与 agent 自测的关系**（两条腿都要）：

```
agent 自测  → 报"我能怎样被叫醒"（它自己知道的，最准）
平台探测    → 补"它测不出的"（沙箱里看不到的），并**交叉验证** agent 的说法
若两者冲突  → 以**跑通**为准（F2 的自检），模板只记跑通过的那种
```

### F4 拆掉（只留模板）
9. 拆掉验证间：**桥进程停掉、桥产物删掉、测试会话结束、探针清掉**；
10. **只留**：模板（含验证证据） + 一条**审计**（谁在何时验过、结果如何）；
11. 验证间本身从界面列表移除（或折叠为"已完成的验证"）。

**开工时**（工作间里）：照 ② 的模板**直接实例化**具体桥；
若模板 `verified=false`，界面**明说"这条还没验证过"**（不许假装通了）。

## 5. 数据模型改动（最小集）

```jsonc
// harness.metadata["bridge_templates"][0]   ← 唯一那条（裁定 1B）
{
  "name": "…", "kind": "file_poll", "params": {…}, "match": {…},
  "source": "auto|user|ai",
  "complete": true, "missing": [],
  // ★V42 新增：验证证据（"跑通过"的凭据）
  "verified": true,
  "verified_at": 1791…,
  "verified_by": "sandbox",         // 在低耗验证间里验的
  "evidence": {"probe_id": "probe_…", "session_name": "…", "artifact_kind": "…",
               "picked_up": true, "answered": true}
}
```

- 成员上的 `bridge_ref.verified` **继续**表示"这条具体桥被验证过"（两个层级各自的凭据，不混）；
- 验证间用 **`sandbox=true`** 标记，正式工作间不受影响。

## 7. 明确不做 / 待定

- **不做**：给每个 harness 建"正式工作间"来验证（那正是要避免的重）。
- **待你定**（见 §8）。
- **风险（我如实标出）**：验证间与真实工作间**环境等价**，但**使用强度不同**；
  真实开工时若 agent 侧有变化（如它自己更新了），模板可能过期。
  ⇒ 建议界面在模板上显示 `verified_at`，**超过一段时间提示"建议复验"**（先不做，等你定）。

## 8.5 ★老板裁定（2026-10-11 22:30，**已定，实施不得自行增删**）

| 问题 | 裁定 | 落实口径 |
|---|---|---|
① 验证间每个 harness 一个？ | **各自一个** | 注册尾部为每个 harness 建自己的低耗验证间；互不干扰、拆得干净 |
② 回写用实测值还是用户填的值？ | **按 示例Harness-E 建议**（= **实测值优先**） | 回写"跑通过的那份配置"；用户填的仅作 `source` 参考 |
③ 自动检测会不会浪费 token？ | 「**用户使用时发现坏了再点击检测**吧，自动检测会不会太浪费 token 了，**如果全脚本的话另说**」 | ⇒ **默认不自动检测**；**平台侧探测全部走脚本（零 token）**，做成"点一下才跑"的按钮；只有拿到模糊结果、确有必要时才允许一次 AI 判断，且**界面须标明这一步花了 token** |
④ （老板新增）平台能不能主动去拉桥 | 「**要是平台有 agent 可以去拉桥就好了**，这样就不怕外端 agent 因为沙箱等限制无法检测自身接口了」 | ⇒ 新增 **§4.5 平台侧主动探测**（进程/端口-HTTP/文件三层，脚本、零 token），与 agent 自测**互相交叉验证**；冲突时**以跑通为准** |

**"建议复验"（原问题 3）**：老板口径已隐含"**用户使用时发现坏了再点检测**" ⇒
**不做后台自动复验、不做超期提醒**；只在界面上显示 `verified_at`，并提供【重新检测】按钮。
