## 〇' 一句话结论

**接入的真正门槛不在"配置能不能填对"，而在"配好之后，桥有没有真的在跑"。**

> **前 4 步绿 = 配置可行；第 5 步（持久跑桥）绿 = 真的接上了。**
> 别把前者当后者 —— 这是真机实测里最贵的一条教训（新 agent 拿到"配置可行"就停住了）。

## 一 验收线（改完必跑，全绿才算完）

```powershell
# 1) 后端全量 —— **裸跑**即可：pytest.ini 的 testpaths 已含两处
#    ⚠️ 别再手写某一个路径：2026-10-12 发现我连续多日只跑 agent_community/tests，
#       根 tests/ 那 66 条**一直没被跑过**，对外却报"全量 0 failed"（"看起来成功"）。
python -m pytest

# 2) 前端验收（真浏览器 + 真点击；脚本数 = 目录里 *_check.js 的条数）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\run_fe_verify_all.ps1

# 3) 服务健康（4 项：平台 18920 / Tailscale IP / A2A 9104 / gRPC 9105）
powershell -NoProfile -ExecutionPolicy Bypass -File deploy\healthcheck.ps1
```

**当前实测基线（2026-10-12 本轮，改动后重跑）**：

| 验收线 | 结果 | 取数方式（别只看终端"绿"） |
|---|---|---|
| `python -m pytest` | **1330 条 / 0 failed / 0 skipped**（主线 `agent_community/tests` 1264 + 根 `tests/` 66） | `--junitxml` 解析（终端汇总行在重定向到文件时**不出**，别拿"没看到红"当判据） |
| `deploy\run_fe_verify_all.ps1` | **TOTAL 31  PASS 31  FAIL 0**（且 `_sweep_result.json` 里 nonzero=[] ） | 同时看**明细 JSON**：终端汇总曾被一个 PS 5.1 的坑变成"假全过"（见下） |
| `deploy\healthcheck.ps1` | **4/4 OK** | — |

**"绿"不等于"能接上"** —— 上面三条只保证**没坏**；下面才是**能不能用**。

> ⚠️ 另有一类"绿"是**假绿**：测试看着过了，其实断言根本没执行到
> （本项目实测过：`cmd /c` 起进程失败、而 `assert rc == 0` 照样通过）
> ⇒ 每条判据都要**故意写反例证明它抓得住**（§10）。
>
> ⚠️ **而且"汇总"本身也会骗人**（2026-10-12 实测，出在我自己的前端验收工具里）：
> `run_fe_verify_all.ps1` 原来写 `$bad = $results | Where-Object {...}`，
> 在 **Windows PowerShell 5.1** 下**恰好只有 1 条失败**时，管道返回的是**单个对象**而非数组
> ⇒ `$bad.Count` 得到 `$null` ⇒ 汇总打印成 `PASS 31   FAIL `（空白）、`if ($bad.Count -gt 0)` 为假、
> **脚本 exit 0**。实测证据：先跑出 1 条 FAIL、汇总却报"全过"；2 条以上才正常。
> ⇒ 已改成 `@(...)` 强制数组 + 断言"跑过的条数 == 发现的脚本数"（对不上就报错退出）。
> **教训：验收工具自己也要被验收** —— "全过"必须是**算出来的**，不能是"算不出来"。

## 二 ★核心判据：**换一个目录 + 换一个完全不同的 agent 名，不改一行代码就能走通**

（老板定的铁律，见规则 19。**做不到即未完成**。）

| 检查 | 怎么查 | 不合格的样子 |
|---|---|---|
| 有没有写死"只有我这台机器才有"的东西 | 搜自己的路径 / 真实 harness 名 / 固定端口目录 | 代码或话术里出现真实 harness 名、本机绝对路径 |
| 会不会把"我这台通了"当成"功能通了" | **换目录 + 换名**重跑一遍 | 只在我这条路验过就报"已完成" |
| 有没有假设用户知道技术细节 | 让一个**不知道内情的人**念一遍界面文案 | 文案在讲 `wakeup_method` 这类内部字段名 |

> 2026-10-12 实测抓到过真的漏出去的：一个前端验收脚本里钉着**本机运行时的绝对解释器路径**，
> 而且**已经随仓库推到了公开仓库** ⇒ 换台机器直接跑不起来。已改成 `AC_PYTHON` 环境变量 + PATH 兜底，
> 并加了守卫测试（§5.1）。

## 三 接入五步（对外话术口径，逐字对得上 `register.html`）

| 步 | 用户动作 | 平台必须给出的自证方式 |
|---|---|---|
| 1 注册 | 把**一段**话术粘贴给 AI（只复制一次） | 注册后列表出现该 harness |
| 2 配叫醒命令 | 交"收到任务执行哪条命令"；**人工模式不用填**，空命令回 `mode:manual` 就是正常完成 | 没配就**明说"不会叫醒你"**，不假装 |
| 3 起桥 | `POST …/auto-connect` | `connected/ready` 或 `manual`（人工模式不阻塞） |
| 4 自检 | `POST …/{hid}/verify`（**刚注册即可，不需要工作间**） | 三态 `ok` / `no_reply` / `not_picked`，每态都给下一步 |
| 5 ★持久跑桥 | `bridge/generate` → 用 `launch_hint` **常驻**起桥 → `bridge-test` 探活 | 说清 `verified_scope`、`delivered_confirmed`、`bridges_running`（**逻辑桥数**） |

**"选桥型 / 存桥模板"并进第 1 步自动派生，不单独算一步**（两处口径必须一致，否则就是§7 那类"看起来成功"）。

## 四 自检七步（内部粒度，与五步是同一件事的两种颗粒度）

> 原表停在「自检」，但**自检通过 ≠ 真接入**：自检跑的是**验证间里平台自己起的那只桥**，测完即拆。
> **不在 harness 侧常驻跑桥，平台派的活只会躺在队列里没人取。** 故补第 7 步。

| 步 | 用户动作 | 平台必须给出的自证方式 | 失败时要说什么 |
|---|---|---|---|
| 1 注册 | 粘贴一段话术 | 注册后列表出现该 harness | 缺哪个必填项、为什么必填 |
| 2 选桥型 | 选一张卡（字段来自 `/api/bridge-catalog`） | 卡片列出"你要准备什么" | 不支持就**如实说不支持**，不硬撑 |
| 3 存桥模板 | 填命令 / 目录 / 地址 | 保存后能读回，缺项标 `missing` | 缺什么、去哪补 |
| 4 配叫醒 | 填"收到任务执行哪条命令" | `GET /api/harness/{hid}/wake` 的 `configured` | 没配就**明说"不会叫醒你"** |
| 5 起桥 | 起桥进程 | 桥进程能查到、能回报 | 起不来给**原因**，不说"已启动" |
| 6 自检 | 点「发送自检」/「大厅快速验证」 | 三态 `ok` / `no_reply` / `not_picked` | 每一态都要有**下一步该干什么** |
| 7 **持久跑桥** | `bridge/generate` → 用 `launch_hint` 常驻起桥 | `bridge-test` 探活 + `bridges_running`=1（**逻辑桥数**，父子链算一只） | 第二只**被拒绝启动 = 正常保护**（先停旧的再起）；`bridges_running`>1 且带 `bridge_warning` ⇒ 停掉多余的只留一只 |

**★三条硬要求**：
1. **三态都要能复现**：故意不起桥 → 必须 `not_picked`；起了桥但 agent 不回 → 必须 `no_reply`；
   两个都不做**不得**出 `ok`。**造假一态就算不合格。**
2. **只有 `ok` 才写"已验证"**（老板口径："让它先跑通才写入具体模板里"）。
3. **`ok` 也必须写清"验的是什么范围"**（`committed.verified_scope`，见 §5.4）——
   **不写清范围，`verified=true` 就会被读成"整条链路都通了"，那是说过头。**

## 五 现行口径（实测修订后的口径）

### 5.1 桥型模板必须**通用**（老板 2026-10-12 要求；本轮补齐）

| 你的自测结果（第 1 步） | `wakeup_method` | 该生成哪种桥 |
|---|---|---|
| A 能被执行命令拉起 | `acp` | `cli_acp`（桥负责拉起会话、把件送进去） |
| B 能盯着一个文件夹 | `file_poll` | `file_poll`（桥盯着 inbox 搬件） |
| C 有常驻网页接口 / D 人工中转 / E 都测不出来 | `http_api` / `clipboard` / `http` | `pending_poll`（桥轮询平台把件落盘） |

- **拿不准就 `pending_poll`** —— 它不需要你额外提供接口或目录，**任何 harness 都能跑**。
  话术里写的是一张**对照表**，不是某一种 agent 的专属做法。
- **模板里不许有"只有某台机器/某个 agent 才有"的东西**：已加守卫测试，
  扫 `register.html` + `bridge_templates/**` + `examples/*.py`，出现真实 harness 名或本机坐标即红。
- ★**模板渲染出来的桥必须自带单实例锁**（本轮补，见 §5.6）——
  之前**只有 `examples/` 里两只手写桥有锁**，而用户真正会跑的是**模板渲染出来的那只**：
  文档写着有锁、产品路径里没有 ⇒ **文档比代码先说了话**。

### 5.2 探测只补线索、不下定论

- 只有**对象自己给的 `port_hint` 命中**才推荐 `http_api`；
- 扫到的其它端口一律只作**线索**，明说"**尚不能确定属于它**"，并**劝止**拿它当 `api_base_url`；
- `probe-register` **没有证据时沿用对象自己声明的方式**，不拿猜测覆盖；
- 默认值用 **`clipboard`**（唯一不会连错的选项），不是 `file_poll`。

### 5.3 词汇严格分开（三组不许混）

| 概念 | 合法取值 |
|---|---|
| `wakeup_method`（*靠什么被叫醒*） | `http` / `file_poll` / `clipboard` / `acp` / `http_api` / `mcp` |
| **桥型 / 桥模板**（*用哪只桥*） | `file_poll` / `cli_acp` / `pending_poll` / `script_framework` |
| **探针通道**（*测试件走哪条路*） | `inbox`（file_poll 型）/ `pending_queue`（其余型） |

- `bridge_type` **只能是桥型或 `None`**；没起桥就 `bridge_started:false`，不许报一个"不存在的桥型"。
- `sent_via` 报**真实投递通道**（`inbox` / `pending_queue`），**不是** `wakeup_method`；
  想知道的唤醒方式**单独给** `wakeup_method` 字段。
  · 2026-10-12 踩过：`/bridge-test` 改了，**`/bridge-verify` 同族没改干净**，
    界面显示「发送成功（clipboard）」——一个**根本不存在的通道**，外部 agent 读成了 ✅ 绿。
    ⇒ 口径收敛成**一处函数**，两个端点共用（`_wake_channel`），并有守卫测试盯着别分叉。

### 5.4 "跑通"必须说清**验证范围**（`verified_scope`）

| 通道 | 验的是什么 |
|---|---|
| `inbox`（file_mailbox） | **完整链路**：平台 → 桥 → 你的 agent → 回报 |
| `pending_queue`（桥测试通道） | **仅桥配置**（桥能连平台/领件/回报；**且这只桥是平台在验证间里启动的**）—— **harness 侧是否运行该桥、agent 能否回话，本次未验证** |

### 5.5 探针按桥型选通道

`pending_poll` 这类**轮询平台 API** 的桥必须走平台的"桥测试通道"
（`bridge-test` → `pending_bridge_tests` 队列 → 桥领取并**自动回报**）；
只有 `file_poll` 才走文件邮箱。**拿文件邮箱验 API 轮询型桥 ⇒ 必然假阴性。**

### 5.6 失败要说话 + 三件"防玄学"的实事

- `bridge-test` 的 `success:true` **只表示"投出去了"** ⇒ 新增 `queued:true` / `delivered_confirmed:false`，
  并在 `note` 里给出**怎么才算确认**（看 `{hid}/wake` 的 `bridge_test` 记录，或直接跑 `{hid}/verify`）。
- **名下有几只桥**：`bridges_running` / `bridge_pids` / `bridge_warning`（>1 时告警）。
  · ★**计数口径是"逻辑桥"，不是"进程数"**：本机 `python.exe` 是**外壳**（它会再拉起真解释器，
    **命令行一模一样**）⇒ **一只桥常见 2 个同名进程**。按进程数计会**把一只桥报成两只**、
    给用户**假的重复告警**（真机实测：外部 agent 当场指出"那是父+子进程"——**它对、我错**）。
    修正后的判据：① 在跑 `bridge.py`；② **只认解释器**（排除 powershell/cmd 包裹进程）；
    ③ **父子链算一只**，只数链根。
  · **平台自己起的桥在进程扫描里看不见**（扫描有意排除 `ParentProcessId == 平台`，
    本意是排除"探测动作自己起的子进程"）⇒ `bridge_instances` 改为**两路合并**：
    先查登记表，再扫外部进程。否则 `auto-connect` 明明起了一只、`bridges_running` 却报 0。
- ★**桥脚本自带「单实例锁」**：平台只能**报告**重复桥、**拦不住** ⇒ 守卫放在桥这一层：
  **同一个工作目录 / 同一个 inbox 起第二只会被拒绝启动**（退出码 2，打印
  「另一只桥正在使用同一个工作目录（拒绝重复启动）」；三种桥型各自盯的目录：
  `file_poll` 的 inbox、`pending_poll` 的 work-dir、`cli_acp` 的桥脚本所在目录）。
  · 实现用**持有独占文件锁**（`msvcrt.locking` / `flock`），**不是 pid 文件**：
    pid 文件在崩溃时留僵尸锁、且 pid 会被系统复用 ⇒ 误判；**持锁由操作系统在进程结束时自动释放**。
  · ⚠️ **实测踩坑**：`open(lock,"a+")` 是**追加模式**，初始指针在 **EOF**，而 `msvcrt.locking`
    锁的是"从当前指针起的 N 字节" ⇒ 不先 `seek(0)` 时两只桥**锁在不同字节上、毫无冲突**
    （第一版源码看着全对、实测完全不拦）。**教训：这类保护必须真起两个进程验，源码断言测不出来。**
  · ⚠️ **锁必须内置在模板里**（本轮补）：只有 `examples/` 有锁是不够的，
    用户跑的是**模板渲染件**；三份 L1 模板（`file_poll` / `pending_poll` / `cli_acp`）已补齐，
    并有"渲染 → 真起两只进程"的守卫用例（只做源码断言挡不住上面那个 seek 坑）。
- **验证间是一次性的**：`persistent_bridge.sandbox_dir_deleted` + `how_to_run_persistently`
  —— **别让人去已删除的目录里找桥脚本**。

### 5.7 「该不该起桥」的判据（与 §5.6 同一套口径）

`auto-connect` 靠"是否已有桥在看着这个邮箱"决定要不要起桥。**误判为"有"就会跳过起桥** ⇒
**桥根本没起、界面却看着正常**（本项目最怕的死状态）。原判据三个毛病：
① 不检查是不是桥（任何提到该邮箱路径的进程都算）；② 不认解释器；③ 与 `bridges_running` 两套口径。
⇒ **统一到同一套判据**（在跑 `bridge.py` + 只认解释器 + 父子链算一只）。

**设计原则（不对称性）**：宁可**少认**也不能**多认** ——
少认了会再起一只，**单实例锁会拦下并说明理由**（可见、可恢复）；多认了是**静默不启动**（无从发现）。

### 5.8 持久跑桥的正确姿势（实测核对过）

```
POST /api/harness/{hid}/bridge/generate  {"template": "<桥型>"}
  · **省略 out_dir** ⇒ 落到 <平台>/agent_community/bridges/<harness_id>/bridge.py
  · 若要指定，out_dir **必须在平台的 bridges/ 目录内**（否则 400）
  · 返回 bridge_file / bridge_dir / **launch_hint（现成启动命令）**
→ 用 launch_hint 起桥（**脚本路径含空格时必须带引号**；实测不加会被拆断、进程秒退）
→ POST /api/harness/bridge-test 探活（注意其 success 语义见 §5.6）
```

## 六 真机实测暴露的九个问题（**全部核实为真**）

| # | 现象（外端 agent 的原话/事实） | 根因 |
|---|---|---|
| 1 | 「平台扫到 `127.0.0.1:<随机端口>`，**误判为我的 HTTP API**」 | 探测工具只要本机扫到任意 HTTP 服务（400/405/404 都算）就推荐 `http_api` + 那个端口；开发机上永远有随机本地服务 ⇒ **几乎必然误判** |
| 2 | 「wake 接口拒绝空命令，但 **clipboard 人工模式本身没有 shell 命令**」 | 向**用不到**的人工模式索要"叫醒命令" |
| 3 | 「第 4 步自检要 **workshop_id/member_id**，而我刚注册」 | 话术指向"需要先有工作间"的老端点，而平台**早已有**免工作间的低耗验证间 |
| 4 | 「我**明确声明了 clipboard**，平台却回『你**没有声明**』」 | `pre-register` **从来没存** `wakeup_method` ⇒ 对象的自述被静默丢弃 |
| 5 | 自检返回 `bridge_type: "clipboard"` | `clipboard` 是 `wakeup_method`、不是桥型 —— 词汇混用（同处还有 `"acp"`、`"http_api"`） |
| 6 | 桥明明在跑，却回 `not_picked`（理由「**桥没有在运行**」） | 验证间**一律**把试探丢进**文件邮箱**；而 `pending_poll` 桥**轮询平台 API、根本不读邮箱** ⇒ **结构性假阴性**，且**平台对用户说了假话** |
| 7 | 拿到 `ok` 后，它打算去**验证间隔间目录**里找 `bridge.py` | **验证间隔间跑完即删**，而建议却指向那里 ⇒ **指路指到废墟** |
| 8 | `bridge-test` 回 `success:true, sent_via:"clipboard"`，被读成 ✅ 绿 | `sent_via` 报的是 `wakeup_method`（真实通道是队列）；且 `success` **只代表"投出去了"**，桥没在跑时同样 `success` |
| 9 | 名下有 **2 只桥同时在跑**，平台**一个字都没说** | 无重复桥检测；平台注释里早有"同一邮箱多只桥 ⇒ 重复投递"，但**从未报告出去** |

**九个问题同一个病根**：**拿猜测覆盖对象的自述 / 向用不到的人索要东西 / 把"看起来成功"当成功。**

## 八 平台"假死"的根因：**async 里做同步阻塞**

**症状（从外面看完全不像它本身）**：watchdog 日志报 `TimeoutError: timed out`、
`TCP not listening`（**进程还在、却不再收连接**），然后自动重启；
外端 agent 在接入第 2 步直接报「连接被远程主机关闭」（当时被当成"网络抖动"重试）。

**根因**：`async def` 里直接跑**会等**的同步调用 —— 事件循环被占住，期间平台**不响应任何请求**。
本轮扫出并修掉 **6 处**（同一族）：唤醒前自检里的 `time.sleep` 轮询、桥测试端点里的同步 PowerShell 扫描、
探测工具的两处 `subprocess.check_output`、**同步 `urlopen` 逐个探端口**（最长的一处，实测卡平台 8.9s）、
`auto-connect` 里 `time.sleep(2.0)` 等桥存活。

**修法（两条纪律）**：
- 会等的活（子进程 / 同步网络 / 删目录）⇒ `await asyncio.to_thread(<函数>, ...)`；
- 纯等待 ⇒ `await asyncio.sleep(...)`（**绝不用 `time.sleep`**）。

**验证（修前 → 修后）**：`probe-register` 扫描仍要 12.6s，但期间 `/api/status` 最慢
**8.89s → 0.053s**、采样 207 次 0 失败 ⇒ **平台不再假死**。

**★沉淀成守卫**：`tests/test_async_no_blocking.py` —— **AST 扫全仓**，
`async def` 里不许**直接调用**会等的同步 API；并**自带"有牙"测试**（故意写反例必须报）。
守卫本身也修过两次盲区：① 漏**别名导入**；② 漏**同步网络 I/O**。

## 九 编码三条（中文 Windows 实测会咬人）

1. **父进程按 UTF-8 解码，就必须给子进程设 `PYTHONIOENCODING=utf-8`**
   —— 否则子进程用 GBK 打印，中文全变 `\ufffd`，判据文本被毁；
   **"时红时绿"最危险**：父进程环境里碰巧有这个变量时测试会全绿，真 bug 被当偶发糊过去。
2. **`.cmd` 包装脚本必须纯 ASCII、无 BOM** —— 带 BOM 时 cmd 会把 `@echo off` 当命令、
   把中文注释**当命令执行**。
3. **`.cmd` 不能直接当 trigger**：`Popen(trigger, shell=True)` 在 Windows 不解析 `.cmd`
   ⇒ 要写 `cmd.exe /c "<wrapper>"`。

## 十 治理教训（写给以后的自己）

- **凡是要写进指引的东西，必须先真跑一遍。** 至少三次"我差点又给出一条走不通的指引"：
  探测端口、空命令、「`out_dir` 填你自己的目录」（实测 400）。
- **改了界面文案，必须同改前端验收断言** —— 否则验收直接红（多处这么红的）。
- **扫源码的判据必须先剥注释** —— 有三次判据被自己写的注释打中。
- **"没被调用过"不等于"没问题"**；**"记在测试里（xfail）"不等于"被修掉"**。
- ★**平台"卡住"要先怀疑"事件循环被占住"** —— 症状（超时 / 不收连接 / 自动重启）与原因相距太远。
- ★**守卫自己也要有牙**：每条判据都要"故意写反例证明它抓得住"，否则就是"空转通过"。
- ★**文档不许比代码先说话**：本轮又抓到一次 —— 文档写着"桥脚本自带单实例锁"，
  而**用户实际跑的那只桥（模板渲染件）没有锁**。改完代码要回头核**文档说的那只**是不是同一个东西。
- ★**"同族没改干净"是本病的高发形态**：`/bridge-test` 改了、`/bridge-verify` 忘了；
  `examples/` 加了锁、模板忘了 ⇒ **凡改口径，先列全同族点位**（规则 20 的落地动作）。
- ★**验收工具自己也要被验收**：本轮前端验收汇总在"只有 1 条失败"时**报成全过并 exit 0**
  （PS 5.1 单对象 `.Count` 为 `$null`）⇒ 一次假绿**掩盖**了另一处真失败（fe24 断言按旧按钮文案选元素、
  文案改了它没改）。**两条都修了**。推论：凡是"汇总 / 计数 / 判定"的代码，都要问一句
  **"它算不出来的时候会显示成什么？"** —— 显示成"通过"就是最坏的设计。
- ★**"发布成功"要按"公开仓库能不能独立跑"来判，不能按"脚本报 done"来判**：
  本轮实测公开仓库里裸跑 pytest 有 **13 条 `RuntimeError: There is no current event loop`** ——
  根因是发布脚本**从来不同步根 `tests/`**（只同步 `agent_community/` + 根文档 + `design-docs/`），
  dev 在 2026-10-02 就把那三个模块改成 `asyncio.run` 了，改动**一步都没出去**。
  ⇒ 已把 `tests/` 纳入发布（**copy-only，不删 oss 侧历史脚本**），并实测 oss 侧 pytest
  **1330 条 / 0 failed**（6 条 skip 是"依赖 dev-only 文件"的守卫，属预期）。
  **凡"对外表达"的同步面，漏一个目录就等于漏一条口径。**
