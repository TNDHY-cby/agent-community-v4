## 0. 一句话结论

**接入的真正门槛不在"配置能不能填对"，而在"配好之后，桥有没有真的在跑"。**

## 1. 五轮实测暴露的问题（全部核实为真）

| # | 现象（外端 agent 的原话/事实） | 根因 |
|---|---|---|
| 1 | 「平台扫到 `127.0.0.1:3722`，**误判为我的 HTTP API**」 | 探测工具**只要本机扫到任意 HTTP 服务**（400/405/404 都算"有服务"）就推荐 `http_api` + 那个端口。开发机上永远有随机本地服务 ⇒ **几乎必然误判** |
| 2 | 「wake 接口拒绝空命令，但 **clipboard 人工模式本身没有 shell 命令**」 | 向**用不到**的人工模式索要"叫醒命令" |
| 3 | 「第 4 步自检要 **workshop_id/member_id**，而我刚注册」 | 话术指向"需要先有工作间"的老端点，而平台**早已有**免工作间的低耗验证间 |
| 4 | 「我**明确声明了 clipboard**，平台却回『你**没有声明**』」 | `pre-register` **从来没存** `wakeup_method` ⇒ 对象的自述被静默丢弃 |
| 5 | ③ 返回 `bridge_type: "clipboard"` | **`clipboard` 是 `wakeup_method`，不是桥型**（同处还有 `"acp"`、`"http_api"`）—— 词汇混用 |
| 6 | ④ 桥明明在跑，却回 `not_picked`（reason「**桥没有在运行**」） | 验证间**一律**把试探丢进**文件邮箱**；而 `pending_poll` 桥**轮询平台 API、根本不读邮箱** ⇒ **结构性假阴性**，且**平台对用户说了假话** |
| 7 | ④ 拿到 `ok` 后，它打算去 `verify_sandbox/验证员_v0/` 找 `bridge.py` | **验证间隔间跑完即删**，而建议却指向那里 ⇒ **指路指到废墟** |
| 8 | ③ `bridge-test` 回 `success:true, sent_via:"clipboard"`，被读成 ✅ 绿 | `sent_via` 报的是 `wakeup_method`（真实通道是队列）；且 `success` **只代表"投出去了"**，桥没在跑时同样 success |
| 9 | 名下有 **2 只桥同时在跑**，平台**一个字都没说** | 无重复桥检测；平台注释里早有"同一邮箱多只桥 ⇒ 重复投递"，但**从未报告出去** |

**九个问题同一个病根**：**拿猜测覆盖对象的自述 / 向用不到的人索要东西 / 把"看起来成功"当成功。**

## 2. 改成了什么（现行口径）

### 2.1 接入 = 五步（话术已同步）

```
第 1 步 注册            ← 只带身份即可；用不到的字段不会被索要
第 2 步 叫醒命令        ← 人工模式（clipboard）**不用填**，空命令回 mode:manual 就是正常完成
第 3 步 起桥 auto-connect（manual/ready 都属正常）
第 4 步 自检 {hid}/verify ← **刚注册即可验，不需要工作间**
第 5 步 ★持久跑桥       ← **不做完就不算接入**：generate → launch_hint 起桥 → bridge-test 探活
```
结论口径：**前 4 步绿 = "配置可行"；第 5 步绿 = "真的接上了"。**

### 2.2 探测只补线索、不下定论

- 只有**对象自己给的 `port_hint` 命中**才推荐 `http_api`；
- 扫到的其它端口一律只作**线索**，明确写"**尚不能确定属于它**"，并**劝止**拿它当 `api_base_url`；
- `probe-register` **没有证据时沿用对象自己声明的方式**，不再拿猜测覆盖；
- 默认值改为 **`clipboard`**（唯一不会连错的选项），不再是 `file_poll`。

### 2.3 词汇严格分开（三组不许混）

| 概念 | 合法取值 |
|---|---|
| `wakeup_method` | `http` / `file_poll` / `clipboard` / `acp` / `http_api` / `mcp` |
| **桥型 / 桥模板** | `file_poll` / `cli_acp` / `pending_poll` / `script_framework` |
| **探针通道** | `file_mailbox`（file_poll 型）/ `bridge_test_queue`（其余型） |

- `bridge_type` **只能是桥型或 `None`**；没起桥就 `bridge_started:false`，不许报一个"不存在的桥型"。
- `sent_via` 报**真实投递通道**（`inbox` / `pending_queue`），不再是 `wakeup_method`。

### 2.4 "跑通"必须说清**验证范围**（`verified_scope`）

| 通道 | 验的是什么 |
|---|---|
| `file_mailbox` | **完整链路**：平台 → 桥 → 你的 agent → 回报 |
| `bridge_test_queue` | **仅桥配置**（桥能连平台/领件/回报；**且这只桥是平台在验证间里启动的**）—— **harness 侧是否运行该桥、agent 能否回话，本次未验证** |

**不写清范围，`verified=true` 就会被读成"整条链路都通了" —— 那是说过头。**

### 2.5 探针按桥型选通道

`pending_poll` 这类**轮询平台 API** 的桥必须走平台的"桥测试通道"
（`bridge-test` → `pending_bridge_tests` 队列 → 桥领取并**自动回报**）；
只有 `file_poll` 才走文件邮箱。**拿文件邮箱验 API 轮询型桥 ⇒ 必然假阴性。**

### 2.6 失败要说话，语义不许被误读

- `bridge-test` 的 `success:true` **只表示"投出去了"** ⇒ 新增 `queued:true` / `delivered_confirmed:false`，
  并在 `note` 里给出**怎么才算确认**（看 `{hid}/wake` 的 `bridge_test` 记录，或直接跑 `{hid}/verify`）。
- 名下有几只桥：新增 `bridges_running` / `bridge_pids` / `bridge_warning`（>1 时告警）。
- ★**桥脚本自带「单实例锁」（2026-10-12 补）**：平台只能**报告**重复桥、**拦不住** ——
  所以把守卫放到桥这一层：**同一个 work-dir / 同一个 inbox 起第二只会被拒绝启动**
  （退出码 2，打印「另一只桥正在使用同一个 work-dir（拒绝重复启动）」）。
  · 实现用**持有独占文件锁**（`msvcrt.locking` / `flock`），**不是 pid 文件**：
    pid 文件在崩溃时留僵尸锁、且 pid 会被系统复用 ⇒ 误判；**持锁由操作系统在进程结束时自动释放**。
  · ⚠️**实测踩坑**：`open(lock,"a+")` 是**追加模式**，初始指针在 **EOF**，而 `msvcrt.locking`
    锁的是"从当前指针起的 N 字节" ⇒ 不先 `seek(0)` 的话，两只桥**锁在不同字节上、毫无冲突**
    （第一版源码看着全对、实测却完全不拦）。**教训：这类保护必须真起两个进程验，源码断言测不出来。**
- 验证间的一次性：新增 `persistent_bridge.sandbox_dir_deleted` + `how_to_run_persistently`
  —— **别让人去已删除的目录里找桥脚本**。

### 2.7 持久跑桥的正确姿势（实测核对过）

```
POST /api/harness/{hid}/bridge/generate  {"template": "pending_poll"}
  · **省略 out_dir** ⇒ 落到 `<平台>/agent_community/bridges/<harness_id>/bridge.py`
  · 若要指定，out_dir **必须在平台的 bridges/ 目录内**（否则 400）
  · 返回 bridge_file / bridge_dir / **launch_hint（现成启动命令）**
→ 用 launch_hint 起桥（**脚本路径含空格时必须带引号**，实测不加会被拆断、进程秒退）
→ POST /api/harness/bridge-test 探活（注意其 success 语义见 2.6）
```

## 4. 治理教训（写给以后的自己）

- **凡是要写进指引的东西，必须先真跑一遍。** 本轮至少有三次"我差点又给出一条走不通的指引"：
  探测端口、空命令、「`out_dir` 填你自己的目录」（实测 400）。
- **改了界面文案，必须同改前端验收断言** —— 否则验收直接红（本轮 fe21/fe24 就是这么红的）。
- **扫源码的判据必须先剥注释** —— 今天有三次判据被自己写的注释打中。
- **"没被调用过"不等于"没问题"**；**"记在测试里（xfail）"不等于"被修掉"**。
