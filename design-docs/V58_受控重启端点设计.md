# V58 · 受控重启端点 `POST /api/admin/restart` 设计（2026-10-19）

> 老板 2026-10-19：「① 受控重启端点要不要做…**这个最优解就行，我看不懂**」
> ⇒ 本稿即拍板稿：**做**，但按下面四条闸门做（宁可拒绝，不许把平台弄成永久宕机）。

## 1. 为什么做

现在"重启平台"只有两条路：
- `python tools/update.py --apply --restart`（命令行，用户得会开终端）；
- 手工杀进程等看门狗拉回（更不友好）。

界面上的"更新完要重启"没有可点的入口 ⇒ 用户视角断在这里（产品化准则③「每步对应界面上的用户动作」）。

## 2. 四条闸门（缺一不可，逐条**如实拒绝**并说清怎么改）

| # | 闸门 | 拒绝时 |
|---|---|---|
| ① | **来源必须是本机**（复用 `origin_allowed()`：无 Origin 的走命令行也算本机） | `403` 说出实际来源 |
| ② | 配了 `AC4_SHUTDOWN_PIN` ⇒ 必须带对 `X-Shutdown-Pin` | `403` 提示去哪配 |
| ③ | **必须真有看门狗**（复用 `watchdog_pids()`；按实例端口认，不按关键字盲认） | `409` + `how_to_fix`：**没有看门狗时重启＝永久宕机**，先起 `python tools/watchdog.py --daemon` |
| ④ | body 必须显式 `{"confirm": true}` | `400`：重启会短暂中断所有在跑的工作间，必须显式确认 |

## 3. 行为（**先回响应，再退出**）

```
POST /api/admin/restart  {"confirm": true}
 → 200 {"success":true,"restart_scheduled":true,"eta_seconds":1,
         "watchdog_pids":[...],"how":"看门狗将在 ≤30s 内按原命令行重启（token 不变）"}
 → 0.8s 后本进程 os._exit(0)（复用 `_schedule_self_exit()`，与 V27 关停同一处实现）
 → 看门狗按**原命令行**（含 `--token`）重生 ⇒ 鉴权口径不变
```

**为什么不自己 exec 重启**：自己 exec 会丢"被谁拉起/带什么参数"，还可能与看门狗打架（两个进程抢端口）。
把"拉回来"这件事交给**唯一的那只看门狗**，是既有架构里最稳的路径。

## 4. 明确不做

- **不做**"重启后自动恢复在跑的工作间"：那是另一个能力（且工作间状态已落盘，重启后按原样回来，不需要假装"续跑"）。
- **不做**"重启历史里的任务"。
- **不做**远程（非本机）重启：远端重启＝给别人一个"打一下就宕机"的按钮。

## 5. 判据（`tools/admin_restart_check.py`，真跑）

| 格 | 判据 |
|---|---|
| ① | **没有看门狗时被拒**（409）**且服务仍活着**（再打 `/api/status` 仍 200）——最要紧的一条：不许把平台弄死 |
| ② | 缺 `confirm` ⇒ 400（不静默执行） |
| ③ | 非本机来源（`Origin: https://evil.example`）⇒ 403 |
| ④ | 有看门狗时 ⇒ 200 `restart_scheduled`，且服务在 ≤60s 内**自己回来**（端口重新可连、`/api/status` 200、版本不变） |
| ⑤ | 审计有 `system.restart` |
