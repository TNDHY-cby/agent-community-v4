# V61 · 公司间合作：frp 内网穿透 + 数据目录隔离（2026-10-20，老板方向：「可以先用 frpc 穿透之类的」）

> 前情：`V21_双实例公司间合作演示与数据目录隔离设计.md`（2026-10-07）当时的结论是
> 「放弃"朋友电脑 + Tailscale + 手工交 token"这条外部依赖路径，改用自持双实例」。
> 老板 2026-10-20 给了新方向：**公司间合作可以先用 frp（frpc）穿透之类的**。
> 本稿把 V21 的**自持双实例**与 **frp 穿透**合成一条能落地的路，并明确"哪些是本地能自证的、哪些必须等真服务器"。

## 1. 要办成的事（用户视角）

两个**各自独立部署**的合作社（可以在一台机器的两个目录，也可以是两台机器）之间：
**A 公司把活派给 B 公司 → B 公司的 agent 真干 → 结果回到 A 公司并留痕**。

- A 侧看到的：一条外部任务、一个外部公司、一条回执；
- B 侧看到的：一条来自"外部公司"的入站任务、自己派给员工的活、回报；
- **没有任何一方需要改代码**：换地址、换端口、换目录都只是配置。

## 2. 为什么是 frp（以及它解决什么、不解决什么）

| 问题 | frp 能解决吗 |
|---|---|
| B 公司在 NAT/路由器后面，A 访问不到它 | ✅ **能**：B 侧跑 `frpc` 主动连公网 `frps`，把 B 的本地端口映射出去，A 访问 `frps` 的映射端口 |
| 地址会变（家里宽带换 IP） | ✅ 能：A 只需要记 frps 的固定地址 + 映射端口 |
| 谁能访问（鉴权） | ❌ **不解决**：frp 只是通道。**必须**由平台自己带 token + 端点白名单 + 来源白名单 |
| 数据落在哪 | ❌ 不解决：靠 `AC_DATA_DIR` 隔离（V21 已有） |

⇒ **frp 是"管道"，安全与数据隔离仍是平台的责任**（本稿 §4 三件套）。

## 3. 三层结构（由内到外）

```
┌──────────── A 公司（老板机，18920）────────────┐
│ 工作间 / 员工 / 任务树                          │
│   └── 外部公司「B 公司」＝一个 a2a 对端          │
│        （base_url = 穿透后的地址）              │
└───────────────┬───────────────────────────────┘
                │  A2A 协议（已有 a2a_client.py / a2a_server.py）
                │  Authorization: Bearer <对端 token>
┌───────────────┴───────────────────────────────┐
│            frps（公网，老板提供）               │
│    A 侧：不用装（A 直连 frps 的映射端口）        │
│    B 侧：frpc 把 127.0.0.1:18930 → frps:19030  │
└───────────────┬───────────────────────────────┘
┌───────────────┴── B 公司（另一台机 / 另一目录）─┐
│ AC_PORT=18930  AC_DATA_DIR=<B 自己的数据目录>   │
│   └── a2a 入站端点 + 自己的员工/会议/任务树      │
└───────────────────────────────────────────────┘
```

## 4. 安全三件套（**不做这三件就不许暴露**）

1. **token 必填**：`/api/a2a/*` 与入站端点必须校验 `Authorization: Bearer <token>`
   （沿用 `harness` 的 agent_token 机制；对端 token 只存 sha256 指纹，明文不落盘、不入日志）。
2. **端点白名单（对外模式）**：`AC_EXPOSED=1` 时，**只开**这几类：
   - `POST /api/a2a/*`（收任务/回执）
   - `GET  /api/status`（只给健康位，`ai` 段可关）
   其余（`/api/config`、`/api/admin/*`、`/api/logs/*`、静态页、管理类写操作）**一律 404/403**，
   且**拒绝来自非本机来源的写请求**（复用 `origin_allowed()` + token 校验）。
3. **来源白名单**：`AC_EXPOSED_ALLOW=1.2.3.4,5.6.7.8`（可留空＝不限制但不推荐）；
   命中不了就 403 并**在审计里记下真实来源**（不静默）。

## 5. 数据目录隔离（V21 原有结论，保留）

- 每个实例 `AC_DATA_DIR` **各自独立**（不许共用：`workshops.json`、`audit.json`、桥目录都会互相踩）；
- 端口各自独立（`AC_PORT`）；
- **同一台机器跑两个实例**是允许的（这正是 P1 的验收方式），只要上面两条做到。

## 6. 实施分期（**P1/P2 本轮做，P3 等服务器**）

| 期 | 内容 | 要不要外部资源 | 判据 |
|---|---|---|---|
| **P1** | **单机双实例**：B 用独立 `AC_DATA_DIR` + 独立端口起；A 通过 a2a 投任务 → B 收到并回执 | 不要 | `tools/cross_company_check.py`：A→B 真投、B 真收、回执回到 A、**两侧数据目录互不污染**、token 错 ⇒ 401 |
| **P2** | **frpc 配置生成器** `tools/gen_frpc.py`：输入 frps 地址/端口/token，生成 B 侧 frpc 配置文件（TOML）与启动命令 | 不要（只生成配置） | 同一件判据：生成物字段正确、**文件权限收紧**、**不打印 token 明文**、换地址不提代码 |
| **P3** | **真公网验收**：B 起 frpc，A 用穿透地址投任务 | **要**：frps 地址 + 端口 + token（老板提供） | P1 判据把 base_url 换成穿透地址，其余不变 |

> **为什么 P3 要等**：frps 是"只有老板知道的东西"（地址/端口/token）。P1/P2 完全本地可验证，
> 先把"公司间协作的逻辑 + 配置生成"做实；拿到 frps 之后只是**换一个 base_url**（不改一行代码＝产品化准则）。

## 7. 配置项（登记进 `env_spec`，全部可覆盖）

| 变量 | 用途 | 默认 |
|---|---|---|
| `AC_EXPOSED` | 对外模式（开端点白名单） | `0` |
| `AC_EXPOSED_ALLOW` | 允许的对端来源 IP（逗号分隔，空＝不限） | 空 |
| `AC_A2A_PEER_TOKEN` | 作为**被访问方**时校验的对端 token | 空（对外模式下必填，缺则启动失败并提示） |
| `AC_FRP_SERVER_ADDR` / `AC_FRP_SERVER_PORT` / `AC_FRP_TOKEN` | 生成 frpc 配置用 | 空 |
| `AC_FRP_REMOTE_PORT` | frps 上映射出去的端口 | 空 |

## 8. 明确不做的

- 不做"自动发现对端"（不可靠，且会变成新依赖）；
- 不做把整个实例（含管理页）暴露到公网——**只开 a2a 入站**；
- 不在平台里内置 frps 服务端（那是服务器侧，且涉及公网运维）。
