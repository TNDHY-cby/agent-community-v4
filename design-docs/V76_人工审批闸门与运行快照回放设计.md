## 1. 为什么先做这两件（而不是先做画布）

画布本身是前端；但它要的**三样东西全在后端**，现在都没有：

| 画布要什么 | 现在有吗 | 本设计给什么 |
|---|---|---|
| 流程能**停下来等人点确认** | ❌ 任务只有 created→broadcasting→delegating→completed 等，**没有"等人批"的状态** | `waiting_approval` 状态 + 审批端点（批准继续 / 打回重做 / 终止） |
| 每次运行留一份**不可变执行记录**，能回放证据 | ⚠️ 有 `evidence`（证据链 V55）但**不是整轮快照**，也没回放 | `run_snapshot`：按任务冻结一份"这一轮发生了什么"，可只读回放 |
| 流程可**导入导出**（画布存/取） | ❌ | `workflow.yaml/json` 的读写端点（只用现有字段，不发明 DSL） |

⇒ 先做这三件，前端画布才有东西可画。**不做 UI，不做拖拽，不做节点渲染**。

## 2. 审批闸门（前半）

### 2.1 状态

`TaskStatus` 增加 `WAITING_APPROVAL = "waiting_approval"`。

**进入条件**（只在两处，别扩散）：
1. 任务被派给成员、**回执已验证**（`verify` 通过）之后，若该任务/其工作间设了 `approval_required` ⇒ 进 `waiting_approval`；
2. 工作间 `review` 阶段收集完所有成员回报 ⇒ 若设了 `approval_required` ⇒ 进 `waiting_approval`。

**退出条件**（三选一，都留痕）：
- `approve` 继续 → 回到原状态（记录里记住 `resume_to`）；
- `reject` 打回 → 回 `delegating` 并附**必填**理由（理由为空直接 400）；
- `cancel` 终止 → `cancelled`。

### 2.2 端点（3 个）

```
GET  /api/tasks/{task_id}/approval          当前待批什么（没有就说没有，不许 200 空壳）
POST /api/tasks/{task_id}/approval           {decision: approve|reject|cancel, note: "…", by: "…"}
POST /api/workshops/{wid}/approval-policy    {approval_required: true|false}  # 开/关这个工作间的闸门
```

- 默认 **关**（对齐"自动兜底默认关"）：不设就是旧行为，**不影响现有流程**；
- 非 `waiting_approval` 的任务上调用 → 400 并说清它现在是什么状态（不是 200 假成功）；
- `reject` 必须带 `note`，否则 400（**空理由不许打回**）；
- 每次决策写审计 + 写进 `run_snapshot`（见 §3）。

## 3. 运行快照（后半）

### 3.1 结构（`tasks[task_id].snapshots: list`，每份不可变）

```json
{"snap_id": "sn-…", "at": "…", "kind": "dispatch|reply|approval|complete|fail",
 "task_id": "…", "workshop_id": "…", "actor": "user|harness:…|patrol",
 "summary": "一句人话", "detail": {…}, "evidence_ref": "…"}
```

- **只追加**，不改写（回放才有意义）；每任务上限 `AC_SNAPSHOT_MAX`（默认 200，超了丢最旧并**记一条"已截断"**，不静默丢）。
- 落点：随 `save_state()` 一起持久化（与任务同源，不另开文件）。

### 3.2 端点（2 个）

```
GET /api/tasks/{task_id}/snapshots?limit=50      按时间正序回放（只读）
GET /api/tasks/{task_id}/snapshot?snap_id=…      单条详情（只读）
```

### 3.3 流程定义导入导出（画布的存/取，2 个端点）

```
GET  /api/workshops/{wid}/workflow        导出：{name, nodes:[{node_id,label,kind,status,parent_id}], edges:[{from,to,kind}]}
POST /api/workshops/{wid}/workflow        导入：同结构；只接受**已有字段**，未知字段 → 400 并列出
```

- **导出用现有 `task_tree`**（V75 真值表里"任务树+资源库"已实现），edges 由 `parent_id` 推出来；
- **导入只允许新增节点**，不删除既有节点（防误毁）；未知 kind → 400 说清支持的 kind。

## 4. 判据（两个半程各自一条命令）

**前半** `agent_community/tests/test_approval_gate.py`（真跑 HTTP）：
① 默认关：不设策略时任务**不会**进 `waiting_approval`（旧行为不变）；
② 开了闸门：派活回执验证后进 `waiting_approval`，`GET …/approval` 给出"待批什么"；
③ `approve` → 回到 `resume_to` 记录的状态；
④ `reject` 无 `note` → 400；带 `note` → 回 `delegating` 且 snapshot 里有一条 `approval`；
⑤ 非待批任务上调用 → 400 + 当前状态原话；
⑥ `cancel` → `cancelled`，且审计有记录。

**后半** `agent_community/tests/test_run_snapshot.py`：
① 派活/回执/审批/完成各写一条快照，顺序正确、`kind` 正确；
② 快照**只追加**（同一个 snap_id 不可改：给它再写一次必须新增而不是覆盖）；
③ 超过上限时丢最旧 + 留一条 `truncated` 记录（不静默）；
④ 导出 workflow 的 nodes/edges 与 `task_tree` 一致；导入新增节点成功、未知字段/know 400 并说清；
⑤ 回放端点返回时间正序、`limit` 生效。

## 5. 明确不做

- 不做画布 UI、不做拖拽、不做节点样式（前端）；
- 不做自动审批（人工闸门就是人工）；
- 不引入 YAML 依赖：导入导出用 **JSON**（`workflow.json`），前端要 YAML 自己转；
- 不改现有状态机的其它转换（只**加**一个状态与三条出口）。

## 6. 风险与回退

| 风险 | 处理 |
|---|---|
| 加状态导致别处 `if status == …` 漏判 | 前半做完立刻跑全量；漏判处显式修（不是"应该没事"） |
| 快照让 state 文件变大 | 每任务上限 + 截断留痕；实测一次体积 |
| 导入 workflow 覆盖用户已有树 | 只允许新增，不删改 |
