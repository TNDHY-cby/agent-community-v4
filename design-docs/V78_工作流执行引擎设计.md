# V78 · 工作流执行引擎（把 V76 定义 + V77 预算闸接成"真能跑"）

> 2026-10-22。前置：V76（workflow 定义/快照/审批闸门）、V77（预算与超时闸）。
> 目标：让画布上画的东西**能被平台按顺序真派出去**，并且花不超、卡得住、失败可见。
> 只做后端；画布 UI 归前端。

## 1. 数据从哪来（不发明新格式）

- 节点/边 = 工作间 `task_tree`（`node_id / label / kind / status / parent_id`），V76 已能导入导出；
- 预算 = `run_budget.check()`（V77）；审批 = `approval.maybe_gate()`（V76）；
- 快照 = `run_snapshot.append()`（V76）——每次推进都留一条 `dispatch`。

## 2. 执行语义（就三条，别扩散）

1. **拓扑**：父节点没完成 ⇒ 子节点**不可跑**（父子关系即依赖）；同层按 `task_tree` 里的顺序，稳定可复现。
2. **一次推进一步**（幂等）：`POST /api/workshops/{wid}/workflow/run` 每次只推进**一个**可跑节点；
   重复调用不会重复派同一个节点（节点 status 一旦是 `running/done` 就跳过）。
3. **收口**：节点跑完（回执 ok）⇒ `done`；失败 ⇒ 先 `retry` 一次（`retry_count`），再失败 ⇒ `blocked`
   并在返回里说清"卡在哪个节点、为什么"。整棵树没有可跑节点且有 `blocked` ⇒ 整体 `blocked`。

节点状态（在 `task_tree[].status` 里，**复用字符串**，不改模型）：
`planned` → `running` → `done` / `blocked`；`approval` 型节点停在 `waiting_approval`（借 V76 的任务闸门）。

## 3. 端点（3 个）

```
POST /api/workshops/{wid}/workflow/run        推进一步（返回 {advanced, node_id, state, why})
GET  /api/workshops/{wid}/workflow/run        看执行状态（每个节点状态 + 卡在哪 + 下一步能跑什么）
POST /api/workshops/{wid}/workflow/reset      把 blocked/running 复位（人工干预后重跑，留痕）
```

- 预算超了 ⇒ 409 + `run_budget` 的原话；
- 需要审批的节点 ⇒ 进 `waiting_approval` 并**不再推进**（直到 V76 的审批端点放行）；
- 全部完成 ⇒ `state=done`；没节点 ⇒ 400 说清"先导入流程"。

## 4. 判据 `agent_community/tests/test_workflow_engine.py`

① 拓扑：父未完成 ⇒ 子不可跑；父 done ⇒ 子可跑；
② 幂等：连续两次 run 只派一个节点（第二次返回 `advanced=false` + 原因）；
③ 失败重试一次后 `blocked`，返回里带节点与原因；
④ 预算超 → 409 且不推进；
⑤ 审批型节点 → `waiting_approval`，且未被当作 done；
⑥ reset 把 blocked 复位为 planned 并留痕。

## 5. 不做

- 不做并行分支/条件表达式（画布要就再加，不预先发明 DSL）；
- 不做前端渲染；不自动重试无限次（一次），不做定时轮询（由调用方点）。
