# V82 · 单实例守卫与注册可信性

> 2026-10-22。来源：同赛道借鉴清单 §一.1/§一.2/§二.4（思路，不搬代码）。
> 老板 2026-10-22：「做，值得做的也做」。

## 1. 为什么先做这三件

1. **双写风险是真的**：看门狗会把服务拉起来，人手也可能再 `cli start` 一次 —— 两个进程写同一个
   `AC_DATA_DIR` 会互相覆盖 `tasks.json` / `audit.json`（本项目历史上真丢过数据）。
2. **"注册成功 ≠ 真能用"**：现在只有 `bridge_selfcheck`（桥配置）+ `reply_probe`（真回话），
   缺一层**静态**校验（字段/URL/长度），错误要能在注册那一刻就报出来。
3. **名册会烂**：长期不用的 agent 不清理，界面上一堆"在线但从不回话"。

## 2. 单实例守卫（租约）

- 锁：`<AC_DATA_DIR>/run/platform.lock`，**操作系统文件锁**（不是"写个 pid 文件"）——
  **进程退出内核自动释放**，不会留下死锁；续租由操作系统替我们做（进程活着锁就在）。
- 拿不到锁时两种行为，**显式配置**（不隐式降级）：

| `AC_SINGLETON_UNAVAILABLE` | 行为 | 适合 |
|---|---|---|
| `fail_closed`（默认） | **拒绝启动**，打印"另一个实例正持有数据目录 X，PID/PID 时间"，退出码 3 | 生产/单机 |
| `degraded` | 启动但**明确标记降级**（`/api/status` 里 `singleton.ok=false`），并在日志里警告 | 只想看看界面 |

- 判据：第二个持有者拿不到锁；进程退出后锁自动可用；`degraded` 下能起且状态里说明原因。

## 3. 卡片 schema 校验（静态一致性）

分项校验（每条给 `field` + `why`，不合并成一句"卡片不合法"）：
`harness_name` 必填且 ≤64；`harness_id` 合法字符；`wakeup_method` 在允许集合内；
`wakeup_dir`/`base_url` 若是 URL 必须 `http(s)`；`capabilities` 必须是字符串数组且每项 ≤32。

输出：`{"conformance": "passed|failed", "conformance_errors": [...], "checked_at": ...}`。
**与 `reply_probe` 分开**：静态过了不等于能回话，能回话也不代表字段齐全。

## 4. 名册生命周期（纯函数，先立口径）

| 规则 | 默认值 | 动作 |
|---|---|---|
| 连续 N 天健康检查全失败 | 7 天 | **隐藏**（不删除，可申诉恢复） |
| 健康明细保留 | 90 天 | 清理明细（保留汇总） |
| 死号检查周期 | 48 个巡检周期 | 查一次不再出现的 agent |

本版只提供**纯函数 + 判据**，不接线（接线要健康历史数据模型，下一版做）。

## 5. 不做

- 不做 Redis 后端（单机项目，filelock 够用；要集群再设计）；
- 不搬对方代码，全部自己写（`THIRD_PARTY_NOTICES.md` 仍是空表）。
