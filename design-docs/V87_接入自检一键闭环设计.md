## 1. 要解决的问题（用户视角，不是技术视角）

现在判断"这个 agent 到底接上没"，用户要**自己拼四段 + 两次点击**：

| 用户看到的零散部件 | 用户实际想问的 |
|---|---|
| 卡片声明合规 / 配置能连 / 桥在跑 / agent 能回话（四段分开显示，V82） | 「**我现在到底通没通？**」 |
| 回话探针按钮（V74，真发一条消息） | 「**要不要发？发了会不会打扰它？**」 |
| 名册健康列（V85，连续失败天数） | 「**它以前是不是就不行？**」 |
| 凭据体检（V86，弱值/明文） | 「**是不是我 key 填错了？**」 |

四段分开显示是**对的**（不许一段总绿盖住其余），但它把"综合判断"这件苦活留给了用户。
⇒ 缺的是**一句结论 + 一条有序的下一步**，而不是更多面板。

## 2. 设计：一个端点，一句话 + 一串步骤

```
POST /api/harness/{hid}/selfcheck      body: {"probe": false}   # 默认不真发消息
→ {
    "verdict": "ok" | "blocked" | "stale" | "unverified",
    "one_line": "能接上，最近一次回话是 3 小时前（还在 24 小时有效期内）",
    "steps": [
      {"id":"credential", "title":"凭据",   "state":"ok",      "why":"", "next":""},
      {"id":"card",       "title":"声明合规","state":"ok",     "why":"", "next":""},
      {"id":"config",     "title":"配置能连","state":"ok",      "why":"", "next":""},
      {"id":"running",    "title":"桥在跑",  "state":"ok",      "why":"", "next":""},
      {"id":"reply",      "title":"真回话",  "state":"stale",   "why":"上次回话 3.0 小时前，超过 24 小时即视为未核验", "next":"点「验一次回话」发一条极小消息"}
    ],
    "next_step": "点「验一次回话」（会真发一条消息给这个 agent，内容极小）",
    "checked_at": "..."
  }
```

**判据式定义（不许含糊）**
- `verdict` 只由 `steps` 派生，**一处真相**：
  - 有任一 `state == "blocked"` ⇒ `verdict = "blocked"`（取其 `next_step`）
  - 否则有任一 `stale` ⇒ `stale`
  - 否则全部 `ok` ⇒ `ok`
  - 全部 `unverified` ⇒ `unverified`（**缺数据不许显示成通过**）
- `next_step` 永远指向**最靠前**那个非 ok 的步骤（用户不会一次改五件事）。

## 3. 每一步复用什么（**不新增判断逻辑 = 一处真相**）

| 步骤 | 数据来源（既有实现） |
|---|---|
| `credential` | `credentials.ledger_summary_light()`：有弱值/桥产物明文 ⇒ `blocked` + 「先修 key」 |
| `card` | `card_conformance`（V82）：逐字段错误原样带出 |
| `config` | `harness_capability` 的 `bridge_config` 段 |
| `running` | 同上的 `harness_running_bridge` 段 |
| `reply` | 同上 `agent_can_reply` 段（含 `stale` 判定，V81 的 24 小时窗口） |
| 历史 | `registry_health`：连续失败天数 ⇒ 在 `one_line` 里补一句「这个号过去 5 天全挂过」 |

**不重复实现任何探测**：本端点只做**聚合 + 排序 + 说人话**。

## 4. 三条纪律

1. **默认不打扰**：`probe` 默认 `false`；要真发消息必须显式传 `true`（界面按钮文案必须写清"会真发一条"）。
2. **不在轮询里跑**：状态端点（`/api/status`）**不调用**本端点；它是用户点一下才走的（同 V86 的 scan）。
3. **不进外部只读档**：会暴露这个 harness 的配置形态与失败细节 ⇒ 写进 `EXTERNAL_READONLY_DENY`。

## 5. 判据（全部真请求，`TestClient` + 真文件）

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | `verdict` 与 `steps` 一致 | 造 4 种组合（全 ok / 一个 blocked / 一个 stale / 全 unverified），逐一断言派生结果 |
| 2 | 缺数据不假绿 | 新注册、什么都没验过的 harness ⇒ `verdict="unverified"`，**不是** `ok` |
| 3 | `next_step` 指向最靠前的非 ok | blocked 在第 2 步且有 stale 在第 5 步 ⇒ `next_step` 必须是第 2 步的 |
| 4 | 默认不真发消息 | `probe=false` 时断言消息队列/探针记录**没有新增** |
| 5 | `probe=true` 会真发 | 真跑一次，`reply` 段从 `unverified` 变 `ok`/`failed`（真值，不mock） |
| 6 | 一律不返回明文 | 塞哨兵 key ⇒ 响应体里不许出现（复用 V86 判据） |
| 7 | 不进只读档 | 断言在 `EXTERNAL_READONLY_DENY`、不在白名单 |
| 8 | 性能 | 不传 `probe` 时本地只读聚合，**不许**发起任何网络请求（用假 harness 计时/打桩断言） |

## 6. 明确不做

- ❌ **不做一键修复**：平台不许替用户改桥/改 key（那是私人定制与越权），只给"怎么改"；
- ❌ 不做定时自检（要跑就跑一次，别在后台刷探针，会打扰外部 agent）；
- ❌ 不新造第五个"能力段"（四段是对外契约，本端点只是把它们**汇总**）。

## 7. 工作量与排期

| 段 | 内容 |
|---|---|
| 1 | `platform/harness_selfcheck.py`（纯聚合 + 派生规则）+ 单测（判据 1/2/3/8） |
| 2 | `routers/harness_selfcheck.py`（一个端点，`probe` 走既有探针）+ 只读档 deny |

约半个工作段；风险低（全是既有数据的聚合），**但依赖拍板**：要不要把"综合结论"这件事交给平台。

## 8. 实施记录（4.34.0，2026-10-22）

**落点**：`platform/harness_selfcheck.py`（纯聚合）+ `routers/harness_selfcheck.py`（一个 POST 端点）
+ `tests/test_harness_selfcheck.py`（8 条判据）。

实现时发现**两条设计稿没写清的事实**，按下面口径落地（不改本稿 §2~§5 的契约）：

1. **探针是异步的**：§2 例子里写「`reply` 段从 `unverified` 变 `ok`」，
   但实际 `reply_probe.start()` 只**发出**消息，回执要等 agent 回、
   由 `/api/harness/reply-probe-result` 记账 ⇒ **发出 ≠ 验过**。
   落地口径：`probe=true` 之后 `reply` 段仍为 `unverified`，`why` 写「探针已发出（probe_id=…），
   等它回执才算验过」。判据 `test_probe_sent_is_not_counted_as_verified` 钉住这条，
   **不许**因为"发出去了"就显示成通过。
2. **外部只读档靠 POST-only 天然挡住**，不需要进 `EXTERNAL_READONLY_DENY`：
   `_readonly_allows` 第一步就拒绝非 GET/HEAD；把 `/api/harness/` 整个塞进 DENY 会误伤
   本来允许的 `/capability`。判据 `test_selfcheck_is_post_only_so_readonly_cannot_reach_it`
   断言"路由没有 GET/HEAD + 不在只读后缀白名单"。

**顺带抓到的真实缺陷**（`b723994`）：`HarnessInfo.model_dump()` 默认不转 JSON，
`wakeup_method` 出来是枚举成员 ⇒ `card_conformance` 用 `str()` 一转变成
`'WakeupMethod.CLIPBOARD'`，导致「声明合规」对所有这类 harness **假红**。
已用 `_plain()`（取 `.value`）统一取值，三种入参（枚举 / dict / JSON 模式）得到同一结论。
⇒ 这也说明本功能的价值：**把分散的判断汇总之后，假红/假绿更容易被看见**。
