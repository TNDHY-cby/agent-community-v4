# V89 · 监控室连续画面流（零依赖 PNG 分帧）与帧率控制

> 状态：**已拍板（按老板 2026-10-23「重要核心功能直接落地」的授权）并已实施**
> 上游：`V88_监控室窗口画面墙设计.md`（老板 2026-10-22 拍板①：先做 PNG 快照墙，连续流下一版）
> 写域：后端（DSH）。前端要配合的地方见 §5。

## 0. 一句话

`GET /api/monitor/{id}/stream` 以前**恒 501**（"本版只做快照墙"）。这一版把它做成**真正的连续画面**，
但**不引入 Pillow**：用已有的标准库 PNG 编码器，走 `multipart/x-mixed-replace` 分帧推送，
浏览器 `<img src="…/stream">` 直接就是"活的画面"。

## 1. 为什么不是"等装了 Pillow 才做 MJPEG"

V88 的裁决是"有 Pillow 才有 MJPEG"。真去实现时发现这条路**产品上不成立**：

| 方案 | 代价 | 结论 |
|---|---|---|
| 等 Pillow 才给连续流 | Pillow 进 `requirements.txt` 就是给所有人加一个重依赖；不进则**绝大多数用户永远看不到连续画面** | 不行 |
| 自己写 JPEG 编码器 | 基线 JPEG（DCT/量化/霍夫曼）≈ 300+ 行，出错就是"花了屏" | 不划算 |
| **PNG 分帧走 multipart** | 0 依赖，复用 `png_encode`；体积比 JPEG 大，但 1–2 fps 的"看它动没动"完全够 | **采用** |

浏览器对 `multipart/x-mixed-replace` 的每一段按 `Content-Type` 解码 —— **PNG 段照样能连续渲染**
（这不是标准草案里的特例，是浏览器实现的既有行为；Chrome / Firefox / Edge 均可）。
所以对外口径写清楚：这是**连续画面流（PNG 分帧）**，不是严格意义的 MJPEG。**宁可小，不可大。**

## 2. 契约

```
GET /api/monitor/{harness_id}/stream?fps=2&max_w=320
  200  Content-Type: multipart/x-mixed-replace; boundary=acframe
       每段：
         --acframe\r\n
         Content-Type: image/png\r\n
         Content-Length: <n>\r\n
         X-Monitor-Method: printwindow\r\n
         X-Monitor-Seq: <第几帧>\r\n
         \r\n
         <PNG 字节>\r\n
  501  非 Windows（如实说：窗口抓取只支持 Windows）
  403  这个 agent 没开监控（先 POST /api/monitor/watched）
  404  开了监控但找不到窗口（给"怎么指定窗口"的下一步）
  409  能定位窗口但抓不到（例如 GPU 合成窗口）——**不 stream 一张黑图**
```

- **帧率**：默认取 `AC_MONITOR_FPS`（默认 1），单次请求 `?fps=` 可覆盖，**硬上限 10**（下限 0.2）——
  再高只会烧 CPU 且看不出来；
- **上限时长**：`AC_MONITOR_STREAM_MAX_SECONDS`（默认 600 秒）后**主动收尾**（浏览器会自己重连），
  防止一个僵尸连接把线程占一整天；
- **没人看就停**：连接关闭即停；`note_viewer()` / `auto_stop_idle()` 复用 V88 的"60 秒没人拉就停"；
- **黑图不推**：抓不到（`ok=False` 或纯黑）时**不发帧**，`Content-Type` 保持不变、静默重试，
  连续 5 次失败就**结束流**并在响应头写 `X-Monitor-Why`（宁可断，不给"黑屏但看起来在播"）。

## 3. 实现位置（一处真相）

| 层 | 文件 | 职责 |
|---|---|---|
| 抓帧/编码/节流 | `platform/monitor.py` | `stream_frames()`（**同步生成器**，可单测）+ `fps_of()` 夹紧 + `stream_max_seconds()` |
| 流式端点 | `routers/monitor.py` | `StreamingResponse`：把同步生成器包进 `to_thread`，检测断连 |
| 健康口径 | `platform/monitor.py::health()` | `stream_available: true` + `encoding: "png-frames"`；`jpeg_available` 只是"将来更省流量"的能力位 |

**为什么要一个"同步生成器"**：抓窗口是阻塞的（GDI + ctypes），塞进 async 循环会卡住整个事件循环。
把它做成普通生成器，路由层用 `asyncio.to_thread(next,gen)` 一帧一帧取——既真实可测，又不阻塞。

## 4. 判据（全部真跑）

| # | 判据 | 落点 |
|---|---|---|
| ① | 没开监控 ⇒ 403（不是 200 空流） | `tests/test_monitor_stream.py` |
| ② | 非 Windows ⇒ 501 且说清"只支持 Windows"，**不许谎称没装 Pillow** | 同上（平台分支） |
| ③ | `stream_frames()` 在桩抓帧下产出 ≥3 帧，每帧都是合法 PNG（`\x89PNG` 起头 + IHDR/IDAT/IEND） | 同上 |
| ④ | **帧率夹紧**：fps=100 被压到 10；实际间隔 ≥ 1/fps 的 80%（防止"写着 1fps 实际狂刷"） | 同上 |
| ⑤ | **黑图不推**：连续抓黑 ⇒ 不发帧并结束，`why` 说明原因 | 同上 |
| ⑥ | 有 `max_seconds` 上限（用极小值真跑，确保会自己停） | 同上 |
| ⑦ | 端点级：老 501 文案必须消失；能抓窗口时返回 `multipart/x-mixed-replace` 且首帧是 PNG | `tools/monitor_frame_check.py`（真服务 + 真窗口） |

## 5. 要转前端（ZCode）的三件事

1. 监控室里"放大"用 `<img src="/api/monitor/{id}/stream?max_w=0">` 即可**直接出活画面**，
   **不需要** JS 轮询 `frame`（轮询仍保留：断流时自动回落）；
2. 断流时（`onerror` / 5 秒没有新帧）显示一行"画面流已停（点一下重连）"，**不要**显示黑框；
3. 帧率别在前端写死：读 `GET /api/monitor/health` 的 `fps`，用户要更流畅再传 `?fps=`。

## 6. 不做的事（如实）

- **不做音频、不做录制、不做多路拼接**（V88 的边界不变：只做"看一眼"）；
- **不把画面发到任何外部地址**（V88 §6：`/api/monitor` 在只读档 DENY 里，公网拿不到）；
- **不假装是 MJPEG**：响应里不出现 `image/jpeg`，文档统一叫"连续画面流（PNG 分帧）"。
