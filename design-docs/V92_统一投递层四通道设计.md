# 设计稿 V92 · 统一投递层：四条通道，不是"只能浏览器"

> 状态：**已实施（2026-10-23）**。起因：老板看 V91 后追问「**只能浏览器吗**」。
> 上游：`V91`（CDP 浏览器级投递）；本稿把"投递"收敛成一个**按目标选路**的层。

## 0. 一句话

「发一句话给某个 agent」有很多目标形态，**没有任何一条通道能通吃**。
V92 把四条通道排成梯子，**能核实的排前面**，每条都如实标注"能不能核实"：

| 通道 | 适用目标 | 依赖 | 能否核实 | 实测 |
|---|---|---|---|---|
| `cdp` | Chromium / Electron（Trae、VS Code、Chrome…） | 目标开 `--remote-debugging-port` | **能**（读 `innerText`/`value`） | ✅ 读回 True |
| `native` | Win32 / WinForms / 老应用（有原生文本框子控件） | 无（同会话即可） | **能**（`WM_PASTE` 投 + `WM_GETTEXT` 读回） | ✅ 读回 True |
| `uia` | 暴露 UI Automation 的应用（Win11 记事本 Document、Office…） | Windows + 应用暴露 UIA | **能**（UIA 读回） | ✅ 记事本可读（写入按能力） |
| `clipboard` | 其它任何窗口（没开端口的 Electron、画布渲染、游戏…） | 无 | **不能**（人按 Ctrl+V） | 半自动，如实 `verified=None` |

## 1. 为什么不用"模拟鼠标键盘"当主力（V91 已定，这里固化）

- 会抢焦点、点错位置、把字打到别的程序里；
- 只能"猜坐标"（平台拿不到 Electron 内部元素），且**永远无法核实**；
- 结论：它只在"原生窗口 + 有教过的位置"时作为**补充**，且默认排在三条能核实的通道之后。

## 2. 契约

```
GET  /api/docking/delivery/channels?hwnd=&ws=&title=
     → {ok, channels:[{channel, available, why}], recommended}
POST /api/docking/delivery/send   {text, hwnd?, ws?, idx?, prefer?}
     → {ok, channel, verified(True|False|None), attempts:[{channel, ok, why}], detail, next_step}
```

- `prefer` 锁定一档（排障）：锁定档失败就**如实失败**，不偷偷换档；
- `attempts` 里**每一档都有原因**（守卫 `tests/test_delivery.py` 钉死：脚本没跑起来时也要给原因，
  否则就是"失败不说话"——这一条是测试当场抓出来的）；
- `verified=None` 只出现在 `clipboard` 档，并且一定伴随 `need_human=True`。

## 3. 判据

- **真机** `tools/delivery_check.py`（4/4 绿）：`channels()` 选路正确 → `native` 真投真读回 True →
  没有输入框的窗口**退半自动且不假装成功** → `cdp` 真投真读回 True（全程**不碰鼠标键盘**）；
- **选路逻辑** `tests/test_delivery.py`（5 条）：cdp 优先、native 次之、全败则如实半自动、每档都有原因、prefer 不换档。

## 4. 已知边界（不粉饰）

- Electron **没开调试端口**时，只剩 `clipboard` 半自动档 —— 这是它自己的沙箱决定的，平台无法绕过；
- UIA 覆盖不稳定：Win32/WinForms 的 EDIT 经 MSAA 代理往往**不暴露** ValuePattern（实测 VP=False），
  这类目标归 `native` 通道；UIA 主要覆盖 Document/Office 类；
- 二期：`uia` 增加 TextPattern 范围插入（长文/选区）、`cdp` 增加"投递后回执"绑定。

## 5. 落地到通用框架（2026-10-23 追加，老板：禁止私人化…落地到通用框架）

上层（界面按钮 / 脚本激活 / 唤醒 / 任务提示）**不再各自知道**该用哪条通道、目标是哪个窗口。
统一入口只有两个：

```
GET  /api/docking/harness/{id}/delivery      # 现在能送到哪儿（只读：来源 + 原因）
POST /api/docking/harness/{id}/deliver       # {text, prefer?, idx?, enter?}
```

`resolve_target()` 按**会话名**自动定位，顺序是"能核实的优先 + 记过的优先"：

1. `input_anchor` 里**上次成功过**的页面（直接命中，不再重新找）；
2. 开了调试端口的页面里标题/url 含会话名的那个（→ `cdp`）；
3. 可见窗口里标题含会话名的那个（→ `native` / `uia`）；
4. 都没有 ⇒ **如实说没找到**并给可执行下一步；**不会**偷偷退到半自动（半自动必须显式要）。

成功后把目标写回 `input_anchor`（下次直接命中）。**反私人定制**：本层只认能力
（Chromium/Electron/Win32/UIA），代码里出现具体产品名会被 `tests/test_delivery_harness.py` 判红。

判据：`tests/test_delivery_harness.py`（7 条：记忆命中 / 按名找页面 / 按名找窗口 / 无名如实说 /
找不到给下一步 / 成功记住 / **无产品名**）＋ 真机 `tools/delivery_check.py` ⑤⑥
（只给会话名 ⇒ 自动找到并读回核对；第二次命中记忆）。

## 6. 三处接入（2026-10-23，把「通用框架」真的用起来）

| 上层动作 | 以前 | 现在 |
|---|---|---|
| 一键脚本激活 `POST /api/docking/run-script` | 直接调 `visual_launch.launch`（只认 wmpaste/clipboard） | `delivery.deliver_by_name(档案里的标题或关键词, 话术)` —— 四通道自动选，返回里多了 `channel` 与 `used.channel` |
| 试投 `POST /api/docking/try-activate`（**带 harness_id 时**） | 同上 | `delivery.deliver_to_harness(hid, text)`，返回带 `via="harness"`；**不带** harness_id 时仍是「投给这个窗口」的诊断动作 |
| 通用送话 `POST /api/docking/harness/{id}/deliver` | —— | 新增：上层只说「送给这个 harness」 |

守卫：`test_run_script_uses_archived_params_only`、`test_run_script_pins_method_and_reports_failure_honestly`、
`test_try_activate_with_harness_goes_through_delivery_layer`（**断言带 harness_id 时不许再走 `visual_launch.launch`** —— 防止以后又长出第二套注入逻辑）。

> 说明：`visual_launch`（消息式 / 剪贴板 / 教位置那套）**降级**为两种用途：
> ① 屏2/3 的「投给这个窗口」诊断（用户显式选窗口）；② 原生窗口的可选补充档。
> **产品主路径一律走 `delivery`。**
