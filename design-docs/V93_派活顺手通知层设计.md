# 设计稿 V93 · 派活顺手通知层（可选，默认关）

> 状态：**已实施（2026-10-23）**。上游：`V92`（统一投递层四通道）。
> 这是把 `V92` 从"能送"接到"真用起来"的最后一段：**派活时顺手把话送到对方界面**。

## 0. 一句话

派活（派给某个员工的 harness）原本只写数据（收件箱 / pending / HTTP 回调）。
V93 在**派发总口**加一层**可选**动作：若开了 `AC_DELIVERY_NOTIFY=1`，把要派的那句话
**用 V92 的投递层送到对方界面**（通道自动选、能核实就核实）。

## 1. 三条硬约束（为什么只做这么点）

1. **默认关**：往别人界面上打字是**有副作用**的动作（可能落在人家正在编辑的地方）——
   老板产品准则「自动兜底默认关」，所以 `AC_DELIVERY_NOTIFY=0`。
2. **绝不影响派发结果**：通知失败只记账 + 打日志。否则会出现"因为通知没成所以活没派出去"的荒唐状态。
   实现上用**包装层**（`_dispatch_to_harness` 调 `_dispatch_core` 后再 try/except 通知），
   而不是在 `_dispatch_core` 里到处插。
3. **原因必须说话**：跳过要写"为什么跳过"（没开 / 没有 harness_id / 这次派发没有可投文本），
   失败要写"哪一档、什么原因"（直接用投递层的 `attempts`）。

## 2. 结构

| 层 | 文件 | 职责 |
|---|---|---|
| 开关 + 记账 | `platform/delivery_notify.py` | `enabled()`（读 `AC_DELIVERY_NOTIFY`）、`text_of(payload)`、`notify_dispatch()`（**永不抛**）、`summary_line()` |
| 派发总口 | `platform/server.py::_dispatch_to_harness` | 调 `_dispatch_core` 之后做可选通知；异常只打日志 |
| 通道与核实 | `platform/delivery.py` | 一处真相：cdp → native → uia → clipboard |

**取哪句话**：`message` → `task_text` → `content` → `text`（第一个非空）。都没有就跳过并说明
（只有结构化数据时，平台**不该**自己编一句话打过去）。

## 3. 判据

- `tests/test_delivery_notify.py`（6 条）：默认关不调投递 / 开了成功记下 channel / 失败如实且"不影响派活" /
  没文本跳过说清 / 取文本优先级 / **通知层抛异常时 `_dispatch_to_harness` 仍返回原派发结果**；
- 真机：投递层自身 `tools/delivery_check.py` 6/6（native、cdp 真投真读回，自动发现与记忆）；
- 全量 pytest 与双平台真跑（Windows + WSL Linux）。

## 4. 边界（不粉饰）

- 打开后**仍然可能送不进去**（对方没开调试端口、窗口不在、名字对不上）——
  这时只记账、不重试；要不要重试由用户决定，平台不擅自反复往界面打字；
- 本层**不写状态文件**（落盘归 `state_store`），只返回可记账 dict + 一行日志。
