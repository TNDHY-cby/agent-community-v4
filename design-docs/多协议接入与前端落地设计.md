## 一、背景与目标（负责人指示要点）

> 原话要点，本稿须逐条落地：
> 1. 项目性质：**开源作品集 + 竞赛交付**。
> 2. **禁止对外称「多 Agent 协作平台」**——他人作品的"多 Agent 协作"建立在狭隘理论上（只能平台内部 agents 互相协作）；本项目是**让外端 agents 合作**，充分利用各 harness 的框架差异（**同一个 AI 接入不同 harness 后的 agent 表现不同**）。
> 3. **合作社（信誉 / 能力账本 / 组长 / 决策模式）是主打内容**，是创新点，不是附带机制。
> 4. 要**兼容各种协议**：不同 harness 能接受的协议不同；但**不能一股脑塞一起**，要"多种接口多种选择，让外端 agent 自己选最合适的"。
> 5. 协议是给 **Claude Code / Hermes** 这类外部 harness 真用的，要**真互操作**。
> 6. 协议落地后**还要进前端**，变成平台功能。

**本稿目标**：把"多协议 + 外端自选"从口号变成可发现、可声明、可选择、可在 UI 里看得见的平台能力。

## 一·补、实施优先级（2026-10-02 核规范后**修订**）

核完权威规范（见 §2.6）后，原定顺序要改。**规范对齐必须排在最前**——不然所谓"多协议"是建在过时规范上的空中楼阁，外部 harness 根本接不上：

| 序 | 事项 | 为什么排这个位置 |
|---|---|---|
| **0** | **规范对齐**：MCP → `2025-06-18`；A2A → `v1.0`（发现路径、方法名、`supportedInterfaces[]`） | 不做这步，后面全是白做；这是"真互操作"的前置 |
| **1** | **三副本资产回收**：oss 的 V-22 MCP 客户端 + 脱敏 ACP 桥 | 不做，一次 `publish` 就永久丢件（已加闸拦住） |
| 2 | **出站选路真正接上**：`select_endpoint` + `priority` + `preferred_transport` | 让"agent 自选"从口号变成行为 |
| 3 | 协议声明结构统一：A2A `supportedInterfaces[]` ↔ 内部 `GET /api/protocols` | 用规范的标准做法，不重复发明 |
| 4 | **前端落地**：协议与端点页 + register 指引 + 工作间成员协议展示 | 负责人明确要求"协议还要进前端" |
| 5 | gRPC（= A2A 的第二绑定，不是另起炉灶） | 依赖 0~3 完成后再做 |
| 6 | 作品集交付件：README 重写 / 最小外部 harness 示例 / CI | 竞赛交付需要 |

## 二、现状实测（2026-10-02 勘察结论）

平台现在有**三条互相独立的协议轴**，但它们彼此没有打通，也没有对外暴露成"可选项"：

| 轴 | 枚举/字段 | 位置 | 取值 | 实际使用情况 |
|---|---|---|---|---|
| **出站传输**（平台 → harness） | `TransportType` | `protocol.py:20-25` | `ws` / `http` / `sse` / `pipe` / `grpc` | **只实现了 http**（详见下） |
| **激活方式**（平台拉起 harness 新会话） | `WakeupMethod` | `protocol.py:409-415` | `http` / `file_poll` / `clipboard` / `acp` / `http_api` | 都接好了，是当前真正在用的那条 |
| **入站协议**（外端 → 平台） | 无枚举，散落各文件 | `server.py` / `mcp_server.py` / `a2a_server.py` | HTTP REST / WS / A2A(9104) / MCP(stdio) | V-10 刚补齐 MCP + A2A |

### 2.1 出站传输实现度实测（比"没实现"更麻烦：真真假假）

| 协议 | 实际状态 | 证据 |
|---|---|---|
| `http` | ✅ 真实现 | `adapters.py:59-62`；`harness_adapter.py:377-379` |
| `pipe` | ✅ 真实现 | `adapters.py:130-184`（`PipeAdapter`）；`harness_adapter.py:385/417` |
| `ws` | ⚠️ **半真（伪装）** | 发送端 `harness_adapter.py:359-365` 确实 `ws.send_text`；但**端点 url 是 `ws://127.0.0.1:0/` 占位**（`harness_adapter.py:223`，端口 0）；`waker_protocol.py:235-240` **注释自认**"httpx 不原生支持 WS，这里用 HTTP fallback 模拟"（把 `ws://` 换成 `http://` POST）；`server.py:1876` 硬编码 `"ws_endpoint": ""` → **websocket 永不生效** |
| `sse` | ❌ 纯声明 | 全树 `TransportType.SSE` **零命中** |
| `grpc` | ❌ 纯声明 | 全树 `TransportType.GRPC` **零命中** |
| `acp` | ✅ 真实现，但**绕过枚举** | `acp_bridge.py:60-100` spawn 子进程走 JSON-RPC stdio；接在 `acp_command` 这条独立路径上（`routers/harness.py:303,666`）；**`WakeupMethod.ACP` 无任何分支读取它** |

> 结论：不是"少实现了几个"，而是**枚举里有 2 个是纯画饼、1 个是伪装的、1 个真实现却不走枚举**。

### 2.2 🔴 选路层是**死代码**

- `adapters.py:24-37` 的 `select_endpoint()` **已经写好了** `preferred` 精确匹配 + `priority` 排序 —— 但**全树零调用**（只有 `design-docs/P2` 提过它）。
- **实际生效的 transport 是注册时的单值** `info.transports[0]`（`harness_adapter.py:1158`）——**根本没有选择过程**。
- 端点 `priority` **恒为 0**（`harness_adapter.py:235`），排序机制形同虚设。
- `adapters.py:109` 注释写着"HTTP > WS > PIPE"，**实现只有 HTTP 一个分支**（113-125）——注释与代码不符。
- 平台自己的端点写死 `builtin://orchestrator`（`orchestrator.py:73-77`）。

### 2.3 外端 agent "自选协议"这条链现在走不通

- harness 侧只能声明 `transports: list[TransportType]`（`protocol.py:439`，默认 `[HTTP]`）——**是个集合，没有优先级、没有"我偏好哪个"**。
- **官方注册契约里连 `transports` 都没写**：`design-docs/Harness通用接入协议.md:23-37` 的注册样例**根本没有这个字段**。
- 枚举里**没有 MCP / A2A 值**，所以"我支持 MCP 和 A2A"根本无从声明。
- 非 HTTP/WS/PIPE 的 transport 会生成**空 url 端点**（`harness_adapter.py:213-239` 的 elif 链）。
- 平台**没有把自己**的多种接入方式对外广播：A2A 卡片只有一个 `url` 字符串（`a2a_server.py:112`），**没有 endpoints 数组**。
- **实测存量数据**：9 个已注册 harness **全部**声明 `transports: ["http"]`。
- 结论：现在要让一个 harness 表达"我支持 MCP 和 A2A，优先 A2A"，**现有模型表达不了**；平台也没有地方让外部 agent 看到"你可以用哪几种方式接我"。

**这是 V-10 那次"成果孤立"的镜像版**：

### 2.6 🔴 与权威规范的偏差（2026-10-02 上 GitHub / 规范站实测）

> 依据：[MCP 规范 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)、
> [MCP Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)、
> [A2A 规范 v1.0](https://a2a-protocol.org/latest/specification/)、
> [A2A What's New in v1.0](https://a2a-protocol.org/latest/whats-new-v1/)、
> [A2A Agent Discovery](https://a2a-protocol.org/latest/topics/agent-discovery/)

**MCP**（当前版本 **`2025-06-18`**）

| 项 | 规范要求 | 本项目现状 | 判定 |
|---|---|---|---|
| 协议版本 | 当前 `2025-06-18`；`initialize` 需**版本协商**（服务器不支持请求版本时回自己能支持的最高版） | 硬编码 `2024-11-05`，无协商逻辑 | ❌ **落后 3 个版本** |
| stdio 帧格式 | 换行分隔；**"服务器 MUST NOT 向 stdout 写任何非 MCP 消息"** | 换行分隔 ✅；曾因 `platform/__init__.py` 把启动横幅写进 stdout（V-10 已修） | ✅ 已修，**规范正好为那次修复背书** |
| stdio 日志 | 日志应写 `stderr` | `mcp_server.py` 内多处 `print(..., flush=True)` 未指定流 | ⚠️ 待查 |
| 传输形态 | **Streamable HTTP** 已替代 2024-11-05 的 HTTP+SSE | 未实现（oss 的 `mcp_client.py` 用 Streamable HTTP 做客户端） | ⚠️ |

**A2A**（当前 **v1.0**，已加入 Agentic AI Foundation / Linux Foundation）

| 项 | v1.0 规范 | 本项目现状 | 判定 |
|---|---|---|---|
| 发现路径 | **`/.well-known/agent-card.json`** | `/.well-known/agent.json`（v0.2 时代路径） | ❌ 路径过时 |
| 方法名 | `SendMessage` / `SendStreamingMessage` / `GetTask` / `ListTasks` / `CancelTask` / `SubscribeToTask` / `GetExtendedAgentCard` | `message/send` / `tasks/get` / `tasks/cancel` / `tasks/send` / `message/get` / `agent/get` | ❌ v0.2/v0.3 命名；后三个**根本不是规范方法** |
| **多接口声明** | **`supportedInterfaces[]`**，每项含 `url` + `protocolBinding` + `protocolVersion`（v1.0 把 `preferredTransport` 与 `additionalInterfaces` 合并到这里） | **没有**；Agent Card 里只有一个 `url` 字符串 | ❌ **见下方"重要"** |
| 协议版本位置 | `protocolVersion` 在**每个 AgentInterface** 上（按接口分别版本化） | AgentCard 顶层 | ❌ |
| 绑定 | **JSON-RPC / gRPC / HTTP+JSON 三种正式绑定，规范保证等价** | 只做了 JSON-RPC 一种 | ⚠️ **gRPC 是 A2A 的原生第二绑定** |
| 枚举/字段风格 | `SCREAMING_SNAKE_CASE` 枚举、camelCase 字段、**去掉 `kind` 判别符** | 未对齐 | ⚠️ |
| 错误模型 | `google.rpc.Status` / `ErrorInfo`（`errorInfo.metadata`） | 自造 | ⚠️ |
| 扩展卡片 | `capabilities.extendedAgentCard` | 自造 `authentication` 等 | ⚠️ |

#### ⚠️ 重要：负责人要的"多种接口多种选择"，**A2A 规范里已经有标准答案了**

A2A v1.0 的 `supportedInterfaces[]`（每个接口带 `protocolBinding` + `protocolVersion`）
**就是"我支持这几种接口，客户端自己挑"**，且规范专门定义了
[§8.3 协议声明要求 / §8.3.2 客户端协议选择](https://a2a-protocol.org/latest/specification/) 与 §5.2 协议选择与协商。

→ 我们**不应该另造一套"平台私有协议目录"去重复发明**。正确做法：

1. **对外**：Agent Card 采用规范原生的 `supportedInterfaces[]`（JSON-RPC / gRPC / HTTP+JSON 三种 binding 各一条）
2. **对内**：再把这套结构映射成 `GET /api/protocols`，供前端渲染 + 平台内部 harness 选择（§4.1 相应调整）

#### 结论

V-10 落地的 MCP/A2A 层，是照 **2024-11-05 / A2A v0.2–v0.3 的旧样貌** 实现的（原始代码写于 2026-10 之前，见 §2.4）。
要满足负责人"**真要对外提供互操作能力**"（Claude Code、Hermes 这类外部 harness 真能接），
**必须对齐当前规范**：MCP `2025-06-18` + A2A `v1.0`。

> 这正是"当前阶段遇到问题去 GitHub 找例子"最该先落的一件事：**先把规范对齐，再谈协议目录与前端。**

## 三、设计原则

1. **可发现**：外端 agent 不需要读源码，就能知道"能用哪几种方式接这个平台"。
2. **可声明**：harness 能表达"我支持哪些协议、我偏好哪个"。
3. **可选择**：平台按 声明优先级 → 端点 priority → 声明顺序 选一个**确实实现了**的协议。
4. **不撒谎**：声明了但没实现的协议，**必须从选择池里剔除**，绝不选到空实现（当前 `grpc`/`sse` 就是这种状态）。
5. **不一股脑**：每个协议**独立可选、独立可关**，默认只开已验证的那几种。
6. **零回归**：既有 HTTP 出站 + 5 种激活方式行为不变。

## 四、方案

### 4.1 协议目录（Protocol Catalog）—— 把"怎么接我"变成一等公民

**新增 `agent_community/platform/protocol_catalog.py`**：一份**单一事实源**，描述平台对外暴露的每种接入方式。

```python
# 结构示意（每种协议一条）
{
  "id": "a2a",
  "name": "A2A（Agent-to-Agent）",
  "direction": "inbound",              # inbound=外端来调我 / outbound=我去调它
  "kind": "http",                       # http / stdio / ws / pipe / grpc
  "endpoint": "http://<host>:9104/",    # 运行时按实际 host/port 填
  "discovery": "GET /.well-known/agent.json",
  "status": "available",                # available / not_implemented / disabled
  "best_for": "支持 A2A 生态的外部 Agent（Google ADK / LangGraph / AutoGen 等）",
  "example": "curl http://127.0.0.1:9104/.well-known/agent.json",
  "requires": "独立进程：python -m agent_community.a2a_server",
}
```

**新增端点 `GET /api/protocols`**：
- 返回上述目录（含运行时实际 host/port、各协议 `status`）
- 供**前端渲染**、供**外端 agent 自选**、供**文档生成**

**两份对外投影自动对齐**（同一份 catalog 渲染）：
- A2A 的 `.well-known/agent.json` → 里面列出平台支持的全部入站方式
- MCP 的 `tools/list` → 增加一个 `list_protocols` 工具，让 MCP 客户端也能问到"还能怎么接"

> 这一步直接满足负责人第 4、5 条：外端 agent 有了**自己挑**的依据。

### 4.2 出站协议选择 —— 让 harness 真正"自选"

| 改动 | 文件 | 说明 |
|---|---|---|
| `TransportType` 增补 `MCP = "mcp"`、`A2A = "a2a"` | `platform/protocol.py:20-25` | 让"平台可用某协议触达该 agent"能被声明 |
| `HarnessInfo` 增 `preferred_transport: Optional[TransportType] = None` | `platform/protocol.py:431+` | 显式偏好，**可选**，不填则回落到 priority |
| 新增 `IMPLEMENTED_TRANSPORTS` 常量 | `platform/protocol.py` | 明确"哪些是真实现了的"，`sse`/`grpc` 未实现前不在其中 |
| `select_endpoint()` 改造 | `platform/adapters.py` | 顺序：`preferred`（若已实现）→ 端点 `priority` 降序 → 声明顺序；**跳过未实现协议**并记一条日志 |
| 注册时校验并回显 | `platform/routers/harness.py` | harness 声明了未实现协议 → 注册仍成功，但响应里明确告知"该协议尚未实现，已忽略" |
| `orchestrator.py` 默认值 | `platform/orchestrator.py:75` | 保持 HTTP 默认（零回归），但改为"若 harness 声明了 preferred 则用它" |

### 4.3 入站协议补齐

| 协议 | 现状 | 本稿动作 |
|---|---|---|
| HTTP REST | ✅ 已有（132 处路由） | 纳入 catalog，前端可复制 base url |
| WS | ✅ 已有（`/ws`、`/ws/agent/{id}`） | 纳入 catalog |
| **MCP** | ✅ V-10 已落地（stdio，11 工具） | 纳入 catalog；补一个 `list_protocols` 工具 |
| **A2A** | ✅ V-10 已落地（HTTP 9104） | 纳入 catalog；Agent Card 里列出其它入站方式 |
| SSE | ❌ 未实现 | catalog 里标 `not_implemented`，前端**灰显**并注明"规划中" |
| **gRPC** | ❌ 未实现（方案稿已归档） | **见下** |

**关于 gRPC**：负责人要求"兼容各种协议"，而 `TransportType.GRPC` 早就预留了。
本稿建议**实施**，但按 V-10 已确认的架构原则做成**独立网关进程**（端口 9105）：

- 新增 `agent_community/grpc_gateway.py`（放顶层包，理由同 MCP/A2A：`platform/__init__.py` 会拽入整个 FastAPI 服务）
- 依赖 `grpcio` / `grpcio-tools` → 放 **optional 依赖组**，不装则该协议在 catalog 里自动标 `disabled`（**不影响其余协议**）
- proto 采用**信封式**（`task_id + payload_json + agent_token + meta`），与 HTTP 共用同一数据模型，零协议漂移
- 复用 V-10 已落地的 `identity.check_request_token`，401/403 映射为 `UNAUTHENTICATED` / `PERMISSION_DENIED`

> ⚠️ 这一项会引入重依赖，**请负责人单独拍板**：做 / 不做 / 只保留 catalog 占位。

### 4.5 修复既有伪实现（不然"多协议"是纸上谈兵）

§2.1/§2.2 查出的是**假实现**问题，不修的话，"多接口多选择"只会选到空气：

| 问题 | 处置 |
|---|---|
| `select_endpoint()` 是死代码 | **真正接上**：让 `harness_adapter.send()` 与端点生成器调用它；同时修正 `adapters.py:109` 与代码不符的注释 |
| 端点 `priority` 恒为 0 | 端点生成时按声明顺序赋**递减 priority**；显式 `preferred_transport` 给最高优先 |
| `transport` 取注册单值 `transports[0]` | 改为**经选择得出**；未实现协议自动回落 `http` |
| `websocket_send` 是把 `ws://` 换成 `http://` 的伪装 | **二选一，必须明确，不允许继续伪装**：① 用支持 WS 的客户端**真实现**；② 从 `IMPLEMENTED_TRANSPORTS` 移除 `ws`，catalog 标 `not_implemented`，前端灰显 |
| `server.py:1876` 硬编码 `"ws_endpoint": ""` | 与上一条**同步**处理 |
| `WakeupMethod.ACP` 无任何分支读取 | ACP 实际走 `acp_command` 独立路径。要么把枚举接上，要么在文档明确"ACP 由 `acp_command` 驱动，不经 `WakeupMethod` 分支"——**不能继续两套并存且互不承认** |
| `mcp_client.py` 只在 oss（V-22） | **自 oss 回收**进 dev 主线，并进 catalog 的**出站方向** |
| MCP / A2A 无启动器、无健康检查（全树无 import） | catalog 里标 `requires`（怎么起），前端给"如何启动"提示；长期纳入 watchdog |
