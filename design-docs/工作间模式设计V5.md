# 工作间模式设计（V5）— 已按老板拍板对齐

> 状态：设计稿 v2，6 项关键决策已由老板确认（见 §九）
> 依据：老板 §11 最终原话（唯一权威）
> 范围：平台内置助手已排除，目标 Harness = dsh / Trae / Cursor / Claude Code / Codex CLI / Ollama 等
> 与 v4 关系：**并行共存**，不动现有 `orchestrator.handle_task` 自动派活，V5 是新增的「工作间」协作层，后续再决定删改

---

## 一、定位（一句话）

把平台从「**指挥一群被动工具**」升级为「**一个组长带着一群会主动进厂、能用钩子互相唤醒的员工，在同一个工作间里协作**」。

核心转变（§11 定死）：**推 → 唤，被动 → 主动**。
- 旧（v4）：平台把活 push 给 harness，等回包。
- 新（V5）：平台**唤**起 harness 的新对话，给它「工作区坐标 + 固定流程指引」，让它自己 pull 大厅内容、自己表态进入。

---

## 二、核心原则（§11.1，铁律）

**不要举手制度。** 平台 AI 根据 harness 注册时的身份能力绑定，**直接选定**参与对象，没有举手环节。

> 推论：现有 `waker_protocol.py` 的「举手判断任务」载荷作废，只复用三种传输（file_poll / http_callback / websocket）。

**token 经济原则（老板拍板）。** 平台自己的 token 只花在两处，其余零 AI：
1. 建工作间时**预填名单**——每个工作间一次。
2. **组长定时检查**——限频（每 N 分钟），且「还在工作就不发」（§11.4 已要求）。

钩子检测、是否还在工作、点名识别等**全走纯规则（正则/关键词），不逐消息调 AI**。A2A 讨论的 token 由各 harness 自己承担，不计平台开销。

**经验复用原则（老板拍板）。** 少走弯路 = 少烧 token：平台在**派任务时替 harness 检索好** skill 市场 + 知识库 + 平台记忆库，把命中经验**随任务下发**，harness 拿到直接用（见 §6.6）。检索走**索引/关键词匹配**，不全文读、不逐任务调 AI。

**不依赖外部 AI 自律原则。** 凡是"希望 harness 记得做"的事（设钩子、检索），都改成**平台代做 + 结果随消息下发**，或**平台检测后补做**——钩子已如此（L1/L2/L3），检索同理（见 §6.6）。

## 三、一次完整走查（三级讨论 + 工作循环，老板定稿）

**任务**：用户在大厅发一句简单任务 —— "帮我做一个价格监控工具"。

**第 1 步 · 发布 + 拉入工作间 + 一级讨论（深入需求）**
用户在大厅发布 → 平台 AI 把用户拉进一个新工作间 → **一级讨论**：用户 + 平台 AI 深入聊清需求（监控什么、多久一次、输出什么格式）。

**第 2 步 · 初步选定员工（§11.2）**
平台 AI 根据**一级讨论的内容**，初步选定员工填入列表：

| 职业 | 平台 AI 预选 |
|------|-------------|
| 组长（设计/分配/检查/纠错） | `dsh`（示例，可换） |
| 码农 | `trae-cn`（示例） |
| 搜索者 | `cursor`（示例） |

- 用户只看表面名称，背后链路指向注册列表里的 harness。
- 用户**查看、增删改**。

**第 3 步 · 二级讨论（明确分工详情）**
用户 + 平台 AI，**组长参与**，明确：谁负责哪块、依赖关系、产出。**此阶段仍可改员工列表换人**。

**第 4 步 · 确认 + 激活 + 工作**
确定任务与分工后，用户**审查、甚至自定义修改名单 → 点击确认 → 才激活员工**（每个 harness 开新对话）→ 开始工作 → **组长指挥员工、并参与工作**。

**第 5 步 · 三级讨论（依进度讨论）**
完成一个阶段后，**依进度讨论**：员工反馈进度、组长汇报 → **确认员工列表**（是否换人/加人）。

**第 6 步 · 循环直到完成**
确认后继续工作 → 再三级讨论 → 再工作 …… **循环，直到总任务完成**。

> 关键三点：讨论分三级（需求/分工/进度）、员工列表全程可改、讨论↔工作循环到完成。

## 四、数据模型（新增）

### 4.1 职业（WorkshopRole）
预设：`leader 组长 / coder 码农 / artist 画师 / searcher 搜索者`；**允许用户自定义角色名**。角色只决定"大致分工"，需要时可跨角色干活。

### 4.2 员工（WorkshopMember）= 岗位（配置层）
```
member_id          : 岗位唯一 ID
role               : 职业（leader/coder/... 或自定义）
display_name       : 表面名称（用户看到的，如 "dsh"）
harness_ids        : [harness_id]   ← 背后链路，指向注册列表（一个岗位可绑多个 harness）
```
> 名单里的是「岗位」，不是运行时工人。确认开启后，平台按分工为每个 harness 开出 **1..N 个会话**（见 §4.5），每个会话 = 一个并行工作的"手"。

### 4.3 工作间（Workshop）
```
workshop_id        : 工作间 ID
name               : 名称
members            : [WorkshopMember]
leader_id          : 组长 member_id（= 平台 AI 预选、用户确认的外部 harness）
status             : draft / running / paused / done
hall_task_id       : 关联大厅内容（用户最初发的那句话）
workspace_dir      : 工作区坐标
messages           : 工作间消息流（含钩子事件、任务分配、A2A 讨论）
created_at / updated_at
```

### 4.4 钩子标记协议（HookMarker）— 两种钩子，位置决定语义

| 钩子 | 位置 | 语义 |
|------|------|------|
| **指定钩子** | 主体文本**中间** | 指定对象（点名/称呼，**不激活**） |
| **激活钩子** | 消息**末尾单独一段** | 激活对象去**查看内容**（真正触发） |

- **广向**（激活全体）：末尾钩子写 `@唤:全体`
- **定向**（激活精准对象）：末尾钩子写 `@唤:<角色>`（如 `@唤:码农`）或 `@唤:<员工名>`（如 `@唤:搜索者A`）

检测规则（**纯规则，零 token**，每消息都跑）：
1. **L1 显式钩子**：正则扫末尾 `@唤:...` → 命中即激活，正文剥离单独记录。
2. **L2 规则补钩**（防 harness AI 忘写钩子）：无显式钩子时，纯关键词判断——正文出现「角色名/员工名」+ 求援词（求/请/支援/帮忙/交给你/你来/接手/处理）→ 自动补一个末尾钩子，消息标记「自动补钩」。**不调 AI。**
3. **L3 组长兜底**：L1/L2 都漏 → §11.4 组长定时检查本来就会点名激活，不会硬卡死。

> L2 允许少量误激活：多 poke 一下比卡死好，且激活只是"去读"，不是"去干活"，代价可控。

### 4.5 会话（Session）= 原子工作单元（老板拍板，iLink context_token 模式）
```
session_id         : 会话唯一 ID ← 贯穿所有消息，回复原样带回做路由（= iLink 的 context_token）
harness_id         : 所属 harness（壳子）
workshop_id        : 当前所在工作间（一个会话同一时间只属于一个工作间）
member_id          : 对应哪个岗位
role               : 承担的职业
task_id            : 正在干的子任务
status             : activating / entered / working / idle / blocked / done
```

**多路复用（必需，非可选）：**
- **1 harness → N 会话**：同一 harness 同时开多个会话（聊天）。
- 这些会话可**散进多个工作间**，也可**同进一个工作间并行分工**（一个 harness 派多个手干不同子任务）。
- 平台对会话的「激活 / 任务 / 钩子 / 回复」全部带 `session_id`，靠它路由到正确会话——不再按 harness 粒度，而是按会话粒度。

## 六、平台「唤醒专员」agent + 桥协议扩展

### 6.1 平台唤醒专员（老板拍板：创造一个平台 agent）
新增一个**内部平台 agent**（与 orchestrator 同级注册，如 `wake-agent`「唤醒专员」），职责：
- 收到「确认开启工作间」→ 按分工为每个 harness **开出 1..N 个会话**（每个会话 = 一个并行的手），逐个会话发**激活**。
- 会话是原子工作单元，激活/任务/钩子/回复全部按 `session_id` 路由（§4.5）。
- 内部按 harness 类型分派「开一个会话」的落地方式：

| harness 类型 | 开一个会话的落地 |
|-------------|-------------------|
| **dsh harness（DeepSeek Harness）** | **走 ACP**（Agent Client Protocol，JSON-RPC over stdio）：`session/new` 开新会话（`cwd` = 工作区坐标），`session/prompt` 多轮对话，**一条连接多会话并行**（= 1 harness → N 会话） |
| HTTP 回调类 | POST 激活消息带新 `session_id`，由对方自行开新对话 |
| 文件轮询类（如 Trae，不可回调） | 写激活文件到监听目录，`session_id` 建会话目录 |

> **Spike 实测修正（2026-08-15）**：`dsh --profile headless` 是**一次性**任务（一进一出即退），`--resume` 只属于 TUI app；持续多轮会话必须走 **ACP**（`@deepseek-ai/dsh-acp`，`session/new` + `session/prompt`，一连接多会话，每会话独立 cwd/workspace）。dsh 仓库内已有现成客户端范式 `@deepseek-ai/dsh-subagent-acp`（父 harness 拉 dsh 当子 agent）。

- 复用 `wakeup_bridge` 三种通道（HTTP / 文件轮询 / 剪贴板兜底），**换载荷**（下面 6.2）。

### 6.2 激活新会话载荷（§11.3，不含任务详情）
```json
{
  "type": "workshop_activate",
  "session_id": "sess_xxx",
  "workshop_id": "ws_xxx",
  "workspace_dir": "D:\\workshop\\ws_xxx",
  "role": "coder",
  "workflow_guide": "你的角色是「码农」；先去读大厅内容；读完回复「收到，已进入工作状态。」"
}
```
> 后续所有该会话的消息（任务/钩子/回复）都带同一 `session_id`，回复原样带回做关联路由。

### 6.3 读大厅内容（§11.3）
harness 激活后主动 `GET /api/workshop/{id}/hall`。

### 6.4 确认进入（§11.3）
harness 读完后 `POST /api/workshop/{id}/confirm-entry`，回「收到，已进入工作状态。」。

### 6.5 钩子识别（§11.5）
平台侧在 `message` 端点做两种钩子检测（§4.4 三层），**全纯规则、零 AI**：L1 显式钩子正则 → L2 关键词补钩 → L3 组长兜底。harness 只需在正确位置写 `@唤:...`，无需额外能力。

### 6.6 工作方式优化：平台代检索 + 经验包下发（老板拍板）

> 不靠 harness 记得去检索——平台在派任务时**替它检索好，把经验随任务一起下发**。

1. **登记**（让平台知道它有什么）：harness 注册时上报「skill 市场索引 + 知识库目录索引」= 每个 skill/条目的 `name + description + tags` 清单。
2. **平台代检索**：组长/平台每次派任务，平台先拿任务关键词，去匹配该 harness 的 skill 索引 + 知识库索引 + 平台记忆库（`memory.py` 的 HistoricalTask + CapabilityLedger）→ 命中 N 条，拼成「经验包」。
3. **随任务下发**：任务消息 = 任务本身 + 经验包（可复用 skill 名/描述 + 相关历史经验摘要）。harness 打开任务时经验已在手，无需记得查。

**省钱：** 检索全走索引 + 关键词（平台纯规则，零/低成本），只下发**命中摘要**，不全文读、不整库喂 AI。分工时优先复用「有同类成功经验」的 harness（`CapabilityLedger` 已有，直接加权）。

**兜底：** 流程指引仍保留「第 0 步自查」，作为平台经验包未覆盖时的补查（次选）。

> 已定：skill/知识库索引登记从「可选」变「**必需**」——平台要代检索，必须先知道每个 harness 带了什么。

## 七、组长机制（§11.4 + 老板拍板）

- **组长 = 外端 AI agent harness**（不是平台 Orchestrator）。
- **选定流程**：平台 AI 预选 → 用户查看修改 → 确认（§11.2 名单预填流程，组长行同理）。
- **定时激活**：周期性后台任务（asyncio 循环，参考现有 `_pipe_poll_loop` 形态），对每个 `running` 工作间：
  - 组长 `status == working`（还在工作）→ **不发**（§11.4 "如果还在工作就不发"）
  - 否则 → 向组长 harness 发固定组长指令（§11.4 示例原文）
- "是否还在工作"判定：组长最近一次消息时间戳 / 工作间文件活动，超阈值视为空闲才发。

## 十一、Phase A spike 实测结论（2026-08-15）

真跑了 dsh 的 ACP 自动化入口（`examples/acp-agent`，JSON-RPC over stdio），结果：

| 步骤 | 结果 |
|------|------|
| `initialize` | ✅ 返回 `deepseek-harness-acp` |
| `session/new`（cwd=工作区坐标） | ✅ 返回 sessionId |
| `session/prompt` | ✅ `stopReason: end_turn` |
| `session/update`（回复） | ✅ 收到真实模型回复「收到。」 |

**定论：平台程序化拉起 dsh 新会话、发消息、收「收到。」确认——这条最硬的腿通了。**

关键事实（桥设计必须遵守）：
1. **dsh 会话 = ACP**：`session/new`（cwd=工作区坐标）+ `session/prompt`（多轮）+ `session/update`（收回复）。**不是** headless 子进程（headless 一次性）。
2. **一连接多会话**：一条 ACP 连接可同时拥有多个 session，每个独立 cwd/workspace/cancel → 天然支持「1 harness → N 会话并行」。
3. **cwd = 工作区坐标 = 会话 workspace**：员工产物落在各自 session 的 cwd 目录，顺带解决「工作区文件语义」的一半。
4. **API key 注入**：dsh 的 llm-deepseek 提供方**不认** `.credentials.yaml` 里的扁平 `DEEPSEEK_API_KEY`，须 `export DEEPSEEK_API_KEY`（或走 credentials service 的 provider route）。桥 spawn dsh 时要注入环境变量。
5. **fresh-only + connection-owned 生命周期**：会话不支持 resume/load；连接断开 = 全部会话释放 → V5 的「会话生命周期」绑定「桥连接生命周期」。
6. **现成客户端**：`@deepseek-ai/dsh-subagent-acp` 就是「父 harness 拉 dsh 当子 agent」的成品，平台可直接复用，不必手写 JSON-RPC。
