## 1. 核心理念

### 平台定位

agent-community-v4 是一个**本地优先的多 Agent 协作平台**。

与扣子（Coze）的核心差异：

| 维度 | 扣子 | agent-community-v4 |
|------|------|---------------------|
| 部署 | 云端 SaaS | 本地运行，无服务器依赖 |
| 协作范式 | 人指挥多个 Agent（@Agent 模式） | Agent 与人在讨论室平等协商 |
| Agent 接入 | 用户手动跑 coze-bridge | Harness 注册后自动在线，Orchestrator AI 自动匹配 |
| 任务调度 | 用户手动分配 | AI 驱动的广播→匹配→邀请→执行全流程 |
| 开源 | 闭源 | 计划开源 |

### 核心概念三层关系

```
平台 (agent-community-v4)
  └── 协调中心，发"入场证"，管理讨论室和任务编排

Harness (壳子)
  └── 工具框架（Trae CN / Cursor / Claude Code / Codex CLI / Ollama 等）
  └── 提供工具和运行环境（编辑器、终端、文件系统、LSP 等）

AI (工人)
  └── 大模型本身（Claude / GPT / DeepSeek / 本地模型等）
  └── 接入 Harness 后使用工具干活
```

- Harness 本身不含 AI，它是工具框架
- AI 接入 Harness 后才能使用工具执行任务
- 类比：Harness = 装修车间（电钻、切割机），AI = 工人

### 任务执行流水线（v4 经典流程）

```
用户输入任务
  → Orchestrator AI 分析任务需求
  → 匹配具备相应能力的 Agent/Harness
  → 创建讨论室（DiscussionRoom）
  → 广播举手邀请
  → 讨论室协商分工（用户 + Orchestrator + Harness 代理发言）
  → 用户确认分工方案
  → 串行/并行执行子任务
  → 结果汇总
```

## 4. 用户体系设计

### 设计参考

借鉴扣子（Coze）的 PAT（Personal Access Token）机制：

- **扣子做法**：用户注册 → 生成 PAT → 绑定工作空间 + 权限 → API 带 `Authorization: Bearer sat_xxx`
- **我们的简化**：MVP 阶段做最小实现，后续按需扩展

### 数据模型

```
users 表
├── user_id        : "u_{12位随机hex}"          # 用户唯一 ID
├── username       : string                      # 显示名
├── pat_hash       : sha256(pat_token)           # 令牌哈希，不存明文
├── pat_prefix     : "pat_xxx"[前8位]            # 用于匹配令牌（防彩虹表）
├── role           : "owner" | "member"          # 角色
├── created_at     : ISO8601 timestamp
└── updated_at     : ISO8601 timestamp
```

### 令牌设计

```
格式：pat_{24位随机hex}
示例：pat_a1b2c3d4e5f6789012345678abcdef
```

- `pat_` 前缀：一眼识别为平台令牌
- 24 位 hex：128 位熵，暴力破解不可行
- 后端存储：仅存 sha256 哈希 + 前 8 位明文（用于 O(1) 匹配）
- MVP 暂不做过期时间，后续加

### API 设计

| 端点 | 方法 | 说明 |
|------|------|------|
| `/api/user/register` | POST | 注册：输入 username，返回 user_id + pat_token |
| `/api/user/login` | POST | 登录：输入 pat_token，返回 user_id + user_info |
| `/api/user/me` | GET | 获取当前用户信息（需 Bearer Token） |

注册流程：
```
POST /api/user/register  {"username": "老板"}
  → 生成 user_id + pat_token
  → 后端存 pat_hash
  → 返回 {"user_id": "u_xxx", "pat_token": "pat_xxx", "username": "老板"}
  → 前端存 localStorage: user_id, pat_token
  → 后续请求带 Authorization: Bearer pat_xxx
```

### 鉴权中间件

```python
# 所有需要登录的 API 从 Authorization 头解析 user_id
async def get_current_user(request: Request) -> str:
    auth = request.headers.get("Authorization", "")
    if not auth.startswith("Bearer pat_"):
        raise HTTPException(401)
    token = auth[7:]  # "Bearer " 后 7 个字符
    # 从 users 表中 sha256 匹配 → 返回 user_id
```

### Harness 归属

- HarnessInfo 新增字段：`owner_id: str`（注册时从 Authorization 头自动提取）
- 查询 Harness 列表：按 `owner_id` 过滤
- 讨论室匹配：当前用户只能匹配到自己名下的 Harness + 平台内置 Agent

### 前端入口

index.html 右上角：
```
未登录：显示 [登录/注册] 按钮
已登录：显示 [用户名] + [退出]
```

### 跳过的功能（MVP 不实现）

| 跳过的 | 原因 |
|--------|------|
| 令牌过期 | MVP 够用，以后加 |
| 令牌权限分级 | 先全局权限 |
| 多令牌管理 | 先一个用户一个令牌 |
| OAuth | 太早 |
| 密码登录 | PAT 即密码 |
| 工作空间隔离 | 先全局一个空间 |

## 5. Harness 多会话与智能中继

### 设计背景

当前问题：讨论室（DiscussionRoom）只有"用户 ↔ Orchestrator"对话，Harness 全程被排除在外，只能接收单次指令（ask_hand_raise → reply，execute_task → reply）。

需要的能力：Harness 作为讨论室一等参与者，能看到对话上下文，能被 @ 唤醒参与讨论，能给出有质量的反馈。

### 参考来源

借鉴扣子（Coze）的本地 Agent 多用户协作模式，并结合平台自有讨论室模型，设计了 **Orchestrator 智能中继**模式。

### 核心设计：Orchestrator 智能中继

不傻转发，而是 AI 驱动的智能压缩与解读。

```
讨论室对话
  │
  ├── 用户: "帮我分析这段代码的性能问题"
  ├── Orchestrator: "需要从两个角度入手：I/O 和算法..."
  │
  ├── 🔔 Orchestrator @marvis-main    ← 前端渲染 @ 仪式
  │     │
  │     ├── 幕后工作（用户无感）：
  │     │   ① AI 压缩对话上下文
  │     │      - 提取 Harness 错过的关键信息
  │     │      - 结构化：【任务背景】【当前讨论进展】【期望产出】
  │     │   ② 通过 HarnessBridge 发送压缩后的上下文 + 当前问题
  │     │   ③ marvis-main 返回回复
  │     │   ④ AI 解读 + 压缩 Harness 回复（提取关键信息）
  │     │
  ├── Orchestrator: "marvis-main 认为性能瓶颈在 I/O 层而非算法，建议先做异步文件读取改造，具体方案是..."
  │
  └── 用户: "具体怎么做？" → 继续讨论
```

### 上下文压缩格式（发给 Harness 的 prompt）

```
【任务背景】
{AI 压缩后的任务摘要，3-5 句}

【当前讨论进展】
{Harness 错过的对话要点，按时间线}

【你的角色】
{Harness 的能力描述 + 为什么被 @}

【当前问题】
{用户或 Orchestrator 提出的具体问题}

请基于你的能力和以上背景信息，给出你的分析和建议。
```

### 回复解读规则

Harness 回复可能：
- 啰嗦 → Orchestrator 提取关键信息
- 格式乱 → Orchestrator 结构化
- 上下文不足导致答非所问 → Orchestrator 追加问

Orchestrator 转述到讨论室时以第三人称：
```
行首格式："{harness_name} 认为..."
```

### @ 仪式与智能中继的关系

| | @ 仪式 | 智能中继 |
|------|---------|----------|
| 用户看到 | Orchestrator 在讨论室中 @Harness | Harness 的回复以 Orchestrator 转述形式出现 |
| 实际上 | 前端渲染 @ 动画 | AI 压缩上下文 → 发给 Harness → 解读回复 → 转述 |
| 目的 | 用户感知"请专家"，仪式感 | 信息高效传递，Harness 不被无关上下文淹没 |

### HarnessConvoSession 数据模型

```
HarnessConvoSession
├── session_id        : 会话唯一 ID
├── harness_id        : 对应 Harness 注册 ID
├── agent_id          : 在平台中的 agent_id
├── owner_id          : 所属用户 ID ⬜
├── room_id           : 当前所在讨论室
├── status            : active / paused / closed
├── context_summary   : AI 维护的上下文摘要（每次 @ 时更新）
├── last_at_time      : 上次被 @ 的时间
└── created_at
```

### 与扣子 @Agent 的差异

| | 扣子 @Agent | 我们的智能中继 |
|------|------------|--------------|
| 触发方式 | 用户手动 @ | Orchestrator AI 判断时机自动 @ |
| 消息内容 | 用户原话直接发给 Agent | AI 压缩上下文 + 结构化 prompt |
| 回复展示 | Agent 直接回复原文 | Orchestrator 解读后转述 |
| 多次 @ 衔接 | Agent 自己记住上下文 | AI 维护的 context_summary 增量更新 |
| Agent 自主性 | 被动等待被 @ | 支持主动插话（讨论室消息自动维护上下文，关键节点可自主发言） |

## 6. 任务互助平台设计

### 愿景

用户发布自己解决不了的任务，其他用户（通过他们的 Agent）接单完成。平台做任务分发和质量把控。

### 核心流程

```
用户 A 发布任务
  → Orchestrator 分析任务，判断平台内是否有人能解决
  → 广播到所有在线用户（仅展示任务摘要，不暴露敏感信息）
  → 用户 B 的 Orchestrator 分析 → 发现自己名下的 Harness 能解决 → 接单
  → 创建跨用户讨论室：用户A + Orchestrator + 用户B的Harness（通过智能中继）
  → 执行 → 结果回传 → 用户 A 验收
```

### 数据模型（增量）

```
HelpTask (互助任务)
├── task_id          : 关联平台 Task
├── publisher_id     : 发布者 user_id
├── solver_id        : 接单者 user_id（初始为空）
├── status           : open / claimed / solving / completed / failed
├── reward           : 悬赏描述（MVP 文本，后续可积分）
├── deadline         : 截止时间（可选）
├── created_at
└── updated_at
```

### 权限与安全

| 场景 | 规则 |
|------|------|
| 发布者只能看到自己发布的 | 按 publisher_id 过滤 |
| 接单者只能看到自己接的 | 按 solver_id 过滤 |
| 任务执行时 | 发布者的敏感数据通过 AI 压缩后再发给接单方的 Harness |
| 接单方不可见 | 发布者的原始文件、账号信息等 |

### MVP 范围

| 做 | 不做 |
|----|------|
| 发布/接单/完成基础流程 | 悬赏积分系统 |
| 跨用户讨论室 | 任务评价/信誉系统 |
| AI 压缩敏感信息 | 纠纷仲裁 |
| 本地模拟多人 | 公网多机部署 |
