## 0.1 任务怎么推进（老板 2026-10-24 定，**顺序不许颠倒**）

> 老板原话（摘）：「以后有任务就用**抽象宏观层面**向我介绍功能，我把关后你先把**我的方案更新到项目模型**里，
> 然后用**最小成本跑通一次**，评估可行性，最后再**转通用化**，但每个功能一个循环，
> 不能在实现一大堆功能后才想起来通用化。」

| 步 | 做什么 | 不许做什么 |
|---|---|---|
| ① | **大白话**讲清：这功能给谁用、他点哪儿、背后怎么做到、哪里可能不成立 | 用术语把人绕晕、先写代码后解释 |
| ② | 老板**把关**；通过后，把**他的方案**写进本模型/设计稿 | 自己改口径、把没拍板的当已定 |
| ③ | **最小成本跑通一次**（spike，能用手点/一条命令验证即可），给出可行性结论 | 一上来就做大而全、没验证就落地 |
| ④ | 只有③通过，才**转通用化**（换目录/换端口/换应用都能用） | 攒一堆功能再回头通用化 |

> 反面教材（2026-10-23）：在"把字送进别人的应用"这一件事上，我先做了"模拟鼠标键盘"，
> 再做"浏览器端口"，再做"人教位置"，每一步都没先验证可行性 ⇒ 一整天的成本白花。

## 2. 维护约定（防止模型被历史污染）

1. **只写当前口径**：任何"曾经怎样 / 旧版写的是什么 / 已停更"都不进模型——那是 `CHANGELOG.md` 的活。
   （真需要解释"为什么这么定"，写一句**理由**就够，不要写版本号与旧数字。）
2. **数字必须实测**：分册里的行数/条数/份数，改代码后**同一次**更新，否则守卫会红（见 §3）。
3. **一处真相**：同一个事实只在一处写全，其余分册只放**一句结论 + 链接**。
4. **拆而不散**：新增内容先判断属于哪个分册；跨两册的，写在更"上游"的那册并让另一册链接过来。
5. **改分册要回主索引核对**：主索引 §0 那十条是"给新人的五分钟版"，口径变了要一起改。
