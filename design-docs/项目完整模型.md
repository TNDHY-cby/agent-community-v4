## 1. 一句话与 5 概念

**外端Agent生产合作社** = 把**多个异构 agent（harness 框架影响 agent 能力）**组织到一个**工作间**里协作的
**本地自部署平台**：用户提任务 → 平台建工作间 → 讨论选人 → **自动给每人建会话并命名** → 架桥对接 →
分头干活 → 阶段整合。**平台不替 agent 干活**，只做「**接入、激活、交接、留痕、兜底**」。

**5 概念（贯穿全篇）**：

| 层 | 是什么 | 关键点 |
|---|---|---|
**平台** | 一个本地进程 + 一套前端页面 | 单机（默认 18920）；**供外端 agent 接入**；不代理模型调用 |
**工作间（Workshop）** | 一个项目/任务的组织单位 | 有状态机（§3.1）、自己的目录、共享资料库、任务树 |
**通道（Channel）** | **一个成员在本工作间里「通着的那条路」**：一个会话 ＋ 它的桥 ＋ 它的邮箱收发 | 沟通**该成员**与平台/其他成员/项目；**可停用/新建**（§3.4）；⚠️ **别与「接入通道/接入协议」混**（HTTP/A2A/gRPC/桥脚本，那是另一回事，见 §8） |
**隔间（Compartment）** | **成员干活的地方**＝他在工作间里的文件夹 | 普通成员**只能在自己隔间里写文件**；**可被继任员工继承**（⚠️ 继承机制**尚未实现**，见 §11） |
**成员（Member）** | 一个被选进来的**外端 agent** | 跟**岗位（角色）**走；有自己的**通道实例**与**隔间** |

> 一句话记法：**平台管调度、工作间装项目、通道连 agent、隔间放活、成员是 agent 本人。**

> ⚠️ **两个「通道」别混**（老板 2026-10-10 自查指出自己那句可能不准确）：
> ① **成员通道**（本文简称「通道」）＝**某成员通着的那条路**（会话＋桥＋邮箱），**可停用/新建**〔源码 `workshop.py:59`〕；
> ② **接入通道 / 接入协议**＝平台**对外**的接入方式（HTTP / A2A / gRPC / 桥脚本）——「怎么接进来」的那套协议与脚本
> 〔引用 `Harness通用接入协议.md`、`多协议接入与前端落地设计.md`〕。

## 2. 角色与对象模型

### 2.1 角色（谁会出现在系统里）

> 角色＝**岗位**，由人选/改；一个成员就是某个岗位上的 agent。
> **"现状"列**说明该角色在**当前实现**里到什么程度（诚实标注，不假装）。

| 角色 | 谁（能力专长） | 能做什么 | 现状 |
|---|---|---|---|
**用户（真人）** | 用户本人 | 发任务、参与各级讨论、选人、点开工、点停用/新建通道、点退出并关闭 | ✅ |
**平台（AI 或规则）** | 本平台自身 | 建工作间、主持一级讨论、按能力初选成员、生成命名、执行接入/激活动作、兜底 | ✅（未配 AI 时走规则兜底） |
**组长** | 某个**规划能力出众**的 agent 成员 | 二级讨论中与用户深谈、细化分工、**构建项目详细模型**、**整合最终产品**；**不被员工隔间框住** | ✅ 角色可用；"执笔模型"已实现（`model.md` + AI 草案） |
**后端开发者** | 某个或多个**编程能力出众**的 agent 成员 | 负责后端程序编写 | ✅ 角色名自由填写 |
**前端开发者** | 某个**前端设计+落地能力出众且审美高**的 agent 成员 | 负责前端设计与代码编写 | ✅ 角色名自由填写 |
**信息搜索者** | 某个**擅长在各种环境搜索资料**的 agent 成员 | 搜索并按要求**挑出高价值资料**，**避免其他成员被外界庞大信息污染** | ⚠️ 角色名可用，但**"防污染"没有专门机制**（未实现） |
**巡逻员** | 某个 **computer 工具丰富**（最好用免费 agent/API）的 agent 成员 | **当平台检测不到被分配任务的员工时，前往查看情况并进行维修** | ⚠️ **未实现**：现在只有"掉线抢救"——判定后**通知组长/用户**并重试调起，没有"派人到现场看"这一层（§11） |
**……（角色不限于此）** | 由用户/平台按能力画像安排 | —— | 角色名**不受限**（平台不校验枚举） |

## 3. 状态机模型（六个维度，取值均来自源码）

> **为什么要分这么多**：本项目最大的历史教训是"**一个状态混用会造假象**"（例如"派发出去了"≠"对方收到了"）。
> 所以状态**正交拆分**，界面要读对的那个。

### 3.1 工作间 `ws.status`〔源码 `workshop.py:80`〕
```
draft（草稿/手工建）→ discussing（一级讨论）→ selecting（选成员）
→ division（二级讨论：与组长）→ running（干活）→ review（三级讨论）→ done（收尾）
```
- **由广播任务自动建**时直接进 `discussing`〔源码 `server.py:1365`〕；手工建为 `draft`。

### 3.2 成员生命周期 `member.status`〔源码 `workshop.py:37`〕
```
pending / activating / entered / working / idle / blocked / offline （另有 removed：被移出名单）
```

### 3.3 派发进度 `member.entry_state`〔源码 `entry_state.py:28-34`〕——**与 status 正交**
```
pending（已登记未派发）→ dispatched（已投递，但对方未确认）→ acked（送达确认）
→ entered（已进入工作间/会话就位）｜ blocked（失败，带 reason）｜ timeout ｜ needs_human（超时需人工）
```
- 常见 `reason`：`桥进程未运行`、`派发失败`、`未指定 harness`、`该唤醒方式到不了此状态`、`派发后无回应`〔`:44-48`〕
- ⚠️ **界面必须读 `entry_state`**，不要用 `status` 猜派发进度（这正是"假成功"的来源）。

### 3.4 通道状态 `member.channel_*`〔源码 `workshop.py:64`；设计 V28〕
```
channel_seq（序号，第 1 个＝1）｜ channel_state：pending（未接入）/ active（运行中）/ retired（已停用）
｜ channel_since ｜ retired_channels[]（历次留痕：序号/名字/会话引用/停用时间/原因/归档产物）
```
- **定义**〔源码 `workshop.py:59`，即老板 2026-10-09 拍板时的口径〕：**通道＝该成员在本工作间里「通着的那条路」（一个会话 + 它的桥 + 它的邮箱收发）**；
- 规则：**一个成员同时只能有一条 active 通道**；**停用≠删除**（隔间与产物不动）；**停用后不得再投消息**；
- `establish` 时**序号 +1**、名字追加 `-<序号>`（如 `…-码农-m0-2`），并**自动补做步骤 5（送桥）**。

### 3.5 任务状态机〔源码 `task_state_machine.py:66-75`〕
```
created → assigned → discussing → executing → waiting_reply
→ （stuck-paused ｜ blocked-retrying ｜ timeout）→ done ｜ dropped
```
- 事件：`submit / assign / discuss / execute / report / stuck / block / timeout / retry_ok / retry_fail`〔`:78-87`〕

### 3.6 掉线三态（`offline-report`）〔设计 V23/V26；实测过〕
```
idle（**空闲＝正常态，不救、不叫人**）｜ healthy ｜ rescue（有活＋异常信号 ⇒ 通知组长 → 尝试调起 → 多次不成报用户）
```
- **硬信号**（桥进程确认退出）才允许说"联系不上"；**软信号**（心跳，本项目**心跳可选**）只进详情；
- ⚠️ 这里**只有"通知与重试"**，没有"巡逻员去现场维修"——那是 §2.1 的新角色，**未实现**。

### 4.1 如何**激活一个 agent 新会话**（操作 + 契约）

> ⚠️ **本节讲"激活"，别与"接入"混**（老板规则 20 的教训）：
> **接入**（本节上方步骤 0 ＋ 下方五步话术）解决"**这个 harness 怎么接到平台、怎么架桥**"；
> **激活**（本节）解决"**接进来之后怎么给它开一个新会话并命名**"（步骤 4/7/8/9）。
> **接入的五步**：注册 → 配叫醒 → 起桥 → 自检 → **持久跑桥**；
> 判据：**前 4 步绿＝配置可行，第 5 步绿＝真的接上了**（少第 5 步，平台派的活只会躺在队列里没人取）〔实测 2026-10-13〕。

**一句话**：平台**调用该 harness 注册时提交的 `new_session` 脚本**（`<python> 脚本 --input payload.json`），
**脚本在 stdout 打印 JSON 自证**；没配脚本就走**人工指引**（不算失败）。

**① 注册时先准备好**（步骤 0，`POST /api/harness/register`）：
```json
{
  "harness_id": "示例Harness-A",          // 必填
  "ai": { "model_name": "示例模型" },      // 必填
  "scripts": {
    "new_session":    { "NEW_SESSION_CMD": "python my_new_session.py",  "foreground": "never" },
    "rename_session": { "RENAME_CMD": "python my_rename.py \"{new_name}\"", "foreground": "never" },
    "deliver":        { "DELIVER_CMD": "python my_deliver.py",          "foreground": "never" }
  }
}
```
`scripts.*` **可选**；`foreground` 决定"能不能自动"（`never/optional/required`）。

**② 三条激活路径**：
| 场景 | 怎么触发 | 条件 |
|---|---|---|
**开工自动** | 在工作间点「开工」`POST …/start`（先跑 4/7/8/9） | **配了 `new_session` 且 `foreground ≠ required`** |
**批量** | `POST …/onboard-members`（body 省 member_ids＝全体） | 同上 |
**单个 / 没自动时** | 成员卡按钮 或 `POST …/member/{mid}/establish-session` | 手动，随时可用 |
**换会话（上下文老化）** | 成员卡「停用通道」→「新建通道」：`channel/retire` → `channel/establish` | 先停后建；序号 +1；自动补做步骤 5 |

**③ 你的脚本要怎么写**（最小契约〔源码 `action_scripts.py:160-201`〕）：
```python
# my_new_session.py  ——  平台这样调用你：
#   python my_new_session.py --input <payload.json>      环境变量 AC_ACTION=new_session
#   payload 例：{"name_hint": "<平台给的名字>"}
import json, sys
payload = json.load(open(sys.argv[sys.argv.index("--input") + 1], encoding="utf-8"))
# …在这里真的去开一个新对话（调你的 harness 的 CLI/API/无头入口）…
print(json.dumps({"action": "new_session",
                  "evidence": {"session": {"id": "<会话id>", "name": payload.get("name_hint", "")}}}))
```
- **判定**：退出码 0 且 stdout 有 JSON ⇒ `ok=True`；给了 `evidence` ⇒ **`verified=True`（才算成功）**；
  没给 `evidence` ⇒ `verified=False` ⇒ 界面显示「**⚠ 待人工/未核实**」（准则⑤）；
- stdout 没有 JSON / 脚本不存在 / 超时 ⇒ `ok=False` + `error`（**如实报，不假成功**）。

**④ 没配脚本时（人工模式）**：平台**不报错**，而是给出 `manual[]` 指引（例："请新建一个对话（随后平台会重命名为：…）"），
并把可复制的投递文本落成 `<隔间>/deliver_text.md` —— **人工做完即等效**，平台只是不把它标成"已自证"。

**⑤ 命名与重命名**（步骤 7/8）：名字由**平台生成**：`<工作间id>-<项目>-<职位>-<成员id>[-序号]`，
写进 `session_aliases[0]`（**身份凭据**，放首位）；重命名靠 `rename_session` 脚本，没配就人工复制粘贴。

## 8. 边界模型（最容易做错的地方）

**判断句**：在把外部东西**接进来/唤醒起来**吗？→ 接入类；在**讨论或推进工作**吗？→ 工作间。

> ★**三组词汇必须分开**（老板规则 20 的直接产物；实测外部 agent 拿 `sent_via:"clipboard"` 当 ✅ 绿）：
>
> | 概念 | 回答什么 | 合法取值 |
> |---|---|---|
> | `wakeup_method` | **这个 harness 靠什么被叫醒** | `http` / `file_poll` / `clipboard` / `acp` / `http_api` / `mcp` |
> | **桥型**（`kind`） | **用哪只桥去接它** | `file_poll` / `cli_acp` / `pending_poll` / `script_framework` |
> | **探针通道**（`sent_via`） | **平台这次走哪条路投出去** | `inbox`（file_poll）/ `pending_queue`（其余） |
>
> - 桥型名填进 `wakeup_method` ⇒ **400 拒绝**（`cli_acp`/`pending_poll`/`script_framework` 不是 `wakeup_method`）；
> - `sent_via` 回 `clipboard` ⇒ 是 bug（已修：两处端点共用 `_wake_channel()`；复盘见 `V43` 缺陷 #8，
>   同端点的 `success` 语义见 §9 第 10 条）；
> - 一码归一码：**判据只留一处**（源码 `_wake_channel()`），两处端点共用〔源码/实测〕。

| 面 | 包含 | 不包含 |
|---|---|---|
**接入**（Harness 接入页） | 注册 harness（15+ 字段）、动作脚本与档位、能力声明 | 讨论、选人、干活 |
**激活类**（在工作间） | 建会话、送桥、对接隔间邮箱、**通道停用/新建**、抢救重连 | 讨论内容本身 |

## 9. 诚实性模型（本项目的灵魂，验收先看这节）

1. **`verified` 三态**：脚本"跑了" ≠ "成了"；不能自证的动作 ⇒ 界面显示「**⚠ 待人工/未核实**」，**禁止**显示"完成/成功"；
2. **`entry_state` 单独记派发进度**，不许用 `status` 猜（§3.3）；
3. **停用后不得再投消息**（`member_channel_allows_dispatch`）——否则就是"说了停用、消息照收"；
4. **草案不落盘**：AI 生成的模型只是**草案**，必须人确认后才写文件；
5. **无产物如实说**：整合时全员无产物 ⇒ `has_output=false` + 明写"无产物可整合"，**不算成功**；
6. **缺块如实标**：模型五块缺哪几块，接口与界面都要列出来（"缺 3 块"），**不许当完整**；
7. **平台不认识的 harness** ⇒ 成员标 `blocked` + 原因，**不回"已派发"**；
8. **失败要说话**：没关掉的进程、没送达的消息、没归档成功的文件，都要**逐项报出来**。
9. **"跑通"必须说清验的范围**（`verified_scope`）：文件邮箱通道验的是**完整链路**（平台→桥→agent→回报）；
   桥测试通道验的是**仅桥配置**（而且那只桥是平台在验证间里启动的）——
   **harness 侧是否真跑该桥、agent 能否回话，本次未验证**。不写清范围，`verified=true` 会被读成"整条链路通了"〔实测〕。
10. **"投出去了"≠"送达了"**：`bridge-test` 的 `success:true` 只代表平台把测试件投出去了
    （配 `queued:true` / `delivered_confirmed:false` 与"怎么才算确认"的提示），**桥没在跑时同样是 success**〔实测〕。
10b. **"扫过了"≠"扫全了"**：判据脚本的**文件类型/目录覆盖**必须写清，否则会得出假的"0 残留"。
    实证（2026-10-13）：`temp/verify_clean_20261013.py` 报 `RESIDUAL=0`，但它只扫
    `design-docs/` + `agent_community/` + `tests/` + 根 `README/AGENTS`，**且只认 .md/.txt/.html/.json/.yml/.py/.tmpl/.ps1/.bat**，
    完全跳过 `frontend/**/*.js`、`*.ini` 等 ⇒ 当时 dev 侧其实还有 78 处、oss 侧 110 个文件 403 处真名〔实测 2026-10-13 晚〕。
    **正确姿势**：① 扫两棵树（dev 与 oss）而不是只扫一棵；② 报告里写明扫了哪些扩展名/目录；
    ③ 把"判据本体（守卫文件的正则与禁词表）"和"真泄漏"分开列，别混成一个数字。
10c. **只清一棵树 = 没清**：同一批清理必须**两副本同时落**，并各自 `git commit`。
    实证：`0552166` 声称"design-docs 全清真实名"，实际只清了 dev 工作树，oss 侧 13 份仍带真名（V23 13 处、V36 14 处、V38 11 处）。
10d. **判据本体可以合法带真名**：`tests/scan_sensitive.py`、`tests/scan_rule19_private.py`、
    `tests/test_bridge_catalog.py` 与 `frontend/verify/*_check.js` 的 sanitize 归一化表＋禁词断言
    **必须**写真实名才有判别力（它们就是规则 19 的守卫）；它们命中的是"策略类"告警，不是"随仓库出去的真凭据"。
    历史产物文件（`tests/*_report*.txt`、`frontend/verify/*/result.json`）记录的是**当时真实回显**，清掉等于改证据〔实测 2026-10-13 晚〕。
11. **桥数按"逻辑桥"计**：`bridges_running` 数的是父子链归并后的只数，不是进程数（本机 `python.exe` 是外壳，
    一只桥常见 2 个同名进程）；`>1` 才给重复桥告警〔实测〕。
12. **审计只记"发生过的事"**：① `target` 必须带**具体 harness**（原来写死 `""`，多 harness 下查不了账）；
    ② 心跳只记**上线/恢复跃迁**（每 15 秒一条会把 500 条 ring buffer 刷成纯心跳，真事件被挤出）；
    ③ 对不存在的 harness 发注销**不留"已注销"的假记录**〔实测 2026-10-13〕。
13. **文档承诺的开关必须真的能用** —— 否则比不写更坏。
    **实证（2026-10-14）**：`AC_HOST` 已登记进 `env_spec` / `.env.example` / README，但
    `server.py` 末尾直接 `uvicorn.run(host="0.0.0.0")` ⇒ 设 `AC_HOST=127.0.0.1` **仍然监听 0.0.0.0**〔实测〕。
    用户会照文档改、改完以为生效了，然后拿错误的现象来问"为什么没用"。
    修法：走 `platform_address.resolve_host()`（`--host` > `AC_HOST` > 默认）。
    **判据：这类缺陷读代码看不出来，只有把服务真起起来、看真实监听地址才能发现。**
14. **写在文档里的闸门必须真的会拦** —— "只警告不失败"等于没做。
    **实证（2026-10-14）**：`AC_ENV=production` 缺 `AC_DATA_DIR` / 关停口令 / 访问令牌时，
    服务**一路打警告照样起来**〔实测〕（上一版把生产模式两条都写成 `warn`，理由是"别让开箱即用被自己否掉"——
    那只对**开发**成立）。修法：**开发 → 警告；生产 → 失败**（`EnvError` + 退出码 2，并点名缺哪个变量）。
15. **换行符与 BOM 是"隐形拦路石"**：在开发机上永远看不出来，只有别人 clone 下去才炸。
    ① `.gitattributes` 只钉了 `*.sh`，`Dockerfile` 的续行 `\` 被 CRLF 变成 `\`+CR ⇒ **Linux 上 RUN 指令解析失败**〔实测 2026-10-14〕；
    ② `.ps1` 带中文却丢了 UTF-8 BOM（编辑工具会顺手抹掉）⇒ Windows PowerShell 5.1 按 ANSI 读，
    报满屏"缺少右 )"之类**看不出真因**的语法错〔2026-10-14 又把 `publish_acv4.ps1` 弄丢一次〕。
    修法：`.gitattributes` 按"是否在 Linux 上执行"分 LF/CRLF；BOM 由守卫测试守住（全仓库 `**/*.ps1`）。
16. **"做了验收"和"验收物送到了别人手里"是两件事**：
    2026-10-14 第一版可移植性制度做完了闸门，却**没把 `tools/` 与 `.github/` 放进 `publish_acv4.ps1` 的同步面**
    ⇒ 公开仓库里 `pytest` 与 CI 会**直接失败**（缺文件），而开发机上一路全绿。〔同 2026-10-13 requirements.txt / start.py 那次〕
    **判据：新增的"能跑起来必需的东西"必须同时进 `$rootDocs` / 同步面。**
17. **同步用 `/MIR` 之前，先问"dev 是不是唯一真相"**：`/MIR` 会**删除** oss 侧多出来的文件。
    **实证（2026-10-14）**：同步 `.github/` 用了 `/MIR`，而 dev 没有 `ISSUE_TEMPLATE/`
    ⇒ oss 独有的 `bug_report.yml` / `feature_request.yml` **被删掉**，开发机上完全看不出来。
    **规矩**：`/MIR` 只留给 `design-docs/` 这类"dev 就是权威、删稿要跟着删"的目录；
    其余同步面一律 **copy-only（`/E`）**。
18. **凭据权限也是可移植性的一部分**：推送用的是 Personal Access Token，
    **没有 `workflow` 权限时 GitHub 会拒收整次 push**（
    `refusing to allow a Personal Access Token to create or update workflow ... without 'workflow' scope`）——
    一次推不上去 = **别人拿不到任何更新**，比"CI 不跑"严重得多。
    **现状（2026-10-14 已收口）**：老板在 **GitHub 网页端**建好了
    `.github/workflows/ci.yml`（仓库里唯一一份，`ci/ci.yml` 那份已删除——两份并存必然漂移）；
    **改 CI 的姿势**：网页端直接编辑，或先给令牌补 `workflow` 权限。
    详见 `PORTABILITY.md` §4.1。
19. **"只有 dev 能过"的守卫也是假绿**：守卫里凡引用 dev-only 文件
    （如 `publish_acv4.ps1`、`HANDOVER.md`）都要先判存在再断言。
    **实证（2026-10-14）**：`test_github_issue_templates_are_not_swept_away` 在 oss 侧
    直接 `FileNotFoundError`〔实测〕—— 又一次"开发机全绿、别人那儿红"。
    **判据：新守卫写完，必须拿到 oss 副本里也跑一遍才叫过。**
20. **"依赖没声明"是同一类假绿，而且只有干净环境才暴露**（2026-10-14 CI 第一次真跑就中）：
    `requirements.txt` 只写了 `grpcio`，而 **grpcio 不拉 protobuf**
    （`pip show grpcio` 的 Requires 只有 typing-extensions），仓库根也没有 `pyproject.toml` 兜底
    ⇒ 干净 runner 上 pytest **收集阶段**就 `ModuleNotFoundError: No module named 'google'`
    （`agent_community/proto/agent_community_pb2.py` 直接 import `google.protobuf`）。
    **本机一路 1391 passed，只是因为恰好装着 protobuf 7.36.2**〔实测〕。
    **修法不止补这一个包**：① `requirements.txt` 补 `protobuf>=7.35.1`
    （下限＝pb2 的 gencode，`ValidateProtobufRuntimeVersion` 会校验，**不许调低**）；
    ② 新增守卫 `TestThirdPartyImportsAreDeclared` —— AST 扫 `agent_community/**` 的第三方 import，
    凡未声明的一律判红；③ 用 `temp/deps_mutation_check.py` 突变检验
    （删 protobuf / 调低下限 / 删 fastapi ⇒ 三次全 KILLED）。
21. **CI 里的"兜底安装"是假绿温床**：`pip install -r requirements.txt || pip install <一部分包>`
    —— 兜底装出来的环境和 `requirements.txt` **不是同一个**，跑绿了不能说明任何事。
    **判据**：宁可让它在安装步骤**响亮地失败**，也不要"装个残缺环境然后假装通过"。
    要抗网络抖动就用 `pip install --retries 5 --timeout 60 -r requirements.txt`。

### 10.1 可移植性制度（2026-10-14 立，**三层**；判据见下）

> **判据（老板原话口径）**：**"我这台能跑"不算合格；"陌生环境只改配置就能跑"才算合格。**
> 派任务标准话术：「实现 X。按 `PORTABILITY.md` 的可移植性规则。先列出涉及的环境变量和默认值，再写代码。
> **禁止针对我的电脑。** 验收：在陌生 Linux 容器里只改环境变量即可运行。」

| 层 | 载体 | 内容 |
|---|---|---|
**① 指令层** | `PORTABILITY.md`（规则唯一真相）+ `AGENTS.md` 硬规则章节 + `CLAUDE.md`/`.cursorrules`（**只做指针**，规则 20 不复制） | 禁止硬编码端口/IP/域名/`localhost:数字`/绝对路径/用户名/本地目录/密钥/数据库 URL/API 地址/回调地址；例外须在该行写 `# portability: allow(<理由>)` |
**② 工程层** | `env_spec.py`（登记表 + 条件必需校验 + `assert_ready()`）、`platform_address.py`（端口/**监听地址**/基址唯一解析点）、`config.py`（env > file）、`.env.example` + README 环境变量表（**生成**，`gen_env_docs.py --check` 防漂移）、`Dockerfile`/`docker-compose.yml` | 配置驱动是默认；默认值只用于开发且可被环境变量覆盖；本地适配只改 `.env`（已 gitignore），**不得改源码** |
**③ 验收层** | `tools/check_portability.py`（发布面扫描，**fail=0** 才算过）+ `.github/workflows/ci.yml`（干净 `ubuntu-latest` 作业把三条自查与"只改环境变量也能起"跑成**失败即拦**）+ `pytest` 里的同名守卫 | 三条自查：`check_portability` → `gen_env_docs --check` → `pytest -q`；判据必须**按真结果**写（真起进程看监听地址、真调 `assert_ready()` 看是否抛错），**源码文本断言不算** |

- ⚠️ CI 定义只有一份，在 **`.github/workflows/ci.yml`**（GitHub 唯一会执行的位置）。
  推送令牌缺 `workflow` 权限时，提交里**碰了**这个路径会让 GitHub **拒收整次 push**
  （详见 §9 第 18 条）；**改 CI 走网页端**，或先给令牌补权限。
- 同步工具面（`tools/`、`.github/`）一律 **copy-only（`/E`）**，**不用 `/MIR`**
  （详见 §9 第 17 条的事故）。

- 扫描范围＝**发布面**（`agent_community/`、`design-docs/`、`tests/`、根文档），与 `publish_acv4.ps1` 同步面一一对应；
  dev-only 运维脚本不进范围（否则天天红 ⇒ 人人加排除 ⇒ 判据失效）。
- **默认值登记处**豁免：`env_spec.py`（登记表本体）与 `.env.example`（它的生成物）里的出厂默认值不算硬编码；
  但**产品逻辑**里出现同样的地址仍然判红。
- 守卫有效性的证明方式＝**突变检验**（把实现人工退回错误写法，守卫必须变红）：
  `temp/acceptance_mutation_check.py`（监听地址 / 生产闸门）、`temp/port_test_mutation_check.py`（测试端口）等。
